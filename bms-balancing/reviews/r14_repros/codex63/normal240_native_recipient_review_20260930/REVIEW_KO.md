# NORMAL240 실제 결과 — 독립 수신 검토

2026-09-30. **판정: 고정 실행본의 fresh 0→240초 한정 진단과 선언 표본 비교를 수용한다. 이 한정 수용을 막는 결함은 발견하지 않았다. 전체/정상 gate·전체 수렴·장시간 운전은 INCOMPLETE 유지. 새 실행 승인 없음.**

두 ZIP을 데이터로 검증하고, 검토자가 작성한 별도 CSV 검산기로 수치를 재계산했다. 받은 Java/Python/PowerShell·시험·COMSOL/JVM은 실행하지 않았다. 원본 ZIP·생성 영수증·기존 상태를 수정하지 않았다. 이는 별도 수신 판정이다.

## 2. 독립 수치 검산

원시 CSV를 Decimal 50자리 연산으로 읽었다. 시간과 좌표 집합을 검사했으며 보간·외삽·빈점 대체는 하지 않았다. 좌표는 계약값 대비 10⁻¹⁵ m 허용차, domain 및 각 시각의 241개 순서를 검사했다. 로그에 들어 있는 CSV 35개의 디코딩 바이트도 전달 CSV와 일치한다.

- 저장 시각 3,340개: 엄격 증가, 0→240초. 요청 시각 2,537개 전부 포함.
- 전극별 241좌표·domain 1/3·N/P 각각 804,940행, 합계 1,609,880행. 전체 시간×좌표 집합과 유한값 확인.
- threshold 0, 세 보호식의 저장 시각 값 모두 0, 선언 OCP 표면 범위 내.
- 전체 coupling 최소와 영역별 최소의 최솟값 차는 0. 별도 MinLine 출력과 coupling 최소 차는 최대 5×10⁻¹³ mol/m³로 10⁻⁹ 이내.
- 단위 read-back을 독립 기대 배열과 대조했다. 실제 시간 설정·요청 목록·step cap과 물리 분할 120/60/120, 입자 320/320 기록도 계약과 일치한다.
- native 로그의 시간 적분 1회·240초 도달·Time-stepping completed를 확인했다. 반올림 로그와 정확 저장 시각은 구분했다. 출력된 초기 이후 Tfail/NLfail의 최댓값은 각각 0이며 초기 행의 미출력값은 0으로 채우지 않았다.

초기 Li 세 항은 두 기준과 정확히 같다. 전체 저장 구간 총 Li 상대 변화 최대는 `2.9832574645305909…×10⁻¹⁵`(허용 10⁻⁶), 전압 분해 잔차 최대는 `7.17×10⁻¹⁶ V`(허용 10⁻⁸ V)다. 수치적 내부 일관성이지 실험 정확도는 아니다.

## 3. 실행·종료·예산 경계

compile/batch 각각 1회·각 rc0, native 기록 오류 없음이다. compile 76개·batch 7,898개 이벤트의 순서·해시·root 식별·Job 배정·resume·종료 관측을 검사했다. 소유 프로세스 정리 PASS는 당시 기록의 판정이며 현재 원격 PC의 모든 프로세스를 직접 조사한 결과가 아니다.

native 로그의 시간 적분 Solution time은 1,781초, Class run time은 3,979초, Save time은 23초, Total time은 4,002초다. 이들은 서로 다른 측정 범위다. 위 전체 4,269.865초를 물리시간 240초나 solver 시간으로 부르지 않는다.

`-NoExit` 부모의 종결은 스크립트 최종 기록 경계다. `raw_host_rc=null`을 보존하며 PowerShell 프로세스 자체의 rc0을 만들지 않는다. 자식 native/analysis rc0 및 최종 기록 오류 0과 구분했다. 마지막 `STOP. No rerun…`은 부모 소스의 재실행 금지 안내이며 solver 오류가 아니다.

POST_WRITE는 사용자 콘솔 출력의 후속 전사다. 원본 FINAL_BOUNDARY의 크기·SHA와 pre/post 시간을 대조했다. 선행 잘린 analyzer 출력은 재구성하지 않았다는 한계도 유지한다. PARENT_TRANSCRIPT가 모든 자식 stdout을 담은 완전한 OS 감사라고 주장하지 않는다.

## 4. 전달 최종화

메인 포장 반환 `11faaa`는 rc0이며 수신 메인 ZIP 식별·개수와 일치한다. 이번 사용자 메시지의 마지막 반환 `5d1af4`는 rc0, 보충 ZIP 41,791 bytes/SHA와 일치한다. 출력 0.156초는 재읽기 후·도구 반환 전 snapshot, 1.0677871초는 해당 호출 wall time이다. 전체 native 예산 또는 모든 반환 이후 시간으로 바꾸어 쓰지 않는다.

`USER_SUPPLIED_FINAL_RETURN.json`은 수신자가 이번 사용자 메시지를 전사한 자료다. 보낸 측 원본 파일 바이트나 수신자의 직접 도구 관측이 아니다. 이 출처 수준에서 전달 완료 근거를 수용하며 추가 반환 요청은 필요 없다. 원래 생성 영수증 recipient=null은 수정하지 않았다.

## 5. 보존·정책·관측 한계

선택 보존 목록 전 8,113개/후 8,121개에서 전 목록 식별 전부가 후 목록에 유지됐다. 이 중 이번 ZIP에 바이트가 있어 직접 대조한 참조는 전 8,091개/후 8,098개다. 두 집합은 겹치므로 합산해 독립 파일 수라고 부르지 않는다. 부재 참조는 RECORDS_AUDIT에 열거했다. 전체 PC 보존 증명이 아니다.

결과 MPH는 ZIP에 없다. 보낸 측 크기 4,261,090,658 bytes / SHA `84e22fb9bf83f0a9c819ca38451cefcf8f77c7b49ef46e5783d285ece4e27171` 및 재해시 기록만 대조했다. 전체 prefs·실행파일도 식별 기록의 범위다. MPH를 직접 재해시/재개방하거나 모든 내부 필드가 불변이라고 입증한 것은 아니다.

정책 파일 식별·보안16개 값의 보존과 호출 결속은 PASS로 수용한다. **COMSOL 내부 실효 정책은 UNVERIFIED**다. 16코어 로그는 설정 근거이며 실제 사용률/병렬성을 새로 입증하지 않으므로 actual_cores=UNVERIFIED를 유지한다. native 메모리 표기도 OS 전체 peak 측정이 아니다.

## 6. 종결과 다음 단계

별도 수신 판정은 `ACCEPTED_NORMAL240_LIMITED_DIAGNOSTIC`이다. 원래 overall/normal gate INCOMPLETE, failed/pending/원복, 생성 영수증 recipient=null, OCP 외삽 금지·TIME_CAPS 차이 원인 미확인·후보 C 보류를 유지한다.

추가 240초 재계산·기존 전체 suite 반복은 필요 없다. 다음 후보는 **fresh 0→480초 한정 진단의 오프라인 준비**다. 이는 제안이며 이번 검토 자체가 구현·새 예산·native 실행 승인은 아니다. 240초/B020의 정확 공통 구간 비교, 물리·보호식·허용치 유지, 새 요청 시각·단위·Li 기준을 고정해야 한다.

특히 결과 MPH 약 4.26GB, compile+batch 약 4,060초, 분석 약 150초를 근거로 다음 저장·분석·디스크·전체 예산을 다시 산정해야 한다. solver 적분 시간만 두 배로 늘려 총 예산을 정하지 않는다. 5,400/7,200초를 자동 재사용하거나 임의 downsampling·출력 삭제·정책 완화로 맞추지 않는다. 변경이 필요하면 사전 승인 범위에 명시한다.

장기 목적 시간·운전 프로토콜과 메시/시간 수렴의 미완 목록은 별도 축으로 유지한다. 480초나 그 이후 도달만으로 이들을 자동 종결하지 않는다. 다음 고정 후보의 변경부 검증을 수용한 뒤 native 최대1회를 따로 승인하는 순서를 제안한다.
