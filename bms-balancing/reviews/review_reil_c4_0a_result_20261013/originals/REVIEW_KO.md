# REIL C4-0a 결과 검토

2026-10-13. 판정은 **제출 증거 한정 수용, C4-0a 구현 종결 보류**다. 26개 GREEN 통과 기록과 Phase A 배열 4개의 현재 바이트는 확인했다. 그러나 새 코드에 배열의 기준 결속, 마지막 기록의 시간 한도, 종료 직전 RSS 관측 공백, 구조 오류의 중간 계수 전달 문제가 남는다. 모두 아래 고정 소스의 정적 제어 흐름으로 확인한 P2 보완사항이며, 현재 제출 결과가 위조되었거나 실제 계산이 한도를 넘었다는 판정은 아니다.

이번 회신은 수정·시험·C4-0b·C4-E/A/B의 실행 승인이 아니다. 먼저 아래 변경부만 묶은 보완 범위에 사용자 승인을 받고, 보완 결과를 검토받는 순서를 권한다. 기존 환경 봉인과 정상 기록을 다시 만들 필요는 없다.

## 종결 전 보완 네 항목

### C4-0A-N1 배열 검증을 수용 기준에 직접 결속

**P2 · `bms-balancing/scripts/reil_c4_e3a.py:398–406`, 호출부 462행.** `check_arrays`는 로컬 파일을 로컬 MANIFEST와 맞추고, 로컬 ARRAYS.json의 `npy_sha256` 및 `c6_manifest_sha256` 문자열을 대조한다. 그러나 실제 수용 C6 MANIFEST의 배열 항목이나 외부에서 고정한 C4 MANIFEST SHA와 비교하지 않는다.

한 NPY를 바꾼 뒤 ARRAYS.json의 해당 `npy_sha256`과 로컬 MANIFEST를 함께 갱신하고, `c6_manifest_sha256` 문자열만 유지하면 현재 조건을 모두 만족한다. 원래 `c6_npy_sha256`·raw SHA가 낡아 있어도 이 경로는 보지 않는다. 그러므로 건조 실행이 미수용 배열을 검증된 것으로 계획에 연결할 수 있다. **이번 제출 배열 4개는 독립 바이트 대조에서 일치했으며, 결함은 다음 읽기 시 검증 경계에 있다.** [고정 코드](https://github.com/yonghoon7153-source/Yonghoon-DEM-DFT/blob/c542e056b33d25100bc0519ce492c98d3bcce172/bms-balancing/scripts/reil_c4_e3a.py#L398)

최소 수정은 명시적인 수용 C6 경로와 기대 MANIFEST SHA를 받아 실제 MANIFEST를 인증하고, 네 NPY 해시를 그 인증된 항목과 대조하는 것이다. 또는 이미 독립 수용한 C4 MANIFEST 전체 SHA를 외부 고정 입력으로 대조한다. 같은 ARRAYS.json 안의 다른 주장 필드끼리만 비교하는 것으로 닫지 않는다. 별도 승인 시험에는 **배열·메타·로컬 MANIFEST를 함께 바꾸는 반례**와 같은 분기의 정상 대조를 넣는다.

### C4-0A-N2 마지막 기록 이후에도 시간 한도를 판정

**P2 · `bms-balancing/scripts/reil_c4_monitor.py:317–339`.** `final_record`는 파일 쓰기 전에는 `limit_s`를 확인하지만, 마지막 직렬화·쓰기·재읽기·해시·용량 합산 뒤에는 확인하지 않는다. 예를 들어 한 파일, `t0=0`, `limit_s=1`, 첫 시각 0, 마지막 시각 2라면 출력 크기가 작다는 이유로 `record_state=COMPLETE`와 `final_snapshot_s=2`를 함께 돌려준다. 이는 영구 블로킹이 아닌 정상적으로 돌아온 느린 쓰기에서도 발생한다. [고정 코드](https://github.com/yonghoon7153-source/Yonghoon-DEM-DFT/blob/c542e056b33d25100bc0519ce492c98d3bcce172/bms-balancing/scripts/reil_c4_monitor.py#L317)

마지막 쓰기·재읽기·해시·크기 대조 뒤 시각을 한 번 얻고, 같은 값으로 한도 판정과 반환 snapshot을 만든다. 초과하면 저장 파일·해시를 남긴 채 미완으로 반환한다. 마지막 쓰기 또는 크기 조회가 한도를 넘는 합성 사례를 분리해 확인한다. 현재 두 final_record 시험은 크기 초과와 정상 경로만 다룬다. 기존 2,074초 실행 기록을 초과로 판정하거나 새 예산을 요구하는 지적은 아니다.

### C4-0A-N3 종료 직전 느린 디스크 조회가 RSS 공백을 숨기지 않도록 수정

**P2 · `bms-balancing/scripts/reil_c4_monitor.py:269–280`.** RSS 공백은 다음 `rss_w.observe`에서만 확인한다. 마지막 `worker_end`를 받은 루프에서 RSS가 5.01초에 정상 도착하고 디스크 조회가 6초 걸려 11.01초에 돌아왔다고 하자. 이전 디스크 표본이 약 0.02초였다면 디스크 간격은 15초 이내이고 전체 마감도 30초 이내다. 하지만 RSS 표본은 이미 6초 전이다. 현재 코드는 작업자 종료 분기에서 그대로 빠져 `global_stop=None`을 반환한다. 감시 대상에는 그동안 살아 있는 부모도 포함된다. [고정 코드](https://github.com/yonghoon7153-source/Yonghoon-DEM-DFT/blob/c542e056b33d25100bc0519ce492c98d3bcce172/bms-balancing/scripts/reil_c4_monitor.py#L269)

느릴 수 있는 조회 뒤와 정상 종결 직전에 **두 감시기의 마지막 유효 표본 시각**을 현재 시각과 대조한다. 신선도 확인만으로 새 표본을 만들거나 last_valid를 갱신하지 않는다. 느린 디스크 뒤 마지막 정상 종료 분기의 음성 사례와, 두 간격 안에서 종료하는 양성 사례를 추가한다. OS 하드 제한이나 영구 블로킹 강제 종료를 새로 요구하는 것은 아니다.

### C4-0A-N4 구조 오류의 중간 계수를 작업자 경계에서 보존

**P2 · `bms-balancing/scripts/reil_c4_monitor.py:160–162`; 생산부 `reil_c4_e3a.py:273–275`.** E3a는 구조 오류를 올릴 때 task 식별과 당시 `st`를 `Structural.partial`에 넣는다. 하지만 작업자는 `s.info`만 보내며 partial을 버린다. 그 결과 여러 평가 뒤 구조 오류가 나면 비유한·전극 영역 밖·상자/G 위반 계수가 사라진다. 오류 종류·traceback은 info에 남고 n_eval은 공유 progress로 남을 수 있으므로, 전체 오류나 평가 수가 모두 사라진다고 확대하지 않는다. [고정 코드](https://github.com/yonghoon7153-source/Yonghoon-DEM-DFT/blob/c542e056b33d25100bc0519ce492c98d3bcce172/bms-balancing/scripts/reil_c4_monitor.py#L160)

구조 오류 이벤트에 별도 partial 필드를 직렬화해 부모까지 전달한다. 전역 중지와 `STARTED_INTERRUPTED`는 유지하고 정상 완료 행으로 바꾸지 않는다. 이미 만든 중간 계수가 실제 worker→supervisor 경계 뒤에도 남는 합성 사례로 닫는다. 실제 E3a 자료 실행에서 기록 손실을 관측했다는 주장은 아니다.

## 요청한 질문에 대한 답

1. **감시 보완:** arrival 기준 공백 검사·명시 마감·소유 경로·용량 합산 방향은 수용한다. N2/N3/N4가 남아 종결은 보류한다.
2. **E3a 기록:** 선택 목적 및 전체 목적의 비유한 계수, 예외로 끝난 평가 시도 계수, 기존 dVdQ 호출을 통한 영역 밖 라벨, X/F/G·None 구분, 정확 유리수 잔차와 success 분리는 검토 경로에서 타당하다. N4의 전달 누락은 보완한다. 실제 자료 재실행 완료 판정이나 275회 optimizer 실행 증명이 아니다.
3. **오류 위치:** traceback 안쪽부터 util/우리 wrapper를 구분하는 규칙을 수용한다. 외부 라이브러리 오류를 util 호출 경로로 분류한다는 뜻이지 원인 규명이나 환경 정상의 증명은 아니다. 다음 한정 검증에는 wrapper 내부 오류도 정확히 구조 오류로 가는 대조를 포함하는 것이 좋다. 보존 util 내부에서 삼킨 예외까지 새 wrapper가 관측한다고 주장하지 않는다.
4. **배열 3종 이월:** H 실행기와 같은 코드 경로에서 생성한다는 설계는 합리적이다. 다만 §39의 완료 조건을 실행자가 바꾼 사실은 남는다. **Phase A 4개 완료 / 나머지 3종 미완·0b 이월 제안**으로 수용하고, 사용자 0b 착수 확인 때 목록·배정·봉인 시점을 명시한다. 검토자가 사후 사용자 승인을 만들어 주지는 않는다. 첫 확인적 C4 국소 실행 전 전체 고정 배열 봉인, 동시 Sobol 16개 전부 봉인·앞 12개만 사용 조건을 유지한다.
5. **deepcopy와 순서:** 고정 util의 objective 입력 키와 덧쓰는 출력 키가 달라 호출마다 사본을 쓰는 수치적 근거는 타당하다. GA 0–19 / NSGA 1의 명시 seed 때문에 독립 호출의 case 순 배정도 수용 가능하다. 시간·경고 순서·노트북의 변이된 Model 객체까지 동일하거나 실제 계산 결과의 비트 동일성이 시험됐다는 뜻은 아니다.
6. **GREEN 전 정적 수정 3건:** 합집합·행 집합 비교·F=None 처리 모두 의도와 일치한다. GREEN 이전 편집을 자동 재시험으로 세지 않는다. 원문과 시험 SHA 결속은 유지한다.
7. **합성 NSGA2와 캐시:** 실제 util 합성 사례는 반환과 util-local 오류 모두 허용한 계약 시험이다. 보존 결과만으로 어느 분기였는지 또는 NSGA2 완주를 판정할 수 없다. 지금 재실행을 요구하지 않는다. 향후 승인 시험에서 구조화한 outcome을 별도 저장하면 된다. 2.5초/17.5초 차이의 캐시 설명은 미확인 가설로 유지한다.
8. **다음 순서:** 네 항목의 좁은 보완 및 한정 검증 범위를 먼저 사용자에게 제시한다. 기존 배열·환경·26개 기록을 보존하고, 이번 검토를 반복 전체 suite·재설치·새 자료 실행 권한으로 쓰지 않는다. 종결 뒤 0b 범위와 이월 배열을 사용자에게 확인한다. §41도 그 확인을 면제하지 않는다.

## 실행 경계

현재 CLI는 identity·seal-arrays·계획 건조이며 실제 자료용 supervise/final_record 연결 명령은 아직 없다. 비용 실행 전에는 승인된 단일 원점·reserve·호출당 상한, 같은 전체 출력 루트, 모든 중지/미완 반환의 소비와 소유 정리까지 연결해야 한다. 이번 검토로 C4-E/A/B 준비 완료나 자료 개봉을 허가하지 않는다. COMSOL 및 별도 gate 작업과도 무관하다.
