## 1. P0 — 장부가 존재하기만 하면, 누락된 비용을 0으로 인정합니다.

위치: [melt_quench_uma.py (line 1077)](<codex>/source/tools/ionic/melt_quench_uma.py:1077), [li2s2_stage1_runner.py (line 306)](<codex>/source/tools/ionic/li2s2_stage1_runner.py:306).

ledger_cost()는 장부의 행을 합하지만, 판정 대상 실행들이 모두 장부에 있는지, 비용이 비음수인지, 실행이 종료됐는지 확인하지 않습니다. 다음은 완결된 합성 10런 자료에 대한 실제 재현입니다.

| 장부 상태 | 수정본 결과 |
|---|---|
| {"runs":[]} | 비용 0, stage1_pass; 러너도 rc 0 |
| 10개 중 비용 행 하나 누락 | 9개 비용만 합해 stage1_pass |
| 각 행 wall_h=-10 | 합계 −100, stage1_pass |
| 모든 행이 running, 최종 비용 없음 | heartbeat 값으로 stage1_pass |

장부를 아예 회수하지 않은 경우도 우회됩니다. 처음에는 pending이지만, 러너가 빈 장부를 만들고 종료합니다. 이후 묶음 판정은 비용 0으로 통과하고, 그 중단을 --ack_stop으로 확인하면 러너도 rc 0입니다. 확인 행위가 잃어버린 비용을 복원하지는 않습니다.

고아 런의 비용도 같은 문제입니다. 마지막 heartbeat·파일 수정 시각은 실행이 적어도 그때까지 이어졌다는 증거이지 종료 시각이 아닙니다. 이후 기록 없이 계산하다 죽었다면 과소계산합니다. 시험에서도 이 어림을 확정 비용처럼 받아 stage1_pass로 올렸습니다.

최소 수정: 장부를 실행 목록과 대조하고, 누락·음수·미종료·비용 미확정은 통과를 막으세요. 기존 산출물이 있는데 장부가 없으면 빈 장부로 초기화하면 안 됩니다. 고아 런은 비용 하한과 확정값을 구분하고, 신뢰할 종료 기록이나 보수적인 비용 상한으로 확인하기 전에는 최종 통과시키지 마세요.

## 3. P0 — 그룹 대표 프로세스가 먼저 종료되면 남은 자식은 정리하지 않습니다.

위치: [li2s2_stage1_runner.py (line 146)](<codex>/source/tools/ionic/li2s2_stage1_runner.py:146), [li2s2_stage1_runner.py (line 261)](<codex>/source/tools/ionic/li2s2_stage1_runner.py:261).

_Proc.stop()은 TERM을 그룹에 보내지만, 이후 기다림과 KILL 여부는 self.p.poll() 하나로 판단합니다. poll()은 직접 실행한 자식의 종료만 확인하며 그룹 전체의 종료를 보증하지 않습니다. Python 공식 문서

실패 시나리오는 대표 프로세스는 TERM으로 종료되고, 같은 그룹의 작업 프로세스는 TERM을 무시하거나 아직 정리 중인 경우입니다. 수정본은 대표 프로세스의 종료를 보고 바로 반환하므로, 남은 그룹에 KILL을 보내지 않습니다. 이미 대표 프로세스가 종료된 상태라면 stop_child()는 종료 시도 자체를 생략합니다.

이 분기는 가짜 프로세스 상태로 재현했습니다. 해당 구성의 실제 Linux 프로세스 실험은 이 환경에서 미확인입니다. 현재의 sleep 시험은 모두 TERM에 종료되는 경우라 이 경로를 검사하지 않습니다.

최소 수정: 직접 자식의 회수와 소유 그룹의 잔존 확인을 분리하세요. 대표가 먼저 끝나도 그룹 정리를 완료해야 하며, 정리 실패를 ended나 "담금질은 멈췄다"로 확정하면 안 됩니다. Linux 시험에는 대표 먼저 종료 + TERM을 무시하는 작업 프로세스를 포함하세요.
