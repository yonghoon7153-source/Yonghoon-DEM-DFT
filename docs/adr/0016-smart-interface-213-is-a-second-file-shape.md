# ADR 0016 — Smart Interface 2.13 은 두 번째 파일 모양이다

- 상태: 채택 (2026-08-24)
- 관련: `packages/wrdkit/src/wrdkit/wrd.py`, `.../schedule.py`,
  `packages/wrdkit/tests/synthetic.py`, ADR 0002, CLAUDE.md §0.6

## 맥락

실험실이 Smart Interface 2.13 으로 올라가면서 새 `.wrd` 가 아예 안 읽혔다:

    unexpected root object 'WbcsFile.Data.DataHeaderBase';
    expected WbcsFile.Data.DataFileHeader

`wrdkit probe` 로 열어 보니 파일 구조가 달랐다. 1.x 는 NRBF 스트림 **둘**
(`DataFileHeader`, `DataHeader`)이 앞에 있고 그 뒤가 행 블록이다. 2.13 은:

```
[스트림 1]  WbcsFile.Data.DataHeaderBase
    Version    = "1.6.0.0"
    HeaderSize = 6767            ← 행 블록이 시작하는 절대 오프셋
    HeaderData = byte[4574]      ← raw DEFLATE (zlib 래퍼 없음)
        └─ 풀면 NRBF 스트림 하나, root = WbcsFile.Data.DataHeaderValues
           1.x 의 두 헤더가 하나로 합쳐진 것 + DataCount·EndTime
[HeaderSize 부터]  행 블록
```

그리고 **결정적인 차이 하나: 2.13 은 컬럼 목록을 선언하지 않는다.**
1.x 의 `DataHeader.ColumnList` 에 해당하는 것이 어디에도 없다.

## 결정

### 1. 두 모양을 한 리더가 읽는다. 갈림길은 루트 클래스 이름 하나다

`DataHeaderBase` 면 봉투를 풀어 안쪽 헤더를 쓰고 행은 `HeaderSize` 부터,
아니면 지금까지의 길. 그 뒤 코드(레이아웃·스캔·사이클·정규화)는 **한 줄도
바뀌지 않는다**. 파일이 어디에 있는지가 달라진 것이지 데이터가 달라진 것이
아니다.

### 2. 컬럼은 이 포맷에서만 하드코딩한다. 그리고 버전으로 잠근다

CLAUDE.md §0.6 은 "컬럼 목록은 파일에서 읽고 하드코딩하지 않는다" 이다. 그
규칙의 이유는 계측기가 컬럼을 바꿔도 우리가 따라가게 하려는 것인데, 2.13 은
**애초에 말해 주지 않는다.** 그래서 여기서만 예외로 두되, 예외가 조용히
번지지 않도록 둘을 건다.

- `DataHeaderBase.Version` 이 아는 값(`1.6.0.0`)일 때만 이 레이아웃을 쓴다.
  모르는 버전이면 **읽지 않고 실패한다** — 한 바이트만 어긋나도 모든 숫자가
  그럴듯하게 틀린다. 못 읽는 것이 조용히 틀리는 것보다 낫다 (§0.4).
- 레이아웃을 어떻게 확정했는지를 코드 주석과 스펙에 남긴다. 근거 없이
  적힌 칸은 컬럼으로 만들지 않는다.

### 3. 확정하지 못한 바이트는 컬럼으로 만들지 않는다

행은 128 바이트인데 우리가 이름을 댈 수 있는 것은 116 바이트뿐이다. 남는
12 바이트(`+116..127`)와 `+40`·`+41` 은 **모른다**. 이름을 붙이면 그 순간
CSV 와 화면에 뜻이 있는 척 나간다. 대신 `_Layout` 이 행 보폭을 따로 받는다.

## 어떻게 확정했나 (실측)

파일: `260630_MJ1 multi step CCCV_holder #1 ref_028.wrd`, 5,349,231 바이트,
41,738행, WBRS50 ch27, app 2.1.3.1.

- **행 크기 128** = (5,349,231 − 6,767) ÷ 41,738, 나머지 0. `DataCount` 와도 일치.
- **`+42` = CELL STATUS**: 전류가 0 인 300행에서 1, 전류가 흐르는 41,438행에서
  3. §3 의 `1=휴지, 3=충전, 4=방전` 과 정확히 일치한다. 사이클 분할이 이 칸에
  걸려 있으므로 이것이 가장 중요한 확정이다.
- **`+43` = 제어 상태**: 1 → 평균 0.324 A, 2 → 평균 0.032 A, 0 → 0 A.
  CC / CV 꼬리 / 휴지다. 스케줄의 CC 설정값 0.35 A 와 맞는다.
- **`+32` = TOTAL STEP**: 1..9 로 여덟 번 바뀌고, 헤더의 `SchStep` 이 정확히 9개.
- **`+4` = TEST TIME**: 유일하게 단조 증가하는 int64, 마지막 41,452 s (11.5 h).
  `+12`·`+20` 은 같은 자리에서 리셋된다 (STEP/CYCLE TIME).
- **`+44` 전압** 2.585–4.250 V, **`+52` 전류** 0–0.352 A, **`+60` CHARGE Q**
  0–3.661 Ah (MJ1 정격 3.5 Ah), **`+76` CHARGE E** 0–13.85 Wh.
- **교차검증**: CC 구간에서 측정된 ΔQ ÷ (I·Δt) 의 중앙값이 **1.0000**. 전류
  단위(A), 용량 단위(Ah), 시간 단위(tick)가 동시에 맞아야 나오는 값이다.

## 곁가지로 드러난 것 둘

- **스케줄이 `_seqDataSet` 로 온다.** 1.x 는 `SeqDataSet`(auto-property)였다.
  한 철자만 보던 `_member` 가 2.13 파일을 **스케줄 없이** 읽었고 — 컷오프도
  C-rate 도 없이 — 화면에는 왜 없는지가 안 나왔다. 이제 auto-property·필드·
  `_camelCase` 를 모두 본다.
- **CV 스텝의 값을 전류로 넣고 있었다.** CV 의 `Value` 는 전압인데
  `current_a` 에 들어갔다. 드러날 파일이 없었을 뿐 오래된 버그다 — 이 파일은
  multi-step CCCV 를 CC/CV 스텝으로 번갈아 써서 `4.25` 를 "4.25 A" 로
  만들었고, 그 값은 C-rate 자동 채움까지 타고 들어간다.

## 결과

- 실측 파일이 읽힌다: 41,738행, `trailing_bytes` 0, 스케줄 9스텝.
- 합성 픽스처가 2.13 파일을 **쓴다** (`build_wrd_sif213`). 리더와 라이터가
  서로를 검증하므로 레이아웃이 계약으로 고정된다.
- 새 테스트 8건. 실측 파일로 `WRDKIT_SAMPLE=... pytest` 366건 통과.

## 하지 않은 것

- `+40`·`+41`·끝 12바이트의 의미. 우리가 쓰는 수치와 무관하고, 모르는 것을
  이름으로 덮지 않는다.
- 1.6.0.0 이 아닌 2.x 헤더. 만나면 `probe` 로 보고 여기에 한 줄 더 적는다.
