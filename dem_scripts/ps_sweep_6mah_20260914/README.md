## 4-보. ⛔ `maxattempt` — 원본과 **다른** 실행 파라미터 (사고 `PS-01`, **2026-09-16 정정판**)

원본은 `maxattempt 15000` 이고 이 덱들은 **10000** 이다.  ★ 실측: **5/5 · 100 % ·
`Less insertions` 경고 0**.

### 원인은 **int32 오버플로**다 (소스 판독으로 확정)

```cpp
// LIGGGHTS-PUBLIC  fix_insert_pack.cpp  L403-407
int FixInsertPack::calc_maxtry(int ninsert_this_local)
{ return ninsert_this_local * maxattempt; }      // ← int 곱셈
// L465
while(ntry < maxtry && ninserted_this_local < ninsert_this_local) { … }
```

`ninsert_this_local × maxattempt` 가 int32 를 넘으면 **랩되어 음수**가 되고, 그러면 `while` 이
첫 판정에서 거짓이라 **루프가 한 번도 안 돈다**.  서명은 **0.05초에 0개**다.

⇒ `maxattempt` 는 수치 예산이 아니라 **proc 누적 탐색 배수**다 (LIGGGHTS 기본값 **50**).
40만·2천만은 설계 범위를 한참 벗어난 값이고 **늘릴수록 악화**된다.

**안전 조건** `n_local × maxattempt < 2^31`.  1 proc 최악(162,095)에서 `maxattempt < 13,248`
⇒ `-np` 가 바뀌는 상황이므로 **10,000** 을 쓴다 (1 proc 에서도 안전).

### ⛔⛔ 이 절의 **초판은 틀렸다** — 지우지 않고 정정으로 덮는다

초판은 *"`maxattempt` 는 입자당이 아니라 삽입 전체의 시도 예산이고, 15,000 으로 159,167 개를
요청하면 입자당 0.094 회라 모자라서 0 개가 된다"* 고 적었고, 생성기에 **하한**
(`≥ 1.2 × 예상 입자수`, 바닥 200,000)을 강제했다.

**방향부터 틀렸다.**  참 제약은 **상한**이고, 그 하한 규약은 오버플로를 향해 **미는** 규칙이었다.
- `15,000 × 159,167 = 2.388e9 > 2^31` ⇒ 초판이 *"예산 부족"* 이라 부른 실패는 **오버플로**다.
- 초판이 *"통과 확인값"* 이라 부른 **200,000 과 400,000 은 이제 생성기가 거부한다.**

⚠ 정정판도 완전하지 않다 — 전문가 검산은 **4행 중 1행만** 맞았다 (`n_local` 추정이 부정확;
`distribute_ninsert_this` 의 나머지 분배에 난수가 들어간다).  **실측 `n_local` 은 아직 없다.**
`0.05초에 0개` 라는 서명을 만드는 경로가 오버플로뿐이라 채택했고, 처방이 실측으로 닫혔다.

### ★ 덱이 이제 **스스로 검사한다**

감사 지적(*"삽입 뒤 개수 검사가 전혀 없다"*)에 따라 각 덱이 `unfix ins_mix` 직후에:

```
variable n_ins equal count(all)
if "${n_ins} < <예상의 99 %>" then "print 'FATAL: partial insertion …'" "quit 1"
```

바닥 **99 %** 의 근거 — 성공은 예측치 **±1**, 실패는 0 · 16,202(10 %) · 119,679(74 %) ·
142,965(90 %) 였다.  둘 사이가 비어 있어 99 % 가 깨끗이 가른다.
⛔ **부분 삽입 침대는 조성이 달라 다른 물건이다** — 완주시키지 않는다.

★ 부수 소득 — 삽입 총수가 **예측치와 일치**한다 (10:0 159,167/159,167 · 0:10 163,349/163,349).
§2 의 *"런 뒤 실제 개수와 대조할 것"* 이 닫혔고, 분포가 질량분율로 읽힌다는 규약이 재확인됐다.

⚠ **아직 못 푼 것**: 원본 `real_4` 는 `maxattempt 15000` 으로 같은 규모를 넣고 완주했다
(`docs/data/phase_a_6mah/precompute.json`).  같은 값이 지금 빌드에선 0 이 된다 ⇒ **4/21 세대와
LIGGGHTS 빌드/버전이 다르다.**  침대 비교 자체를 막지는 않지만 *"원본과 같은 조건"* 이라고
쓰려면 확인이 필요하다.

## 4-보-2. ⛔ `processors * * 1` 과 **랭크 상한 2** (사고 `PS-01` 둘째 원인)

`maxattempt` 를 고쳐도 **2랭크에서 여전히 0 개**가 들어갔다.  원인은 **MPI 분해 축**이다.

⛔⛔ **정정 2026-09-16** — 아래 표의 실측은 전부 `maxattempt 400,000`(오버플로 구간)에서
잰 것이다.  **관측 자체는 유효하지만 해석은 바뀐다**: `np` 가 커지면 `n_local` 이 작아져
랩이 덜 일어나므로, 표의 `np` 의존은 **분해 축이 아니라 오버플로를 재고 있었다**.
`processors * * 1` 은 부하 균형상 **유지**하되(침대가 z 0~0.14 인데 박스가 z 1.0 까지라
z 를 쪼개면 대부분 proc 이 빈 공간을 맡는다), *"랭크 상한 2"* 는 오버플로가 고쳐진 뒤
**재측정 대상**이다.  지우지 않고 남긴다 — 무엇을 잘못 읽었는지가 기록이다.


박스가 0.05 × 0.05 × **1.01 m** 로 z 로 극단적으로 길어서 LIGGGHTS 가 z 를 쪼갠다
(`1 by 1 by P`).  삽입 영역은 z 0.005–0.30 이라 **한 proc 에만** 걸리고, 나머지 proc 은
영역이 없는데도 배정을 받아 전부 실패한다.  `processors * * 1` 로 x·y 로만 쪼개면
모든 proc 이 z 전 구간과 영역을 공유한다.

| np | 격자 | `maxattempt` | 삽입 (요청 159,167) | |
|---:|---|---:|---:|---|
| 1 | — | 200,000 | **159,167** | ✓ 경고 없음 |
| **2** | `2 by 1 by 1` | 400,000 | **159,167** | ✓ 경고 없음 · **생산 규약** |
| 2 | `1 by 1 by 2` | 400,000 | 0 | ⛔ |
| 4 | `2 by 2 by 1` | 400,000 | 0 | ⛔ |
| 4 | `2 by 2 by 1` | 4,000,000 | 119,679 | ⛔ |
| 10 | `5 by 2 by 1` | 400,000 | 142,965 | ⛔ |
| 10 | `5 by 2 by 1` | 4,000,000 | 16,202 | ⛔ |

⚠⚠ **기전을 모른다.**  예산에도 랭크에도 단조롭지 않다 — 예산을 10배 올리면 np=4 는
0 → 119,679 로 **늘고** np=10 은 142,965 → 16,202 로 **줄었다**.  `16,202` 가 마침
`159,167 − 142,965` 와 정확히 같은 것도 설명하지 못한다.  np=10 의 x 폭 0.01 m 가 AM_P
지름 0.009 m 와 거의 같은 것은 부분 원인일 수 있으나, np=4 (0.025 m = 충분히 넓다)가
0 인 것은 그것으로 설명되지 않는다.

⇒ 기전 대신 **관측을 규약으로 쓴다**: `np ∈ {1, 2}` 만 정확한 개수를 냈다.  생성기가
`--mpi > 2` 를 **거부**한다 (`--allow-unverified-mpi` 로만 강행 가능).

⛔ **부분 삽입 런은 전량 폐기한다.**  10 % 빠진 침대는 조성이 다른 **다른 물건**이다.
런마다 아래를 확인할 것 — `Less insertions` 가 한 줄이라도 뜨면 그 런은 버린다.

```bash
grep -E "inserted [0-9]+ particle|Less insertions" <케이스>/log.liggghts
```
