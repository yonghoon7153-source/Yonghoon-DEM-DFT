# ADR 0031 — 고정 주소는 우리 도메인 + Cloudflare 터널로 얻는다

- 상태: 보류 (2026-08-26)
  — 이 랩이 7844 를 막아 **여기서는 못 쓴다** (아래 실측).  코드와 시험은 남긴다:
  판단이 틀린 것이 아니라 망이 다르다.  7844 가 열린 곳에서는 이 결정 그대로 된다.
- 관련: ADR 0014(터널과 공유 암호), ADR 0030(이름이 막힌 기계의 중계기),
  `tools/bml` 의 `tunnel_via_named` · `cmd_share_cf` · `cf_setup_steps`
- 대체: ADR 0030 을 대체하지 않는다 — 중계기는 그대로 남는다.  다만 이 결정이
  통하면 **중계기를 쓸 일 자체가 없어진다** (아래 "덤" 참고).

## 맥락

터널 주소가 열 때마다 바뀐다.  그 하나에서 이 저장소의 성가신 것 대부분이
나왔다:

- 다른 기계는 주소가 바뀔 때마다 `bmlout <새 주소>` 를 다시 쳐야 한다.
- 랩 망의 DNS 가 터널 도메인을 거르는 기계에서는 그때마다 IP 를 다시 구하고
  중계기를 다시 띄워야 한다 (ADR 0030).
- 서버를 재시작하면 터널이 죽고 주소가 또 바뀐다 (그래서 `--keep-tunnel` 을
  만들었다).

localhost.run 은 키를 등록해 인증까지 돼도 (`authn: … authenticated`) 무료
티어의 주소를 계속 랜덤으로 준다 — 실측으로 확인했고, 저쪽 배너가 직접
"custom domains → admin.localhost.run" 이라고 적어 준다.  **주소를 고정하는
길은 우리 도메인뿐이다.**

도메인을 샀다 (`bmlwork.kr`, 28,600원/년).  그 도메인을 어디에 물릴지가 이
결정이다.

## 두 갈래

| | localhost.run 커스텀 도메인 | Cloudflare 터널 (named) |
|---|---|---|
| 값 | **$9/월 (연납) ≈ 15만원/년** | **무료** (2026-07 부터 조건 없음) |
| 등록기관 쪽 | CNAME 한 줄 | 네임서버를 Cloudflare 로 |
| `bml` 쪽 | 이미 짜여 있었다 | 새로 붙여야 했다 |
| 붙는 자격 | 등록한 SSH 키 | 대시보드가 주는 토큰 |
| 주소 고정 | 된다 | 된다 |

결과가 같은데 한쪽만 돈이 든다.  그것도 한 번이 아니라 매년, 이 워크벤치가
사는 내내.  **Cloudflare 를 고른다.**

값이 유일한 이유는 아니다.  터널 프로그램(`cloudflared`)은 `bml` 이 이미
받아서 쓰고 있었고 (`ensure_cloudflared`), 랜덤 주소 쪽 길이 그것으로 돌고
있었다.  이름을 붙이는 것은 그 위에 한 겹이지 새 의존이 아니다.

## 결정

`.bml/env` 에 **둘 다** 있을 때만 우리 이름으로 연다:

    WORKBENCH_CF_TOKEN     대시보드가 준 터널 토큰   (bml share cf <토큰>)
    WORKBENCH_TUNNEL_DOMAIN  그때 열 이름             (bml share domain <이름>)

    cloudflared tunnel --no-autoupdate run --token <토큰>

어느 이름으로 나갈지는 **대시보드에 있다** (Public Hostname → `HTTP
localhost:5003`).  `cloudflared` 는 그것을 모른 채 연결만 맺으므로 **로그에
주소를 안 찍는다.**  그래서 로그를 훑는 `try_tunnel` 로는 영영 주소를 못 얻고
60번 세다 실패로 끝난다.  `try_tunnel_named` 는 우리가 아는 주소를 쓰고,
**열렸는지는 똑같이 확인한다** (`confirm_tunnel` 을 둘이 공유한다 — 갈라 두면
한쪽만 고치는 날이 온다).

### 하나만 적혀 있으면 안 연다

토큰만 있으면 어느 주소로 나갔는지 이쪽이 모른다 — 확인할 대상이 없으니
확인을 건너뛰게 되고, 그 순간 화면이 거짓말을 한다.  이름만 있으면 붙을
자격이 없어 아무 데도 안 나온다.  둘 다 `bml share` 전에 `bml status` 가
말해 준다.

### 실패해도 랜덤 주소로 흘러가지 않는다

이것이 이 결정에서 제일 중요한 한 줄이다.  고정 주소를 설정해 둔 사람은
"열렸습니다" 를 보고 `bml.bmlwork.kr` 을 남에게 알려 주는데, 정작 열린 것이
`xxxx.trycloudflare.com` 이면 **화면은 성공이고 상대는 아무것도 못 연다.**
그 어긋남은 상대가 연락해 오기 전까지 아무도 모른다.  그래서 우리 이름이
설정돼 있으면 그 길뿐이고, 안 되면 안 됐다고 말하고 멈춘다.

## 덤 — 이쪽이 주소 고정보다 크다

랩 망의 DNS 차단은 **알려진 터널 도메인 목록**이지 우리 이름이 아니다.
`bmlwork.kr` 은 그 목록에 없다.  그러면 받는 쪽에서 이름이 그냥 풀려서
`bmlonly`·중계기(ADR 0030)·IP 전달이 **통째로 필요 없어진다.**

중계기 코드는 지운 것이 아니라 남겨 둔다.  다음에 또 어떤 이름이 막힐지 모르고,
그때 처음부터 다시 만드는 것보다 낫다.

## 실측 — 이 랩은 7844 를 막는다 (2026-08-26)

세워 놓고 돌려 봤다.  **안 된다.**

    공용 DNS 로 진짜 엣지 IPv4 를 구했다:  198.41.192.27 · 198.41.192.7
    그 IP 에 직접 TCP 7844:                 못 붙는다
    cloudflared 로 quic(UDP) → http2(TCP):  둘 다 못 붙는다

이 기계의 해석기는 같은 이름에 **IPv6 만** 준다 (`2606:4700:a0::1` … `::10`).
A 레코드가 안 나온다.  그것과 무관하게 진짜 IPv4 엣지에도 못 붙으므로, 이름
문제가 아니라 **포트 문제**다.

`cloudflared` 는 7844 로만 나간다 — quic 은 UDP 7844, http2 는 TCP 7844, 443 은
갱신·토큰 확인용이지 데이터 길이가 아니다 (Cloudflare 문서).  그래서 이 망에서는
어떤 설정으로도 안 된다.

**틀린 것은 판단이 아니라 전제였다.**  "Cloudflare 가 무료이고 결과가 같다" 는
지금도 맞다.  다만 이 랩이 그 포트를 막는다.  7844 가 열린 망에서는 이 ADR
그대로 된다 — 그래서 코드도 시험도 지우지 않는다.

**도메인과 Cloudflare DNS 는 그대로 쓴다.**  이 결정에서 산 것 중 죽은 것은
`cloudflared` 한 갈래뿐이다: 이름은 여전히 우리 것이고, 랩의 DNS 차단 목록에도
없고, DNS 를 우리가 즉시 고칠 수 있게 된 것(TXT 레코드 등)은 다음 길에서 그대로
쓴다.  Cloudflare 요금은 0원이었으므로 잃은 돈도 없다.

## 결과

주소가 안 바뀐다.  다른 기계는 `bmlout https://bml.bmlwork.kr` 을 **한 번만**
치면 되고, 서버를 재시작해도 그대로다.  받는 쪽에서 이름이 풀리므로 `bmlonly`·
중계기·IP 전달 절차가 통째로 빠진다.  값은 0원이다.

## 대가

- **네임서버가 Cloudflare 로 간다.**  등록기관(후이즈)의 DNS 화면은 이제 아무
  일도 안 한다.  도메인 소유권은 그대로다.
- **업로드 한 파일이 100 MB 를 넘으면 Cloudflare 가 막는다** (무료 요금제).
  우리 서버 상한은 512 MB 라, **랩 안에서 되던 파일이 밖에서만 안 되는** 경우가
  생긴다.  그때 413 은 Cloudflare 가 주는 것이라 화면은 우리 탓처럼 보인다 —
  그래서 `cf_setup_steps` 가 미리 말해 둔다.
- **토큰이 하나 더 생긴다.**  가진 사람은 그 터널로 붙을 수 있으므로 암호와
  같은 급으로 다룬다: `.bml/env` (600, git 에 안 올라간다), 화면에 다시 안 찍고,
  로그에도 안 남긴다.
