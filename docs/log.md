## [2026-08-21] create | 누가 무엇을 했는지 — 이름과 활동 기록
서버를 하나로 모으니 바로 나온 질문이다. 이름 하나를 브라우저에 저장해서 모든
요청에 헤더로 보내고, 저장된 것에 붙인다. 검증하지 않는다 — 이 랩의 질문은
"누가 바꿨어" 이지 "네가 너임을 증명해라" 가 아니다 (ADR 0012).

`created_by`/`updated_by` 와 활동 기록은 라우터가 아니라 SQLAlchemy flush
리스너가 쓴다. 새 엔드포인트는 생기는 순간부터 기록되고, 빠뜨릴 곳이 없다.
리스너가 두 단계인 이유: 무엇이 바뀌었는지는 flush 전에만 읽히고, 새 행의 id 는
flush 후에만 존재한다 — 한 곳에서 다 하려다 모든 "추가" 기록의 id 가 비었다.

기록하지 않는 것도 정했다. 사이클 행(업로드 한 번에 만 개), 파서가 채운 필드
(업로드가 두 사건으로 읽힌다), 같은 값을 다시 저장한 것.

헤더 인코딩에서 하나 걸렸다. HTTP 헤더는 ASCII 만 담아서 한글 이름을 그대로
넣으면 요청이 브라우저를 떠나기도 전에 거절된다. 퍼센트 인코딩해서 보내고
서버가 되돌린다. 이 랩 이름은 대부분 한글이라 이게 빠지면 기능 자체가 없다.

같이: 데이터 폴더가 없을 때 bml 이 마운트된 드라이브 목록과 세 갈래 해결책을
같이 보여 준다. 문서의 예시 경로를 그대로 붙여넣은 경우가 가장 흔한데, 그때는
"드라이브를 꽂으세요" 가 오히려 오답이다.

## [2026-08-21] feat | 시험 조건 입력 — 라이브러리에서 비어 보이던 칸들

C-rate 는 계측기가 아는 값이라 스케줄에서 채운다 (CLAUDE.md §0.3). 형성 C-rate

전혀 다른 시험이다.

`num()` 이 0.2 를 "0.20" 으로 쓰는 것을 두 번째로 만나서 `plain()` 으로 뺐다 —
측정값을 유효숫자로 맞추는 것과 적힌 값을 그대로 보여 주는 것은 다른 일이다.

`curl 로 직접 확인` 한 줄로 끝났다. 1분을 이미 물어봐 놓고 답을 안 보여 준
것이다. 그 한 문장이 대처가 전혀 다른 셋을 한 덩어리로 만든다: **000**(이
기계가 그 주소로 못 나갔다 — 7844 를 막는 망은 처음 보는 도메인도 같이 막는
일이 흔해서, 정작 상대 쪽에서는 열려 있다), **5xx**(터널이 아직 우리 서버에
못 붙었다), **404**(엉뚱한 서버). 이제 마지막으로 본 코드를 `tunnel.last-code`
에 남기고 `tunnel_code_meaning()` 이 뜻을 붙인다. 000 이면 "먼저 상대에게
찔러 달라고 하라" 로 안내한다 — 여기서 주소를 버리면 열린 터널을 손으로 닫는
셈이다. `bml status` 의 '공유 주소' 줄도 같은 말을 쓴다.

곁들여, 터널 프로그램이 이미 죽은 경우(`try_tunnel` 반환 3)를 살아 있는
경우(2)와 갈랐다. ssh 가 `remote port forwarding failed` 로 3초 만에 끝나도
우리는 남은 57초를 죽은 주소에 대고 물어봤고, 그 뒤 "그래도 열어 둡니다" 로
죽은 주소를 내보냈다 — `bml status` 는 그 주소를 아예 인정하지 않으므로 둘이
어긋났다. `wait_until_alive` 가 pid 를 함께 보고, 죽었으면 곧바로 접는다.
여기서 `kill -0` 만으로는 부족했다 — 터널은 `disown` 한 자식이라 끝나도 우리가
거두지 않아 좀비로 남고, 좀비에게도 `kill -0` 은 성공한다. `process_alive()` 가
`/proc/<pid>/stat` 의 상태 글자까지 본다. 회귀 테스트는
`tools/tests/test_bml_tunnel.sh` (Makefile·CI 에 등록).

## [2026-08-22] fix | 000 이 어느 층에서 끊긴 것인지까지 짚는다
실측: `curl https://a1ef13c23c42c8.lhr.life/api/health` →
`OpenSSL SSL_connect: SSL_ERROR_SYSCALL` / `000`. 이름은 풀렸고 443 에도
붙었는데 **TLS 손을 잡다가 끊겼다** — 7844/TCP 를 막던 그 망의 장비가 SNI 에
찍힌 `lhr.life` 를 보고 끊은 것이다. 터널은 멀쩡히 살아 있었고, 다른 망에서는
열리는 주소였다.

그런데 `000` 한 덩어리로는 이것이 (a) 이름이 없다(터널이 닫혔다) (b) 443 에
못 붙는다(나가는 길이 막혔다) (c) TLS 가 중간에서 끊긴다(도메인 차단) 중
무엇인지 갈리지 않는다. 셋의 다음 수가 정반대다 — (a) 는 다시 열어야 하고,
(c) 는 **아무것도 하지 말고 상대에게 주소를 그대로 줘야 한다.** (c) 를 (a) 로
읽으면 멀쩡한 터널을 손으로 닫고 처음부터 다시 하게 된다.

`tunnel_block_layer()` 가 dns → tcp → tls 순으로 한 층씩 짚는다
(getent / `/dev/tcp` / curl). tls·tcp 로 판정되면 `bml share` 와 `bml status`
가 "터널 문제가 아닙니다 — 이 기계의 망이 막습니다" 로 단정하고, 다시 열라는
안내를 **하지 않으며**, 이 기계에서는 `localhost:5003` 을 쓰라고 한다.
도구가 없으면 그 층은 `unknown` 으로 두고 단정하지 않는다 (§0.4).
