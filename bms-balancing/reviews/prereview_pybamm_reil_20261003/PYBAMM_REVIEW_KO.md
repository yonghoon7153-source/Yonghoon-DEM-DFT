# PyBaMM 환경 고정 사전 검토

2026-10-03. 게이트 차수 밖의 설계 의견이다. 대상은 커밋 00ed85b4402169bae788b7269ffe69d76a0c40aa이며 구현·설치·측정·requirements 변경 승인이 아니다. G87-N1 및 GATE88과 분리한다.

## 결론

환경 고정은 필요하다. 다만 A–E 중 하나를 모든 용도에 적용하기보다 **정본 재생성용 B 프로필, 현재 검증용 C 프로필, 새 생산을 통제하는 D를 구분**하는 것이 맞다. A 상한만 또는 E 문서 경고만은 생산 재현성 통제가 아니다.

현재 검증 환경 C를 우선 동결하되 이를 정본 생산 환경과 같다고 선언하지 않는다. 정본을 다시 만드는 작업은 B에 해당하는 역사적 환경을 복원·확인하거나, 명시적으로 새 세대 생산으로 분류해야 한다. 기존 정본의 데이터 검증을 수행하는 validator까지 무조건 역사적 producer 환경으로 되돌릴 필요는 없다.

## 근거 대조와 정정 세 건

### P1 버전 차이의 크기와 원인을 분리해야 한다

[요청문 §1](https://github.com/yonghoon7153-source/Yonghoon-DEM-DFT/blob/00ed85b4402169bae788b7269ffe69d76a0c40aa/degradation-degeneracy/docs/22p_gap/PYBAMM_PIN_PREREVIEW_20261003.md#L21)의 “균일 격자면 6e-8 V”는 두 조건 전체에 대한 요약으로는 부정확하다. [10월 1일 원문](https://github.com/yonghoon7153-source/Yonghoon-DEM-DFT/blob/00ed85b4402169bae788b7269ffe69d76a0c40aa/wiki/raw/repositories/2026-10-01-pybamm-26.8-vs-26.9-synthetic-truth.md#L48)은 다음과 같다.

| 동일한 균일화 설정에서 비교한 조건 | full-cell 최대 차이 |
|---|---:|
| pristine | 3.614e-4 V = 0.3614 mV |
| degraded | 6.002e-8 V |

또한 26.8/26.9 비교에서는 PyBaMM뿐 아니라 pybammsolvers 0.9.1→0.10.0, CasADi 3.7.2→3.8.1도 달라졌다. 관측된 2.707 mV는 이 두 환경의 차이다. 이것을 PR #5755 하나의 효과로 확정하거나 균일 격자에서 남은 차이를 solver만의 효과로 확정할 수 없다. 균일화 비교는 격자 해상도도 바꿨다.

공식 [PR #5755](https://github.com/pybamm-team/PyBaMM/pull/5755)는 비균일 노드 간격의 보간·외삽을 수정한다. 이는 메커니즘상 관련 근거지만, 해당 두 환경 비교에서 다른 변경의 기여를 제거한 대조는 아니다. 원문 수치와 이 한계를 같이 보존하면 된다. 이번 결정을 위해 #5755 원인 분리 실험을 새 필수 과제로 추가할 필요는 없다.

### P2 패키지 세 개 고정과 재현 환경 전체 고정은 다르다

요청문 B의 “정본 재생성 환경의 drift 전부”는 “명시한 세 배포판의 버전 drift”로 좁혀야 한다. Python, NumPy/SciPy, 플랫폼·아키텍처, native 라이브러리, 실제 wheel/source 및 로컬 패치, solver 옵션이 남는다.

특히 제출된 #5813 비교는 PyBaMM 버전 문자열을 유지한 패치 환경에서도 바이트가 바뀌는 사례다. 공식 [PR #5813](https://github.com/pybamm-team/PyBaMM/pull/5813)는 auxiliary domain을 통한 좌표 의존성과 평균 연산을 수정한다. 고정 버전이 최신 물리 정확성의 보증은 아니고, 알려진 버그 수정을 영원히 금지하자는 뜻도 아니다. 수치가 달라지는 업데이트는 새 프로필·새 세대로 다루자는 뜻이다.

운영 프로필에는 Python/플랫폼, 전이 의존성을 포함한 lock, 배포 파일 해시 및 패치 여부를 연결한다. 설치 해시만으로 설치 후 소스 변경까지 감지했다고 하지 않는다. 필요한 production 파일의 실제 origin·무결성 확인 범위를 정한다. [pip 공식 문서](https://pip.pypa.io/en/stable/topics/repeatable-installs/)도 버전 고정, 해시 확인, 플랫폼별 wheel 묶음을 서로 다른 재현 수준으로 설명한다.

요청문에 함께 등장하는 requirements 주석 Python 3.11과 역사적 생산 Python 3.10.12는 섞지 않는다. 후자는 요청문·인계문이 인용하는 값이며, 실제 B 프로필 확정 때 producer manifest와 당시 환경 기록으로 확인할 대상이다.

### P3 환경 식별 기록과 허용 환경 강제는 별개다

고정 소스에서 확인한 범위:

- src/io.py:233–275는 Python·플랫폼 및 주요 패키지를 기록한다.
- src/io.py:1344–1348은 effective_solver의 필수 정보 존재를 검사한다.
- src/grid.py:264–266은 실제 solver와 환경을 서명에 넣는다.
- src/grid.py:273–298은 worker의 solver가 parent 서명과 같은지 검사한다. 이는 청크 저장 전 검사이며, 승인된 프로필로 생산하기 위한 최초 허가 검사와 같지 않다.
- src/runner.py:36 이후에는 IDAKLU 생성 실패 시 CasADi fallback 경로가 있다.

따라서 “환경을 전혀 기록하지 않는다”는 평가는 틀리다. 현재 부족한 것은 **독립적으로 승인된 expected profile과 새 생산 환경의 대조**다. 실행 환경을 그대로 읽어 expected identity를 만드는 D는 이 문제를 해결하지 못한다.

## 비교를 승인할 때 고정할 범위

두 조건은 초기 sentinel로는 유용하지만 전체 3,069조건·경계 사례를 대표한다고 볼 근거는 없다. “약 10초”도 해당 제출자의 예상이지 설치·기동·실패 기록까지 포함한 보장 예산이 아니다.

1. **목적부터 구분한다.** 원본 파일 보존은 원본 SHA 불변, bitwise replay는 대응 수치의 정확 일치, 새 세대의 과학적 호환성은 사전 허용치와 영향 범위의 문제다. 서로 대체하지 않는다.
2. **환경을 한 묶음으로 대조한다.** Python이 다르면 환경 간 비교로 명명한다. 라이브러리 한 개의 인과 효과라고 부르지 않는다.
3. **비교 대상은 전압만이 아니다.** 동일 조건·물성·실제 solver/mesh/시간 규칙, 용량과 종료 이벤트, PE/NE/full-cell 값, Li 및 failure classification을 보존한다. 서로 다른 종료점의 SOC 정규화 전압 일치가 절대 용량 차이를 가리지 않게 한다.
4. **문턱은 사용 목적에 맞춰 사전 고정한다.** solver의 rtol/atol 1e-6은 전압 절대 오차 1 μV 보증이 아니다. scientific compatibility를 주장하려면 기존 label 경계·목적함수·효과 크기에 대한 영향을 따로 정한다. 지금 자료만으로 보편적인 새 숫자 문턱을 발명하지 않는다.
5. 두 조건이 통과해도 “선택 두 조건의 sentinel 통과”다. 범위 밖을 포함한 환경 동등성으로 승격하지 않는다. 반대로 미세 차이가 관측됐다고 과거 데이터 검증 결과를 자동 폐기하지 않는다.

## D의 최소 설계와 닫힘 조건

설계상 expected profile → 승인 계획 → parent 실제 환경 → worker 실제 환경 → 산출물/영수증의 연결을 명시한다. 각 단계에서 요청 class와 실제 class, 버전과 설치 바이트/패치, solver 설정을 구분한다.

음성 사례는 최소한 잘못된 배포판, 허용하지 않은 fallback, 같은 버전의 변조, 계획의 profile SHA 변경, worker 불일치, identity 누락, resume 환경 변경을 포함한다. **허가 전 불일치가 solve에 도달하지 않는지**와 저장 후 evidence 검사 양쪽을 따로 확인해야 한다. 이는 다음 승인용 검증 제안이지 이번 실행 지시가 아니다.

역사적 artifact를 읽는 validator와 새 truth를 생산하는 guard를 분리한다. 현 validator가 옛 producer의 자료를 검사할 수 있다는 것과, 현 환경으로 옛 자료를 동일하게 다시 만들 수 있다는 것은 다른 주장이다.
