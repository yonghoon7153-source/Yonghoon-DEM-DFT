## 2. Q2 무엇의 증거로 충분한가

**보충 20은 충분하다.** 믿을 수 있는 최종 핀의 실행기가 만든 원본 JSON+로그에 P0–P10과 E1/E2를 적용하면, 요청한 범위인 전체 입력 지문 일치·등록값 일치·정상 dry-run 완료를 확인할 수 있다. 정상·음성 대조가 함께 성립한다.

다음 문구로 범위를 고정하는 것이 정확하다.

> 최종 핀의 실행기가 생성한 사전 점검 완료 영수증과 전체 로그를 대조하였다. 보충 20의 전체 입력 지문은 등록값 및 반입 파일 재계산과 일치하고, 관측 ON·필수 검사 성공·정상 dry-run 완료를 확인하였다. 이 증거는 실제 생산 완료, 수치 결과의 타당성, 저자의 발사 승인 또는 v1.3 배포 승인을 대신하지 않는다.

한정은 다음 네 가지다.

1. **실제 발사 절차에서는 `--approved-sha`를 준다.** 생략하면 경고만 내는 것은 비준된 정책이다. 올바른 SHA·접두는 P10/F7/G7에서 통과하고, 다른 SHA는 거부했다. 그러나 전달한 문자열과의 일치가 저자의 승인 자체를 증명하지는 않는다.
2. **`runner.sha256`은 기록이지 자동 대조 항목이 아니다.** `run_network_194_parallel.py:2753`에서 기록하지만 P0–P10은 이를 비교하지 않는다. 그 칸을 없애거나 해시만 바꿔도 검사는 통과한다. 따라서 “모든 실행 도구의 파일 지문까지 자동 인증”이라고 쓰면 안 된다. 이전 판정 §6의 최종 핀 및 실행기·인계 도구 변경 확인 조건을 유지한다. 이번 입력·완료 결함을 다시 여는 사유는 아니다.
3. 영수증·로그 전체를 일관되게 고친 위조에 대한 외부 진위 인증은 아니다. 이는 요청서가 제외한 범위이며, 부분 캡처·중단·누락 검사는 별도로 작동한다.
4. 포장기는 파일별 원자적 교체를 사용한다. 두 파일 전체를 하나의 파일시스템 트랜잭션으로 보증한다는 뜻은 아니다. 검사는 둘의 존재·SHA·바이트 수가 맞지 않으면 수용하지 않는다.

194개 배치에는 아래 수동 등록 대조가 추가로 필요하다.

## 3. Q3 production194 수동 대조는 허용하되 기록을 남긴다

**수동 대조로 이번 해제조건을 충족할 수 있다. 자동화를 새 필수 해제조건으로 추가하지 않는다.** 다만 `preflight-verify rc=0`만으로 194의 등록 §2 일치를 주장해서는 안 된다.

실제 반례: 기본 lhs TSV를 끝 개행 하나가 추가된 사본으로 바꿔 생성과 검증 양쪽이 같은 새 기본 입력을 읽게 했다. ID·raw 표는 그대로이고 **P0–P10은 통과**하지만 등록 §2의 TSV SHA는 다르다. raw SHA까지 바꾼 같은 형태도 내부 비교는 통과한다. 원래 핀의 입력으로 검증하면 P9가 거부한다. 이는 새 결함이 아니라 요청서 §3이 공개한 “현재 입력과의 일치 ≠ 사전 등록값과의 일치”의 경계다.

현 검토 핀의 실물 재계산은 §2와 **다섯 키 모두 일치**했다.

| 항목 | 재계산 및 등록값 |

| n / missing_raw_sha | 194 / 빈 목록 |

발사 전에는 **검사를 통과한 바로 그 영수증/로그의 전체 지문**을 등록 §2와, code_fp를 §3과 대조하고 결과를 남긴다. 최소 기록은 영수증 경로·로그 SHA·승인 핀·각 항목의 기대/실측 전체 값·일치 여부·확인자다. 짧은 접두만 눈으로 비교하거나 “P0–P10 통과”로 이 단계를 대체하지 않는다. 자동 등록 대조는 반복 실수를 줄이는 개선으로 권고하되, 이번 두 건의 닫힘과 구별한다.
