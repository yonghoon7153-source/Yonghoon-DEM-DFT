### 3. 시도했으나 발견 아님 (모두 실행함, `n0*`)

- N01 `flock`(util-linux) ↔ Python `fcntl.flock` — 같은 flock(2): python 보유 중 `flock -n` rc 1, 해제 뒤 0; CLI 보유 중 python `LOCK_NB` → BLOCKED. (질문 1c 닫힘. WSL drvfs/9p 위 `out/` 은 미실측.)
- N02 `.lock`·`.part`·`.meta.json`·`.meta.XXXX.part` 가 `degeneracy_*.json` / `matrix_*.csv` / `matrix_{state}*.csv` glob 에 안 걸린다 (compare_states · ne_shape 실측). 질문 1d 닫힘.
- N03 shell 에 `export BMS_RUN_ID=stale…` 가 남아 있어도 `run` 이 명령마다 새 id 를 앞에 붙인다 — 물려받은 id 로 게시되지 않음. verify.py 의 세 명령은 자식 process 를 안 띄운다 (질문 4 의 상속 경로 없음; 의도적 재사용은 F08).
- `write_meta` 의 잠금 안 재확인 → sha256 → mkstemp/os.replace 순서, `verify_unit` 의 meta→CSV→CSV 읽기 순서: 단일 다른 게시자의 끼어들기는 실측(F05b) 에서 잡혔다. 세 번째 게시자까지의 순열은 안 돌렸다.
- `mv` 실패 시 `.part` 잔존(run_states.sh:181 rc 미검사, :186 은 else 분기만) — 읽기만 했고 실행 안 함 (mv 를 실패시킬 현실적 조건이 없어서). 발견으로 세지 않는다.
- 재개 관점: `STATES=100` 부분 재실행은 옛 묶음을 보존하는 설계(R3-08) 라 그 자체는 발견이 아님. 단 한 상태의 degeneracy·matrix·profile 은 서로 무관한 세 uuid 라 "같은 invocation·같은 코드" 를 meta 로 잇는 값은 없다 (`git_commit`·`starts` 로만 간접) — 실행 없이 본 관찰이라 세지 않는다.

### 4. 가장 센 것 셋과 한 줄 권고

1. **F01** — degeneracy 게시를 stdout 리다이렉트에서 떼어 verify.py 안의 잠금 게시로 옮기기 전에는 R5-04 를 "닫힘" 으로 보고하지 않는 편이 맞다.
2. **F02** — ne_shape 도 같은 게시 규약(고유 임시·잠금·run_id·sha256·잠금 안 meta) 으로.
3. **F05a + F07** — `--verify-unit` 에 시도 id 를 주고, 소비자(compare_states·ne_shape) 가 `verify_unit` 을 부르게 하면 F01·F02·crash 의 섞인 묶음이 표에 들어가지 않는다.
