## 1. KG50RF-01 · P1 — 명령 순서가 같아도 소비되는 설정값은 달라진다

**무너지는 결론:** KG50R-03 / KG50P-01의 “준비 구간 설정 보존” 및 이전 최소 해제조건 ②의 완전한 닫힘.

**위치:** `scripts/resume_ckpt.sh:432–468`의 `setup_order`, `:313–318` 및 `:332–338`의 마지막 문자열 저장, `:482–498`의 상태 대조, `:741–745`의 결합. [고정 소스](https://github.com/yonghoon7153-source/Yonghoon-DEM-DFT/blob/bf8cf21c6466cdb9411f9320711b871c2d1c651e/scripts/resume_ckpt.sh#L432).

현재 검사는 재개 준비 구간이 원 준비 구간의 **순서 보존 부분열**이고 마지막 정의가 같으면 수용한다. 중간 정의를 지우는 경우에는 이것이 값 보존을 보장하지 않는다.

받은 D2 덱을 복사한 파생 반례에서, 원 덱의 중력 선언을 다음으로 바꿨다.

```text
variable g_probe equal 98.1
variable g_probe equal 196.2
fix gravi all gravity ${g_probe} vector 0.0 0.0 -1.0
variable g_probe equal 98.1
```

재개 덱은 두 번째 `variable g_probe equal 196.2`만 생략했다. 나머지 문구와 순서는 같다. 재개 쪽 fix는 `read_restart` 뒤에 있다.

| 관측 | 실제 결과 |
|---|---|
| 원 덱이 fix에 전달하는 중력 크기 | **196.2 m/s²** (`units si`) |
| 재개 덱이 fix에 전달하는 중력 크기 | **98.1 m/s²** |
| 정적 CLI / `check()` | **rc 0 / 문제 0** |
| 시험 절단 | **rc 0**, `180000 2000 0 159` |
| 시험 run 합 | **rc 0**, `2000 1 [run 2000]` |
| 첫 긴 run 뒤 프로그램 | 64개 명령 동일로 판정 |

끝의 변수 복원은 이미 fix에 전달한 값을 소급해서 바꾸지 않는다. equal 변수의 재정의·사용 시점 평가와 `${...}` 치환은 [공식 고정 버전 variable 문서](https://raw.githubusercontent.com/CFDEMproject/LIGGGHTS-PUBLIC/3d5c00f20519e6bb6eb6756f51f1ad36564e649d/doc/variable.txt)에 따른다. 이 문헌 확인이 실제 ibb 바이너리 신원 인증을 대신하지는 않는다.

추가로 양쪽에 **같은** `98.1*(step+1)` 수식을 넣어도 원 덱 step 1과 재개 step 20001에서 소비값은 **196.2 / 1,962,196.2 m/s²**로 달라지지만 세 Python 검사가 모두 통과했다. 이 값들은 소스 의미에 따른 산술이며 입자 운동을 실행해 얻은 측정값이 아니다.

**한정:** 원문 D2의 중력·dt를 잘못됐다고 한 것이 아니다. 변경하지 않은 D2는 정상 수용됐고, 이 재정의는 파생 반례에만 있다. G0–G3까지 실제 통과했다는 주장도 하지 않는다. 그러나 설정 보존을 담당하는 정적 관문 자체의 보장은 반증됐다. 짧은 물리 시험이 이를 우연히 발견할 수 있다는 사유로 정적 계약을 닫을 수 없다.

**최소 해결:** 명령이 값을 소비하는 시점까지의 변수 정의·의존성을 보존해야 한다. 좁은 상수 표현만 지원하고 모르는 재정의·실행 상태 의존 치환을 거부하는 구현도 가능하다. 단순히 변수 존재, 마지막 정의, 순서만 확인하는 방식은 불충분하다. 중간 정의 삭제와 동적 equal 두 부류를 음성 대조로, 정상 상수·안전한 생략을 양성 대조로 둔다.

**해결 증거:** `independent/program/cases/d2_drop_intermediate_variable_definition/`와 `d2_runtime_dependent_eager_variable/`를 수정 후 거부하고, `d2_received_baseline` 및 `archived_after_settling_baseline`을 유지해야 한다. 현재는 미충족이다.

## 2. KG50RF-02 · P1 — 검사한 덱과 러너가 실행할 덱이 묶이지 않는다

**무너지는 결론:** 프로그램 검사·짧은 시험·본 제출 입력이 동일한 사슬이라는 주장. P03의 덱/러너 해시를 추가한 것만으로는 닫히지 않는다.

**위치:** `scripts/resume_ckpt.sh:1145`, `:1151`, `:1168`, `:1180`, `:1186`, `:1279`, `:1283`. [러너 검사](https://github.com/yonghoon7153-source/Yonghoon-DEM-DFT/blob/bf8cf21c6466cdb9411f9320711b871c2d1c651e/scripts/resume_ckpt.sh#L1151).

정상 러너의 입력 인자 끝에 `.bak`만 붙였다.

```bash
mpirun --oversubscribe --bind-to none -np 56 lmp_mpi -in input_kg50_d2_b50_r56.liggghts.bak
```

시험 러너도 자동 치환으로 `…r56t.liggghts.bak`를 읽는다. 현재 grep 조건은 토큰 전체가 아닌 부분문자열이므로 세 조건 모두 참이다. 주석이나 별도 명령·실행 중 파일 변경조차 필요하지 않다.

- 검증 대상 `$D`에는 정상 D2 재개 덱을 두었다 → 실제 `check()` **문제 0**.
- 실제 본 러너가 읽는 `.bak` 덱에는 첫 `run 180000` 뒤 `velocity all set 1.0 0.0 0.0`을 추가했다 → 이 파일을 검사하면 실제 `check()` **문제 1**.
- 두 덱에서 생산 `cut_trial()`로 만든 2,000-step 시험 덱은 **바이트 동일**했다. 추가 명령은 시험 구간 뒤에 있다.
- `main_inputs.sha256`은 정상 `$D`와 러너 `$RN`만 묶으므로 그대로 일치한다. 실제 실행할 `.bak` 본 덱은 그 목록에 없다.

즉 정상 시험 관측이 주어졌을 때 같은 시험에서 같은 G0–G3 결과를 받을 수 있지만, 본 실행은 검사하지 않은 다른 파일로 이어진다. 셸 조건 전사와 파일 관계로 보인 경로 반례이며, 실제 sbatch 호출이나 제출 성공을 관측했다고 쓰지 않는다. 받은 원본 D2 러너가 실제로 `.bak`를 읽는다는 주장도 아니다.

**최소 해결:** wrapper가 제한된 규격의 러너를 직접 만들고 실제 cwd·검증된 입력 절대 경로·단일 실행을 고정하는 것이 명확하다. helper 러너를 받는다면 허용한 정확한 명령 구조를 검사하고 모르는 형태를 거부해야 한다. grep 끝에 경계 하나를 붙이는 것만으로는 주석 속 정상 문구·잘못된 cwd·둘째 실행 명령을 닫지 못한다. 영수증은 **실제로 읽을 파일**을 묶어야 한다.

**해결 증거:** 가짜 sbatch가 제공 로그만 복사하지 말고 실제 러너의 cwd/argv를 기록하도록 시험한다. `.bak`, 잘못된 cwd, 주석에만 있는 정상 명령, 둘째 MPI 실행을 제출 전에 거부하고 정상 러너는 유지해야 한다. 현재 `scripts/test_resume_ckpt.py:69–83`의 가짜 제출기는 러너를 실행하지 않아 이 연결을 확인하지 못한다.

재현 파일은 `independent/launch/runner_suffix/`, 반환값·해시는 `independent/launch/results.json`이다.

## 3. KG50RF-03 · P2 — Q5 로그의 추가 상태 명령을 놓친다 (부수 발견)

**범위:** 이번 재개 도구의 P1이나 Q3 생성 허용 목록과 별개인 **Q5 실행 출처 검사**다.

**위치:** `scripts/kg50_q5_verdict.py:329–359`, 특히 `:352–359`. [고정 판독기](https://github.com/yonghoon7153-source/Yonghoon-DEM-DFT/blob/bf8cf21c6466cdb9411f9320711b871c2d1c651e/scripts/kg50_q5_verdict.py#L329).

생산 생성기로 만든 W1 일곱 폴더와 작은 합성 관측을 사용해 실제 `run(repo_verify=True)`를 호출했다. 기준 (a)/(b)는 합격이었다. A의 로그에서 `run 200000` 앞에 `velocity all set 1.0 0.0 0.0` **한 줄만** 추가해도 일곱 `repo_verify=ok`, (a)/(b) 합격이 유지됐다. 덱·manifest·덤프는 바꾸지 않았다.

판독기는 기대 명령이 순서대로 포함되는지만 확인하므로 추가 실행 명령을 놓친다. 이 반례가 실제 물리 궤적을 재현한 것은 아니다. 현재 실제 Q5 결과가 오염됐다는 주장도 아니다. 확인된 것은 추가 상태 명령을 포함한 로그가 출처 관문을 통과한다는 사실이다.

**최소 해결:** 이 검사를 “기대 명령의 순서 있는 포함”으로 정확히 한정하거나, 변수 치환 echo·print·진단과 실제 명령을 구분하는 규약 및 실제 실행 덱 신원 연결을 추가한다. 모든 여분 로그 줄을 거부하는 수정은 정상 치환 출력까지 막을 수 있다. 이 한정을 해결하기 전에는 `repo_verify=ok`를 실행 프로그램의 완전한 동일성 증명으로 인용하지 않는다.

재현은 `independent/q5/results.json.extra_echo_provenance`와 `syn/extra_runtime_command/`에 있다. 생성 덱 허용 목록은 아래 다섯 변이를 실제로 거부했으므로 그 계약까지 실패했다고 확대하지 않는다.

## 6. Q1–Q3 답

### Q1. 이전 최소 해제조건 ①–⑤를 닫는가

**전부 닫히지 않는다.** ① 압축 재개 거부, ③ 현재 호출만 승격하는 구조, ④ 공유 파서·run 합산의 수정은 수용한다. ② 전체 프로그램의 설정값 보존은 KG50RF-01 때문에, ⑤ 실제 실행 입력까지 묶는 신원 사슬은 KG50RF-02 때문에 부분이다. wrapper/helper `-A/-H` 비교 자체는 시작·본 제출 직전에 구현됐다. 이것이 helper가 만든 러너의 실행 의미를 증명하는 것은 아니다.

### Q2. D0.7 NP56·2,000-step `-T` → 원자료 검토 → 본 제출 순서를 열어도 되는가

**순서 자체는 맞지만, 현 핀의 자동 경로에는 GO를 주지 않는다.** KG50RF-02는 본 실행뿐 아니라 “시험 러너가 예산 검사한 시험 덱을 읽는다”는 연결도 빠뜨린다. 두 P1을 수정하고 가짜 실행기로 실제 cwd/argv까지 묶는 시험을 먼저 통과시킨 뒤, **실제 `-T` 증거 수집 단계만** 별도로 열 수 있다.

그 단계에서는 최신 wrapper·실제 helper, 선택 checkpoint, 실제 실행 덱/러너, NP·잡 안 바이너리, trial job/로그·G0–G3의 원자료를 묶어야 한다. settling 중 checkpoint면 보통 2000 step, after_settling이면 준비 `run 1`을 포함해 **2001 step**임을 명시한다. `-T` 뒤 출력하는 `-A/-H` 본 명령은 이전 시험의 직접 승격이 아니라 **새 호출에서 새 시험부터 다시** 수행한다.

실제 `-T` 영수증 검토 전에는 본 제출 GO가 아니다. 두 P1의 수정과 실제 사슬 증거가 충족되어도 Q5·물리 타당성·checkpoint의 완전한 미시 상태 동일성은 각각 별개다. 이 검토에서는 어떤 물리 실행도 시작하지 않았다.

### Q3. W2 setup은 생성 허용 목록만 검사한다는 §12-4 개정을 수용하는가

**그 한정대로 수용한다.** W2 상태 변이 다섯 개는 원문 `-C`에 해당하는 Python 검사에서 등록된 오류 네 줄을 그대로 내면서도, 생성기의 허용 목록에서는 모두 거부됐다. 따라서 책임 위치에 대한 새 설명은 맞다. 고정 본 덱·등록 변환과 생성 후/반입 후 허용 목록 대조를 유지해야 한다.

이를 독립 물리 검증이나 W2 GO로 확대하지 않는다. 등록 `:300`의 §12-2는 여전히 비준 전이며 실제 판독기가 W2 네 가지 모두 거부했다. `:359`의 W2-6도 미결이다: 생성은 D0.7만 지원하지만 전체 (b)는 두 침대를 요구한다. §12-4 기대 줄 개정으로 이 둘이 닫히지는 않는다. Q5 로그 출처 인증에는 KG50RF-03 한계도 남는다.

## 7. 새 P1로 부풀리지 않은 한계

- **P07:** 큐 이름 검사는 현재 suffix와 `r숫자` 계열만 포괄한다. 다른 custom suffix의 같은 케이스 작업을 전부 찾는 검사가 아니다. 고정 suffix 운영 제한을 유지한다.
- **P08:** 정적 checkpoint 대조는 basename을 허용한다. G1의 N/KE는 전체 위치·회전·질량·접촉 이력의 독립 동일성 증명이 아니다. 채택하지 않은 상태 reader를 슬쩍 구현된 것으로 간주하지 않는다.
- **P09/P10:** NBSP/일부 `&` 문법 및 빈 대체 STL의 정적 수용을 재현했다. 알려진 파서 차이·파일 존재 검사 범위다. 실제 LIGGGHTS에서 반드시 오류로 닫힌다는 주장은 이번 환경에서 재현하지 못했다.
- **checkpoint·binary 영수증:** `:1183`의 checkpoint SHA는 기록되지만 `:1180/:1279` 재검사 목록은 덱/러너만이다. `:1179`의 바이너리 SHA는 제출 셸 PATH이며 잡 안 환경의 신원은 아니다. 바이트 불변을 보증하려면 실제 사용할 대상까지 연결해야 한다.
- **유한성:** `:1062/:1068`의 `fin()`은 숫자 문법 정규식이다. `1e9999`도 문법상 수용한다. 엄밀한 유한성에는 범위·변환 결과 검사도 필요하다. 실제 AWK나 실제 로그로 false-green을 관측한 것은 아니므로 별도 P1로 세지 않았다.

## 8. 재현과 최소 해제 증거

배포 ZIP을 푼 루트에서 다음을 실행한다. 제품 리포는 읽기만 하고, 결과는 새 폴더에 만든다. Bash·LIGGGHTS·SLURM·네트워크를 호출하지 않는다.

```bash
python3 -I -B reproduce.py --out /새로운/빈_결과폴더
```

Windows에서는 `python3` 자리에 사용 가능한 Python 실행 경로를 쓴다. 생성된 `independent/program/results.json`, `independent/launch/results.json`, `independent/q5/results.json`과 `run_receipt.json`을 읽는다. `reproduce.py`의 rc 0은 **이번 발견을 재현했다**는 뜻이며 대상 도구 GO가 아니다. 결과 폴더 안의 `repo/`도 고정 바이트 사본이다.

우리 트리에서 실제 셸까지 재확인할 때의 기존 명령은 별도로 다음과 같다. 이번 환경에서 이 세 명령의 통과를 독립 주장하지 않는다.

```bash
python3 scripts/test_resume_ckpt.py
python3 scripts/kg50_q5_branches.py --selftest
python3 scripts/kg50_q5_verdict.py --selftest
```
