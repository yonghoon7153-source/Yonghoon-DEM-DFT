# v1.8 — D2 개발 덱의 밀도·계획수·코팅 쌍 되읽기 (2026-10-24)

> D2 개발 덱과 메타의 실제 내용을 함께 읽는다. 개발 검사 통과와 실제 믹서 실행·코호트 등록은 별개의 기록이다.

## 쉬운 판

같은 100,000개 계획도 밀도 세대가 바뀌면 상별 계획수가 달라진다. 이 예에서 gen1은 AM_P 176 · AM_S 859 · SE 98,965개이고, lab20261014는 143 · 699 · 99,158개다. 새 개발 검사는 덱의 밀도·입자 분포·삽입수를 읽어 메타에 적힌 계획과 맞는지 확인한다.

코팅 비교는 **같은 비코팅 ρ 세계**에서 NCM 표면 비를 ρ에서 1로 바꾼 두 덱을 받는다. SE와 벽의 규칙은 유지하며, 두 덱에 같은 오밀도·중력·점착 오류가 들어 있어도 실제 덱으로 절대값을 검산한다. AM_P+SE 두 상 구성도 검사한다.

사용자의 전체 비준으로 제시된 설계·정책 방향에 따른 개발을 이어간다. 구체적인 새 S1 수준·시드·코호트 표와 실제 장비·실험 입력, 이를 묶는 등록·관문 구현과 실행 증거는 아직 완성되지 않았다. 이번 **개발 PASS는 실제 실행, 접촉 적격성, 발사 또는 실험 결과의 인증이 아니다**.

## 자세한 판

세 가지 개발 전용 경로를 추가했다. 아래의 경로는 사용자가 생성한 덱과 그 `deck_meta.json`을 뜻한다.

```bash
python3 -I scripts/mixer_deck_readback.py \
  --d2 <비코팅/in.mixer> <비코팅/deck_meta.json> --json <되읽기.json>
python3 -I scripts/mixer_deck_diff.py <비코팅/in.mixer> <코팅/in.mixer> \
  --allow D2 --meta-ref <비코팅/deck_meta.json> --meta-new <코팅/deck_meta.json> \
  --json <쌍비교.json>
python3 -I scripts/mixer_smoke_blind.py \
  --d2-plan <비코팅/in.mixer> --d2-meta <비코팅/deck_meta.json> --json <계획수.json>
```

- `readback`은 실제 텍스트 SHA·바이트, 밀도 세대와 활성 상, E·ν·반경·CGF, 중력, 인쇄 CED로 계산한 절대 Bo와 기하평균 힘, 벽 `0.0256 × ρ`, 정적 겹침, 시간·step·주기, 삽입 계획수를 검사한다. 알 수 없는 계약 키와 중복 JSON 키, 비유한 수와 숫자의 Unicode·underscore 표기를 거부한다.
- `diff --allow D2`는 양쪽을 각각 검산하고 같은 밀도·ρ·Bo·시드·시간·계획수를 요구한다. CED 밖 명령 토큰은 같아야 한다. ρ=1인 세계는 변화가 없는 퇴화 비교로 명시한다.
- `smoke --d2-plan`은 실제 삽입 명령과 질량 분율에서 나온 **계획수**만 검사한다. 실제 입자 덤프 수, 접촉 유효성, 정착 해제, 확인 런의 증서를 만들지 않는다.
- 삽입 영역·분포·메시 참조, 구 적분기, 삽입 fix 제거 시점, 두 정착 run 이후의 회전 순서를 검사한다. 삽입 전에 fix를 지우거나 존재하지 않는 영역을 참조한 덱은 계획수 검사에서 통과하지 않는다.
- 기존 A/B/U/E/EB와 등록된 고-Bo 셀·코호트·스모크 계약은 그대로다. 새 개발 보고서는 `registered: null`, `execution_authorized: false`를 기록한다.
- 이 계약은 전체 실행 덱 인증이 아니다. 메시 파일의 실제 형상·실물 장비 일치, 모든 난수열의 생성기 서명, 실행 바이너리·재개 이력·실측 결과는 별도 검증 대상이다. 비교에서 같은 기하 토큰을 요구해도 실물 형상을 인증하지 않는다.

회귀 입력의 ρ와 Bo는 실험 보정값이나 새 스캔 수준이 아니다. `MXD2-01`의 개발 소비자 부분을 다루며, S1의 구체적인 셀·코호트·정책 구현·등록과 D3 실험 앵커는 후속 기록으로 남긴다.
