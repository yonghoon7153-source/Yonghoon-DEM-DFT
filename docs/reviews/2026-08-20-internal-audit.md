### H1. `apps/api/app/routers/analysis.py:81` — ADR 0004 위반: 사이클 테이블·비교의 유지율이 기준 사이클 부재 시 조용히 다른 사이클로 재기준화됨

**무엇이 잘못됐나.** ADR 0004 결정문은 '기준 사이클이 파일에 없으면 조용히 1번으로 떨어지지 않는다. reference_available=False 로 표시하고 어떤 사이클을 대신 썼는지 문장으로 남긴다'고 명시한다. health.build_report 는 이를 지키지만, _cycle_rows (analysis.py:77-81)는 기준 사이클(기본 3)이 complete 목록에 없으면 '첫 complete 사이클'로 조용히 대체하고, CycleTableOut 에는 reference_available/노트 필드 자체가 없으며 reference_cycle 필드는 여전히 요청값(3)을 돌려준다. 실패 시나리오 1: 이제 막 2사이클 돈 구동 중 셀의 GET /api/samples/{id}/cycles → retention_pct 가 formation 인 1번 사이클 대비로 계산되는데(ADR 0004 이 금지한 바로 그 혼합), 응답과 웹 CycleTable 의 기준 표시는 3번을 가리킨다. 시나리오 2: _012 연속 파일(사이클 201~)만 가진 샘플로 GET /api/compare/cycles?metric=retention → 그 셀의 유지율은 201번 대비, 옆 셀은 3번 대비인 곡선이 같은 축에 겹쳐 그려져 셀 간 비교가 무표시로 오염된다. 수치가 조용히 틀리는 연구 데이터라 가장 위험하다.

**반박 결과.** Confirmed by direct code reading. analysis.py:76-81 (_cycle_rows) silently falls back to the first complete cycle when the reference cycle is absent, while sample_cycles/run_cycles (lines 153, 181) return reference_cycle = the requested value (3) and CycleTableOut (schemas.py:231-238) has no reference_available/retention_note field to signal the substitution. ADR 0004 (docs/adr/0004-cycle-three-reference.md:22-24) explicitly requires reference_available=False plus a sentence naming the substitute; wrdkit/health.py:262-287 implements that correctly (and uses a better fallback: earliest complete cycle at-or-after the reference), proving the router path is an unguarded divergence, not documented intent. Both failure scenarios are reachable: (1) a running cell with <3 complete cycles gets retention_pct computed against formation cycle 1 — exactly what the ADR forbids — while the web CycleTable (CycleTable.tsx:50-54) shows no reference badge and no warning; (2) compare_cycles (analysis.py:358) rebases a continuation-only sample (cycles 201+, a workflow CLAUDE.md documents) to cycle 201 = 100% and overlays it on the same axis as cycle-3-based cells with nothing in the payload distinguishing the baselines, so a degraded cell renders as pristine. Tests (test_analysis.py:51-57) only cover the reference-present case. This is silent numeric corruption in research-facing output plus a direct ADR violation; only /report and /dashboard are defended.

**제안 수정.** In _cycle_rows, mirror health.build_report's fallback (earliest complete cycle with cycle_number > reference, else first complete) and return what was actually used: change it to return (rows, reference_used) or accept an out-param. Add to CycleTableOut: reference_cycle_used: int | None and reference_available: bool (and optionally a retention_note string reusing health.py's wording so web i18n.ts:83 already translates it). Populate in sample_cycles, run_cycles; in compare_cycles add reference_cycle_used/reference_available per series so the web Compare view can annotate mixed-baseline curves. Update CycleTable.tsx to badge reference_cycle_used instead of the requested value and render a warning row when reference_available is false. Add tests: a sample whose records start at cycle 201 (cycle_offset) asserting reference_cycle_used==201 and reference_available==false, and a 2-complete-cycle running cell asserting the same flags; plus a compare_cycles test asserting the per-series fields.

### H2. `apps/api/app/routers/analysis.py:497` — 다중 셀 뷰(dashboard/compare)에서 basis 폴백이 무신호 — raw mAh 값이 mAh/g 라벨 아래 섞여 표시됨

**무엇이 잘못됐나.** services.normalized(services.py:379-386)는 분모가 없으면 조용히 raw mAh 를 반환하고, 셀별 effective_basis 로 폴백한다. 단일 셀 응답은 basis_fallback_reason 으로 이를 알리지만(analysis.py:152) 다중 셀 경로엔 집계 신호가 없다: dashboard 는 행별로 폴백된 값을 만들고도 최상위에 요청 basis 를 그대로 찍고(497행), compare_cycles 의 y_label 은 resolve_cell(None) 기반이라 항상 'Capacity (mAh)'(377행), 시리즈별 basis(373행)는 프런트가 무시한다. 실패 시나리오: 기본 basis 가 mAh/g 인 상태에서 질량 입력된 셀 A(207.7 mAh/g)와 질량 미입력 셀 B(raw 5.2 mAh)를 대시보드/비교에 올리면 Dashboard.tsx:211 헤더 '방전용량 (mAh g⁻¹)' 아래에 B 의 5.2(실은 mAh)가 표시되고, Compare.tsx:95 는 요청 basis 로 축을 붙인 채 두 곡선을 한 축에 겹친다. Compare.tsx:105 는 '같은 기준으로 정규화되어 비교됩니다' 라고까지 명시하므로 사용자는 혼합 단위를 의심할 수 없다 — 셀 B 가 40배 나쁜 셀로 읽힌다.

**반박 결과.** Verified end-to-end; the failure path is reachable with default settings and nothing defends it. (1) services.py normalized() explicitly returns raw mAh when cell.divisor(basis) is None, and effective_basis() falls back per cell. (2) In dashboard (analysis.py:442-497) each row's discharge_capacity is normalized with that row's own effective basis, yet the top-level payload is {"basis": basis, "basis_label": basis_label(basis)} — the requested basis. The per-row "basis": used field exists but Dashboard.tsx never reads it (grep confirms row.basis is unused in apps/web/src); the table header at Dashboard.tsx:211 prints basisUnit(basis) from client state, whose sticky default is 'mAh/g' (Dashboard.tsx:30), and the cell renders row.discharge_capacity bare (line 245) with no badge. So a mass-less cell's raw mAh sits under a '방전용량 (mAh g⁻¹)' header. (3) compare_cycles' y_label (analysis.py:377) is computed from resolve_cell(None), which never has mass/area, so effective_basis always collapses to ABSOLUTE — the label is wrong in the opposite direction, and it doesn't matter because Compare.tsx ignores the API's y_label and per-series basis entirely, computing yLabel = basisAxis(basis) from the requested basis (Compare.tsx:91-95) while overlaying per-cell-fallback values on one axis; the page subtitle (Compare.tsx:105) affirmatively states all cells are normalized to the same basis. (4) The repo clearly intends fallback to be signaled: single-cell responses carry basis_fallback_reason (analysis.py:152,180) and SampleDetail.tsx:196-200 renders a warning — that protection is simply absent from the two multi-cell paths. (5) No ADR covers this; grep of docs/adr for basis/fallback finds nothing (ADR 0001 is about storage only), and CLAUDE.md rule 4 (추정값을 실측값처럼 내보내지 않는다 — signal missing inputs, never pass unlabeled values off as another kind) is violated in spirit: a raw-mAh number is presented under a mAh/g label with an explicit false assurance. Severity: this is display-layer mislabeling, not DB/export corruption, but it is the default UX (mAh/g is the sticky default basis, and freshly-uploaded cells have no mass until someone enters it), it targets exactly the cross-cell comparison views researchers use to judge cells, and the UI text forecloses suspicion — so high is justified.

**제안 수정.** Minimal fix in two layers. API: in dashboard rows add "basis_fallback_reason": cell.missing_for(basis) if used != basis else None (the used basis is already emitted per row), and in compare_cycles emit per-series basis_fallback_reason the same way; also fix compare_cycles y_label to reflect the requested basis rather than resolve_cell(None) (or drop it, since the web ignores it). Web: Dashboard.tsx render a warn badge (reuse the existing '대체' badge pattern, Dashboard.tsx:274-278) next to discharge_capacity when row.basis !== basis, with the reason as title; Compare.tsx, when any series' basis differs from the requested basis on a capacity metric, show an Alert naming the offending cells (and/or dash/exclude those series) and drop or qualify the '같은 기준으로 정규화되어 비교됩니다' subtitle. Test: extend the compare/dashboard API tests with one massed and one mass-less sample requesting basis=mAh/g and assert the per-row/series fallback signal is present.

**처리.** _(갱신 라운드에서 기록)_

### H3. `apps/api/app/routers/runs.py:78` — 중복 업로드 재부착 경로가 sample 존재 검증·cycle_offset 재계산·renumber 를 전부 건너뛴다

**무엇이 잘못됐나.** upload_run 의 dedupe 분기(76-83행)는 기존 run 의 sample_id 를 바꿔 커밋만 하고 곧장 반환한다. (1) 비중복 경로에만 있는 `session.get(Sample, sample_id) is None` 404 검사(90행)가 없어, 존재하지 않는 sample_id 로 같은 파일을 재업로드하면 SQLite 는 FK pragma 가 꺼져 있으므로(db.py 에 PRAGMA foreign_keys 없음) run 이 유령 샘플에 조용히 매달린다. (2) auto_cycle_offset/renumber_sample_runs 를 호출하지 않아, 예: 샘플 S2 에 이미 100 사이클짜리 run(offset 0)이 있는 상태에서 미배정 run 과 같은 바이트를 ?sample_id=S2 로 재업로드하면 그 run 이 offset 0 그대로 붙어 S2 의 사이클 테이블에 cycle 1 이 두 개 생긴다. _cycle_rows 의 기준 사이클 탐색(`next(r for r in records if r.cycle_number == 3 ...)`)과 compare/profiles 의 `cycle_number == cycle` 매칭이 임의의 한쪽을 집어 유지율·프로파일이 잘못 나온다. PATCH /runs/{id} 경로(146-149행)는 같은 재부착에서 offset 재계산을 하므로, 어떤 경로로 붙였느냐에 따라 결과가 달라지는 조용한 데이터 오염이다.

**반박 결과.** Verified in apps/api/app/routers/runs.py:76-83: the dedupe branch commits `existing.sample_id = sample_id` and returns before the 404 sample-existence check (line 90), and calls neither auto_cycle_offset nor renumber_sample_runs. db.py sets no PRAGMA foreign_keys, so SQLite silently accepts a nonexistent sample_id. The re-attach-via-reupload flow is intended (test_a_second_upload_can_attach_an_orphan_run) but only tested against an empty sample; attaching an orphan run to a sample that already has runs leaves the orphan at offset 0 with CycleRecord.cycle_number 1..M unchanged, producing duplicate cycle numbers in the sample. Reference-cycle-3 lookup, retention, compare and profile endpoints match on cycle_number and pick an arbitrary duplicate — silent corruption. The PATCH /runs/{id} path (lines 142-165) performs the 404 check, offset recomputation, record rewrite and renumber for the identical operation, so results differ by attach path. No ADR documents the omission as intentional.

**제안 수정.** In the dedupe branch, mirror the PATCH re-attach logic: before mutating, raise 404 if `session.get(Sample, sample_id) is None`; then set `existing.sample_id`, and (when `cycle_offset_source == "auto"`) call `auto_cycle_offset(session, sample_id, existing.start_time, existing.original_name, exclude_run_id=existing.id)`, rewrite the run's CycleRecord.cycle_number values, `session.flush()`, and `renumber_sample_runs(session, sample_id)` before committing — or simply factor the PATCH attach block into a helper and call it from both paths. Add a test: upload run A to sample S, upload orphan B, re-upload B's bytes with ?sample_id=S, assert B's offset == A.cycle_count and no duplicate cycle_number in S. Separately consider enabling PRAGMA foreign_keys=ON via a connect event listener.

### H4. `apps/api/app/routers/runs.py:79` — sha256 중복 업로드 시 기존 run 을 다른 샘플로 조용히 이동시키고 어느 쪽도 renumber 하지 않음

**무엇이 잘못됐나.** upload_run 의 dedupe 분기(76-83)는 같은 바이트가 다시 오면 sample_id 가 다를 때 existing.sample_id 를 덮어쓰고 바로 commit 한다. 이때 (1) 이전 샘플의 renumber_sample_runs 가 호출되지 않아 남은 연속 파일들의 cycle_offset/cycle_number 가 사라진 run 의 사이클 수만큼 부풀려진 채 남고, (2) 새 샘플 쪽도 renumber 되지 않으며 run 은 이전 샘플에서 쓰던 cycle_offset(예: _012 로서 100)을 그대로 갖고 온다. 실패 시나리오: 샘플 A 에 _011(100사이클, offset 0)·_012(offset 100)가 있는 상태에서 두 번째 PC 가 같은 _012 파일을 샘플 B 를 지정해 업로드 → _012 가 A 에서 소리 없이 빠져나가고(A 의 데이터가 경고 없이 줄어듦), B 에서는 사이클 번호가 101부터 시작한다. 두 샘플의 사이클 테이블·기준사이클 3 조회·유지율이 전부 조용히 틀어진다. 단순 재업로드가 데이터를 이동시키는 파괴적 동작이라는 점 자체도 문서화된 "중복은 no-op" 계약과 어긋난다.

**반박 결과.** Verified in apps/api/app/routers/runs.py:76-83: the dedupe branch overwrites existing.sample_id and commits with none of the machinery the PATCH endpoint (lines 142-165) runs for the identical operation — no sample-existence check, no auto_cycle_offset, no CycleRecord.cycle_number rewrite, no renumber_sample_runs for old or new sample. Since cycle_number is persisted (services.py renumber/persist paths), the moved run keeps its old offset (e.g. 100) in the new sample and the old sample silently loses a file; renumber only fires on some later mutation of each sample, so cycle-3-reference queries (retention, ICE, knee per ADR 0004) read wrong numbers indefinitely. The cross-machine scenario is the project's own stated use case (docstring: "the same file often arrives from two machines"; CLAUDE.md: two-person lab). No ADR documents reassignment-on-dedupe; tests only cover orphan-attach into an empty sample, which hides the missing renumber. Bonus defect in the same branch: sample_id existence is only validated in the non-dedupe path (line 90), so re-upload with a bogus sample_id commits a dangling FK. This is silent data corruption of cycle numbering across two samples with no error surfaced — real, not style.

**제안 수정.** In the dedupe branch of upload_run: (1) if existing.sample_id is not None and differs from the requested sample_id, refuse to move — return the existing run unchanged (or 409 telling the user to use PATCH /api/runs/{id}, which does this correctly); (2) when attaching an orphan (existing.sample_id is None), first validate session.get(Sample, sample_id), then mirror the PATCH logic: set existing.cycle_offset = auto_cycle_offset(...) with cycle_offset_source="auto", rewrite its CycleRecord.cycle_number values, session.flush(), and call renumber_sample_runs(session, sample_id) before commit. Add tests: re-upload with a different sample moves nothing; orphan attach into a sample that already has an earlier file yields continuous, collision-free cycle numbers.

### H5. `apps/api/app/routers/runs.py:165` — update_run 이 run 을 떼어낸/옮겨간 뒤 '이전' 샘플의 run 들을 renumber 하지 않는다

**무엇이 잘못됐나.** renumber_sample_runs(session, run.sample_id) 는 변경 '후' 의 sample_id 로만 호출된다. detach_sample=true 면 run.sample_id 가 이미 None 이라 renumber 가 즉시 return 하고(services.py 133행), 샘플 A→B 재배정이면 B 만 renumber 된다. 실패 시나리오: 샘플 S 에 _011(100 사이클, offset 0), _012(offset 100) 가 있을 때 PATCH /api/runs/{_011.id} {"detach_sample": true} 를 하면 _012 는 offset 100 을 유지해 S 의 사이클 테이블이 101번부터 시작한다. 기준 사이클 3이 존재하지 않게 되어 _cycle_rows 가 조용히 첫 완료 사이클(=101번)로 fallback 하고, 유지율·knee·대시보드 trend 가 전부 어긋난다. 같은 상황을 delete_run(199-202행)은 삭제 전 sample_id 를 잡아 renumber 하므로 올바르게 처리한다 — PATCH 경로만 빠져 있다.

**반박 결과.** Verified in apps/api/app/routers/runs.py: update_run (line 133-168) sets run.sample_id to None (detach_sample) or to a new sample, then calls renumber_sample_runs(session, run.sample_id) at line 165 with only the POST-change value; the pre-change sample_id is never captured. renumber_sample_runs (services.py:126-133) returns immediately for None, so on detach the old sample is never renumbered, and on A→B only B is. delete_run (runs.py:198-202) proves the intended behavior by capturing sample_id before deletion and renumbering the old sample — the PATCH path is the one mutation missing it. Offsets/cycle_numbers are persisted (Run.cycle_offset, CycleRecord.cycle_number) and renumber_sample_runs has only three call sites (upload/patch/delete), so there is no read-time repair: after detaching _011 from a two-file sample, _012 keeps auto offset 100 and its cycles stay numbered 101-200. Downstream, analysis.py _trend (505-512) silently falls back to usable[0] when cycle_number==reference_cycle is absent, and _cycle_rows (73-79) finds no reference row, so retention, knee search, and dashboard trends silently use cycle 101 as the baseline — a direct silent violation of the reference-cycle-3 invariant. No test in apps/api/tests/test_runs.py covers detach or reassignment renumbering.

**제안 수정.** In update_run, capture previous_sample_id = run.sample_id before applying payload changes; after session.flush(), call renumber_sample_runs for both: renumber_sample_runs(session, run.sample_id) and, if previous_sample_id differs, renumber_sample_runs(session, previous_sample_id). Add a regression test: two-file sample, PATCH detach the first file, assert the remaining run's cycle_offset drops to 0 and its CycleRecord.cycle_number starts at 1 (and the A→B reassignment variant).
