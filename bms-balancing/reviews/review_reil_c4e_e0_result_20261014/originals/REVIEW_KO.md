# REIL C4E E0 결과 검토

2026-10-14. **E0의 제출된 시험 결과는 한정 수용하지만, E1 준비 완료 판정은 보류한다.** 필수 보완은 N1 하나다. 실행 모듈 다섯 개에 승인된 기대 해시가 없어서, 시작과 끝이 같은 미승인 변경본을 거부하는 조건이 빠져 있다. 후보·시험·기존 증거는 수정하지 않았다.

## 검토 기준

고정 HEAD는 `5cb6ab95c8c461cf940dcf94b90c30e8a3e3659c`다. 첨부 발송문은 11,081 B / SHA256 `1c3751573cff39331b3d12ca1830d3d2329f4578270313ef14bdc82583cbf216`로 저장소 파일과 동일하다. 이전 v3 검토 HEAD `05614f07…`부터 10개 커밋을 대조했다. 변경은 새 실행 진입점·새 시험·감시 선택 인자, 새 증거·문서·검토 회신 보존에 한정된다. 기존 시험 7개와 e3a/h/hb/c5/p0/c6, 기존 배열·봉인·증거의 변경은 이 비교에 없다.

v3 요청 해시는 `29cd92a44db97fc29893adc6bc5dda75d610486cdd5d169eafd6df537bd9029a`다. 착수 전 커밋 `cac26575…`의 상태 §66에는 사용자 발언 “권고대로 E0 승인”과 §6-2 GREEN 계산 예외까지 채택한 범위가 기록돼 있다. 이는 실행 전 저장소에 보존된 승인 인용문이며, 검토자가 당시 사용자 대화 원본을 별도로 관측한 것은 아니다. 실행 권한을 새로 부여하지 않는다.

## N1 필수 보완

**우선순위 P1 — E1 시작 전 승인된 소스와의 일치 검사가 필요하다.**

v3 §4-6은 실행 모듈·e3a·monitor·c5·p0에 신뢰 기대 SHA와 시작·끝 SHA를 함께 두도록 요구한다. 그러나 `expected_identity()`는 자료/P0/발췌/MANIFEST만 채운다. `identity_problems()`는 기대값이 `None`이면 비교를 생략한다. 제출된 실제 `PLAN_E.json`에서도 다섯 모듈의 `expected`가 모두 null이다.

- 요구: [v3 요청 225–228행](https://github.com/yonghoon7153-source/Yonghoon-DEM-DFT/blob/5cb6ab95c8c461cf940dcf94b90c30e8a3e3659c/bms-balancing/docs/REIL_C4E_APPROVAL_REQUEST_v3_20261014.md#L225).
- 누락·생략: [실행 코드 465–489행](https://github.com/yonghoon7153-source/Yonghoon-DEM-DFT/blob/5cb6ab95c8c461cf940dcf94b90c30e8a3e3659c/bms-balancing/scripts/reil_c4e_run.py#L465), 같은 파일 308–321행.
- 판정: 같은 파일 347–348행은 시작·끝 불변과 기대값 문제 목록을 쓰지만, 생략된 모듈 기대값은 문제가 되지 않는다.
- 외부 결속: 단계 실행기의 50–53, 61–65행은 HEAD/porcelain을 기록할 뿐 승인된 커밋·바이트와 비교하지 않는다. `stage_verdict()` 369–375행 역시 rc/timeout만 더한다.

따라서 모듈이 시작 전에 바뀌고 그 상태로 끝까지 유지되면, 현 소스 식별 조건은 이를 거부하지 않을 수 있다. **이번 제출 소스가 실제 변조됐다는 뜻은 아니다.** 이번 검토에서는 GREEN·끝 해시 16개를 현재 커밋 바이트와 독립 대조해 모두 일치했다. 문제는 향후 E1에서 그 일치를 강제하는 연결이 없다는 점이다. d_6은 실행 중 변화는 검사하지만 “기대 해시 누락”과 “시작=끝인 잘못된 소스”를 거부하는 근거는 제공하지 않는다.

최소 정정 방향은 별도로 신뢰할 수 있는 소스 목록에 승인된 다섯 모듈의 SHA256을 고정하고, 실행 전 실제 바이트를 대조한 뒤 동일 기대값을 시작·끝 식별 표 및 수용 판정에 연결하는 것이다. 자신의 해시를 자기 파일에 넣는 순환 방식은 필요 없다. 외부 launcher의 사전 검사 등으로 해결할 수 있다. 목록 자체의 신뢰 근거·정확한 경로 집합·누락 거부 조건을 함께 명시해야 한다. 기대 누락이나 불일치는 자료 적재·작업자/최적화 진입 전에 차단해야 한다.

정정 시 필요한 검증 축은 정상 기대값, 기대 항목 누락, 시작부터 잘못되었으나 끝까지 동일한 소스, 실행 중 변화다. 기존 시험·로그를 고치거나 이번 PASS를 소급 변경하지 않는다. **새 정정 범위·검증안과 예산을 먼저 제안하고, 별도 승인 전에는 정정 시험이나 E1을 실행하지 않는다.**

현재 `plan-e`의 `identity_ok=true`도 환경과 명시된 기대값 항목의 통과로만 읽는다. 승인된 모듈 출처까지 확인했다는 뜻으로 확대하지 않는다.

## 제출 결과 확인

| 단계 | 외부 기록 | 내부 결과 | 수용 범위 |
|---|---:|---|---|
| identity | 23.074 / 60초, rc0 | ok, problems 없음 | 기록된 환경 식별 결과 |
| RED | 1.924 / 600초, rc1 | 21 실패, NotImplementedError 19 + TypeError 2 | 사전 선언된 골격·인터페이스 실패 |
| GREEN | 43.901 / 600초, rc0 | 180 passed, pytest 43.03초 | 기존159 + 새21의 제출 결과 |
| plan-e | 2.430 / 300초, rc0 | PLAN_E 한 파일 | 건조 계획 및 식별 기록, N1 제한 |

네 단계의 stderr는 모두 0 B이고 timeout은 거짓이다. 외부 기록 합은 71.329 / 1,560초다. 기존 시험 수는 26+14+51+15+5+43+5=159이며, 새 시험은 매개변수화 없는 21개 함수다. RED 원문과 현재 새 시험의 Git blob·바이트가 같고, GREEN/끝 SHA 목록도 원바이트가 같다. GREEN 당시 HEAD는 `d2708ab7…`이고 두 구현 파일은 작업 중 변경 상태였으므로, HEAD만이 아니라 함께 남긴 파일 해시로 `57dfe290…`의 구현 바이트를 결속한다.

보존된 단계별 기록과 덮어쓰기 거부 실행기는 각 1회의 기록된 실행을 지지한다. “재시험 0”은 제출자의 기록과 일치하지만, 기록되지 않은 실행까지 독립 OS 감사로 배제했다는 뜻은 아니다. RED는 틀린 완성 구현에 대한 변이 시험이 아니며, GREEN 음성 대조와 구분한다.

`PLAN_E.json`은 27,355 B / SHA256 `1538407567bf1950ff744efe80e39cf3423c0a19f213d9e18db0dd1d91f8fa3a`다. 계획은 66호출, 기대 평가 1,501,500, 작업자별 404,500 / 404,500 / 388,000 / 304,500이다. 275 optimizer runs는 계획값이고, 건조 실행의 optimizer 호출은 0으로 기록돼 있다. P0·봉인 MANIFEST·노트북 발췌·다섯 모듈의 제출 바이트도 계획의 관측 해시와 일치한다. 환경의 과거 C6 검사는 재수행이 아니라 기존 근거 인용이다.

## 공개한 변경과 한계의 처리

| 항목 | 판단 |
|---|---|
| named origin 및 프로토콜 제한 | E1 제안 방식으로 수용 가능. 같은 고정 URL·커밋·filter·두 git show 경로, checkout 없음, 새 목적지·크기/SHA 대조를 유지한다. https만 허용·prompt 금지는 범위를 좁힌다. E1 승인문에는 실제 argv/env를 채택해야 한다. |
| 넓어진 입력 검사 | 필수 정정 없음. error 행을 포함한 모든 완료 wall의 검사와 일치하며, 통상 지역 오류를 비용 통계에 넣거나 결과값 기준 중지로 바꾸지 않는다. |
| 모듈 기대값 공란 | **N1 필수 정정.** HEAD/porcelain 기록만으로 대체할 수 없다. |
| P0 불일치 뒤 빈 출력 폴더 | 승인 순서상 경로 단계에서 생성한다. 실패 후 최적화에 도달하지 않고 재사용도 거부하므로 필수 정정 없음. |
| 감시 전 중지의 외부 기록 | 사유 stdout·외부 stderr/meta를 함께 보존한다면 수용 가능. run-root 결과가 생성됐다고 주장하지 않는다. |
| 첫 쓰기 전 기록 마감 초과 | 기존 함수는 RECORD_INCOMPLETE/time 위반으로 종료하고 최종 수용이 거짓이다. 필수 변경 없음. 아직 쓰지 못한 호출 행까지 파일로 보존됐다고 주장해서는 안 된다. |

GitHub/프록시의 실제 E1 fetch 성공은 로컬 저장소 시험으로 입증되지 않는다. 접근 실패·시간 초과·해시 불일치 시 정지하며, 다른 출처·재시도·임의 clone으로 바꾸지 않는다. 선택적 개선으로는 fetch의 `TimeoutExpired` 때 부분 argv/단계 기록을 구조화해 보존하는 방안이 있다. 현재도 외부 오류/비정상 종료로 실패하므로 이번 필수 차단 항목으로 추가하지 않았다.

## 예산과 표기 정밀도

2,364.4초는 종결 기록의 커밋·push·결과 문서·발송문 이전 snapshot이다. 전체 작업 최종 반환까지 4시간 이내였다는 독립 증거로 확대하지 않는다. 최대 단일 자식 RSS 285,672 KiB는 RUSAGE_CHILDREN 사후 관측이며 동시 프로세스 합이나 강제 상한이 아니다.

**N2 비차단 표기 보충:** 증거 63,527 B는 종결 파일 작성 전 값이다. 현재 제출 증거 파일 합은 66,173 B이고 차이 2,646 B는 `06_end.json` 자체다. 둘 다 64 MiB보다 작다. 후속 설명에서 경계만 바로 적고 원본 기록은 수정하지 않는다.

가짜 평가 396의 기존 머리말 오기는 제출자가 이미 393=198+65×3으로 정정했다. 지역 오류 호출이 평가 전에 예외를 내므로 타당하다. 검증된 시험 원바이트는 유지한다. 두 실제 NSGA2 결과의 5,000평가 반환 기록과 §6-2 예외를 확인했으며, 나머지 COBYQA/fork/Sobol 등은 정적 구조 집계이지 새 독립 실행 계수 로그가 아니다.

## 회신과 다음 경계

Q1: 제출 E0 시험·건조 결과 및 네 구현 조건은 한정 수용한다. 그러나 N1 때문에 E0 전체 준비 완료 및 E1 GO 가능 판정은 보류한다.

Q2: named origin과 프로토콜 제한은 고정된 E1 제안 방식으로 수용 가능하다. 실제 실행 승인은 아니며 N1 해소·정정 검토·사용자 별도 E1 GO를 대체하지 않는다.

Q3: 공개사항 3–7 중 필수 보완은 4번, 모듈 기대 해시 연결이다. 나머지는 위 경계로 수용한다.

E1 자료 반입·개봉·66회 실행, C4-A/B, 설치·환경 변경, COMSOL은 승인하지 않았다. 실제 E3a COMPLETE 증거와 C4-A 진입 근거는 아직 없으며, 7-1/7-2 및 후속 범위는 기존 상태를 유지한다. 이 검토에서는 파일·JSON·로그·해시·코드 텍스트만 읽고, 받은 프로그램의 import·시험·최적화·자료 개봉은 실행하지 않았다.
