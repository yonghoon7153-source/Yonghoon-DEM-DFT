## 3. 최종 핀 재확인 순서 — 1저자 계획 비준

1. **최종 핀 S0 단계1/저장본 확인**: 1저자 실행용 별도 고정 블록을 준비하고 결과 전 등록·신원·기계/환경·기대/실패 규칙을 대조한다. 이번 ⑥ 블록에 S0를 몰래 연결하지 않는다.
2. **현행 Q11 블록**: 현재 결속 하네스와 소스 핀을 고정한다. `consume.adopt`의 동일성·수렴·GPU/backend·정해진 반복·출처 조건을 각각 확인한다. 과거 “v8” 실행 기록과 현행 “v8” 파일은 이름만으로 같다고 간주하지 않는다.
3. 두 결과를 1저자가 수용하고 지원 환경·시간/자원·실행 시점을 고정한 뒤 **시도3 GO**. 결과/중단 상태 수령 뒤에만 **시도4 GO**. 저장본은 시도3→4 그대로 보존한다.

근거는 final_pin_impact.json. 이전56f4cfbb1의 step3_sigma.py·se_material.py는 최종 핀과 바이트 같고, ca_s0_census.py에는 단계2 역사 관문, payload에는 audit 기록 경로가 더 있다. 과거 B의 README는 개발 자료로만 읽었으며 원 결과JSON·원 로그를 새로 읽지 않았다. 과거 실행 Q11 블록과 현행 결속 블록의 바이트도 다르다. 이 비교가 재실행 결과나 새 채택 판정은 아니다.

기존 watcher는 등록된 이전 S0 계획 경로를 계속 참조한다. 새 S0 결과를 그 경로에 덮거나 자동 채택하지 않는다. 새 계획의 신원·입력 사슬·문턱/bed 신원 일치와 채택 위치를 검토한 뒤 필요하면 별도 변경→시험→핀 재고정을 거친다. 과거 개발 자료가 최종 핀 자격을 대신하지 않는다.

## 5. 검사와 인계

block_checks.json은 ASCII·본문MD5·Bash 문법·승인 없음 거부·별도 내부 공격의 실제 범위를 기록한다. 현장/전체 감시 셸 실행은0이다. 기존 shared ledger와 게이트를 바꾸지 않았고 제안만 ledger_proposal.json에 둔다. 최종 전달 ZIP의 이름·해시를 쪽지로 공유하며 Claude 복귀 뒤 기존 사슬 다음에 cherry-pick -x 한다.
