2026-09-16 기준 · bms-balancing

지금까지 이룬 것

BMS 쪽 작업은 세 갈래로 독립해 있다 — 규진팀 마이크로쇼츠 COMSOL 모델, α·β 산출을 서명·검증하는 하네스, 그리고 α·β 열화 정량화 자체. 셋은 서로 다른 속도로 움직였고 닫힌 정도도 다르다. 이 화면은 그 셋을 나란히 놓고, 각 갈래에서 실측으로 닫힌 것과 아직 아닌 것을 같은 크기로 적는다.

이 화면의 숫자는 전부 사본이다. 인용 근거로 쓰지 않는다. 정본은 산출 artifact 와 그 .meta.json, 그리고 bms-balancing/reviews/ · bms-balancing/docs/ 의 원문이다. 원문에 붙어 있는 모집단·범위 경고를 뗀 채로 옮기지 않는다.

1 세 갈래 — 어디까지 왔나

① COMSOL

마이크로쇼츠 6.3 재구축

원본 모델에 대해 우리가 세웠던 주장(M1)을 철회하고 명세를 다시 썼다. 아홉 축의 수렴 진단이 전부 우리 재계산까지 끝났고, 그 뒤 후처리 회수가 어디서 막혔는지도 원시 자료로 확인했다. 전체 수렴은 미완이고 본 실행은 보류 — 모델 검증 완료가 아니다.

② 하네스

α·β 산출 검증층

산출 다섯 종에 계약·서명·validator 를 붙였고 외부 적대적 게이트 리뷰 R13·R14 를 통과했다. 리뷰가 열어 둔 항목은 지금 없다 — R13 §7 · R14 §5 가 남긴 것을 R16 에서 전부 닫았다. 다만 그 "없음" 은 우리 쪽 장부 기준이고, 다음 라운드 요청문은 아직 제출하지 않았다.

③ 정량화

BML α·β 열화 정량화

반복값의 원인을 찾아 닫았고, pyDMA 의 정답 있는 데이터와 실데이터 폭 측정까지 걸었다. 답은 LLI 가 가장 좁고 LAM 두 축은 폭과 함께만 말할 수 있다 — 이것은 미결이 아니라 측정된 결론이다.

2 ③ 정량화 — 가장 크게 닫힌 것

이 갈래가 이번 작업의 과학적 결론을 낸 곳이다. 네 단계를 밟았고, 각 단계가 앞 단계의 답을 한 번씩 뒤집었다.

  1. 받은 결과를 그대로 세었다 — 경계에 붙은 값들

    규진팀 실험 CSV 전부에서 피팅 결과 97 행을 세었다. 32 행이 상자 경계에 정확히 붙어 있고, 16 행이 음수 LAM(전극이 늘어났다는 뜻)이며, 한 상태의 LAMNE 폭이 34.7 %p 였다. 강한 음수는 전부 a_NE 가 상한에 붙은 행이다 — 측정이 아니라 경계가 만든 값이다.

  2. 원본 MATLAB 을 받아 주장을 확정·철회했다

    추측으로 세운 주장 사슬을 전부 철회하고 소스에서 다시 세웠다. a_NE ≥ 1 은 버그가 아니라 의도된 물리 제약 이었고, 반복값의 원인은 rng(0) 오염이었다 — 규진팀이 이미 찾아서 고친 것이다. 우리가 새로 발견한 결함이 아니라는 사실을 그대로 적었다.

  3. 우리가 다시 뽑았다 — 두 경로가 일치한다

    그들 파이프라인을 rng 없이 돌린 것과 우리 Python 포팅이 ~1e-3 안에서 일치하고 난간 경고가 0 이다. 시작점만 바꾼 재실행의 차이는 1e-7 — 즉 시작점이 정한 적합이 아니다. 반복값 문제는 여기서 닫혔다.

  4. pyDMA 의 정답 있는 데이터에 걸었다

    공개 도구 pyDMA 의 검증 예제(P45B 셀)에 우리 포팅을 걸었다. LLI 는 세 구현이 0.09~0.18 %p 안에서 일치한다. LAM 두 축은 1.0~1.5 %p 로 흩어지고 CU2 음극은 부호까지 갈린다. 그리고 우리만 다른 게 아니다 — pyDMA 자신의 두 방법도 같은 축에서 부호가 갈린다.

결정 실험 — "설정이 달라서 아닌가?" 에 답했다

남은 의심은 설정이었다. pyDMA 의 Track C 는 γ 를 반쪽전지만으로 먼저 적합해 초기값으로 쓰고 하한을 0.02 로 둔다. 우리는 초기값 0.25 · 하한 0 이었다. 그래서 fit_gamma_si 를 포팅해 설정을 맞추고 다시 돌렸다.

실행 (CU2)LLILAMcaLAManγ
우리 기본 — γ 초기 0.25 · 하한 03.001.98−1.260.2407
우리 Track C — γ 초기 0.0200 · 하한 0.023.001.98−1.260.2407
pyDMA blend (참조)3.181.55+0.270.2240

γ 초기값을 12 배 옮겼는데 네 값이 표시 자리까지 전부 같다. 즉 LAM 차이는 설정이 아니다. multistart 가 초기값과 무관하게 같은 점으로 가므로 "덜 수렴해서 다르다" 도 아니다 — 목적함수·파라미터화가 다르면 최소가 다른 곳에 있다는 뜻이다.

결론: 이 데이터에서 LAM 분할은 점추정으로 보고할 수 없고 폭과 함께 보고해야 한다. 이것은 이 저장소가 합성 진실의 축퇴 행렬로 재던 것과 같은 결론에 외부 공개 데이터로 독립 도달한 것이다. LLI 결론은 흔들리지 않는다.

그래서 실데이터에서 폭을 쟀다 — 그리고 안 좁아졌다

"폭과 함께 보고하라" 까지는 pyDMA 예제에서 나온 말이다. 그 다음 물음은 우리 실데이터에서 그 폭이 얼마나 되고, 정보를 더 넣으면 줄어드는가 였다. 흔히 기대하는 자리다 — dQ/dV 는 전극 특징이 가장 뾰족하게 나오는 표현이라 목적함수에 넣으면 해가 조여질 것 같다. 축 하나만 바꿔 두 번 돌렸다 (w_dqdv 0 → 1, 나머지 설정·입력·코드 동일).

축dQ/dV 끔 — 최대 폭dQ/dV 켬 — 최대 폭배
LAMPE3.137 %p3.388 %p1.08
LAMNE2.439 %p7.099 %p2.91
LLI1.172 %p1.402 %p1.20

정보를 더 넣었는데 폭이 넓어졌다. 그리고 한 자리에서는 부호가 사라진다 — cycle 1 의 LAMNE 구간이 −0.60 ~ +6.50 %p 로 0 을 가로지른다(점추정은 3.32). 같은 자리가 dQ/dV 끔에서는 [6.59, 9.02] 로 부호가 정해져 있었다. 음극이 줄었는지 늘었는지조차 말할 수 없게 된다.

난간이 같은 자리를 독립으로 짚었다 — dQ/dV 켬에만 경고 하나, a_NE 가 사용자가 세운 하한에 정확히 붙었다. 폭이 넓어진 것과 경계에 붙은 것은 같은 사건의 두 얼굴이다 — 자유도가 남아 해가 상자 벽까지 미끄러졌다.

LLI 는 두 설정 모두에서 가장 좁다 (1.17 / 1.40 %p, LAM 두 축의 3.1~7.1 %p 대비). 합성 진실의 축퇴 행렬 · pyDMA 검증에 이어 세 번째 경로로 같은 순서에 닿았다. 이번 것은 문헌 곡선을 고정한 채 목적함수만 흔든 것이라 앞의 둘과 축이 다르다.

§13-5 가 열어 뒀던 둘도 닫혔다. ① mode_profile_extrema 를 cycles 경로에 붙였다 — 붙이고 다시 재 보니 합집합 이득이 0 이라 기본은 꺼 둔다(껐다는 사실도 산출에 적힌다). ② γ 사전 적합이 하한 0.02 에 붙던 것 — pyDMA 쌍으로 RMSE 0.473923 을 자릿수까지 재현했고, 진짜 원인은 초기값도 방향 규약도 아니었다. 아무도 RMSE 의 크기를 안 보고 있었다 — 실데이터에서 이 사전 적합은 애초에 잘 맞지 않는다(합성 대비 세 자릿수 차이). 그래서 γ 는 점 하나가 아니라 식별 띠와 맞춤 정도를 같이 낸다.

2·5 한 문단으로 옮길 때 — 이렇게 쓴다

③ 갈래의 결론을 밖으로 옮길 일이 많다. 줄이면서 뜻이 바뀌는 자리가 정해져 있어서, 옮겨도 되는 문장과 그 옆에 반드시 붙는 단서를 같이 적는다.

옮겨도 되는 문장

LLI 는 좁고, LAM 분할은 폭과 함께

같은 데이터·같은 잔차를 내는 해가 LAM 두 축에서는 넓게 퍼지고 LLI 에서는 좁게 모인다. 그러니 LAM 은 점추정 하나로 보고하지 않고 구간으로 보고한다. 서로 다른 세 경로(합성 축퇴 행렬 · pyDMA 공개 데이터 · 실데이터 폭 측정)가 같은 순서에 닿았다.

옮기면 틀리는 문장

"LAM 은 원래 못 잰다"

측정된 것은 못 잰다가 아니라 이 목적함수·이 입력에서 해가 하나로 정해지지 않는다이다. 점추정 자체는 계산되고, 독립 구현 둘이 ~1e-3 안에서 일치한다. 틀린 값이 아니라 혼자서는 답을 고르지 못하는 값이다 — 구간을 좁히는 길(다른 입력·반쪽전지·held-out)은 닫히지 않았다.

옮기면 틀리는 문장

"LLI 는 정확하다 / 맞다"

잰 것은 좁다(식별 폭)이지 맞다(참값과의 거리)가 아니다. 둘은 다른 양이고 참값은 실데이터에 없다. 실제로 LLI 에도 난간 L2 (LLI ≈ 1−x_cell)에서 남는 차이가 있다.

반드시 같이 가는 단서

이 폭들은 하한이다

재는 방식이 도달 가능한 해를 전부 훑지 않으므로 참 폭은 이보다 넓을 수 있다(산출의 width_is_lower_bound 가 행마다 True). 게다가 문헌 곡선 선택이 만드는 폭은 여기 안 들어갔고 그쪽이 더 크다 — 두 축을 합치지 않았다.

반드시 같이 가는 단서

모집단이 좁다

폭 측정은 셀 하나(HD_knee) · 사이클 셋 · 허용 0.01 이다. 파우치 네 상태에서는 같은 순서가 4/4 로 재현됐지만 원통형으로는 넘어가지 않는다(그쪽 잔차 증가는 관측일 뿐 원인 미확정). 셀 종류를 건너뛰어 일반화하지 않는다.

실무에 제일 쓸모있는 한 줄

dQ/dV 를 더 넣는 것이 답이 아니다

목적함수에 dQ/dV 가중을 올리면 폭이 줄지 않고 LAMNE 는 2.9 배가 되며 한 사이클에서는 부호 식별까지 잃는다. 반대로 "dQ/dV 끔이 옳다" 는 것도 증명되지 않았다 — 좁은 쪽이 참에 가깝다는 근거는 따로 필요하다.

왜 이게 "미결" 이 아닌가. 열린 항목이 없다는 말과 답이 시원하다는 말은 다르다. 물었던 것은 "α·β 열화 정량화를 어디까지 믿을 수 있나" 이고, 거기에 측정으로 답했다 — 믿을 수 있는 범위가 축마다 다르고 LAM 에서는 그 범위가 넓다는 것이 답이다. 부정적 결론도 결론이다. 남은 것은 이 결론의 미결 부분이 아니라 다음 일이다 — 새 모델 설계 요구서, 게이트 리뷰 요청문 둘(갈래마다 하나씩 — 아래 §3), 그리고 ① COMSOL 의 A 보완.

3 ② 하네스 — 숫자가 살아남게 만든 층

위 ③ 의 결론이 의미를 가지려면 그 숫자가 어디서 어떤 코드로 나왔는지가 고정돼야 한다. 그 층을 이 갈래에서 만들었다.

쉬운 말로 — 하네스가 대체 뭘 하는 건가

우리가 “LAMNE 폭 7.099 %p” 같은 숫자를 냈을 때, 몇 달 뒤에 누가 그걸 쓰려면 어느 코드·어느 입력·어느 환경에서 나온 숫자인지가 같이 붙어 있어야 한다. 안 붙어 있으면 그건 숫자가 아니라 소문이다.

우리가 그걸 당해 봤다. 규진팀에서 받은 결과표 97 행이 정확히 그 상태였다 — 표는 있는데 어떻게 나왔는지가 없어서 재현을 못 했고, 결국 “근거로 쓰지 않는다”로 끝났다. 하네스는 우리 숫자가 남한테 그렇게 보이지 않도록 만드는 층이다.

숫자 하나가 태어나서 정본이 되기까지 다섯 관문을 지난다.

  • ① 산출 계약 — “양식이 맞나”. 산출 파일은 다섯 종류뿐이고 각각 무슨 열이 있어야 하는지 정해져 있다. 핵심은 모르는 형식이 오면 “일단 통과”가 아니라 거부라는 것. → 형식이 슬쩍 바뀐 산출이 조용히 섞여 드는 것을 잡는다.
  • ② provenance 서명 — “영수증”. 행마다 실행 번호가 붙고, 파일 옆에 영수증이 같이 나온다. 거기 적히는 것: 실행 전·후의 코드 버전 · 쓴 라이브러리 판 · 명령줄 전체 · 읽은 입력 파일의 지문. 전·후를 둘 다 적는 게 요점이다 — 산출 도중에 코드가 바뀌면 둘이 달라지고 그것도 기록에 남는다.
  • ③ validator — “내용이 계약을 지키나”. ①이 양식이면 이건 내용이다. 열이 있나, 단위가 맞나, 숫자가 형식적으로 말이 되나.
  • ④ 난간 — “물리적으로 말이 되나”. 해가 상자 경계에 붙었나, 산술 항등식이 성립하나. 제일 실전에서 일하는 놈이다 — 규진팀 97 행 중 32 행을 이걸로 잡았고, 위 §2 의 폭 측정에서도 우리가 결론을 말하기 전에 난간이 먼저 “a_NE 가 하한에 붙었다”고 신고했다. 다른 방법으로 같은 곳에 닿은 것이다.
  • ⑤ 폭 측정기 — “애초에 답이 하나인가”. 앞의 넷이 “이 숫자를 믿을 만한가”를 본다면 이건 답이 유일한가를 본다. 점추정 하나 대신 도달 가능한 범위를 잰다. 이게 없었으면 우리는 “LAMNE = 3.32 %p”라고만 적고 넘어갔을 것이다 — 그게 −0.60 ~ +6.50 사이 어디든 될 수 있다는 걸 모른 채로.

그리고 그 위에 승격 게이트가 있다. 다섯을 종합해서 “이 산출을 정본으로 올려도 되나”를 기계가 답한다. 설계 원칙 하나가 여기 박혀 있다 — 모르는 것을 안다고 적지 않는다. 비교가 불가능한 축(예: 옛 정본에 환경 기록이 아예 없음)은 통과도 불통과도 아닌 별도 코드로 뺀다. 통과로 세면 거짓말이고, 실패로 세면 옛 정본이 영원히 못 올라온다.

matrix · profile · degeneracy · shape · cycles. 종류 판정이 fail-closed 라 모르는 형식은 통과가 아니라 거부다.

통과한 것

외부 적대적 게이트 리뷰

R13 은 승격·legacy 동결 조건을 닫았고, R14 는 GO 다. 리뷰어가 인용한 tree 해시를 우리 쪽에서 확인해 일치시켰다.

GO 의 범위를 넓히지 않는다. R14 GO 는 R14 범위 한정이다 — 전체 하네스 · BML 과학 타당성 · COMSOL · 장시간 실행 승인이 아니다. 리뷰어는 전수 재실행을 하지 않았다고 스스로 밝혔고, 그 말을 그대로 옮겨 둔다. 열린 조건도 남아 있다.

R14 가 “다음 라운드” 로 미뤄 둔 셋을 닫았다. ① 승격 묶음의 산출들이 서로 다른 커밋에서 나올 수 있는데 게이트가 그것을 안 봤다 — 이제 혼재를 계약 위반으로 세고, 예외는 규칙이 아니라 기록이다(두 개의 전체 커밋과 코드 동등성 검토 범위를 적고, 정확히 그 집합에만 걸린다). ② 옛 정본과의 일회성 이관에 별도 판정을 준다 — 포괄 허용 플래그로 통과를 만들지 않고 승격 자격은 여전히 false 다. ③ 기록용 명령이 산출 위치를 말없이 가정하던 것을 오류로 바꿨다.

그리고 도구가 남의 기계에서 처음 돌며 네 번 걸렸다. 이미 흡수된 브랜치로 push 하라는 안내, 어디에 서야 하는지 말하지 않던 블록, 묶음마다 다른 manifest 이름, 항목 목록 키의 갈림. 넷 다 재현 시험부터 닫았고, 그중 하나는 내 첫 수정이 반만 고쳐 한 번 더 걸렸다 — 시험이 철자 하나만 보고 있었기 때문이다. 지금은 접근 자리 전부를 센다.

R16 — 리뷰가 열어 둔 항목이 지금은 없다

R13 §7 과 R14 §5 가 "다음 라운드" 로 남긴 것을 한 라운드에서 전부 닫았다. 닫혔다는 말의 뜻은 좁다 — 리뷰어가 지목한 구멍마다 재현 시험을 먼저 빨갛게 만든 뒤 막았고, 그 시험이 지금 저장소에 남아 있다는 뜻이다.

이 라운드에서 내 결함 둘이 끝에서 끝까지 돌려서야 나왔다. 묶음 영수증에 도구의 지문 대신 상태 문자열을 실어서 깨끗한 트리에서도 언제나 "다름" 이었고, 또 하나는 이 저장소가 모노레포라 경로를 푸는 기준이 한 칸 어긋난 것이다. 단위 시험 일곱은 전부 초록이었다 — fixture 가 지문을 직접 넣어 줬기 때문이다. 이 저장소가 여러 번 겪은 그 모양이다.

"열린 항목 없음" 의 범위. 우리 장부가 비었다는 뜻이지 외부가 통과시켰다는 뜻이 아니다. R14 GO 는 여전히 R14 범위 한정이고, 그 뒤 라운드(R14 다음) 요청문은 아직 제출하지 않았다. 다음 리뷰가 새 항목을 여는 것이 정상이며 — 지난 열다섯 라운드가 매번 그랬다.

합칠 수 있나 — 네 층으로 갈라야 한다

① 과학 결론

이미 합쳐지는 중이다

새 모델 설계 요구서가 정확히 그 자리다. 거기 첫 표가 합성 축퇴 행렬 · pyDMA · 실데이터 폭을 한 줄씩 놓았고, 유일성 측정 절은 dd 의 합성 프레임을 "구분 시험을 먼저 돌려 보는 곳" 으로 끌어들였다. 세 경로가 같은 순서에 닿았다는 것 자체가 합쳐진 결과다.

② 교훈·패턴

합쳐야 한다

"fixture 가 진실을 가린다" · "증인은 기계 독립이어야 한다" · "종료 코드 0 이 성공이 아니다" 는 프로젝트 소속이 없다. 위의 겹침 표가 그 증거이고, 이런 것이 모이는 자리는 위키다.

③ 코드

한 방향으로만, 아주 조심해서

dd 의 코드 신원은 정해진 몇 개 경로만 본다. 공용 라이브러리를 만들어 그 안에 넣으면 하네스 쪽 사정으로 한 줄 고칠 때마다 dd 의 10 시간짜리 산출물이 무효화된다. 그러니 하네스가 dd 의 설계를 베껴 쓰는 건 되고 (dd 는 안 움직인다), dd 가 하네스를 가져다 쓰면 안 된다. 지금은 복사가 공유보다 낫다 — 중복 비용보다 무효화 위험이 크다.

④ 리뷰 번호

합치지 않는다

번호를 합치면 한쪽 라운드가 다른 쪽을 막는다. 지금은 독립이라 어느 쪽이든 먼저 낼 수 있다. 공유하는 것은 외부 리뷰 예산뿐이고, 그 사실이 위 §3 의 번호 혼동을 만든 원인이기도 하다.

③ 이 왜 규칙이 되었나. 이것은 취향이 아니라 이 저장소가 이미 한 번 값을 치르고 배운 경계다. 서브 브랜치를 본진이 흡수할 때 그 흡수가 안전했던 이유가 바로 bms-balancing/ 이 dd 의 코드 신원 바깥에 있다는 것이었다. 그 경계를 지우는 방향의 "공통화" 는 같은 값을 거꾸로 치르는 일이다. 최소주의 사다리(중복을 줄여라)를 여기에 적용하지 않는다.

둘로 가른 것 하나 (§17 → §18). 후기 시간상한을 강화한 실행은 코어 수까지 2 → 16 으로 같이 바뀌어 있었다. 그래서 원래 시간식을 16 코어로 돌린 통제 해를 하나 더 받아, 코어 축과 cap 축을 따로 쟀다 — 위 표의 마지막 두 줄이다. 코어 축은 1e−12 mV 급이고, 결합 차이의 사실상 전부가 cap 축이었다. 다만 해 셋만으로 두 축의 상호작용이 없다고는 말하지 않는다.

증거 보존. 건너온 묶음 열네 개를 bytes 그대로 저장하고 각 항목의 sha256 을 옆의 manifest 와 대조했다. 줄끝 정규화로 bytes 가 갈리는 사고를 한 번 겪고(그리고 되돌리고) .gitattributes 규칙을 묶음마다 먼저 넣는 순서로 바꿨다. 커밋한 뒤에도 바이트를 다시 대조한다 — 최근 다섯 묶음은 111·50·41·21·8 건 전부 불일치 0 이었다.

도구가 남의 기계에서 처음 돌자 네 번 걸렸다. 지금까지 이 보존 스크립트는 우리 기계에서만 돌았다. 사용자 기계에서 처음 돌리자 흩어진 전제가 한꺼번에 드러났다 — 이미 흡수된 브랜치로 push 하라고 찍던 안내, 저장소 루트에서 돌아야 하는데 그 말을 안 하던 블록, 묶음마다 다른 manifest 이름, 그리고 항목 목록의 키가 entries·files· payload 로 갈리는 것. 넷 다 재현 시험부터 닫았다. 안내문은 사람이 그대로 붙여 넣는 코드다 — 코드와 같은 규율로 본다.

후처리가 어디서 막혔나 (§21). 정상 guard 실행은 시간 적분을 5 초까지 끝냈다 — 우리가 원시 로그를 세어 확인했다(줄 987 · 채택 간격 986). 죽은 것은 그 뒤 후처리이고, 원인은 좌표 증거가 쓴 변수 하나가 COMSOL 에서 정의되지 않은 것이다. 모델 결함이 아니라 증거 구현이 넣은 것이고 기준 소스는 안 바뀌었다. 여기서 한 가지가 더 읽힌다 — 종료 코드 0 이 성공이 아니다. compile 과 batch 가 둘 다 0 을 냈는데 로그 안에 치명 오류가 있었고, 그쪽 worker 가 그것을 잡아 실패로 적었다. 우리 하네스가 자체 리뷰에서 닫은 축과 같은 모양이다.

이어진 API 복구 시도는 모델을 열기도 전에 막혔다 — Java 가 자기 입력을 읽는 첫 단계에서 파일 접근이 거부됐다. 그래서 모델 복사 로드가 실패한다는 것은 확인된 적이 없다. 그것이 다음 제안(저장 해 전용 API 경로)이 성립하는 근거이고, 동시에 "Desktop 에서 열렸으니 batch 에서도 열린다" 고 쓰면 안 되는 이유다.

갈래가 인계됐고, 준비본이 독립 검사에서 막혔다 (§23·§24). COMSOL 쪽 작업이 다른 손으로 넘어갔고 우리는 보존과 검토만 한다. 넘어온 A 단계 준비본은 포장은 깨끗했고(크기·지문·항목 수·CRC 전부 통과) 합성 시험 38 개도 그쪽 기계에서 다시 통과했다. 그런데 수신 측 독립 검사가 세 자리를 막았고, 놀랍게도 셋 다 우리가 이미 값을 치른 축이었다 — ① 소비자가 기대 속성 1,143 중 991 만 골라 값이 전부 맞아도 거부되는 것 ② 새 코드가 플랫폼 줄바꿈(Windows CRLF)으로 쓰는데 계약이 지문으로 고정한 기준 표는 LF 인 것 ③ 단위를 하나 몰래 바꿔도 전체 판정이 통과로 나오는 것. 저쪽 양성 fixture 가 기대값을 키 하나로 줄여 접점을 지나가지 않았기 때문이다 — fixture 가 진실을 가린다는 이 저장소의 규율 그대로다. 순서는 A 보완 → 재검토 → B 별도 승인이고 승인 값은 false 그대로다. 우리 쪽 COMSOL 호출 0 · 제출 코드 수정 0 · 승인 변경 0.

이 갈래는 아직 "모델 검증 완료" 가 아니다. 여섯 축의 이번 표본 민감도가 기준을 만족했다는 것이고, 전체 수렴 · 0.1 s 이후 시간 정확도 · 참값 오차 · 장시간 운전 GO 는 전부 미입증이다. 4.25 V CV 가 양극 OCP 표 하한과 충돌하는 문제도 그대로다. 전해질 양수는 후처리 검사이고 실시간 중단은 미구현이다.

5 아직 아닌 것 — 경고를 떼지 않는다

위 넷을 읽고 나갈 때 같이 가져가야 하는 문장들이다. 떼면 다른 주장이 된다.

① COMSOL

본 실행 보류

전체 메시·시간 수렴 미완. 원본/실험 OCP·물성 출처 대조 미완. 전체 프로토콜 · 12 h 휴지 · 유한 누설 · sweep 미실행. "본 실행 GO" 는 이 저장소 어디에도 없다.

② 하네스

"없음" 은 우리 장부 기준이다

리뷰가 열어 둔 항목은 지금 없지만, 다음 라운드는 아직 제출 전이다. R14 GO 는 R14 범위 한정이고 전체 하네스 · BML 과학 타당성 · COMSOL · 장시간 실행 승인이 아니다. 리뷰어는 전수 재실행을 하지 않았다고 스스로 밝혔다.

③ 정량화

폭은 하한이고 모집단이 좁다

셀 하나 · 사이클 셋 · 허용 하나 · optimizer 한 종류다. 참 폭은 잰 값보다 넓을 수 있고, 문헌 곡선 선택이 만드는 폭은 여기 안 들어갔다 (그쪽이 더 크다). pyDMA 참조값은 우리가 직접 돌린 것이 아니라 검증 스크립트에 적힌 기록이다. held-out 예측은 아직 없다.

전 갈래

원자료는 이 저장소에 없다

규진팀 원자료(xlsx) · .mph · MATLAB 원본은 공개 저장소에 커밋하지 않는다. 화면과 문서에는 결론만 있고, 재현하려면 원자료를 가진 기계가 필요하다.
