- 프롬프트의 파일 SHA256 17개 전부 일치, 배포 MANIFEST의 93개 항목 검증 통과예요.
- 생성기 `run_all_text()`와 배포 `run_all.sh`가 일치하고, jobs.json의 도구 SHA도 맞아요.
- CJ판 대비 입력 90개와 D3 기준값은 불변이에요. 18개 구조의 원본 SHA·원자 순서·좌표·셀 대조도 통과했어요(좌표/셀 오차 < 1e-8 Å).
- CJ 원본 `probe_pack_cj.py --assert-fixed`와 CI 원본 `repro_ci.py --assert-fixed`를 그대로 v6에 실행했고 둘 다 종료 0이에요. 결과 파일은 별도 리뷰 폴더에 썼어요.
- CJ의 17개 오류 주입은 전부 종료 4·성공 메시지 없음·임시 `.part` 없음이에요. 둘째 mv 실패를 제외한 16개는 기존 쌍을 바이트 단위로 보존해요. 둘째 mv는 선언대로 새 tar/옛 SHA가 남고, SHA 대조는 실패해요.
- 관리파일/매니페스트를 쓰고도 오류 반환, 조용한 누락, 중복, 같은 줄 수의 이름 교체, cat/wc/cut의 출력 후 오류, 빈 SHA 출력, 존재검사 grep 오류, find의 출력 후 오류 등 **추가 차단 시험 16개**도 전부 종료 4·구본 보존이에요.
- 정상·복구 경로는 25개 구성원·SHA 대조 성공, 잡 파일 없는 run/은 MANIFEST+env.txt 두 개·종료 0이에요. 승격 뒤 정리 실패는 종료 0·경고·정상 SHA로 바뀌었어요.
- 합성 18잡 최종 집계는 G3/G4/G5 PASS·CLI 종료 0이고, 봉인 파일럿 교체는 PILOT_NOT_SEALED·CLI 종료 3을 유지해요. 부분 PP 준비 실패는 종료 1·금지 파일 미포함이에요.

위 시험은 Windows의 Git Bash/GNU 도구에서 수행했어요. 업체 Linux/VASP 환경의 실제 실행 검증은 아니에요.
**native selftest 194개 전체와 작성자 돌연변이 12개 전체를 재현했다고 주장하지 않아요.** native selftest는 `simple-dftd3` 부재로 합성 패키지 생성에서 멈췄어요. 요청서가 허용한 대로 배포 D3 기준값과 독립 합성 입력을 사용했으며, D3를 새로 계산하지 않았어요.
실제 VASP·QE·UMA 계산, 원격 서버 접근, 저장소 소스 수정은 하지 않았어요.

## S1 — 목록 내용 검증의 기준

**현재 기준을 수용해요. 같은 find를 한 번 더 돌려야 한다고 요구하지 않아요.**
관리파일 수를 디스크에서 세는 변경은 CJ 결함을 정확히 닫아요. 반면 허용 목록을 만드는 도구 자체가 성공을 반환하면서 거짓 목록을 내면, 그 산출물을 다시 세는 것만으로는 알아낼 수 없어요. 같은 구현을 재실행하는 것도 독립적인 보증이 아니에요.

다만 수신 검사의 보증 범위는 좁혀 적어야 해요. `build_v5_vasp_package.py:800–815`는 잡 폴더·필수 입력·실행 기록·입출력 해시를 검사하지만, **모든 보조 반송 파일의 누락을 MISSING으로 만드는 것은 아니에요.**
독립 주입에서 find가 두 stdout.log만 빼고 종료 0이면 25→23개 구성원 묶음이 종료 0·SHA 대조 성공으로 나왔어요. 수신 양성 픽스처도 stdout.log 없이 통과해요. 따라서 허용되는 설명은 다음과 같아요.

> 성공을 반환하는 열거 도구의 잘못된 출력은 포장 단계의 잔여 위험이다. 수신 검사는 필수 과학 증거의 결측을 차단하지만, 모든 보조 로그의 완전성을 보증하지는 않는다.

이는 실제 GNU find의 조용한 누락 버그를 발견했다는 뜻이 아니에요. **성공 응답을 위조한 시험으로 명시된 신뢰 경계를 확인한 것**이고, 이번 GO를 막을 새 P1로 세지 않아요.

## S2 — grep -q 예외

**이 위치의 존재검사에는 수용 가능해요.** 일치를 실제로 읽었다면 그 이름이 있다는 명제는 성립해요. 이 검사는 파일 전체가 오류 없이 읽혔다는 보증으로 쓰면 안 돼요. 뒤의 tar·정렬·cmp는 별도의 전체 처리와 종료값 검사를 유지하고 있어요.
GNU grep도 -q에서 일치가 있으면 오류가 있어도 종료 0일 수 있다고 명시해요: [GNU grep Exit Status](https://www.gnu.org/s/grep/manual/html_node/Exit-Status.html).

선택 권고로 `grep -xF ... > /dev/null`로 바꾸면 전체 읽기 오류도 검사하는 의미가 더 분명해져요. 하지만 현재 위치에서 이름이 없는 목록을 통과시키는 재현은 없고, 이를 필수 수정으로 올리지는 않아요. `-q`만 제거한다고 디스크 전체 무결성이 증명되는 것도 아니에요.

## S3 — 쓰기 검사와 내용 검증

**둘 다 유지하세요. 첫 검사를 빼지 마세요.**
명령 종료값은 '작업 중 오류를 보고했는가', 내용 검증은 '결과의 개수·필수 이름이 맞는가'를 봐요. 서로 다른 명제예요.
'정상 출력을 쓰고 오류 반환' 주입은 첫 검사의 필요성을 분리해서 시험하는 적절한 방법이에요. 내용이 맞아 보여도 보고된 오류를 무시하지 않는다는 계약을 검증해요. 조용한 누락·중복·같은 개수의 이름 교체는 둘째 검사를 검증하고, 이번 직접 실행에서도 차단됐어요.
이 결과를 모든 파일시스템 장애나 동시 변경까지 입증한 것으로 확대하지 않으면 충분해요.

## S4 — 종료 0 또는 1 + SHA 대조

**찬성이에요.** 종료 1은 실패한 계산의 기록을 반송하기 위한 경로예요. 포장 성공·전송 무결성과 계산 성공을 분리하는 것이 맞아요. 그 자료의 에너지 사용 여부는 수신 검사와 G3/G4/G5가 결정해요.
종료 4는 포장만 다시 해서 종료 0+SHA 대조, 종료 2는 원인을 해결하기 전 제출하지 않는 현재 규칙을 유지하세요.
