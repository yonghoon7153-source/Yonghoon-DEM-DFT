# Gate85 원문 증거 보충 검토

2026-10-01. 이번 보충은 기존 85차 판정을 덮어쓰지 않고, 탐침과 재생 로그의 출처·관측 수준을 갱신한다.

**결론: 탐침 및 g61 후속 clean 재생의 증거 보충은 한정 수용한다. G85-N1 P1과 2a 종결 보류는 유지한다.** 새 커밋은 증거·문서만 추가하며, 실제 closure 구성원 검증 코드는 바뀌지 않았다. 수신 스크립트·pytest·변이·복원·COMSOL은 실행하지 않았다.

## 파일 식별과 실제 수신 범위

고정 커밋은 `1b49700e65fb6408caa48124df365264e32480a9`이다. 직전 요청 HEAD b49c24fa에서 한 커밋 앞이며, 비교에서 RUN_SCOPE·tests·mutation_replay 변경이 없다. source_digest는 직전 58개 바이트 검증값 `ba51cd20caa10b7b`를 동일 코드의 식별로 유지한다. 이번에 생산 함수를 실행해 재계산한 값은 아니다.

첨부 `README (1).zip`은 **24,843 bytes**, SHA-256 `bd21e18a142705c45b013b8168fb295e8a10e56d59f0bbf31304edf03b2e7b95`, 9 entries다. CRC·중복/대소문자 충돌·경로·링크 및 각 파일 크기/SHA를 확인했다. README (1).md는 커밋 README.md와 바이트가 같다.

README 표는 25개 payload의 크기와 **SHA-256 앞 16자**를 적고 있다. 전체 SHA manifest가 있다는 뜻으로 바꾸지 않았다.

| 범위 | 직접 확인 |
|---|---:|
| 고정 커밋의 README 외 파일 | 18 |
| 첨부 ZIP의 README 외 파일 | 8 |
| 양쪽 중복 | 5 |
| 합집합으로 확인한 표의 파일 | **21/25** |

원격에서 받은 텍스트는 Git blob SHA까지 확인했다. 중복 5개 파일은 ZIP과 커밋의 전체 바이트가 같다. ZIP에만 있는 세 파일은 `g61_replay_clean.log`, `g61_replay2.log`, `g85_replay_all.log`이며, 커밋 파일로 표현하지 않는다. README 식별과는 일치한다.

다음 네 파일은 첨부에도 없고 고정 커밋의 해당 경로 조회도 404였다.

- `full_regression_91f00a72/g84_full.log`
- `full_replay_aborted/g84_replay_all.log`
- `g61/g61_mutant.log`
- `request_commit/g85_send.log`

따라서 “표의 원문 25개 전부를 이 커밋에서 직접 확인”은 아직 성립하지 않는다. 기존 원문이 남아 있다면 별도 보충할 수 있으나 **이를 위해 계산·시험을 재실행할 필요는 없다.** 이 누락을 새 코드 P1로 추가하거나, G85-N1 보완 전에 큰 진단을 다시 여는 조건으로 삼지 않는다.

근거는 SUPPLEMENT_INTEGRITY.json과 원격 조회 JSON이다.

## 탐침 증거의 수용 범위

원 출력 277 bytes에는 다섯 경우 모두 `STARTED_AND_FINISHED fits=True`가 있다. `as_run.py`는 복원된 command.txt의 heredoc 본문과 바이트가 일치한다. 그러나 두 파일 모두 세션 기록에서 후속 복원됐다는 출처는 유지한다. 이번 바이트 일치가 당시 세션 원본을 검토자가 직접 관측했다는 뜻은 아니다.

원 실행은 “clean d81fdc01”로 부르지 않는다. 정정된 출처는 **HEAD 2bceaf9e + 커밋 전 시험 파일이 있는 작업 트리**다. 2bceaf9e→d81fdc01 비교의 변경은 tests 두 파일뿐이며 RUN_SCOPE 불변은 확인했다. 당시 미커밋 바이트 전체까지 직접 재검증한 것은 아니다.

후속 실행은 최초 기록과 따로 수용한다.

| 기록 | 확인한 내용 | 한계 |
|---|---|---|
| d81fdc01 원 스크립트 첫 호출 | scratch 상위 디렉터리 부재로 FileNotFoundError, rc1 | 결함 거부 증거가 아님 |
| d81fdc01 재현판 및 환경 마련 뒤 원 스크립트 | 각각 다섯 항목이 실행 완료, rc0 | 후속 시험이며 최초 실행을 소급 정화하지 않음 |
| f89b1401 재현판 | 명시 null/패딩/다른 digest/source/reference 다섯 거부 + 실제 hex64 양성 완료, rc0 | 제공된 로그 및 스크립트 대조이며 독립 재실행 아님 |
| f89b1401 원 스크립트 | 네 거부, null 이름표의 한 경우 완료 | 실제 null을 넣지 않고 새 fixture의 유효 digest를 사용하므로 null 거부 실패로 읽지 않음 |

특히 **f89b1401의 원 스크립트 첫 호출도 FileNotFoundError/rc1**이다. README는 이 첫 실패를 d81 쪽에서만 상세히 설명하지만 f89 로그에도 남아 있다. 오류를 삭제하거나 다섯 거부 결과와 합치지 않는다.

이 자료로 기존 “탐침 원문 미수신, 제출 요약만 있음”은 **“원 출력·후속 복원 스크립트·명시적 재현판을 직접 읽어 확인함”**으로 갱신한다. 기존 11개 새 API 부재 예외를 결함 RED로 세지 않는 구분은 계속 맞다. 재현판의 `PROBE_COMMIT`은 환경변수 표식이며 그 한 줄 자체가 archive/clean 상태의 독립 인증은 아니다.

## 전체 재생과 g61 정정

### 완료된 전체 재생

`g85_replay_all.txt`에서 독립적으로 센 결과는 **물었다 344행 / 안 물었다 1행**, 요약은 ran 345다. 문제는 g61의 선언 증인 불일치 하나이며, ZIP으로 받은 wrapper log는 다음을 기록한다.

- 시작/종료 HEAD 28d0effe, status=0.
- 전체 replay rc=1.
- preimage 마지막 문장은 정확히 한 번 등장한다고 보고한다. wrapper는 해당 pipeline의 개별 rc를 따로 기록하지 않으므로 그 문장 관측과 rc를 섞지 않는다.

### g61 후속 실행

최초 정정 후 기록 `g61_replay2.log`의 실제 HEAD는 **28d0effe, status=1**이며 출력이 tail -5로 잘렸다. 앞선 85차 회신의 “f89 정정 후 단독 확인”은 코드 계보 요약이었고, 실제 첫 호출의 HEAD/dirty 상태는 이번 자료대로 정정한다.

새 `g61_replay_clean.log`는 b49c24fa, 시작/종료 status=0, 필터 없는 결과를 담는다. **replay 1회 rc0와 emit-expect 1회 rc0를 별도로** 기록하며, 두 node의 증인은 모두 `Failed: DID NOT RAISE _ReplayError`다. f89→b49 비교에는 tests·mutation_replay·RUN_SCOPE 변경이 없다.

따라서 현재 근거는 **28d0effe 전체 344/345 + b49c24fa에서 g61 한정 재생 및 증인 출력**이다. 최종 커밋 전체 345/345 한 번 실행으로 바꿔 쓰지 않는다. 최초 dirty·절단 기록도 그대로 보존한다. 이 로그는 ZIP에서 실제 확인했지만 현재 고정 커밋 경로에는 없다.

### 중단된 첫 전체 재생

ENOSPC 종료는 원문에서 확인된다. 다만 README의 “그때까지 193 물었다 / 3 안 물었다 / 실행오류 1”은 제공 원문 행 집계와 다르다.

- `물었다` 접두 완성 행: **190**
- `★ 안 물었다` 행: **3**
- `★ 실행오류` 접두 행: **15** — 마지막 하나는 traceback과 이어진 불완전 행

이는 로그의 **행 표식 집계**이며 15개의 독립 원인 또는 정상 완료한 15개 시나리오라는 뜻이 아니다. ENOSPC 연쇄 오류가 보이며 종료 요약도 없으므로, “196번째/193·3·1”을 원문 전체의 확정 결과로 쓰지 말고 해당 요약의 측정 시점이 별도라면 구분해야 한다. 원문을 고치거나 이 중단본을 다시 실행하지 말고 설명만 정정하면 된다. 완료된 후속 전체 재생의 344/345 수치는 이 문제와 분리해 수용한다.

## 전체 회귀와 smoke

고정 커밋의 두 pytest stdout에서 각각 `2039 passed, 1 xfailed` 및 3416.78초/3105.74초를 확인했다. smoke stdout도 통과 문장을 담고 있다. 다만 실행 HEAD/status·외부 rc·시작/종료 시각을 기록하는 `g84_full.log`와 `g85_send.log`는 미수신이므로, 그 항목은 아직 발신 보고와 wrapper 소스 설명 범위를 넘겨 직접 관측으로 승격하지 않는다.

xfail 한 node의 이름은 이 두 -q 로그에 없다. README가 설명한 별도 모듈 재실행의 출력도 이번 25개 표/첨부에는 없으므로, node 식별의 출처는 제출자 설명으로 유지한다. 이를 확인하려 추가 시험을 하라는 요구가 아니다.

## 기존 판정에 미치는 영향

1. 탐침과 g61 후속 증인의 원자료 부재 한계는 위 범위에서 해소된다.
2. 과거 시험 5건의 검증 근거 공백은 후속 성공으로 소급 사라지지 않는다. 생산·수치 오류를 확인했다는 뜻도 아니다.
3. G85-N1은 **사후 validator가 선택된 목록을 실제 config 전체 dependency 집합에 연결하지 못하는 문제**다. 이번 탐침은 시작 전 계획 거부를 검사하므로 이 문제를 시험하거나 고친 것이 아니다.
4. 생산 코드 변경 0이므로 기존 P1, 2a 종결 보류, 2b·실행 GO 미승인을 그대로 유지한다.

다음 주된 작업은 별도 사용자 승인에 따른 **G85-N1 한정 보완**이다. 이번 기록상 범위/집계 정정은 그 회신에 함께 넣을 수 있다. 원래 Gate85 보고서·ZIP·영수증은 변경하지 않았고 로컬 138개 파일 전후 SHA가 동일하다.
