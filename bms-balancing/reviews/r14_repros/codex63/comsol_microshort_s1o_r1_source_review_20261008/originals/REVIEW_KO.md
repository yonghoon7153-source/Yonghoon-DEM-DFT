# S1O-R1 정정본 독립 정적 검토

2026-10-08 · 수신 소스·계약·검증안·전달 기록 검토. 이 회신은 실행 승인이 아니다.

## 결론

**S1O-N1–N4의 소스 정정은 해당 반례와 계약 범위에서 정적 수용한다. 다만 검증안에 P2 세 건이 있어, 현재 계획 그대로 기능 시험을 시작하면 안 된다.** 생산 코드를 다시 고치라는 판정이 아니라 추출 봉인·관측 필드·양성 대조 연결을 먼저 정정하라는 판정이다.

소스 수용, 기능 검증 준비, 전달 종결은 다음처럼 구분한다.

| 판정 축 | 이번 판정 |
|---|---|
| 본체·보충 ZIP 무결성 | 수신 바이트의 크기·SHA·CRC·파일 집합 일치 |
| N1–N4 소스 정정 | STATIC_ACCEPTED_WITHIN_REVIEWED_SCOPE |
| 승인 범위 대비 변경 | 7개 변경의 전후 식별 일치, 나머지 공통 코드 13개 불변; 범위 밖 생산 변경 발견 없음 |
| 8군 130사례 검증안 | P2 세 건 정정 및 사전 봉인 조건 충족 전에는 시험 착수 보류 |
| 기능 검증 | NOT_RUN; 이 검토에서 후보 함수·수신 시험 실행 0 |
| 전달 최종 종결 | 본체 포장 반환과 이후 보존 기록 확인; ZIP 밖 보충 최종 반환·closeout 원파일 미수신 |
| native | native_ready=false; 미승인·미실행; 설치본·어댑터 OPEN 유지 |

받은 Python/PowerShell/Java를 import·dot-source·컴파일·호출하지 않았다. 검토자가 작성한 ZIP/바이트/JSON/텍스트/AST 구문자료 검사와 독립 스칼라 산술만 사용했다. 아래 분기 결과는 **정적 추론**이며 새 시험 PASS가 아니다. 현지 실행 PC의 파일·prefs·프로세스를 새로 관측하지 않았다.

## 1. 고정 입력과 보존

| 자료 | 크기 | SHA-256 |
|---|---:|---|
| 정정 본체 ZIP | 813,053 B | `0a18cb64f8bcbcd4725b45088ee310f85e9292a1ffdced2332b5102f5fd6f9dc` |
| 전달 보충 ZIP | 3,750 B | `4cfd310ae5c019cce63a2ce012debfa9307f44ac739c1253cc07a5cf0c8d73b2` |

본체 116 payload+manifest, 보충 4 payload+manifest의 정확 집합·크기·SHA·CRC·중복/경로를 확인했다. CODE_MANIFEST 21개도 일치한다. `INPUT_CHECK.json`에 별도 수신 관측을 남겼다. 파일명에 붙은 `(1)`은 수신 이름이며 바이트 식별에 영향이 없다.

`CHANGED_FILES.json`의 7개 전후 크기·SHA는 이전 준비본 사본과 현재 사본에 모두 맞는다. consumer는 `charge_balance`·`analyze`의 함수 소스가 바뀌고, Parent는 관련 결속·정확 십진 비교가 보강됐다. P0의 허용 문구 하나를 역치환하면 이전 Java 전체 바이트 SHA로 돌아온다. control·P1–P3·나머지 공통 계약 13개는 바이트가 같다. 검증안의 새 파일 교체와 이력을 별도로 식별했다.

제출된 ORIGINALS_BEFORE/AFTER의 116개 경로·크기·SHA가 같고, POST_PACKAGE_ORIGINALS_CHECK의 후속 보존 주장도 읽었다. 이는 제출 기록 대조이지 116개 원본을 원격 PC에서 지금 다시 해시한 관측은 아니다. 이번 수신 파일과 이전 검토 자료는 변경하지 않았다.

## 2. N1–N4 소스 종결

좌표는 `received/main/`에 펼친 원바이트의 1-based 행이다. 함수 호출 없이 소스와 계약을 대조했다.

### N1 — 일부 charge 구간만 제출하는 반례

`candidate/consumer.py.inactive.txt:226–237`은 실제 native 전체 시간 벡터, 끝시각, 정상/보호 분기 및 charge/global/native의 정확 시간 집합을 확인한다. 전 구간 native/global을 유지하고 charge만 0–1초로 줄이면 `:236`의 `CHARGE_GRID_BINDING`에서 거부된다. native도 함께 줄이면 actual endpoint 결속(`:232–235`)이 필요하며 정상 종료의 configured end 확인(`:365–366`)도 남는다.

`:238–264`는 동일 시각 global Li와 charge Li·단위·출처 식별을 연결한다. `analyze:380–400`은 run/manifest 및 실제 입력의 source identity 대조를 거친 후 이 전체 축을 전달한다. Parent의 `S1NativeAxis:170–217`, `S1ChargeFields:108–155`도 독립 Native 축과 같은 새 구조를 소비한다.

정상 설정120/actual120/safe120과 보호 설정120/actual90.1/safe90은 구별된다. 보호 시 charge는 실제 마지막90.1까지 유지하되 비교만 safe90까지 한다. native/raw adapter가 아직 OPEN이므로 이 소스 결속이 실제 COMSOL 원시 관측을 이미 입증한다고 해석하지 않는다.

### N2 — 누적 양수 속 구간 역행

consumer `:284–300`은 누적량과 별도로 매 인접 구간의 dqN/dqP를 계산한다. 누적 q가 25.001→25.00025로 여전히 양수여도 증분 −0.00075는 −0.0002보다 작으므로 `REVERSE_LI_INCREMENT`로 거부하고 첫 위반 구간·전극·값을 보존한다. 기존 누적 역행 이유도 유지된다.

정확 −0.0002와 그 내부는 거부 경계 밖이며 해상도 제한 상태로 구분한다. 허용치를 넓히지 않았다. `analyze:409–410`에서 오류의 상세 구간 기록을 보존한다. 정상 선형 전하 흐름이 이 검사 때문에 필연적으로 거부되는 경로는 발견하지 않았다.

### N3 — 개수만 같은 위조 시각 배열

Parent `S1TimeVector:59–68`은 0 시작·엄격 증가·유한·범위를 확인한다. `comparison_times`를 `"0"` 255개로 바꾸면 `S1Coverage:85`에서 호출한 해당 검사에 의해 `COMPARISON_TIME_ORDER_OR_RANGE`로 거부된다. 같은 길이의 다른 증가 벡터도 `:88–90`의 고정 요청 내용 대조를 통과해야 한다. 비교⊆교집합⊆native 저장 격자 관계는 `:93–104`에서 별도로 확인한다.

Expected.required_count는 전체 요청255의 수다. 보호 actual90.1/safe90에서는 동일 고정 요청 중 safe 이하를 부모가 다시 유도하여249개를 요구한다. full intersection은 actual90.1까지 가능하다. 전체 count와 안전 prefix를 혼동해 정상 보호 자료를 무조건 거부하던 구조가 아니다. `PROTECTIVE_STOP_INCOMPLETE` 경로도 그대로 유지한다.

정확 십진 비교는 `S1ExactDecimal/S1ExactCompare:27–58`에서 수행된다. `0.0010000000000000000001`은 0.001보다 크고, 정확0.001은 포함 경계다. double로 정보를 잃은 운송 값은 거부하도록 계약화했다. 아직 Python→JSON→PS5.1의 실제 기능 검증 증거는 없다.

### N4 — P0 요약 표식

P0 `:439`의 `accepted tsteps storage`를 원 문구로 되돌리면 이전 전체 바이트 SHA `20c1acc9aa8287ed71363ea12dbea3d54a6a211a4752493560e21f85bc6f6d95`와 같다. `tout=tsteps`, 물리·초기화·σ·OCP·해상도·cap·출력 API 본문을 바꾸지 않은 문구 정정으로 수용한다.

## 3. 기능 검증 전에 정정할 P2 세 건

### R1-V1 / P2 — S1Sha 추출이 빈 문자열로 봉인됨

위치: `VALIDATION_PLAN_R1.json:5231–5236`, 실제 함수 `candidate/Parent.ps1.inactive.txt:23`.

계획은 시작23/끝22와 빈 문자열 SHA `e3b0c442…b855`를 지정한다. 실제 23행은 한 줄 함수이며 90 UTF-8 bytes다. 같은 잘못된 슬라이스와 해시를 비교한 `PLAN_STATIC_AUDIT.json`의 PASS는 함수 추출 완료를 증명하지 못한다. 현 계획대로면 필수 S1Sha 정의가 없거나, 하네스가 선언 밖에서 보충하게 된다.

최소 조치: **23–23행**, 선언된 LF 정규화·끝 LF 제외 규칙의 SHA `13c6456b30805e3b02063ca8cb804b201d948c5518bf01b102610297236d8eed`로 정정한다. 시작≤끝, 비어 있지 않음, 함수 이름·실제 범위·필수 함수 집합도 정적으로 검사한다. 기존 잘못된 PASS 기록은 보존하고 정정 이유를 추가한다. 생산 함수 수정이나 기능 probe는 필요 없다.

### R1-V2 / P2 — PARENT12의 관찰 필드가 실제 반환과 다름

위치: `VALIDATION_PLAN_R1.json:2888–2915`, 특히2914. 실제 반환: Parent `:370–373`.

PARENT12는 S1FinalReturn의 정상 최종 경계 양성인데 `return_value.status`를 읽도록 했다. 실제 함수는 `limited`를 반환하며 status가 없다. 이전 결정의 status나 하네스가 만든 별도 status로 대신하면 최종 기록 후 판정을 검증한 것이 아니다.

최소 조치: **`return_value.limited` + `powershell_final_boundary_classification`**으로 정정한다. PARENT09/10/11/16과 같은 관측 구조를 사용하고 실제 writer/readback/clock의 최종 경계를 확인한다. 생산 반환에 새 status를 넣어 시험에 맞추지 않는다.

### R1-V3 / P2 — 공유 양성 대조가 다른 함수를 가리킴

위치: `VALIDATION_PLAN_R1.json:1083`, `:2906`, 공통 규칙 `:4950` 및 각 사례의 `positive_control_case_id`.

INIT07/08/10의 계수 검사는 INIT01(compare_initialization)에 연결됐지만 해당 함수 양성은 INIT09다. PARENT09/10/11/16의 S1FinalReturn 대조는 PARENT01(S1Decision)에 연결돼 있다. 이것은 같은 source/function/fixture seal에서만 대조를 공유한다는 계획과 맞지 않는다.

최소 조치: 계수 검사는 유효한 INIT09, 최종 반환 검사는 정정한 PARENT12와 연결하고 실제 대조 입력·도달 함수·단일 차이 또는 사전 열거한 복수 leaf 변경을 고정한다. 양성 자신은 스스로의 실제 성공 관측으로 구분한다. 하네스의 숨은 함수 호출·미집계 시작으로 메우지 않는다.

동시에 모든 대조 매핑을 정적으로 감사한다. READ01의 “then exact profile” prose와 target/reach 목록, RESOURCE 전이 사례의 자체 양성과 공유 대조, INIT11/12의 다른 함수 대조도 명확히 한다. 이를 전부 “양성 부재”로 단정하지는 않지만 실제 대상 함수와 봉인된 대조가 연결돼야 한다. 기존130 ID 안에서 해결되지 않으면 입력/사례 수와 승인을 다시 고정하고 시험 전에 멈춘다.

## 4. 검증안의 수용 부분과 최초 봉인 조건

8군130 고유 ID = 기존98 유지 + 신규32, Python99 + Windows PowerShell5.1 31로 일치한다. 군별15/12/12/8/29/7/16/31이다. P0 문구 정적 확인1은130 기능 사례에 합산하지 않는다. 43개 추출 중42개는 유효한 비어 있지 않은 범위와 해시가 일치하며 나머지1개가 R1-V1이다.

PARENT03의 safe prefix249, PAIRED04의 D=0.001V/S=0.002V/h/E_D=E_S=0→INCONCLUSIVE, 정확 십진 경계와 double 운송 거부의 설계는 정적 대조상 맞는다. 정상·보호·초과 producer 결과를 실제 Python에서 만들고 raw JSON을 부모가 읽도록 한 방향도 수용한다. 실제 성공 여부는 아직 알 수 없다.

새 하네스가 아직 없다는 이유만으로 별도 결함을 만들지 않는다. 다만 다음 사항은 최초 봉인의 필수 조건이다.

- 봉인 시점을 분리한다. 첫 엔진 전에는 소스·하네스·입력·기대 이유·명령·엔진·출력 연결 규칙을 고정한다. Python 세션에서 생성한 실제 producer JSON은 그 후, PowerShell 전에 바이트/SHA를 고정한다. “첫 시험 전 실제 producer 출력”을 만들려고 미등록 예비 함수 호출을 하지 않는다.
- PARENT14의 실제 analyze INCONCLUSIVE producer ID/입력 및 INIT·READ·RESOURCE의 대조 연결을 명시한다. 수제 요약이나 집계 밖 analyze 실행을 사용하지 않는다.
- PARENT_R108/R114처럼 의도적으로 여러 leaf를 바꾸는 사례는 변경 경로를 정확히 열거한다. 임의의 “한 필드만” 문구와 동시에 남겨 두지 않는다.
- 130은 한 입력씩의 고유 사례 수이지 assertion 수가 아니다. 대조를 재실행해 개수를 부풀리거나 숨은 parameterization을 추가하지 않는다. 정확 첫 이유와 도달 함수가 다르면 FAIL이다.

제안 예산720+420+300+300+120=1,860초와 엔진 각1세션은 산술상 정합적이다. 실제 비용을 측정한 값이나 완료 보장은 아니다. 시간 내 봉인·시험을 못 마치면 미완으로 멈춘다. 현재2700초 정정 예산에서 전용하지 않는다.

세 P2와 위 봉인 사항은 **다음 별도 검증 승인에 포함할 좁은 사전 정정 조건**으로 묶을 수 있다. 받은 본체/원 manifest를 덮어쓰지 않고 새 계획·하네스 봉인에서 이력을 연결한다. 생산 바이트 변경, 추가 사례·세션·예산이 필요하면 조건부 범위를 벗어나므로 새 승인 전 중지한다. 이번 회신 자체는 그 별도 승인이 아니다.

## 6. 회신 및 다음 한 건

1. N1–N4는 정적 소스 정정 수용으로 기록한다. 기능 성공·microshort 물리 효과·실제 실행 가능성을 얻었다고 쓰지 않는다.
2. 다음 별도 승인에 R1-V1–V3의 검증안 정정·사전 봉인 명확화를 포함한다. 생산 코드는 그대로 두고, 조건을 충족한 경우에만 Python1/PS5.1 1세션 한정 검증을 수행하고 멈춘다. 문안은 `VALIDATION_APPROVAL_DRAFT_KO.md`에 있다.
3. 기능 검증을 통과해도 설치본 초기화 직후 t0·실제 계수 연결·native/raw·OS 자원 감시/중지 어댑터는 자동 종결되지 않는다. native_ready=false, 전체/정상 gate INCOMPLETE, 정책/실제 코어 UNVERIFIED, OCP 외삽 금지와 과거 실패/영수증 경계는 유지한다.
