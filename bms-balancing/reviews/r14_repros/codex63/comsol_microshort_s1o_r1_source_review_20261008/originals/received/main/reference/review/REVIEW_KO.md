# S1-O 오프라인 준비본 독립 정적 검토

검토일: 2026-10-07. 대상: COMSOL_MICROSHORT_S1O_OFFLINE_PREPARATION_20261007.zip.

## 판정

**패키지 무결성과 비활성 부분 준비는 수용한다. 현재 소비자·부모에는 수정할 결함이 있어, 현 바이트 그대로의 98사례 검증 착수는 권고하지 않는다. 먼저 좁은 오프라인 정정본과 갱신한 검증안을 제출한다. native 실행 준비 완료나 실행 승인이 아니다.**

`native_ready=false`를 유지한다. 설치본 초기화·계수 연결, raw/native 어댑터, OS 감시·중지의 OPEN은 정직하게 공개됐으며, 이번 준비 범위 안에서 이를 완성하지 않았다는 사실 자체를 결함으로 세지 않았다. 다만 이미 작성한 소비자와 부모의 계약 이행 누락은 OPEN과 구분해야 한다.

| 심사 축 | 판정 |

| 수신 ZIP·manifest·코드 식별 | PASS — 수신 파일에 대해 직접 대조 |

## 2. 수정 필요 사항

### S1O-N1 / P1 — 수지 자료의 시각 집합·종료시각이 실행 증거와 결속되지 않는다

위치: `candidate/consumer.py.inactive.txt:220`, `:312`, `:316`–318. 관련 `:183`, `candidate/Parent.ps1.inactive.txt:112`–113. 계약: `contracts/CHARGE_BALANCE.json:32`, `:56`, `:116`.

계약은 전류/재고 자료를 실제 저장 시각 전체와 시작·끝에 연결한다. 그러나 `charge_balance`의 시각 조건은 행 2개 이상, 첫 시각 0, 증가 순서뿐이다. `analyze`는 이 함수에 기대 종료시각/전체 시각 집합을 넘기지 않는다. `compare_policy`의 집합 대조에도 `charge`가 없다. 부모도 `charge.records`의 개수 하한만 확인한다.

정적 반례: 나머지 정상 120초 자료·초기화·계수·전압·프로파일을 그대로 두고 charge만 t=[0,1]로 끝낸다. 면적 1, I=j=R_N=0.25, R_P=-0.25의 상수 전류와 이에 일치하는 N→P 재고 이동, 일정한 전해질 재고, 해당 구간의 적분오차 bound=0을 둔다. 이 짧은 구간의 수지는 CONSISTENT다. 별도의 global/profile은 전체 요구 시각을 충족하므로, 현 분기에는 잘린 charge를 이유로 `evidence_validity=VALID` 및 `AWAITING_S1_LIMITED_EXTERNAL_REVIEW`를 막는 검사가 없다.

영향은 실제 실행이 잘렸다는 주장이 아니라, **120초 완료 증거에 1초 수지 증거를 붙여도 현재 소비자가 범위 차이를 잡지 못한다**는 것이다. 미래 raw 어댑터가 OPEN인 사실로 현재 함수의 계약상 집합 검사를 대체하지 않는다.

필요한 정정:

- 검증된 native 저장 격자와 charge 시각의 정확한 집합·순서·시작·끝을 대조한다. global의 Li 항과 charge 재고 항도 같은 원자료·시각에 결속한다.
- 보호중단에서는 실제 저장 범위와 비교 safe prefix를 구분한다. 비교가 t_minus에서 끝난다는 이유로 수지의 실제 종료 증거를 임의로 버리지 않는다.
- 정상 양성, 끝부분 누락, 중간 시각 누락, 같은 개수의 다른 시각 반례를 고정한다. 처음 거부한 이유·단계를 남긴다.

### S1O-N2 / P2 — 누적 수지가 양수이면 중간 구간의 역방향 이동을 놓친다

위치: `candidate/consumer.py.inactive.txt:237`–238, `:251`–255. 계약: `contracts/CHARGE_BALANCE.json:110`.

계약은 실제 시각 간 signed increment에 deadband를 적용한다. 현재 코드는 t=0 대비 누적 q_N/q_P만 음수인지 검사한다. 이전 행 대비 증분 검사가 없어, 총 누적량이 양수인 중간 역행을 CONSISTENT로 남길 수 있다.

독립 산술 반례(단위 C/m²; 전류 0.25 A/m² 일정, 적분 bound=0):

| t(s) | q_I=q_RN=q_RP | q_N=q_P | 누적 잔차 | 현재 허용치 |
|---:|---:|---:|---:|---:|
| 0 | 0 | 0 | 0 | 0.0002 |
| 100 | 25 | 25.001 | 0.001 | 0.0027001 |
| 100.001 | 25.00025 | 25.00025 | 0 | 0.002700025 |

모든 누적값은 양수이고 모든 누적 잔차는 허용치 이내다. N/P를 반대 부호로 같은 양만큼 바꾸면 총 Li도 일정하다. 그런데 마지막 구간의 q_N/q_P 증분은 **-0.00075**, 계약 deadband **-0.0002**를 넘는 역방향이다. 원점 대비 검사로는 잡히지 않는다. 이 세 점 이후 정상 양성 자료를 이어도 이미 있었던 역행을 없던 일로 만들 수 없다.

필요한 정정: 이전 행 대비 Δq_N/Δq_P를 검사하고 최초 위반 구간·값을 보존한다. 누적 수지 일치와 방향 판정은 별도 축으로 둔다. 양의 누적량 속 음의 증분, 경계값, deadband 안 반올림을 각각 검증한다. 수치 문턱을 느슨하게 바꾸지 않는다.

### S1O-N3 / P2 — 부모의 비교 시각 검사가 배열 내용 대신 개수에 그친다

위치: `candidate/Parent.ps1.inactive.txt:117`–124, `:168`–187.

부모는 common_requested_count, comparison_count와 배열 길이를 확인하지만 comparison_times/full_intersection의 유한성·순서·중복·정확한 요구 시각·부분집합 관계를 검사하지 않는다.

정적 반례: 그 밖의 유효한 consumer 결과에서 두 시각 배열을 각각 `"0"` 255개로 바꾸고 count/status/maxima 등을 유지한다. 현재 coverage 분기는 이를 내용으로 거부하지 않는다. 따라서 부모가 malformed nested evidence를 독립 대조한다는 범위에서는 검사가 불충분하다.

이는 고정된 정상 producer가 실제로 그런 결과를 냈다는 뜻도, 해시 검사를 우회하는 공격이 관측됐다는 뜻도 아니다. **부모의 명시된 방어 경계**에 대한 반례다.

필요한 정정: 신뢰된 계약의 정확 요청 목록 및 검증된 safe end로 기대 비교 목록을 유도한다. 관측 결과의 count를 기대값으로 복사하지 않는다. 실제 교집합은 정렬·유일·유한·범위를 검사하고, 비교 목록과의 포함 관계도 검사한다. 같은 길이 중복/다른 시각/비유한/누락 반례와 실제 Python 양성 출력의 부모 소비를 연결한다.

### S1O-N4 / P3 — P0 저장 정책 설명 문자열이 실제 설정과 다르다

위치: `candidate/variants/P0.java.inactive.txt:416`, `:439`, `:540`. 계약: `contracts/POLICY_VARIANTS.json:2248`–2249.

P0는 `tout=tsteps`인데 요약 로그는 `requested tlist storage`라고 쓴다. 실제 runtime readback은 따로 있어 설정 자체의 오류는 아니다. 다만 P0/P1의 대조 축이 저장 정책이므로 P0 문구를 정정한다. P1–P3의 tlist 설정이나 물리 본문은 바꾸지 않는다. 이 경미한 항목만으로 native 실패를 주장하지 않는다.

## 3. 결함과 구분하는 검증안 고정 조건

아래는 현재 공개된 한계 또는 아직 만들지 않은 fixture의 구체화 문제다. 별도 P1로 늘리지 않는다.

1. **PARENT03 보호중단:** 예컨대 t_minus=115이면 공통 요청 prefix는 254개다. 고정 255를 Expected에 주면 목표 PROTECTIVE_STOP 분기보다 coverage에서 먼저 거부된다. 검증된 safe end와 고정 요청 목록으로 기대값을 유도하고 목표 단계 도달을 확인한다.
2. **PAIRED04 문턱 동률:** D만 양의 문턱과 같다고 해서 INCONCLUSIVE가 정해지지 않는다. D=.001, S=.001, E_D=E_S=0이면 NOT_DISTINGUISHABLE_WITHIN_T, S=.002이면 INCONCLUSIVE다. D/S/E 네 값을 시험 전에 모두 고정한다.
3. **부모 정밀도:** `0.00100000000000000001`은 Decimal에서 .001을 넘지만 binary64에서는 .001로 반올림된다. 부모는 요약 모순으로 거부할 수 있다. 이는 SOURCE_CONTRACT_LINKS가 공개한 fail-closed 한계이지 silent PASS가 아니다. Python→JSON→PowerShell 경계 fixture에서 실제 기대 판정을 명시한다. 문턱을 완화해 해결하지 않는다.
4. **어댑터 OPEN:** 변형별 own requested times, raw readback·초기화·계수·cohort 연결은 미래 immutable adapter가 고정 소스에 묶어야 한다. 이번에는 실제 OS/COMSOL 연결을 구현했다고 읽지 않는다.
5. **부분 생성 실패:** 미래 `create_exclusive_evidence_and_reserve_one_attempt`가 일부 생성 후 예외를 내는 경우 소유/미완 기록 계약을 정해야 한다. 아직 없는 native 어댑터의 OPEN 조건이며 이번 소스의 native 누수 관측으로 세지 않는다.

현재 98 ID는 중복 없이 Python82/PowerShell16으로 맞는다. 수정 후 새 반례를 추가·세분하면 새 실제 사례 수를 다시 보고해야 한다. 숫자 98에 맞추려고 기존 양성이나 이유 검사를 삭제하지 않는다. fixture/harness/엔진 식별·추출 범위·새 source seal·이유/도달 단계를 첫 실행 전에 고정한다. 현 검토에서 시험은 실행하지 않았다.

## 4. 유지할 설계와 OPEN

- dense 1337 / sparse 255(187+50+18), 전극별 241좌표와 전체 저장 교집합의 별도 보고는 정합하다. P0→P1 저장, P1→P2 요청, P2→P3 cap의 분리도 유지한다.
- K 기본4+수치대조16+pilot4=24, 명목 60시간은 미승인 상한이다. 바로 전체 실행을 승인할 근거가 아니다. 120초 pilot을 300초 이후·2700–3600초 기울기 검증으로 읽지 않는다.
- 설치본의 일관 초기화 직후 t0, 생성식/실제 계수/API, raw/native 연결, OS 자원/중지·소유 정리는 여전히 OPEN이다. 합성 검증이 통과해도 자동 종결되지 않는다.
- raw-bound quadrature bound가 없으면 전류 적분의 강한 수지 판정은 INCONCLUSIVE를 유지한다. near-zero 방향 미분해와 재고 보존 판정은 같은 의미가 아니다.
- 기존 S0·NORMAL480·B-min 수용 및 과거 실패/원복/recipient=null을 다시 열거나 수정하지 않는다. 전체/정상 gate INCOMPLETE, 실효 정책/실제 코어 UNVERIFIED, OCP 외삽 금지를 유지한다.

## 5. 전달·시간 기록의 증거 수준

수신 ZIP의 크기와 SHA는 사용자가 붙인 외부 영수증과 일치한다. 그러나 외부 DELIVERY_RECEIPT.json과 FINAL_PACKAGE_TOOL_RETURN.json 자체는 이번 첨부에 없으며, 그 내용은 사용자 메시지로 받았다. 그러므로 해당 sidecar 원파일 바이트·SHA까지 수신자가 검증했다고 쓰지 않는다.

보고된 receipt snapshot은 전체 2299.118492800044 / 3600초, 전달 7.799025900043944 / 300초다. 후속 반환 전사의 chunk `892caf`, rc0, wall 7.0828027초와 출력의 최종 snapshot 2299.133349100128초 / 전달 7.813882200127864초는 **보고된 범위에서는 한도 이내**다. 호출 wall time을 snapshot에 더하지 않는다. 원점 전 intake와 전사 파일 작성 후까지의 전체 종료 실측은 별개다. rc0은 포장 도구 반환이지 native 실행 PASS가 아니다.

ZIP 안 선택 원본 10개 AFTER는 포장 전 기록이다. 포장 후에도 불변이라는 내용은 외부 영수증의 제출자 보고로 구분한다. 현지 보존 기록은 유효한 증거이나 검토자가 실행 PC를 재관측한 것이 아니다. 이 한계는 위 코드 결함을 발견·판정하는 데 장애가 되지 않는다.

## 6. 다음 한 건

좁은 정정 범위는 N1–N3의 소비자/부모 검사, N4의 P0 로그, 관련 계약·검증안이다. 현재 봉인본과 최초 정적 오류 기록을 보존하고 별도 정정본을 만든다. **현재 승인 없이 수정·검증을 실행하지 않는다.**

정정 후 새 바이트/SHA·최소 diff·검증 ID/기대 이유 표를 먼저 제출한다. 그 뒤 사용자 별도 승인으로 한정 기능 검증을 진행한다. 기존 전체 suite 재실행, COMSOL/JVM, 실측 초기화/계수 probe, 실제 OS/Job/콘솔 시험, 정책 변경, approval/runtime/token 생성, P/M/N 실행은 포함하지 않는다.

문서 작성 스킬은 결론·관측 근거·정적 추론·미실행 조건을 분리하고, 기존 파일을 고치지 않은 독립 회신으로 작성하는 데 사용했다.
