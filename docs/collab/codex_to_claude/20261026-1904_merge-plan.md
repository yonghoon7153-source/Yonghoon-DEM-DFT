## 4. SHA 결속: 유지할 역사와 새 실행의 조건

이번 표는 최신 `pqwtv8` 관측 시작점에 선택한 원본 37커밋을 반입할 때의 **참조 의미와 실제 검사 코드**를 분리한 감사다. 이전 ZIP의 target별 effective patch는 재사용하지 않았다. 새 handoff와 요청 쪽지를 읽었다. 이전 관측에서 바뀐 것은 공유 설명 2개·SE 펠릿 README·새 인계 2개뿐이며 원장/검사기/선택된 Codex 원본은 불변이다. 이 bounded delta로 아래 결속 분류를 유지한다. 실제 반입 대응 SHA는 Claude의 통합 뒤 확정한다. 아래 `branch~N`은 `이 쪽지의 동결 가지 목록` 시점의 위치이며 가지가 이동한 뒤 다시 계산하는 번호가 아니다. SHA 자리 표시는 고유 커밋 제목으로 해석할 원본 참조다. 원본 검토 이력과 새 mainboard 실행 이력을 전역 문자열 치환으로 섞지 않는다.

### findings.json — 실행 가능한 최소 병합 지시

`ledger-fragments.json` v3의 append_note_operations는 **새 finding 배열이 아닌 기존 note 추가 지시**다. ids의 각 기존 항목을 정확히 한 번 찾고 기존 note 뒤에 append_text를 덧붙인다. 기존 status와 나머지 필드는 유지한다. 11개 기존 ID 모두 대상 스냅샷에서 open임을 대조했다. ULPR 네 항목은 개별 수정 범위, MXD2-01은 후속 소비자 수정, 02–06은 생성기 수정 제안, 07은 D3 개정 설계를 구분했다. 과거 미지원 기록은 지우지 않는다.

ULPRI-01/02와 T12R-01은 실제 외부 보고서의 P2 ID이므로 **새 원장 항목으로 등재할 수 있다**. 원장에 없다는 이유만으로 발명된 ID로 취급하면 안 된다. conditional_new_records는 해당 원문·수정 증거·외부 종결 원문을 연결한 조건부 레코드다. 지금 JSON 문법은 유효하지만 claimed_fixed_sha의 placeholder가 남아 있으므로 그대로 원장에 붙이면 SHA 검사가 실패한다. 메인에 수정 커밋을 반입하고 실제 새 SHA로 치환한 뒤 claimed_fixed로 추가할 수 있다. 외부 CLOSED는 verification_note/verified_in에 별도로 보존한다. 원문의 P2 범위만 등재하며 전체 물리 GO를 붙이지 않는다.

verified 전환에는 claimed_fixed_sha, evidence_tests, verified_sha, verified_by가 필요하고 opened_in 파일이 실제 존재해야 한다. claimed_fixed_sha와 통상 verified_sha는 HEAD의 조상 커밋이어야 한다. verified_repo는 진짜 외부 저장소 검증의 예외이며 내부 cherry-pick 대응을 피하는 수단이 아니다.

**현재 스키마의 구체적인 표현 한계:** 허용 actor는 claude/codex/user뿐이며 owner == verified_by이면 verified를 거부한다. 구현 Codex와 별도 외부 Codex 검토자를 세션별로 구분할 필드가 없다. 독립 외부 검토를 했다는 이유로 verified_by를 user/claude로 허위 지정하지 않는다. 메인 Claude가 실제 독립 검증을 수행한 증거와 자기 조상 SHA를 갖춘 뒤 owner=codex, verified_by=claude로 전환하거나, 기존 스키마를 그대로 두려면 claimed_fixed + 외부 CLOSED 설명을 유지한다. 이는 외부 판정 철회나 추가 외부 재리뷰 요청이 아니다.

fix 선택자는 `codex/unloading-ulpri~1`(표지 수정), `codex/dem-gen2-t12r~1`(오프라인 수정)다. closure 선택자는 각각 codex/ulpri-closure 및 codex/t12r01-closure 동결 tip이다. 제목과 위치가 일치하는지 확인하고 메인 대응표를 작성한다. import_mapping_required는 전달 보조 정보이므로 실제 원장에는 옮기지 않아도 된다. 최종 SHA가 없는 지금 단계에 가짜 hex를 만들지 않는다.

### claims.json / doc_refs_allowlist.tsv

claims 추가 없음. 상태 인계와 실패 관찰은 새 과학 주장·경쟁 가설·등록값이 아니다.

allowlist는 추가 대신 **기존 cross_branch 두 행 삭제**가 필요하다. ledger-fragments.json의 doc_refs_allowlist_remove에 대상 경로·종류·원격 ref의 세 필드, 원문 행 SHA256(개행 제외), 반입 파일의 기대 SHA256을 담았다. 원문 행에는 Codex 원 SHA가 있어 새 쪽지에는 그대로 인용하지 않는다. 대상은 20261026-1608_nonrint-facts-query.md와 20261026-1816_nonrint-facts-reply.md다. 이전 trial의 파일 바이트 대조는 기존 증거이며 최신 target의 두 원문 행과 동결 원본 파일 해시는 이번 delta에서 다시 확인했다. 새 메인 반입 바이트 확인을 대신하지 않는다. 메인 반입 뒤 해당 경로가 존재하고 기대 해시와 일치할 때만 정확히 두 행을 삭제한다. 존재하는 파일의 cross_branch 예외는 check_doc_refs.py의 verbose 경로에서 stale 오류가 된다(350, 366–370행). 이 코드는 if verbose 안에 있어 현재 check_all.sh의 --quiet 호출은 stale 두 행만으로 실패하지 않을 수 있다. 따라서 전체 게이트 PASS를 두 행 정리의 대체 확인으로 쓰지 않는다. 반입 뒤 행·바이트 조건을 직접 확인하고 삭제하며, verbose 문서 검사로도 확인한다. 검사기 수정은 이번 반입 준비 범위 밖이다. friendly-meitner의 db/properties/sdcp_linio2_binding_phaseA.csv와 webapp/data.py 예외 두 행은 무관하므로 유지한다. 새 예외나 검사기 변경으로 통과시키지 않는다.

findings 검사기에는 알 수 없는 키 일괄 거부가 없으며 verified_in은 허용되는 메타데이터다. 전달용 import_mapping_required는 실제 finding 배열에 넣기 전에 제거한다. placeholder와 SHA/독립 actor 조건은 앞 절대로 해소해야 한다.

schema-proof.json은 관찰 대상의 파일 OID/SHA256, 기존 ID와 수를 보존한다. 스키마와 근거의 읽기/계산 결과일 뿐 새 메인 트리 게이트 통과 증거가 아니다. 실제 공유 기록은 수정하지 않았다.
