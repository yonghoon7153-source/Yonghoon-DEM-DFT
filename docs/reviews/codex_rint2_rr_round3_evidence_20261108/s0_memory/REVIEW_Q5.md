## 2. 선언된 예외 둘과 CP-ORD

**예외 ① 수용.** carbon_junction.py:1295–1318은 무리 안 대표 접점을 거리² 띠·중점·선분 i/j로 정하고, 마지막 정렬의 동률도 최근접 선분 i/j로 푼다. PTIE의 두 instance는 같은 piece 쌍·같은 Ci를 가지며 새 순서는 32개 독립 순열/여러 chunk 크기에서 모든 칸이 비트 동일했다. 옛 구현은 후보 나열에 따라 순서가 달라진다. 다만 이를 단순 출력 서식 변경이라고 부르면 안 된다. 같은 파일 :895–908의 면 배정은 동률에서 먼저 본 instance를 고르므로, 예외가 있는 입력의 하류 원장·지문 변화도 함께 이 예외의 영향 범위다. REPORT:29–30은 그 사실을 이미 공개한다.

**예외 ② 수용.** 후보용 반올림 여유를 최종 접촉 기준 완화로 읽지 않는다. :1183의 검색 반경에는 여유가 있지만 :1240–1243의 실제 판정은 그대로 d <= D다. 독립 재현: d=0.19999999999999996 µm, D=0.2 µm, 옛 중점 거리=1.3000000000000003 µm, 옛 반경=1.3 µm. 옛 query_pairs는 0쌍, 새 후보는 [(0,1)]이다. S0 M5에서도 구 접촉 0→1, 최소 거리 inf→0.5 µm를 재현했다. 이는 옛 누락을 고치는 명시된 예외이며 실제 침대의 발생 여부·효과 크기는 아직 알 수 없다.

**CP-ORD 이동 수용.** test_carbon_junction.py:2957–2990은 현재 생산 후보 함수 `_near_seg_pairs`의 실제 출력을 뒤집고 섞는다. 옛 `query_pairs`에만 주입하여 공허하게 통과하는 구조가 아니며 n_perm>0도 요구한다. 4개 합성 침대 × 두 순열의 실제 접점·분산점·포트·계·σ 비트 동일을 독립 재실행했다.

## 3. 후보 완전성과 메모리 한계

carbon_junction.py:1096–1107의 조각은 원 선분 위 구간을 덮는다. 가까운 원 선분 두 점이 놓인 조각의 중점 거리는 h_a+d+h_b 이하이므로 :1183의 2*max(h)+D 검색은 수학적으로 참 쌍의 상위집합이다. `_ball_seg_candidates`(:1110–1159)도 구 중심에서 최근접점까지 거리 + 조각 반길이의 삼각부등식을 쓴다. 최종 실제 거리는 ca_s0_census.py:536–538 및 :567–571에서 다시 검사한다. `_self_pairs`도 :1447–1454에서 같은 후보 함수를 사용하여 옛 전역 반경 호출을 남기지 않았다.

합성 7,084선분의 후보 17,701,828→61,131과 S0 2,000구의 1,294,323→1,720은 이번 상주 시험에서 다시 계산됐다. 이 숫자는 실제 침대 메모리 5 GB의 인증이 아니다. `_PAIR_ENTRY_BUDGET`은 전체 RSS 상한이 아니고, :1193–1208은 한 점의 큰 이웃 집합을 예외로 허용하며 전체 후보 key를 누적한다. `_closest_chunks`도 통과 쌍을 모으고, `_touch_len_all`은 큰 instance 하나를 쪼개지 않는다. 보고서에 이미 남긴 `_cand_pairs` 긴 꼬리 위험과 실침대 peak RSS 미측정을 유지해야 한다.

## 4. S0 계획 SHA

ca_s0_census.py:1466–1473은 새 도구 SHA를 source에 넣어 make_plan(:882–895)을 호출한다. plan_bytes_of(:832–835)는 source까지 포함해 정준 직렬화한다. 따라서 도구 SHA만 바뀌어도 계획 SHA가 바뀌는 것이 정상이다. 숫자·식 변경을 의미하지 않으며 옛 SHA로 덮어 맞추면 잘못이다.

소비자 rint_r_chain.py:1762–1777은 단계1 보고의 계획 SHA를 현재 S0 계획과 대조하고, :1789–1812는 census/registry 일곱 파일을 현재 코드와 대조한다. 독립 합성 호출에서 현재 지문은 통과, carbon_junction 지문만 다르면 CODE_PIN_MISMATCH에 해당하는 사유를 반환했다. 새 단계1 결과를 채택할 때는 새 S0 계획 해시를 다시 봉인해야 하며, 실행 핀→봉인 핀 차이·R 계획의 숫자·정책은 별도로 확인해야 한다.

## 5. kgy 채택 조건의 답

**REPORT:98의 `rc 0 + 여섯 파일 존재`는 필요한 완료 점검이며, 독립 채택의 충분조건 전체로 쓰기에는 짧다.** 새 실험 설계나 값 선정은 요구하지 않는다. 기존 §8 Q8의 조건을 그대로 붙여 다음을 확인하면 된다.

1. 새 빈 폴더·SBE 한 침대·stage1·기존 입력·σ 비열람·입력 무쓰기·실패 보존. ca_s0_census.py:1727–1742는 stage1 한 킷 및 출력 혼합 금지를 검사한다.
2. **S0 Python 자식의 최종 rc=0**이고 신호/메모리 중단이 없을 것. tools/run2.sh:15는 자식 rc를 rss.log에 적은 뒤 echo가 성공하므로 감시 셸의 `$?=0`만으로 성공을 판정하면 안 된다. 새 finding으로 확대하지 않고 요청된 채택조건의 명료화로 남긴다.
3. 같은 킷 이름의 여섯 산출물이 모두 존재하고 실제로 읽힐 것. JSON의 stage/kit/code/input, 두 NPZ의 실제 배열, 계획 정준 바이트 SHA와 .sha256 및 보고 plan.sha256, payload 로그 신원을 대조할 것. 이름이 있는 것과 완성 내용·연결이 있는 것을 구분한다.
4. 실행 환경·고정 코드 지문·새 핀, 실제 종료/신호·시간·RSS 기록을 같이 보존할 것. 5초 간격 RSS 로그의 최대는 표본 최대다. 실제 peak RSS를 주장하려면 자식 프로세스의 고수위값도 확보하거나 표본 최대라고 한정한다. 이 리뷰는 실제 kgy 자격을 인증하지 않는다.
5. 예외 둘이 실제 침대에 영향을 주는지 현재로선 미확인이라는 문구를 유지. 단계1·⑥·계획 봉인·단계2·R의 기존 순서를 바꾸지 말 것.
