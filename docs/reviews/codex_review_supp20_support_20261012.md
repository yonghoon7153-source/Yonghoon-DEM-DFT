## 1. SUP20-01 / P2 — 재검사의 배치 신원이 두 벌이며 서로 결합되지 않음

**무너지는 결론:** “check_v13도 실제로 받아들인 두 배치에 대해 같은 code_fp를 다시 강제한다.” 정상 build의 교차검사 및 이미 계산된 σ의 정확성을 반증한 것은 아니다.

위치: [lhs_release_build.py:2493](https://github.com/yonghoon7153-source/Yonghoon-DEM-DFT/blob/b429c3c1df0956d2721861d89cc29a2d56f2b581/scripts/lhs_release_build.py#L2493), 특히 **2504–2510**. 배치별 관문은 `_v13_gate_recheck_one`의 `batch_gate.batch_root`를 읽지만, 교차검사는 따로 저장한 `batches[name].root`를 읽는다. 두 경로가 같은지 검사하지 않는다. 후자가 없거나 존재하지 않는 디렉터리면 `all(isdir(...))`가 거짓이 되어 교차검사 자체가 생략된다.

### 실제 함수 반례

제출 시험의 합성 입력 생성기를 재사용해 정상 214 인계표와 서로 결합된 두 배치 증거를 만들었다. **실제 build_v13은 해시를 기록한 산출물 27개와 빌드 manifest 1개, 총 28파일을 생성**했으며 실제 check는 문제 0이다. 반환값 `n_files=27`은 manifest 작성 전 집계다. 또 다른 supp20 ROOT는 자기 감사/다시 읽기는 유효하지만 code_fp가 다르게 만들었다.

| 입력 / 조작 | 실제 결과 |
|---|---|
| 정상 194+20 build → check | 생성 성공 / 문제 0 |
| 다른 code_fp의 보충 ROOT를 정상 build에 제공 | **ReleaseError, 생성 거부** |
| 빌드 manifest의 `supp_batch`만 다른 유효 ROOT의 증거로 교체; `batches.supp20.root`는 원래 ROOT 유지 | **check 문제 0** |
| 위 교체에 더해 `batches.supp20.root`도 실제 교체 ROOT로 일치 | check 교차 문제 2개 |
| 교체 ROOT 대신 `batches.supp20.root`를 존재하지 않는 경로로 지정 | **check 문제 0** |
| 정상 묶음에서 교차 ROOT 하나만 없는 경로로 변경 | **check 문제 0** |

합성 기준 fp는 `250a59b21293b394…`, 교체 보충은 `3b0ef9f1f2245699…`다. 이는 시험용 축소 봉인 집합의 지문이며 실제 32파일의 생산 지문으로 인용하면 안 된다. 다른 모든 기록을 일관되게 바꿔야만 생기는 반례가 아니다. **빌드 manifest 안에 남아 있는 서로 모순되는 두 ROOT를 검사기가 놓친다.**

동일한 재검사 미완성으로 **`supp_batch.code_identity`를 삭제하거나 `sealed_changed=['webapp/app.py'], allowed=[]`로 바꿔도 문제 0**이다. 최상위 194 `code_identity`에는 있는 검사([2452행](https://github.com/yonghoon7153-source/Yonghoon-DEM-DFT/blob/b429c3c1df0956d2721861d89cc29a2d56f2b581/scripts/lhs_release_build.py#L2452))가 보충 쪽에 없다. 같은 “배치마다 대칭으로 재판정” 수선에 포함한다.

### 최소 수정·해결 증거

1. 배치마다 검증한 관문 ROOT를 **유일한 교차검사 입력**으로 사용한다. 중복 저장한 `batches` ROOT/expect_set/datasets/n이 있다면 그 권위 입력과 대조한다.
2. 필수 ROOT 결손·비문자열·존재하지 않음은 검사 생략이 아니라 거부다.
3. 보충에도 194와 같은 code_identity 존재·명시 승인 계약을 적용한다.
4. 위 정상/반례를 build와 check에 상주시킨다. 다른 ROOT의 개별 관문은 정상이라는 대조를 남겨 엉뚱한 외피 결손 때문에 실패한 것으로 세지 않는다.

재현: `python run_checks.py release_probe`. 세부 입력 생성과 출력은 `probes/release_probe.py`, `evidence/release_probe.json`. 합성 build에서만 τ 실제 원천 재독해를 대역으로 두었다(제출 V21과 같은 한정). **check 및 배치 관문·교차검사는 대역 없이 실행했다.** 실제 보충 g2 값이나 생산 배치를 만든 시험이 아니다.

## 2. SUP20-02 / P3 — mono_AM_S 네 행의 원천 P/S 슬롯 설명 오류

위치: [lhs_design_dataset.py:2275–2276](https://github.com/yonghoon7153-source/Yonghoon-DEM-DFT/blob/b429c3c1df0956d2721861d89cc29a2d56f2b581/scripts/lhs_design_dataset.py#L2275).

새 `lhss_w_AM_P` 설명은 이를 AM_P 질량분율이라고 부르고 `ps_frac = P/(P+S)`라 적는다. 그러나 실제 **lhss_001·002·003·020은 mono_AM_S**다. 원천 P 슬롯은 각각 0.3·0.3·0.3·0.375, S 슬롯은 0이어서 저 식은 1을 주지만, 올바르게 변환된 `ps_frac`는 모두 **0**이다.

두 타입 덱에서는 원천 P 슬롯이 **일반 AM 자리**다. 실제 어댑터는 kind로 상을 옮겨 정확히 계산한다. 오류는 수치나 배치 ID가 아니라 열 사전이다. 유사한 lhsx 설명에서 이어받은 오류이며, 이번에 새 lhss 사전에도 복사됐다.

해결: P/S 원천 슬롯의 mono 규약을 명시하고 비율 식은 bimodal에 한정한다. mono_AM_P=1, mono_AM_S=0을 적는다. CSV나 계산을 바꿀 필요는 없다. `python run_checks.py design_probe`의 `evidence/design_probe.json`으로 네 행을 대조할 수 있다.

## 3. Q1–Q4 답

### Q1 — 같은 발사 SHA를 강제할까?

**과학적 동등성에 전체 커밋 SHA 일치까지 항상 필요한 것은 아니다.** 같은 수치 봉인·기대 g2·입력 규약을 유지한 문서 전용 변경은 수치 모델을 바꾸지 않는다. 다만 **같은 code_fp만으로 실행기·인계기까지 같다고 말하면 안 된다.** 이번에도 수치 32파일은 같지만 실행기와 HANDOVER 두 파일은 바뀌었다.

이번 등록 §4는 이미 같은 발사 커밋을 선택했고 두 배치를 연달아 돌릴 계획이다. **그대로 같은 깨끗한 발사 핀을 쓰는 것을 권고한다.** 다른 SHA를 허용하려면 경고만 보고 넘어가지 말고, 실행기/인계/입력 차이와 새 도구 시험을 확인하여 발사 전 §8에 이탈 승인을 남긴다. “모든 상황에서 SHA 불일치 무조건 금지”라는 새 과학 조건은 추가하지 않는다. SUP20-01은 SHA 강제 여부와 별개로 고쳐야 한다.

### Q2 — 설계 열 정의의 원천 꼬리 제거

**현행 생성 형식에서는 동의한다.** 생성기가 붙인 ` · 원천 = <경로>`만 제외하면 정의가 같아야 한다는 뜻이다. 실제 공유 설계 열 22개를 비교했고, 경로만 바꾸면 수용, 정의 본문·source·caveat를 각각 바꾸면 거부한다. 경로 문자열까지 같게 요구하면 서로 다른 설계 CSV를 정상적으로 구별하는 표시를 오히려 금지한다.

이는 **열 정의의 동등성** 검사다. 원천의 진위나 파일 내용 검사는 아니다. 현재 `split`은 지정 구분자 뒤를 전부 버리므로 의미 본문을 그 뒤에 추가하는 새 서식을 도입하면 다시 검토해야 한다. 현행 실제 생성 정의에서 그런 반례는 없었다.

### Q3 — X_DERIVED + NA_NOT_DESIGN_INPUT

**검토 핀의 어댑터를 거치는 현재 20개에 대해서는 충분하다.** 설계 28행 중 후막 8을 제외한 20행 × 40열을 별도 SI 구 부피·질량/부피분율 계산으로 재구성하여 **800셀 불일치 0**이었다. 생성 CSV도 바이트 동일(SHA-256 `df505b79a756ee3fe2759c740bfb43282dd69035c5a9fb9354a657300117dc0c`). 10행은 2.0 mAh/cm², 10행은 빈칸이다.

이 본 열은 **면용량의 측정값이 아니라 고정 면용량 설계 규칙의 표지**다. 빈칸은 0·실패·미측정값 보간 대상이 아니며, `am_pct`와 함께 새 독립 노브로 넣지 않는다. 부피분율 설계에서 역산한 면용량은 별도 출처 열에 남기는 현재 선택과 정합적이다. 실제 20행은 70 wt% 경계에서 최소 7.5 %p 떨어져 있어 경계 근처 부동소수 허용치 차이는 이 집합에 영향을 주지 않는다.

한정: 배포의 `v13_blank_problems`는 비어 있어야 하는지만 검사한다. 임의 인계표의 fixed 행에 99를 넣으면 build/check도 통과하며 기존 lhs 행에서도 같은 일이 난다. **이번 새 어댑터가 99를 생산한다는 뜻은 아니고, 기존 신뢰 입력 경계**다. 임의 편집 인계표까지 이 규칙으로 인증하려면 유한 수치=2.0 검사나 봉인 설계와의 대조를 추가할 것. 이 관찰을 새 정상 생산 경로의 P2로 부풀리지는 않는다.

### Q4 — 214 적합 + 194 참고 줄

**동의한다.** 기존 적합 대상·두 식·고정 상수는 유지하고, 보충을 포함한 적격 관통 행으로 적합한 뒤 194만 별도로 적합해 `reference_without_supp`에 넣는다. 194 참고 줄을 추가 관측으로 중복 투입하지 않는다.

“214”는 전체 입력 행 수이지 반드시 적합 행 수가 아니다. 합성 경로에서는 전체 214 / 적합 189, 194 참고는 적합 170이었다. 실제 보충 결과의 적합 수로 인용하면 안 된다. 커밋된 옛 g1 194 자료에 대한 별도 경로 대조는 적합 170·미퍼콜 제외 24였고 direct와 wrapper 결과가 같았다. **g2 214 적합 계수의 검증은 아직 하지 않았다.**

원 194 측정 셀은 보충 결합 전후 불변이어야 하지만, 새 적합식에서의 194 예측값·잔차는 바뀔 수 있다. “요약만 달라진다”를 후자의 계산 열까지 불변이라는 뜻으로 확대하지 말 것. 독립 생성 대조에서 194 주 표·Physics 부록·각 열 사전 **8파일은 바이트 동일**했다.

## 4. Q5 — 기존 194와 남는 발사·배포 조건

### 기존 194

기본 `--cohorts=lhs,lhsx`, 정확한 194 집합/ID 지문, 관측 OFF 거부가 유지된다. 새 함수를 통한 일반화 외에 preread의 핵심 수치/상세 판정 경로는 바뀌지 않았다. **R7의 194 기술 결론을 철회할 새 근거는 발견하지 못했다.** 새 보충 버전으로 실행할 때는 새 도구 바이트의 사전 점검을 해야 한다.

### 관측 강제의 공개된 한계

등록 집합을 못 세우면 `registered_production_set`은 None을 반환한다. 정확한 20개짜리 외부 수확 경로를 넣더라도 기본 등록 폴더가 없으면 관측 필수 판정이 빠지고 후속 명령은 `--expect-case` 20개가 된다. 반대로 등록 폴더가 성립하면 OFF는 거부하고 `--expect-set supp20`을 낸다. 19·21·대체·후막 집합의 등록 조회와 상세 다시 읽기 반례도 거부했다.

이는 요청서가 공개한 정책이고 기존 194에도 있던 한계다. 이번 탐침의 preflight는 원자료 없는 합성 환경·일부 선행조건 대역을 사용했으므로 **실제 생산 발사 우회나 배포 우회를 증명한 것으로 세지 않는다.** 그러나 “preflight rc=0 하나로 보충 생산 등록까지 인증”한다는 운영은 금지해야 한다.

### 최소 순서

1. **SUP20-01 재검사 반례를 닫고 SUP20-02 문구 정정.** 수치 32파일은 바꿀 필요 없다. 수정 판의 양성·반례 결과로 짧은 재확인.
2. 같은 수확기 판의 r3 20개·union·코호트 TSV를 반입, r2와 키별 대조. 설명되지 않은 차이가 있으면 숫자를 맞춰 덮지 않고 원인 기록.
3. 등록 §2의 원자료 표 SHA·TSV SHA를 실제 파일에서 계산하여 채우고 저자 비준. 실행기가 **등록 supp20을 성공적으로 반환**하며 ID 지문이 등록과 같은지 확인.
4. 고정 발사 핀에서 fast16+real4 및 등록된 점검을 완료. 같은 깨끗한 핀, 새 ROOT 둘, 각각 관측 ON, 기대 g2, 수치·인계 도구 지문, raw/TSV 지문 대조. 일반 계획으로 강등된 `--expect-case`만을 supp20 등록 증거로 사용하지 않는다.
5. **저자의 별도 발사 승인** 후 194 → 보충 20. 이 리뷰는 실행 명령이나 승인을 대신하지 않는다.
6. 완료 뒤 배치마다 정확한 최종 집합, SEALED, 완료 시도별 import 결합, audit, 각각 `--expect-set production194`/`supp20` 상세 판정. 그 뒤 실물 생산→게시→인계와 고친 build/check의 두 ROOT 결합을 확인한다.

최소 목록에서 새로 빠진 것은 “**build와 check가 같은 권위 ROOT를 사용한다는 일치 검사**”다. 단순히 두 곳에서 같은 이름의 함수를 부르는 것으로 충분하지 않다. 이번 결함은 배포 도구 층이므로 향후 계산이 이미 완료돼도 이 결함만으로 214를 재계산할 이유는 없다.

## 5. Q6 — 빈 등록을 채우면 재검토 없이 발사 가능한가?

**현재 핀에서는 아니다.** 새 P2가 남고 r3 실물이 없어서 아직 발사 입력을 인증할 수 없다. 최소 수선 뒤에는 설계를 다시 심사할 필요 없이 **수정 diff + 채운 입력 봉인/사전 점검 영수증의 짧은 확인**으로 충분하다.

특히 `registered_id_set('supp20')`은 ID 집합 지문을 검사한다. **등록 문서에 채운 raw SHA 표·코호트 TSV 값까지 자동 비교하는 함수는 아니다.** 탐침에서 raw SHA와 TSV 바이트를 바꾸면 실제 입력 지문은 달라지지만 같은 20 ID의 등록 판정은 유지됐다. 따라서 다음을 한 영수증에 대조해야 한다.

- 정확한 supp20 ID 지문 `991cf1150b183f64bc69926a8b3e7c05453ec47e13b89ba3a6ad2fd2c981c694`.
- 등록 §2의 raw-table/TSV 값 = 반입 파일에서 재계산한 값 = 실제 발사 dry-run이 낸 값.
- r3 수확기 판·설계 CSV/어댑터·union·원 덤프/메시 같은 프레임 계약, r2 차이표.
- 실행기·수치·인계 도구 핀, 관측 ON, 새 ROOT 둘, 사전 점검 결과와 저자 발사 승인.

입력만 기계적으로 채웠고 이 대조가 전부 같다면 새 모델 리뷰는 불필요하다. 입력이나 규약·도구가 달라졌거나 설명되지 않은 값 차이가 나오면 그 차이만 다시 본다. **아직 없는 데이터를 앞으로 잘 채울 것이라는 약속은 현재의 GO 근거가 아니다.**

등록 §4의 fetch 예시는 옛 `claude/sdcp-dem-manuscript-si-pqwtv8`를 가리킨다. 실제 발사 전 현 브랜치 `claude/stoic-knuth-NObVQ`와 최종 핀으로 명령도 맞출 것. 이는 현재 계산값의 결함으로 별도 등급을 매기지는 않았다.
