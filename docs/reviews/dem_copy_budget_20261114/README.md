# DEM — 합성 사본 관측과 예약량 계산 연결

## 1. 결과와 범위

바탕 ebe810d87f23f6bd06a95cc6fcda04abc0eedfad의 `docs/reviews/dem_trial_isolation_20261114/` 모델을 변경하지 않고 복사 호출을 관측했다. 최종 **11메서드 실패0·오류0**, 예약량 명부를 약화한 **3변형 검출**이다. 기존 물리 solver import·실행0, 실제 메모리 측정0, 연구 결과0, 전체 HOLD.

소스 신원은 관측기 안의 SHA256으로 확인한다. 대상은 기존 합성 모델·그 안의 작은 seed·기존 메모리 수명 계산기 세 파일뿐이다. 실제 덱·dump·저장본·장비 자원을 입력받지 않는다. 기준 모델의 생산 코드 반입이나 Rint/믹서/LHS 실행 GO가 아니다.

## 2. 무엇을 관측했나

| 위치 | 같은 순간의 서로 다른 최상위 상태 객체 | 관측 |
|---|---:|---|
| 첫 복사 완료 | 2 | 보관 상태가 복사 원본이며 새 trial이 따로 있음 |
| 둘째 복사 완료, 반영 전 | 3 | 보관 부모·trial·반환 사본이 서로 다름. 부모는 아직 보관 상태 |
| 성공 반환 | 2개의 역할 확인 | trial이 새 보관 상태이고 반환 사본은 별개 |
| 지정한 실패 위치 | 복사1회 | 반환 사본 생성 전 실패, 보관 부모의 내용 그대로 |

`deepcopy` 관측은 attempt 호출 구간에만 설치하고 finally에서 원 함수를 복구한다. 기록에는 객체 주소를 싣지 않는다. 관측기가 객체를 목록에 붙잡아 수명을 늘리지 않도록 ID 비교 결과만 남긴다. 같은 시점의 살아 있는 객체 비교에만 ID를 사용하며, 끝난 시도 간 ID 재사용을 입자 신원으로 해석하지 않는다.

이 수는 **최상위 Python 상태 객체 수**다. 내부 immutable 정수의 공유·객체 헤더·allocator·입력 fixture·JSON·호출자가 보유한 snapshot까지 포함한 전체 메모리 peak가 아니다. 소멸/GC 또는 실제 배열의 할당·해제를 확인하지도 않았다. 기존 합성 모델은 단일 소유자·동기 조건이며 관측기도 동시 호출·파일 동시 변경 자격을 주장하지 않는다.

기본/rod 성공2행과 등록된 rod 실패11위치를 `observations.json`에 보존했다. 13행은 13개 추가 고유 시험이 아니며 11메서드 내부 대조와 겹친다. 실패한 시도의 낮은 사용량으로 성공에 필요한 예약량을 줄이지 않는다.

## 3. 명부 누락이 만드는 차이

관측한 세 역할을 별도 배열 예약으로 구현한다는 **가정** 아래 `declared_plan`이 old·trial·returned의 겹침을 선언하고, 기존 `memory_liveness.account`에 넘긴다. 사건 번호와 해제 시점은 계획 입력이다. 실제 구현의 완료 장벽·할당/해제 관측을 대신하지 않는다.

| 합성 계획 | 사본당 선언 예약 | 한도 | 계산 peak | 한도 판정 |
|---|---:|---:|---:|---|
| old + trial + returned | 6 B | 17 B | 18 B | 1 B 초과 |
| 반환 사본 누락(의도한 불완전 명부) | 6 B | 17 B | 12 B | 겉으로는 한도 안 |
| 기존 별도 snapshot 1개도 유지 | 6 B | 23 B | 24 B | 1 B 초과 |

6 B는 손 계산 표지이며 실제 상태 크기가 아니다. 사본을 view로 구현한다면 소유·수명·가변성 근거를 따로 제시해야 하며, 여기의 독립 사본을 근거 없이 view로 바꾸지 않는다. 실제 host/device 분류·정렬/통신/직렬화·runtime 여유는 아직 미정이다. 계산기가 빠진 항목을 스스로 찾아 주지는 않으므로 명부 완전성 근거가 필수다.
