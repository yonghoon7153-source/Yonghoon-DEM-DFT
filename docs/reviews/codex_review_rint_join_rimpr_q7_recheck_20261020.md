### Q4 — 연기의 의미

`RIMPR-03`은 `\d`가 전각 정수를 허용하는 형식 제한 문제다. 원자 ID·type·step·count·접촉 ID·scaffold type을 전각으로 바꾼 합성 입력은 PASS/정량 ACCEPT였으며, 숫자로 읽은 입자·ID는 ASCII 기준과 같았다. ASCII 생산 덤프 지원이라는 범위를 명시하고 원장을 open으로 유지한다면 별도 보강으로 미룰 수 있다.

`RIMPR-04`는 입력의 유한성과 **계산 결과의 유한성**이 다르다는 문제다. 좌표가 약 `1e160`인 한-AM 합성 자료에서 `:767`의 제곱합이 넘치면 `delta_bound_um=inf`가 된다. `am_iface_ledger`의 `step3_sigma.py:1201–1202`는 이 **파생된 무한 반올림 폭**을 그대로 전달받으면 거부한다. 그러나 **모든 산술 넘침을 후단이 막는 것은 아니다.**

그 경계를 구분하는 추가 반례도 재현했다. 정상 AM 두 구·scaffold는 그대로 두고 SE 두 구를 x=`1e160`, `2e160` sim, 각각 r=`0.001` sim으로 추가했다. 같은 직교 상자를 `0 … 3e160` sim으로 잡아 네 입자가 모두 상자 안에 있도록 했다. 두 SE가 닿을 수 없는데도 접촉 행에 δ=`0.0005` sim을 적었다.

| 실제 함수 결과 | x 규모 `1e150` 대조 | x 규모 `1e160` 반례 |
|---|---:|---:|
| 안정한 `hypot`으로 센 실제 거리 [sim] | `1e150` | `1e160` |
| 안정한 계산의 허용오차 [sim] | `1.0000000001776356e145` | `1.0000000001776357e155` |
| 현 코드의 거리·허용폭 norm | 유한·유한 | `inf`·`inf` |
| `n_delta_pos_mismatch` | 1 | **0** |
| `max_delta_pos_ratio` | 99,999.99998223643 | **NaN** |
| 조인 / 정량 관문 | REJECT / ValueError | **PASS / ACCEPT** |

`rint_iface_join.py:641–645`의 `dd > wd`가 `inf > inf`가 되어 거짓으로 평가되는 것이 원인이다. 여기서는 AM의 `delta_bound_um`이 정상값 `2.732324012649634e−05 µm`이므로 후단의 무한 폭 검사가 발화하지 않는다. 옛 핀에서도 같은 결과였다.

이것은 **기존 RIMPR-04의 영향 범위 보강**이지 새 회귀나 새 ID가 아니다. 전역 G-frame 인증의 false-PASS이지만 비현실적으로 큰 입력이고 정상 AM 입자·AM 계획은 그대로라, 이번 반례만으로 생산 σ 오염이나 P2 승격을 주장하지 않는다. 다만 “후단이 반드시 거부하므로 무해”라는 설명은 철회해야 한다.

다음 조건을 지키면 지금의 진단·개발 묶음에서 연기하는 데 동의한다.

1. 두 항목을 verified/closed로 바꾸지 않음.
2. “유한한 입력이면 모든 기하 계산이 안전하다”는 주장 금지.
3. 조인만 단독 신뢰해 새 정량 소비자로 연결하지 않음. 현행 원장·정량 관문을 유지하되 그것이 비-AM 거리 넘침까지 전부 막는다고 주장하지 않음.
4. 정량 채택 전에 결과 유한성 및 수치적으로 안정한 거리·오차폭 계산을 검토함. 데이터 범위를 제한한다면 사후 관찰이 아니라 명시적 입력 계약으로 둠.

헤더 P3도 같은 의미의 후속 보강으로 분리할 수 있다. 이것이 이번 두 최소 해결의 닫힘을 취소하지는 않지만, **조인 형식 검증 전체가 완결됐다는 선언은 아직 불가**하다.

| CNC 등록 r=0 = OFF | 0 / 0 | 0.004141925781633665 |
| CNC 양의 r_face 두 배 | 152 / 0 | 0.0035313954366456347 |
| RRM 정상 | 67 / 85 | 0.003334457143882423 |
| RRM 등록 r=0 | 67 / 85 | 0.0037299595666211234 |
| RRM 양의 r_face 두 배 | 67 / 85 | 0.0030984308118989293 |

각각 자유도 8,527, 잔차 약 `6.2–6.6e−15`. 위 여섯 경우의 **전체 반환 객체와 배열 바이트는 옛/새 코드에서 동일**했다. 직접해법은 같은 조립을 정밀 비교하려고 쓴 시험용 callback이며 생산 CG 실행인 것처럼 표시하지 않는다. 별도로 원래 CPU CG를 사용한 OFF·CNC 정상·RRM 정상·RRM 0의 네 비교도 전체 반환값이 같고 수렴했다(잔차 약 `8.6–9.2e−9`).

iface OFF에 대해서는 격자 간격·입자 순서·bridge·기존 r1 활성 여부를 바꾼 16건의 raster와 전체 반환값이 옛/새 코드에서 같았다. 무한한 모든 입력에 대한 비트 동일성 증명은 아니다.

양의 r_face 두 배는 **일반 값 관문**을 통과한다는 대조다. RRM의 등록과도 맞는다는 뜻은 아니며, 신뢰한 원장을 사용하는 `rrm_check`는 변경된 RRM 계획을 `rface_mismatch` 등으로 거부한다.

## 6. N9b를 둘로 나눈 기록은 타당함

### (a) 옛 NaN 우회의 크기를 등록 r=0으로 기록

옛 모듈에서 RRM 막 67행을 NaN으로 바꾼 계획과 등록된 r=0 계획은 CSR 행렬·우변까지 같다. 따라서 다음 동일성이 실제로 성립했다.

- σ_eff: `0.0037299595666211234 S/cm`, hex `0x1.e8e4acb544bd1p-9`
- 자유도: 8,527
- 잔차: `6.2089744354216986e−15`
- φ 배열: 형상 `20×20×39`, float64, 바이트 동일
- φ SHA256: `c62f28305cd8a7428cfe578908690d91f4b66d006c8a18c8ebf2d3077c03014f`

이는 현재 NaN도 통과한다는 주장이 아니고, 두 계획의 모든 메타데이터가 같다는 주장도 아니다. **옛 잘못된 조립의 크기를 현재 유효한 0 계획으로 남긴 것**은 타당하다.

### (b) 유한한 cut 삭제는 여전히 원장 검사 책임

절단 85행을 지운 계획은 남은 r_face가 유한·비음수이므로 일반 값 관문을 통과하고, 일반 솔버에서 `0.0040840140889134725 S/cm`를 낸다. 그러나 실제 RRM wrapper는 CG 전에 거부한다.

특히 resolve_k를 그대로 4로 두고 절단만 지운 경우, planner 재생성 검사를 시험에서 비활성화해도 독립 원장 대조가 `film_off_outside(n=85)`를 낸다. 따라서 수정본을 자기 자신과만 대조해서 우연히 막힌 것은 아니다.

Q7에는 누락된 행을 복원하거나 원장 완전성을 증명하는 역할이 없다. RRM 경로를 일반 솔버 직접 호출로 교체해도 된다는 결론은 나오지 않는다.

## 7. “봉인 32 무변경”의 정확한 범위

**두 Rint 수정 커밋 자체**(`3b9d51789`, `2b9efa253`)가 봉인 목록 32개를 건드리지 않았다는 것은 맞다. `step3_sigma.py`의 두 핀 사이 수치 코드 변경도 Q7 관문 한 곳뿐이다. S3 `NUMERIC_MODULES` 여섯 개는 두 핀 사이 모두 동일하다.

그러나 **대조 핀 dcb97 → 검토 핀 2b9 전체 구간**에서 32개가 전부 같은 것은 아니다. 실제 Git blob 비교에서는 다음 네 개가 다르다.

- `scripts/network_conductivity.py`
- `scripts/tau_flux.py`
- `webapp/app.py`
- `webapp/pipeline_service.py`

그 사이 다른 작업의 변경을 이번 Rint 패치의 변경으로 돌리지 않는다. 반대로 두 Rint 커밋이 봉인 밖이라는 사실을 **두 전체 스냅샷의 봉인 지문이 같다**는 주장으로 확대해도 안 된다. 권장 문장:

> 이번 Rint 수정 두 커밋은 봉인 32개를 변경하지 않았다. 대조 핀 이후의 다른 트랙 변경까지 포함한 전체 스냅샷의 동일성은 별도다.

이번 검토가 새 봉인이나 이전 봉인의 재사용을 승인한 것은 아니다.
