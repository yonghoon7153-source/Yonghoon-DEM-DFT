## 새 문구 문제: 정상 trial/main의 deck 신원을 같다고 요구함 (P2)

위치: `docs/50kg/codex_kg50_d07_compress_resume_request_20261103.md:54`.

요청은 `본 job LMP_IDENTITY 세 칸 (lmp · 덱 · 체크포인트) = -T 신원과 같음`을 요구한다. 하지만 `-T` job의 덱은 `input_kg50_d07_b50_r56t.liggghts`, 본 job의 덱은 `input_kg50_d07_b50_r56.liggghts`다. 전자는 run 2 → 판정 → run 1998로 자른 시험, 후자는 압축 루프와 이완을 포함한 본 덱이다. 정상 동작부터 경로와 바이트가 다르다.

근거:

- `scripts/resume_ckpt.sh:2140–2155`: `trial`에 따라 `시험 덱`/`재개 덱`과 각 SHA를 골라 다른 신원 출력·해시 관문·`-in`을 만든다.

재현: `probe_identity_mapping.py`가 원본의 `runnerck.render` 함수 AST만 추출했다. 합성 덱 두 개의 실제 SHA-256을 넘겨 도구의 실제 render 출력 두 개를 저장했다. 러너는 실행하지 않았다.

| 본 job | 1 | `322aeec7870695760c160bacef5c87ef3f55c6ae7b91e8721399eab1354fb5b1` |

최소 해결은 코드 일반 고침이 아니라 §4-2의 비교 대상 명시다:

1. 승인된 `-T` 시도와 새 본 호출 시도의 receipt **1행끼리**, **5행끼리** 경로와 SHA가 같다.
2. 각 시험 job의 `LMP_IDENTITY.deck` 경로/SHA는 그 시도의 receipt **3행**과 같다. 자동 G0도 이를 확인한다.
3. 본 job의 `LMP_IDENTITY.deck` 경로/SHA는 승인된 receipt **1행**과 같다. 시험 identity의 deck과 같을 것을 요구하지 않는다.
4. 본 job의 `checkpoint` 경로/SHA는 승인된 receipt **5행**, 실제 시험 job의 checkpoint와 같다. `lmp_mpi` 경로/SHA는 승인된 실제 시험 job과 같다. shell PATH에서 찍힌 `tool.txt` lmp 값만을 실제 잡 신원으로 대신하지 않는다.

이 지적은 기존 PAI 일반 결함을 새로 선언한 것이 아니다. 이번 한 건 요청서가 새로 적은 수동 대조 규칙의 타입 불일치다. 문자 그대로 따르면 안전 쪽의 불필요한 취소가 생긴다. 이를 느슨하게 무시하지 말고 위 대응으로 고쳐야 한다.

## 수동 확인은 시점·미출력·늦은 main도 포함해야 함

11-01 판정문 `:187–188`은 승인 receipt를 **제출 전/시험 중** 대조하고, 불일치 **또는 확인 지연**이면 **시험과 같은 시도의 main 유무/최종 종료**를 확인하며, 신원/결과가 없을 때도 별도 읽기 전용 상태 확인을 요구했다. 새 요청서 `:54–55`는 이를 `다르면 본 job scancel ...`로 줄여 적었다.

현재 도구 `:2340`, `:2441–2463`은 새 시험 종료 후 사람이 확인했다는 별도 관문 없이 자동 main을 제출한다. 따라서 새 호출 receipt 1/5행 대조는 시험이 진행 중일 때 끝내는 것으로 적어야 한다. 늦거나 불일치할 때는 시험 상태와 같은 시도의 `main_job.txt`/큐를 확인하여 실제 제출된 두 job의 종료를 확인한다. main 신원이 없거나 job 시작 전 종료된 경우에도 `sacct/squeue`로 끝 상태를 확인한다. `scancel` 호출 성공, guard 종료, 신원 줄이 안 나온다는 사실은 차단 완료가 아니다.

이는 11-01 KG50Y4D2-04/05의 수동 보완을 보존하는 조건이다. 새 일반 P1이나 지킴이 v3 구현 요구가 아니다.

## Q4의 좁은 조건과 예외

실제 v3 덱 `:125,167,174,213,222–231` 및 순수 Python 산술은 루프 진입 E=1+200000+1+200000=400002, N=5000, restart 간격=200000을 확인한다. 따라서 S0가 이 간격의 배수이면 `(S0-E) mod 5000=4998`, r=2다. 1000000, 1200000, 1400000, 2000000 표본을 계산해 같은 결과를 얻었다. 이것은 **스케줄의 산술**이지 미래 checkpoint의 파일 유효성·상태·원 로그 존재를 보증하지 않는다.

후속 허용 범위의 최소 조건:

1. 같은 케이스, 원 덱/물리/NP56/r56/`-t 2000`/도구·헬퍼 고정. 사람의 재개이며 자동 재제출 없음. source job의 종료를 확인한 뒤 폴더와 로그·덱·receipt를 보존하고 원 run335457도 보존한다.
2. 선택한 새 checkpoint의 S0/경로/SHA와 그 파일을 쓴 source job·실제 덱·로그를 기록한다. 새 `-T`에서 G0–G3를 다시 확인한다. source의 S0+2가 CPU>0 run-end이며 해당 덱의 압력 판정 자리라는 근거를 보존한다.
3. **그 checkpoint를 승인한 새 -T**와 이후 main 호출 사이에서 위의 receipt/identity 대응을 다시 적용한다. 처음 337078과 새 checkpoint의 5행이 다르다는 것은 당연하다. 이전 checkpoint의 승인값을 새 checkpoint 승인값으로 읽지 않는다.
4. 다음 판정에서 이미 목표에 닿아 시험이 quit/G0 실패하면 현재 경로에서는 본 제출 없음(`resume_ckpt.sh:1740–1779`, 절차 `:486,500`). `-t<=2`로 줄여 통과시키는 변경은 이번 범위에서 자동 허용하지 않는다. 그때 짧은 재확인이 필요하다.
5. TIMEOUT이 checkpoint 직후라 S0+2 원 로그 증거가 없거나, 덤프가 빠지거나, 원 job과의 연결을 못 하면 같은 조건을 충족했다고 하지 않는다. relaxation TIMEOUT도 checkpoint가 없으므로 마지막 압축 checkpoint로 되돌아가는 새 시험이며, 이완 상태를 이어받는다고 표현하지 않는다.

`§3-1 꼴`을 이후 모든 경우에 문자 그대로 `Loop ... for 5000 steps`로 해석하면, 새 checkpoint 없이 같은 S0를 다시 쓰는 첫 2-step 재개 run에서는 불필요하게 거부된다. 새로 더 늦은 checkpoint(예: 1200000)에서는 정상 원 루프의 5000-step 끝이 기준이다. 같은 S0의 재재개는 source의 실제 첫 run이 2였다는 기록과 판정 맥락으로 따로 설명하거나 짧은 확인으로 넘기면 된다. 무조건 5000이라는 문자열 하나로 미래 source의 의미를 대체하지 않는다.
