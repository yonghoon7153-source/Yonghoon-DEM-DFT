## 3. 새 지적

### KG50Q3B-01 · P2 — 영수증 첫 비교가 본 제출 뒤로 밀렸다

**위치:** 요청서 **78–88행**, `scripts/resume_ckpt.sh:2324`, `:2340`, `:2454`, `:2461`, `:2478`. 이전 판정 `codex_review_kg50_y4_draft2_20261101.md:187`의 조건과 대조했다.

요청서 78행은 “✅ 본 제출 job 줄이 나온 뒤”에 새 영수증과 승인된 `cff47c44…`를 처음 비교하도록 한다. 그런데 도구는 다음 순서다.

1. 새 영수증을 쓰고 그 SHA를 이번 호출의 `MIS`로 기억한다.
2. 시험을 제출한다.
3. G0–G3가 통과하면 현재 파일이 **이번 호출의 영수증**과 같은지 검사한다.
4. 본 job을 제출한다.
5. 제출 결과를 보고서에 쓰고 stdout로 보여 준다.

3번은 **이번 호출 내부 불변성** 검사다. 승인한 이전 `-T`의 `cff47c44…`와의 대조가 아니다. 새 호출의 입력이 승인 자료와 다르지만 정적 대조·시험을 통과하는 경우, 서로 다른 새 영수증이 내부 검사에는 통과한다. 요청서대로 기다리면 본 job 제출 뒤에야 차이를 발견한다. 본 job은 이미 RUNNING일 수도 있다.

**무너지는 결론:** “11-01의 사전 수동 대조 조건을 그대로 유지했다.” 실제 도구가 잘못된 덱을 썼다는 관측은 아니며, 일반 도구 전면 수정 요구도 아니다.

**최소 해결:** §4-6의 확인 순서를 바꾼다. 승인 영수증은 **새 시험이 끝나기 전에** 대조한다. 본 신원은 본 job 시작 후에 확인하되, 그때까지 영수증 비교를 미루지 않는다. 확인 지연·결손도 불일치와 같은 중단·상태 확인 대상으로 한다. 본문 §6에 대체 조건을 적었다.

**재현:** `python -I -X utf8 -B operations_review/probe_final_schedule.py`. 이는 실제 소스의 영수증·제출 순서와 호출 내부 hash 검사의 논리 모델만 실행한다. scheduler를 부르지 않는다. 기존 11-01 수동 조건의 후퇴를 이번 요청서에서 구체적으로 지적한 것이다.

### KG50Q3B-02 · P3 — 600,000 step은 “판이 표면에 처음 닿는 시점”의 증명이 아니다

**위치:** 요청서 **58행**, 본 덱 `docs/data/kg50_decks_20261027_v3_b50/kg50_d07_b50/input_kg50_d07_b50.liggghts:175`, `:176`, `:178`.

덱의 `z_max`는 입자 **중심 z의 최대값**이다. 판은
`z_max + r_AM_P + plate_margin`에 놓인다. 따라서
`0.142972 − 0.136972 = 0.006 m`는 중심 기준 거리이며, 입자 표면까지의 간극이 아니다. 반경 0.003 m를 갖는 입자가 중심 최고점에 있다면 처음 설정한 표면 간극은 0.003 m다. 작은 입자가 최고점이면 다른 반경·높이 조합을 계산해야 한다. 이후 200,000-step 안정화의 구조 변화도 있다.

`0.006 / (0.01 × 1e−6) = 600000`이라는 산술은 맞지만 접촉 개시의 증거가 아니다. 압력이 목표의 **0.03999278%**라는 것도 낮은 판 반력을 뜻할 뿐, 첫 접촉 시각을 유일하게 정하지 않는다.

**최소 해결 문안:** “해당 시점 판 압력은 목표의 약 0.04%다. 초기 중심 기준 판 거리로 계산한 600,000 step은 참고 기하이며 실제 표면 접촉 개시 시점은 미측정이다.”

**영향:** 남은 시간의 설명·보고 문구만 고친다. Q3(나)의 2-step 산술이나 한 건 재개를 막는 결함은 아니다. D2 끝 step을 그대로 대입하면 남은 3,485,002 step, 20,000 step/h 가정에서 **174.2501 h**다. D0.7의 완주 시각·TIMEOUT 횟수를 측정한 값이 아니므로 “가능성”·“추정” 한정은 유지한다.

## 4. 독립 검산과 실제 시험 기록

### 4-1. 제어 흐름

본 덱 run 합은 `1 + 200000 + 1 + 200000 = 400002`다.

```text
E = 400002, N = 5000, S0 = 1000000
p = (S0-E) mod N = 4998
r = N-p = 2
판정: 1000002 → 1005002 → 1010002 → …
```

`loop_phase`(:1179), `q3b_fix`(:1655), `cut_trial_q3b`(:1739)의 실제 Python 부분을 추출해서 호출했다. 시험의 helper 입력만 명시적인 합성 `qb_raw(order='r075')`다. LIGGGHTS 실행을 흉내 낸 입자 계산은 없다.

- 첫 판정에서 목표 미만이면 원래 5,000-step 루프로 진입한다.
- 목표와 같거나 높으면 그 루프를 건너뛰고 원래 이완 전이로 간다.
- `-t 2000`은 `run 2 → 원 조건 판정 → run 1998`이다.
- 첫 판정에서 목표에 닿으면 시험이 종료되어 기대 끝 1,002,000을 못 채우므로 G0 승격이 막힌다.
- 5,000개 위상 잔여 전수, 시험 예산 10개, 구조 변이 12종을 포함한 **40/40** 독립 검사 통과. 위상 0·지원하지 않는 일정은 거부했다.
- 이 합성 제어 흐름의 0.30은 코드 압력 입력이며, 본 덱의 실물 환산 목표는 **300 MPa**다.

고정 LIGGGHTS-PUBLIC `3d5c00f20519e6bb6eb6756f51f1ad36564e649d`의 구현을 대조했다. [Modify::add_fix](https://github.com/CFDEMproject/LIGGGHTS-PUBLIC/blob/3d5c00f20519e6bb6eb6756f51f1ad36564e649d/src/modify.cpp#L784)는 같은 ID/style의 재정의를 기존 칸에 넣고, unfix 후 새 fix는 뒤에 붙인다. Restart 상태는 ID/style로 연결하며 칸 번호만으로 연결하지 않는다.

명시된 동적 fix의 칸을 투영하면 다음과 같다.

```text
본 덱:    zwall_bot, integr, gravi, top_mesh, zwall_top, damp, move_press
5b 결과:  zwall_bot, integr, top_mesh, zwall_top, gravi, damp, move_press
```

남은 차이는 중력과 상판 벽의 상대 순서다. 이 덱의 중력·점성력·접촉력은 같은 순간 상태에서 가산형이고, 선형 판 이동은 힘 피드백 제어가 아니다. integrator·mesh·move_press의 상호 순서는 유지된다. 이 한 건에서 새로운 비가환 물리 연산 반례는 찾지 못했다.

다만 사전 공격문의 “f를 읽는 fix 없음”은 너무 강하다. [벽 구현](https://github.com/CFDEMproject/LIGGGHTS-PUBLIC/blob/3d5c00f20519e6bb6eb6756f51f1ad36564e649d/src/fix_wall_gran_base.h#L202)은 접촉 전 힘을 보관하고 뒤에서 새 힘−옛 힘으로 mesh 반력을 추출한다. 정확 산술에서는 같은 접촉 증가량이지만, 부동소수 합산·뺄셈의 반올림은 판 반력에도 영향을 줄 수 있다.

따라서 **“같은 순간 상태의 힘 법칙을 유지하며 수치 재시작 차이는 허용 비교로 확인”**이라고 쓴다. “장시간 궤적도 roundoff 크기로만 다름”, “모든 차이의 원인이 fix 순서임”, “미래 목표 도달 주기 동일”을 뜻하지 않는다. 이번 G3의 작은 차이도 원인별 분해가 아니다.

## 6. 적용할 수동 조건 — 새 지킴이 없이

요청서 §4-6을 다음 순서로 읽어야 조건부 GO가 성립한다.

1. **호출 전:** source run335457 및 승인된 시험 시도를 보존한다. source checkpoint와 도구/헬퍼 승인값, NP56/r56/-t2000, 중복 호출 없음, 담당자가 새 시험을 지켜볼 수 있음을 확인한다.
2. **새 시험 중·본 제출 전:** 이번 호출의 정확한 attempt를 특정하고 `main_inputs.sha256` 전체 SHA를 아래 승인값과 대조한다. 같은 호출 내부 검사 통과를 이 비교의 대체물로 쓰지 않는다. 로그의 “본 제출 job”을 기다렸다가 처음 비교하지 않는다.
3. **시험 신원:** 새 시험의 덱은 영수증 **3행**, checkpoint는 **5행**, lmp는 승인한 바이너리 신원과 대조한다. G0–G3가 새로 통과해야 한다.
4. **본 job 시작 후:** 본 덱은 영수증 **1행**, checkpoint는 **5행**, lmp는 승인값과 대조한다. 시험 덱의 SHA와 본 덱 SHA를 같다고 요구하지 않는다. 빈 출력·잘린 출력·다중 신원은 일치로 처리하지 않는다.
5. **불일치·확인 지연·결손:** 해당 시도의 시험 상태와 본 제출 여부를 함께 확인한다. 이미 제출됐거나 뒤늦게 나타난 본 job도 포함하여 중단 대상 job의 최종 종료를 확인한다. 취소 명령 실행, 로그에 아직 없음, 지킴이 종료 중 어느 것도 종료 증거가 아니다. 11-01 §6-2/3의 수동 책임을 그대로 유지한다.
6. **그 뒤:** 읽기 전용 감시와 결과 보존. 끝 압력·낙폭·R5_abs/signed drag 정의 구분, 결과 반입 전 재고·다중 프레임·소비 경계 조건은 유지한다.

## 7. TIMEOUT 뒤의 조건부 범위

`200000 = 40 × 5000`이므로 같은 E=400002의 더 늦은 200,000-step 배수 checkpoint에서도 잔여는 2다. 그러나 이 산술은 실제 파일의 유효성·원 로그·runtime 상태를 대신하지 않는다.

후속을 같은 절차 범위에 넣으려면 매번:

- source job 종료와 폴더/로그/덱 보존, 새 checkpoint의 step·경로·SHA를 고정한다.
- 같은 모델·규약·도구·헬퍼·NP56·-t2000으로 **새 -T**를 수행한다.
- 해당 source의 실제 다음 압력 판정 자리 S0+2를 원 로그·덱 맥락으로 확인한다.
- 그 새 시험의 승인 영수증을 기준으로 §6의 비교를 다시 한다. **cff47c44…·164824ea…는 이번 checkpoint 값**이므로 다음 checkpoint에 그대로 요구하지 않는다.
- 새 비교 실패를 문턱 완화나 -t 축소로 우회하지 않는다.

다음은 짧은 재확인 대상이다.

1. TIMEOUT이 S0 또는 S0+1에 발생하여 필요한 S0+2 원 로그가 없는 경우.
2. 첫 잔여 판정에서 목표에 닿아 -t2000 시험이 조기 quit/G0 실패한 경우. -t≤2로 줄여 통과시키는 것은 이번 승인에 포함하지 않는다.
3. 더 늦은 checkpoint가 없어 같은 S0를 다시 쓰는 경우. 직전 재개 source의 첫 판정은 **Loop for 2 steps**일 수 있다. “항상 Loop for 5000”이라는 문자열만으로 판단하지 않는다.
4. 물리 덱·fix 종류·이동/정지 규약·NP·실행 신원·도구가 바뀌거나, source/receipt 연결·원자료를 잃은 경우.

이완 TIMEOUT은 이완 상태를 이어받는 것이 아니다. 마지막 압축 checkpoint에서 압축 말기와 이완을 다시 수행하는 새 시도다. 미래 완주나 정해진 TIMEOUT 횟수를 승인한 것은 아니다.
