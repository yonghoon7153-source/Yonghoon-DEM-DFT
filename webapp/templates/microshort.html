마이크로 쇼츠 — 어디까지 왔고 무엇이 막혀 있나

전지 안에서 두 전극이 아주 약하게 이어져 조금씩 전류가 새는 현상을 마이크로 쇼츠라 한다. 이 갈래는 그것을 계산으로 재현해 언제 어떻게 드러나는지 보려는 것이다. 지금 상태는 한 줄로 이렇다 — 모델의 격자는 아홉 축까지 우리가 다시 세어 확인했고, 그 다음 단계인 “결과를 꺼내는 일”이 막혀 있다. 본 실행은 시작하지 않았다.

0 용어 — 이것만 알면 아래를 읽을 수 있다

아래 본문은 전문 용어를 그대로 쓴다. 절마다 “쉬운 말로” 칸을 달아 같은 내용을 다시 적었다. 먼저 용어 열 개만 정의한다.

마이크로 쇼츠 (micro-short)
두 전극을 갈라 놓는 막(분리막)을 통해 전자가 조금씩 새는 상태. 전지가 스스로 조금씩 방전된다. 완전히 끊어진 것도 완전히 붙은 것도 아닌 중간이다.
COMSOL
편미분방정식을 수치로 푸는 상용 해석 프로그램. 이 갈래의 모델은 COMSOL 6.3 에서 돈다.
MPH 파일
COMSOL 의 모델 파일. 형상·물성·설정·계산된 해가 한 파일에 들어 있다.
메시 (mesh) · 요소
공간을 잘게 나눈 격자. 잘게 나눌수록 정확해지지만 계산이 오래 걸린다. 물리축은 전지 두께 방향의 분할 수, 반경축은 활물질 입자 하나를 반지름 방향으로 나눈 수다.
메시 수렴 (convergence)
격자를 더 잘게 나눠도 답이 더 이상 안 움직이는 상태. 움직이면 아직 격자 때문에 생긴 오차가 남아 있다는 뜻이다.
시간상한 (time cap)
계산이 한 번에 뛸 수 있는 시간 간격의 최대치. 작게 잡으면 정확하고 느리다.
후처리 (post-processing)
계산이 끝난 뒤 결과에서 원하는 값을 꺼내는 단계. 전압·농도를 표로 뽑는 일이다. 계산 자체와 별개이고, 이 갈래가 지금 막혀 있는 곳이 여기다.
batch · rc (return code)
batch 는 화면 없이 명령으로 돌리는 실행 방식. rc 는 프로그램이 끝나며 남기는 숫자이고 0 이 보통 “정상 종료”를 뜻한다. 이 갈래에서 rc 0 인데 실패한 사례가 실제로 나왔다.
guard (보호식)
계산 도중 값이 물리적으로 말이 안 되는 곳(예: 농도가 0 아래)으로 가면 멈추게 하는 검사식.
manifest · sha256
manifest 는 묶음 안에 어떤 파일이 몇 바이트로 들어 있는지 적은 목록이고, sha256 은 파일 내용을 지문처럼 요약한 값이다. 한 글자만 달라도 지문이 바뀐다.

1 이 갈래가 하려는 일

원본 모델은 열화 모드를 파라미터로 주입한 full-cell DFN 에 분리막 전자전도를 얹어 마이크로 쇼츠를 켜고 끄는 1D 모델이다. 분리막의 전도도 sigma_short 를 축으로 두고, 그 값을 바꿔 가며 쇼츠가 있을 때와 없을 때가 어떻게 다른지 본다.

우리가 여기서 하려는 것은 그 모델을 COMSOL 6.3 에서 다시 짓고, 믿을 수 있는 상태로 만든 다음 진단을 돌리는 것이다. 명세는 bms-balancing/docs/COMSOL_REBUILD_SPEC.md 이고, 원본 모델에 대한 검토는 docs/MICROSHORT_MPH_REVIEW.md 다.

쉬운 말로

전지 하나를 컴퓨터 안에 만들어 놓고, 전극 사이에 아주 약한 누전을 일부러 넣었다 뺐다 하면서 전압이 어떻게 달라지는지 본다. 그 차이를 알면 실제 전지에서 측정한 곡선만 보고 “이 전지에 누전이 있다”를 말할 수 있게 된다.

지금 단계는 그 실험이 아니다. 컴퓨터 안의 전지가 제대로 만들어졌는지를 확인하는 단계다.

2 먼저 — 우리가 틀렸던 것

우리가 “확정 버그” 라고 적었던 M1 은 발견이 아니었다. 외부 리뷰가 정적 반례만으로 그것을 잡았고, 우리는 문서를 v3 로 다시 썼다. 원인은 우리 쪽 추출 도구였다 — 정규식으로 설정을 긁는 판이 자식 노드의 플래그를 부모로 전파해 엉뚱한 결론을 만들었다.

그 뒤 바뀐 결론이 다섯이고, 그중 하나는 Events 인터페이스 자체가 꺼져 있었다는 것이다. 교정 도구는 --self-test 로 그 반례를 고정한 채 태어났다 — 분석 스크립트에도 증거 규율을 건다.

쉬운 말로

우리가 “원본 모델에 버그가 있다”고 적었는데 틀렸다. 모델이 아니라 우리가 모델을 읽으려고 만든 도구가 잘못 읽은 것이었다.

이 갈래를 이어받는 사람이 알아야 할 것은 이것이다. 문서에 남아 있는 M1 은 철회된 주장이고, 인용하면 안 된다. 철회했다는 사실까지 문서에 적혀 있다.

읽으면 안 되는 것 하나. 위 값들은 서로 다른 시각의 최대값이라 수열이 아니다 — 비를 내어 수렴 차수로 읽지 않는다. 그리고 각 줄의 판정은 “이번 표본의 민감도”에 한정된다. 전체 수렴 완료가 아니다.

쉬운 말로

격자를 두 배로 촘촘히 했을 때 답이 얼마나 달라지는지 아홉 번 쟀다. 두 번은 기준을 넘었고(입자를 40→80, 80→160 으로 쪼갤 때) 더 쪼개니 들어왔다.

그러니 “이 정도 격자면 된다”가 아니라 “지금 쓰는 격자는 이 시험에서 기준 안에 들었다” 까지다. 다른 조건에서도 그렇다는 말은 아무도 안 했다.

4 계산이 다른 기계에서 돈다 — 그래서 규율이 하나 더

이 갈래는 COMSOL 이 다른 기계에 있고 결과가 ZIP 으로 건너온다. 그래서 규칙을 하나 더 뒀다 — 받은 요약을 그대로 옮기지 않는다. 원시 CSV 를 우리 쪽 산술로 다시 계산해 같은지 본다.

보존

bytes 그대로, 그리고 커밋 뒤에도 다시

재계산

마지막 축(물리 300→600)은 묶음 보고값 · 수신 측 독립 재계산 · 우리 재계산이 표본 수·최대값·최대 시각·전극·위치까지 같았다. 전압은 묶음이 적어 준 열을 믿지 않고 두 경계의 값에서 다시 만들었다.

도구가 남의 기계에서 처음 돌자 네 번 걸렸다. 보존 스크립트는 그동안 우리 기계에서만 돌았다. 인계 과정에서 처음으로 다른 기계에서 돌리자 숨어 있던 전제가 한꺼번에 드러났다 — 이미 쓰지 않기로 한 브랜치로 push 하라는 안내, 저장소 맨 위에서 돌아야 하는데 그 말을 안 하던 블록, 묶음마다 다른 목록 파일 이름, 그리고 목록의 키 이름이 셋으로 갈리는 것. 넷 다 재현 시험부터 닫았다.

쉬운 말로

남이 보내 준 결과를 그대로 베끼지 않고 원본 표를 열어 우리가 다시 계산한다. 같으면 그때 문서에 적는다.

그리고 파일이 오는 길에 한 글자라도 바뀌지 않았는지 지문을 대조한다. 저장소에 넣은 뒤에도 한 번 더 댄다 — 넣는 과정에서 줄바꿈이 바뀌어 지문이 깨진 적이 실제로 있었기 때문이다.

5 지금 막혀 있는 곳 — 계산이 아니라 결과 꺼내기

여기가 이 화면에서 제일 중요한 절이다. 세 번 시도했고 세 번 다 다른 자리에서 멈췄다.

① 정상 guard 실행 — 시간 적분은 끝났고 후처리가 죽었다

계산 자체는 5 초까지 갔다. 우리가 원시 로그를 직접 세었다 — 줄 987, 채택 간격 986, 시각 0 에서 5 초까지. 죽은 것은 그 뒤 값을 꺼내는 단계다.

원인은 좌표를 기록하려고 더한 식이 쓴 변수 하나가 COMSOL 에서 정의되지 않은 이름이었다는 것이다. 모델의 결함이 아니라 증거를 뽑으려고 더한 코드가 넣은 것이고, 기준 소스는 안 바뀌었다. 그 결과 필요한 표가 하나도 안 나왔다 — 만들어진 파일 목록에 적힌 것이 하나뿐인 것을 우리가 세어 확인했다.

그리고 여기서 하나가 더 읽힌다. compile 도 batch 도 rc 0 을 냈는데 로그 안에는 치명 오류가 있었다. 그쪽 실행기가 그것을 잡아 실패로 적었다 — 종료 코드만 보고 성공이라 하지 않는다. 우리 하네스가 자체 리뷰에서 닫은 축과 같은 모양이다.

② API 복구 시도 — 모델을 열기도 전에 막혔다

다음 시도는 프로그램으로 모델을 다시 열어 값을 꺼내는 것이었다. 그런데 모델을 여는 단계까지 가지도 못했다. 코드가 자기 입력 파일을 읽으려는 첫 순간에 COMSOL 의 파일 접근 정책이 거부했다.

그래서 “모델 복사 로드가 안 된다”는 확인된 적이 없다. 이 구분이 다음 절의 제안이 성립하는 근거다. 새 계산 0 회 · 새 표 0 개 · 설정 변경 0 회.

③ 화면에서 손으로 — 일부만 회수했다

세 번째로, 저장된 부분 결과 파일을 COMSOL 화면에서 열어 표 다섯 개를 손으로 내보냈다. 그것을 우리가 다시 셌다 — 저장 시각 987 개가 모두 유일하고 순서대로이며, 전해질 농도의 전체 최솟값이 세 영역 최솟값의 최솟값과 매 행에서 같고, 보호식 조건이 987 시각 전부에서 0 이었다. 기준 해와의 전압 차는 여덟 창 전부 기준 안이다.

그러나 공간 비교는 중단됐다. 전극마다 좌표 241 개를 찍어 표면 조성을 비교해야 하는데, 화면에서 하는 평가가 원래 계약과 같은 것인지 증명하지 못했다. 중단한 것은 옳은 판단이다 — 다만 공식 문서가 “다르다”고 말한 것은 아니다.

쉬운 말로

계산은 끝났는데 결과를 꺼내는 데서 세 번 막혔다.

첫 번째는 결과를 꺼내려고 더한 코드가 문법에 없는 이름을 썼다. 계산은 멀쩡했고 꺼내기만 죽었다. 두 번째는 프로그램이 파일을 열 권한이 없어서 모델을 열어 보지도 못했다. 세 번째는 사람이 화면에서 직접 열어 표 다섯 개를 뽑았는데, 그 표들은 우리가 다시 계산해 확인했지만 전극 속 위치별 비교는 못 했다.

그러니 지금 있는 것은 부분 회수다. 그것을 전체가 끝난 것처럼 쓰면 안 된다.

6 다음 단계 — 순서를 뒤집었고, A 는 이미 끝났다

막힌 자리를 우회하지 않고 정면으로 여는 제안이 나왔다. 저장된 해만 읽는 전용 후처리 경로를 만드는 것이고, 그러려면 COMSOL 의 파일 접근 범위를 넓혀야 한다. 검토 결론은 경로는 조건부 수용, 권한 변경과 구현과 실행을 한꺼번에 승인하는 것은 보류였다.

B파일 접근 범위를 넓히고 후처리 1 회 · 끝나면 원복미승인·미실행

왜 순서를 뒤집었나. 원안은 권한을 먼저 넓히고 코드를 만든다. 그러면 코드가 컴파일에서 막혀도 넓어진 권한만 남는다. 되돌린다 해도 불필요한 노출 기간이 생긴다.

A 에서 실제로 만들어진 것. 실행용 Java 하나, 전용 launcher 와 Windows 프로세스 전송층, 옛 분석기를 건드리지 않는 별도 분석기, 고정된 출력 계약, 그리고 합성 오프라인 시험 38 개가 통과했다. COMSOL 호출 0 · 실제 preferences 복사/변경 0.

그런데 “통과”의 뜻이 좁다. 준비 문서가 이전 표현을 스스로 철회했다 — “파일 로드만 유일한 미확인”이라고 적었던 것을 거둬들였다. 실제로 시험하지 않은 것은 이렇다. Java 타입·API 호환성 · 실제 정책 전파와 파일 읽기 · loadCopy · native 결과 형식 · Windows 프로세스 격리 — 전부 실물 미시험이다. 합성 시험이 지나갔다는 것은 그 항목들의 성공 증거가 아니다.

합성 시험이 덮은 축은 넓다. 완전·부분·누락·중복·비유한 출력, 잘못된 좌표와 시간, compile 실패, rc 0 인데 치명 오류, timeout 과 잔류 프로세스, 원복 실패, 그리고 숫자는 통과했는데 정리가 미완인 경우까지 넣었다. 다만 Windows 프로세스를 실제로 만들고 죽인 시험은 아니다.

다섯 조건에 어떻게 답했나.

조건준비된 구현
권한보다 코드를 먼저소스·의존 파일을 지문으로 고정. 기본 실행은 계획만 출력하고, 실제 동작은 그 지문에 묶인 별도 승인 파일을 요구한다
원복 방법적용 1 세션 + 원복 전용 1 세션, 각각 모델 로드 0. 전용 설정 파일 하나만 다루고 기본 설정은 덮어쓰지 않는다
강제 종료 처리정상 예외에서만 사후 검사를 시도하고, 강제 종료는 마무리 코드가 돌았다고 가정하지 않는다. 바깥 상태 파일에 미결로 남긴다
구성 불변 판정기존 노드의 속성·선택·연결을 전후로 대조하고 새로 만든 것만 허용. 이력에서 결과 전체를 제외하지 않는다
새 소비 계약옛 분석기를 불러오지도 고치지도 않는다. 제외 항목을 명시하고, 속성 개수 1143 을 통과 기준으로 쓰지 않는다

프로세스 정리는 이름으로 죽이지 않는다. 새 뿌리 프로세스를 멈춘 채 만들어 전용 Job 에 넣고 그 다음에 깨운다. 시간이 넘으면 그 Job 만 끝낸다. 이름으로 일괄 종료하거나 권한을 올리는 일은 없다. 소유를 확인하지 못한 COMSOL 프로세스는 자동으로 죽이지 않고 미결로 남긴다 — 다른 사람이 쓰던 세션을 죽이지 않기 위해서다.

첫 시험은 실패했다. 그리고 그것은 COMSOL 실패가 아니다. 운영체제 임시 폴더의 권한 때문이었고, 같은 업무 폴더 안의 새 디렉터리로 바꿔 통과했다. 준비 문서가 그 실패를 COMSOL 실패나 정책 변경으로 세지 않는다고 명시한다. 실패의 원인을 바꿔 적지 않는 것이 이 갈래 전체의 규율이다.

쉬운 말로

막힌 것을 뚫으려면 프로그램에 파일을 읽을 권한을 더 줘야 한다. 그런데 코드를 먼저 만들고 그 다음에 권한을 주자로 순서를 바꿨다. 권한부터 주면 코드가 잘못돼서 아무것도 못 해도 권한만 넓어진 채 남는다.

그 코드는 이미 다 만들어져 있다. COMSOL 없이 돌려 보는 시험 38 개도 통과했다. 다만 그 시험은 가짜 상황을 만들어 본 것이고, 진짜 COMSOL 을 부르거나 진짜 프로세스를 죽여 본 적은 없다.

그러니 “준비가 끝났다”와 “될 것이다”는 다른 말이다. 준비 문서가 그 구분을 스스로 적어 놓았다.

7 인계 묶음에 무엇이 들어 있나

2026-09-15 에 인계 묶음이 만들어졌다. 바깥 ZIP 안에 문서 셋과 548 MB 짜리 본체 ZIP 이 들어 있다. 본체는 항목 201 개이고 만든 쪽에서 경로·집합·크기·지문·CRC 를 검사해 통과했다.

들어 있는 것

실물 입력 하나와 기준 자료

저장된 해 MPH 한 개(1,266,539,803 bytes), 기준 원시 자료, 실패한 두 작업의 소스·로그·상태, 화면 부분 회수 세션과 수신 확인, 정책·경로 검토, A 준비 소스·계약·시험 기록. 그리고 묶음을 검사하는 도구 하나 — 표준 라이브러리만 쓰고 COMSOL 을 부르지 않는다.

안 들어 있는 것

전체 백업이 아니다

기준 MPH, COMSOL 설치·라이선스·전체 설정, 과거 대형 민감도 ZIP, 역사적 파일 전체는 없다. 제외된 대형 ZIP 은 이름과 크기만 목록으로 남겼고, 그 목록은 내용을 담았다는 증거가 아니다. 문서 안의 옛 링크가 이 묶음 하나에서 다 열리지도 않는다 — 실제 포함 여부는 목록 파일로 판단한다.

우리 저장소와 어긋나지 않는다. 본체 ZIP 안의 목록 파일 지문 넷이 우리가 따로 보존해 둔 묶음의 것과 같다 — 화면 부분 회수 세션, 그 안에 재사용된 물리축 묶음, 전해질 복구 기록, 보호식 실행의 원시 CSV 목록. 서로 다른 경로로 온 자료가 같은 바이트를 가리킨다.

이 묶음은 실행 승인이 아니다. 만든 쪽이 첫 줄에 그렇게 적었다. 그리고 과거 문서에 적힌 “승인합니다”가 새 담당자에게 실행 권한을 주지 않는다는 문장도 같이 적었다. 승인 파일의 값은 거짓으로 두었고, 인계만으로 그것을 참으로 바꾸지 않는다.

9 인계받는 사람에게

가장 먼저 알아야 할 것 하나. 다른 PC 에서 기존 launcher 를 그대로 실행하지 말 것. 코드와 계약에 원래 기계의 절대 경로가 박혀 있다. 먼저 읽기 전용으로 검토하고, 사용자가 A 후속 작업을 승인하면 경로·환경·출력 계약을 맞춘 뒤 새 지문과 시험 결과를 다시 제출해야 한다.
