### 2-3. 최소 해결 증거

## 3. Q1·Q6 — 단계 결합과 미분류 단계 수정은 닫힘

`scripts/run_network_194_parallel.py:658–733`의 공용 계약은 닫힌 키·단계·정수형과 `expected = worker 1 + executed에서 유도한 단계 수`, `observed = expected`를 검사한다. `lhs_release_build.py:1350–1378`가 이를 시도마다 호출하고 합계를 검사한다. 별도 느슨한 사본을 사용하지 않는다.

실제 audit CLI가 parser 영수증 쌍 삭제를 거부한 뒤 낸 binding을 194 상세 픽스처에 이식했다. 최상위 실패 요약을 남기든 지우든 **ReleaseError·출력 없음**이다. 여섯 원 반례는 build뿐 아니라 생성 후 증거 해시 캐시를 갱신한 check에서도 거부한다.

`Mystery Stage`와 `Stage E`를 각각 넣은 실제 감사의 binding에는 `unclassified`가 남고, 공용 계약은 최상위 실패 목록과 무관하게 거부한다. 제출된 pilot의 정상 v2 binding 세 개는 통과한다. `unclassified` 삭제·비어 있지 않음·`in_process=True`·expected parser 삭제도 거부한다.

v1을 “고친 실행기로 audit 재실행”이라 거부하는 것은 타당하다. v1에는 필요한 상세가 없으므로 정상이라고 추론하면 안 된다. **재감사는 계산 재실행이 아니다.** 기존 ROOT를 보존하려면 이번 요청처럼 JSON은 밖에 쓰고, 배포가 소비할 때 새 감사가 어느 ROOT·manifest에 속하는지 결합한다.

정상 재시도는 과잉차단하지 않는다. 독립 감사에서 `started/finalized=6/5`인 interrupted→done, `10/10`인 완료 두 시도는 rc=0이다. 이전 완료 시도의 계획이 사라진 경우는 rc=1이다. 총 프로세스 수의 부등식과 **완료 시도별 결합**을 구분한 처리가 맞다.

## 8. 재현과 전달

리뷰 폴더의 `run_checks.py`는 원본 source를 변경하지 않고 개별 로그·rc·시간을 기록한다. 의존성은 NumPy/SciPy/NetworkX/Flask 등 기존 리뷰 런타임을 사용한다. 다른 PC에서는 이 파일의 **의존성 경로만** 설치 환경에 맞추고, source의 해시는 바꾸지 않는다.
