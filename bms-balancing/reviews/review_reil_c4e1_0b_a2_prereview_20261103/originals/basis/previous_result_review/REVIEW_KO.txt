1. Q1 — 중지 처리와 절차

승인 요청 §4-1은 c에서 기대와 다르면 RED 원기록을 커밋하고 e로 끝내도록 정한다. 이번 원문은 정확한 FAILED 9 / PASSED 24이지만 l33의 실패 원인과 예외 메시지가 기대와 다르므로 GREEN으로 가지 않은 판단이 맞다. 승인 요청의 예측 줄 번호는 참고다. 1063과 1065의 숫자 차이 자체가 중지 사유는 아니다.

커밋 연결은 e7d3d9fc(착수 전 상태) → 2ad8cc2c(§91 승인 기록/보존 규칙) → 69dacaab(복사 넷/착수 기록) → 419c0652(RED 원기록) → 7f73e640(끝 기록) → a38c878f(§92/발송문)이다. 인접 비교가 모두 1 commit 앞섬/0 뒤짐이다. 승인 기록과 사전 봉인이 기록된 RED 시작 시각보다 앞서고, RED 뒤 launcher는 v5 그대로이며 GREEN 자료가 없는 이유가 03_end.json에 남았다. 제출된 기록 안에서 승인 범위를 벗어난 수정·자동 재시험·GREEN 진행의 증거는 찾지 못했다.

외곽 기록: started=true, pytest rc=1, outer rc=1, timed_out=false, cleanup empty/deadline_hit=false/errors=[], end_problems/errors=[], runner_ok=true. 자식 17.027초/120초, 정리 0.002초/15초다. runner_ok는 RED 기대표 통과를 뜻하지 않는다. settle의 zombie 두 PID는 reaped 목록과 같고 alive는 비어 있다.

원천 14행은 시작=끝=고정 EXPECT이며, 별도 해시 로그 두 파일도 같다. 현재 고정 커밋 원문 또는 이전 수신본+변경 없음 비교로 연결한 14개 소스 바이트와 일치한다. 착수 SHA 10개와 끝 기록의 사본 5개도 연결된다. 증거 12파일은 69,968 B다. 실제 RED의 HEAD는 69dacaab이며, 최종 보고 HEAD a38c878f와 혼동하지 않는다.

§91의 사용자 “승인”은 실행자가 착수 전에 커밋한 기록으로 확인했다. 플랫폼의 사용자 메시지 원본을 독립 인증한 것은 아니다. Git 이름 확인·비밀 검사·재시도 없음에 관한 전체 셸 원반환은 별도 제출되지 않았으므로 원장 및 관측 파일의 범위에서 판단한다. 기존 요청이 요구하지 않은 자료를 사후 재생성할 필요는 없다. 절차 Git의 커밋 이력은 저장소 문서/파일 순서에 관한 근거이며 OS 실행 감사 로그가 아니다.

00_start→03_end는 기록 시각상 193초다. §91/92의 단계 a 시각을 포함하면 253초로 2시간 이내이며, 이후 push/문서까지의 전체 실측으로 확대하지 않는다. §92의 “커밋·push·문서는 끝 기록 뒤”는 종결 커밋·push·문서에 한정해서 읽는다. a/b/c 커밋은 절차대로 끝 기록 전에 있다. 새 절차 이탈로 판정하지 않는다.

2. Q2 — l33 원인과 이전 검토 정정

E1_0B_RESULT_N1 (P2): tests/test_reil_c4e1_launch.py 1059–1061의 post()는 L.postcheck에 extra=t.extra를 넘기지 않는다. 해당 기본값 EXTRA_EXECUTED는 실제 reil_c6_profile.py 및 env_profile.py의 크기/SHA다. _tree의 25 B/21 B 가짜 파일과 대조하므로 기본 postcheck가 문제 두 개를 반환한다.

실제 stdout 57–63행은 1063행 assert post()["problems"] == []에서 멈춘 것을 보여 준다. 첫 항목은 가짜 reil_c6_profile.py의 25 B / 676ef3bd…와 실제 고정값 15,915 B / 408afc4b…의 불일치다. 두 번째 항목의 완전한 문장은 pytest 출력에서 생략됐다. 두 번째 파일의 원인은 소스 대조로 추론할 수 있지만 생략된 원문을 실제 관측한 것처럼 복원하지 않는다.

v5 postcheck 536/544–545행과 v6 601/609–610행은 모두 이 기본값과 대조를 사용한다. 따라서 이 fixture 결함은 v6에서도 의도한 cleanup 판정 전에 기본 postcheck를 막는다는 정적 판단이 성립한다. v6 GREEN을 실행해 확인했다는 뜻은 아니다. 최소 정정은 이 직접 호출에 extra=t.extra를 명시하는 것이다. 생산 코드의 기본값이나 해시 검사를 완화할 이유가 없다.

캡처한 launcher 대조 파일에서 직접 L.postcheck 호출은 한 곳이다. identity 경로에서는 data/data_files가 사용되지 않고 repo/env/records는 fixture에서 명시한다. 정상 기준이라는 말은 이 시험이 구성한 postcheck 기준을 뜻한다. _pre(t,"identity") 전체의 성공이나 실제 identity 단계 성공으로 확대하지 않는다. 관련 세부 대조는 L33_CAUSE_REVIEW.json에 있다.

이 누락은 제가 이전 정적 검토에서 놓친 부분이다. 2026-11-03 v2 REVIEW_KO.txt 34행의 “l33은 정상 기준 결과를 확인한 뒤 …”와 기대 경로에 정적 모순이 없다는 포괄적 판단은 l33에 관해 철회·정정한다. 앞선 검토에서 미발견한 사실도 남긴다. 원 검토 파일은 고치지 않고 REVIEWER_CORRECTION.json으로 연결했다. 기존 E1_0B_N1의 l23/l29/l30 원인 구분 정적 종결과 이번 l33 신규 정정 요구는 별개다.

3. Q3 — 여덟 RED의 활용 범위

l14/l23/l25/l28/l29/l30/l31/l32는 각 FAILURES 절의 첫 traceback·최종 예외·정확 메시지 또는 승인된 접두와 일치한다. FAILED/PASSED의 누락·추가·중복은 없고 UNEXPECTED_RED_CAUSE, 수집/내부 오류, 중단 표시는 없다. 이는 이번 v5/v7 조합에서 실제 도달한 경로의 과거 증거로 보존할 수 있다.

다만 l23은 첫 rewrite에서, l30은 localtls에서 멈췄다. 뒤의 입력을 모두 실행한 결과가 아니다. l28/l31/l32는 v5에 없는 인터페이스에서 실패한 기록이며 새 cleanup 기능 동작을 검증한 결과가 아니다. 24 PASSED도 이번 RED 조합의 관측일 뿐 v6의 GREEN 결과를 대신하지 않는다.

다음 시도의 최종 RED 판정에는 새로 봉인한 controls/runner/요청서로 전체 33개를 다시 확인해야 한다. 이전 여덟과 새 l33을 이어 붙여 새 gate를 통과시켜서는 안 된다. 전체 RED가 기대표와 일치한 뒤에만 승인된 다음 단계의 GREEN을 허용한다. 여기서 재시험을 시작하지 않았으며, 다음 시도는 기존 1회 승인에 포함되지 않는다.

작성자의 보조 판정기가 마지막 “9 failed, 24 passed in 14.25s”를 summary의 추가 줄로 센 것은 별도 오분류다. 이 줄은 요청서가 요구한 마지막 요약이며 오류 줄이 아니다. 보조 판정기 원문은 제공되지 않았으므로 그 프로그램 전체는 검토하지 않았다. 원 stdout과 고정 판정식을 독립 대조했을 때 실제 중지 사유는 l33이다.

4. Q4 — 다음 정정 범위안에 포함할 것

제시한 방향은 타당하다. 순서는 정정 범위안을 먼저 확정하고, 그 범위에서 초안·승인 요청을 갱신한 뒤 사전 검토와 사용자 E1-0b 재승인을 받는 것으로 명확히 한다. 이번 회신 자체는 코드 수정이나 실행 승인이 아니다.

- l33 직접 호출에 extra=t.extra를 전달한 controls v8 후보. postcheck 정상 기준→deadline_hit→미종료 상태의 기존 구분을 유지하고 생산 검사를 완화하지 않는다.
- 직접 호출의 repo/env/extra/data/records 기본값이 fixture 대신 실파일을 가리키는지 정적으로 대조한다. 이 확인을 위해 probe나 부분 실행을 추가하지 않는다.
- 변경된 controls 크기/SHA를 runner _FIXED/EXPECT, 봉인표, 복사 명령, 착수/끝 기록 기대값에 함께 반영한다. runner 자신의 바이트도 바뀌므로 새 식별이 필요하다. 33/71의 집합과 RED 예외표·예측 줄을 새 바이트에 연결한다.
- 새 증거·작업·cache 경로를 승인 요청에서 고정한다. 기존 SP/c4e1_0b_steps와 20261103 증거 폴더가 이미 있으므로 원 요청을 그대로 재사용하면 착수 중지 조건에 걸린다. 옛 기록을 삭제·재사용·이름 변경해 피하지 않는다. runner WORK/증거 이름 규칙과 end writer의 이름 검사까지 영향을 확인하고 필요한 변경만 범위안에 열거한다.
- 이번 12개 원기록·중지 결과와 이전 검토 오류를 그대로 연결한다. 보조 판정의 요약 줄 오분류를 새 기준과 혼동하지 않게 명시한다. 새로운 보조 판정 도구를 쓰려면 고정 판정식과 책임 범위가 검토 가능해야 한다.
- 기존 RED 전체→일치 시 GREEN, 예상 밖 결과 즉시 다음 단계 중지, 자동 수정/재시험/대체 금지와 실행 범위·예산을 새 요청에 유지한다. 실제 구체 바이트·경로·배정은 후속 요청의 검토 대상이다.

현재 기록을 고치거나 더 풍부한 l33 출력을 얻기 위해 과거 시험을 다시 돌릴 필요는 없다. 현재 자료로 원인과 중지 판단은 충분히 검토 가능하다.
