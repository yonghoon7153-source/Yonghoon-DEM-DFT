# ADR 0034 — 고정 주소는 우리 VPS 한 대로 얻는다

- 상태: **채택 — 다만 아직 세우지 않았다** (2026-08-27)
- 결정한 날: 2026-08-26.  아래 '올리기 전에' 는 2026-08-27 에 붙였다.
- 검증: [Codex 적대 리뷰 22건](../reviews/2026-08-27-codex-vps-result.md) —
  승인 보류. 랩 PC 쪽은 닫았고 설치본은 다시 썼지만, **일회용 VPS 에서 한 번
  통과하기 전에는 실제 주소로 올리지 않는다** (아래 '올리기 전에')
- 관련: ADR 0014(터널과 공유 암호), ADR 0030(중계기), ADR 0031(Cloudflare 터널 —
  이 랩에서는 7844 가 막혀 못 씀), `tools/vps-setup.sh`,
  `tools/bml` 의 `tunnel_via_vps` · `cmd_share_vps`

## 맥락

주소를 고정하려고 도메인을 샀다 (`bmlwork.kr`).  그것을 어디에 물릴지 두 번
시도했다:

1. **localhost.run 커스텀 도메인** — 됨이 확인됐다 (SSH 붙고 인증까지 통과,
   `_lhr` TXT 레코드만 없었다).  다만 $9/월(연납) ≈ 15만원/년이다.
2. **Cloudflare 터널** — 무료인데 **이 랩에서 안 된다.**  `cloudflared` 는
   7844 로만 나가고 (quic 은 UDP, http2 는 TCP, 둘 다 7844), 이 망이 그것을
   막는다.  진짜 엣지 IPv4 에 직접 붙어 봤고 안 됐다 (ADR 0031).

그런데 **SSH 는 나간다.**  실측:

    /dev/tcp/github.com/22        → OK
    /dev/tcp/ssh.github.com/443   → OK

임의의 호스트로 22 도 443 도 열려 있다.  그러면 남의 터널 서비스를 살 이유가
없다 — 우리가 한 대 두고 우리 SSH 로 넘기면 된다.

## 결정

    [랩 PC]  bml 서버 :5003
       └─ ssh -N -R 5003:localhost:5003 ─→ [우리 VPS]
                                             nginx :443 (Let's Encrypt)
                                                └→ 127.0.0.1:5003
    bml.bmlwork.kr  --A-->  VPS 공인 IP   (Cloudflare DNS, **회색 구름**)

`bml share vps <사용자@호스트>` 와 `bml share domain <이름>` 이 **둘 다** 있을
때만 이 길로 간다.  VPS 만 있으면 어느 주소로 나갔는지 이쪽이 모르고, 이름만
있으면 그 이름이 가리키는 기계가 없다.  그리고 이 길이 실패하면 **랜덤 주소로
흘러가지 않는다** (ADR 0031 과 같은 이유).

### 회색 구름 — Cloudflare 프록시를 안 거친다

무료 요금제의 프록시는 올리는 파일 하나가 **100 MB** 를 넘으면 막는다.  우리
서버 상한은 512 MB 다.  그대로 두면 **랩 안에서 되던 파일이 밖에서만 안 되는**
일이 생기고, 그때 413 은 우리가 준 것이 아닌데 화면은 우리 탓처럼 보인다.

DNS 만 Cloudflare 에 두고 TLS 는 VPS 에서 끝낸다.  차단 목록 회피라는 덤은
그대로다 — 막히는 것은 알려진 터널 도메인 목록이지 우리 이름이 아니고, 그건
프록시를 켜든 끄든 같다.

### 전달 포트를 0.0.0.0 에 열지 않는다

`GatewayPorts` 를 켜면 `-R` 로 전달된 5003 이 VPS 의 모든 인터페이스에 열린다.
그러면 **인터넷 아무나 nginx 를 건너뛰고 TLS 없이** 들어온다.  nginx 는 같은
기계 안에서 127.0.0.1 로 붙으므로 켤 이유가 없다.  설치본이 `GatewayPorts no`
를 확인하고, 시험이 keepalive 스크립트에 `0.0.0.0` 이 없음을 고정한다.

### nginx 쪽에서 챙긴 것

- `client_max_body_size 512m` — 우리 서버 상한과 맞춘다.  여기서 막으면 413 이
  나는데 그 413 은 워크벤치가 준 것이 아니라 화면이 엉뚱한 곳을 가리킨다.
- `proxy_buffering off` — 실시간 갱신은 SSE 다 (`/api/events`).  버퍼링하면
  nginx 가 응답을 모아 두고, 화면은 남이 고친 것을 영영 못 받는다.
- `proxy_read_timeout 3600s` — SSE 는 20초마다 heartbeat 를 보내므로 기본
  60초로도 살지만, 20 MB 업로드가 느린 망에서 끊기는 것을 막는다.

### 끊기면 다시 붙되, 영원히 두드리지는 않는다

감독자 스크립트가 `ssh` 를 다시 띄운다.  다만 **붙자마자 죽는 것이 20번
이어지면 멈춘다** — 그건 고칠 수 있는 문제가 아니라 설정 문제이고 (키가 안
올라갔거나 저쪽 포트가 이미 잡혔거나), 무한히 두드리면 로그가 그것으로만 차서
진짜 이유가 묻힌다.

## 결과

주소가 안 바뀐다.  다른 기계는 `bmlout https://bml.bmlwork.kr` 을 **한
번만** 치면 되고, 재부팅해도 그대로다.  받는 쪽에서 이름이 풀리므로
`bmlonly`·중계기(ADR 0030)·IP 전달이 통째로 빠진다.  남의 서비스 사정으로
주소가 바뀌는 일도 없다.

## 올리기 전에 — 일회용 VPS 에서 한 번

Codex 리뷰가 22건을 냈고 그중 8건이 "지금 만들면 설치가 인증서 전에 멎는다"
부류였다.  고쳤지만 **이 저장소에서는 하나도 못 돌려 봤다** — 컨테이너에
nginx·sshd·certbot 이 없다.  그래서 승격 조건을 여기 적어 둔다.  버릴 수 있는
VPS 를 하나 만들어 아래를 순서대로 통과시키고, 그 다음에 실제 이름을 건다.

1. `sudo bash vps-setup.sh --check <도메인>` — 80·443 이 **두 층** 다 열렸나.
2. `sudo bash vps-setup.sh <도메인> <메일>` 이 끝까지 간다 (certbot 포함).
3. `sudo sshd -T -C user=bml-tunnel,host=x,addr=127.0.0.1 | grep gatewayports`
   → `gatewayports no`.
4. `ss -H -ltn 'sport = :5003'` → `127.0.0.1` **하나**.  `0.0.0.0`·`[::]` 도,
   `[::1]` 만 있는 것도 실패다.
5. 밖에서 `nc -vz <VPS> 5003` → 실패해야 한다.
6. 랩 PC 에서 `bml share` → 공개 주소가 200.  **200 만으로는 모자란다** —
   `bml` 이 `/api/health` 의 `instance` 를 로컬 것과 맞춰 본다 (Codex #8).
   손으로도 한 번:  `curl -s https://<도메인>/api/health` 와
   `curl -s http://127.0.0.1:5003/api/health` 의 `instance` 가 같아야 한다.
   다르면 그 주소는 **다른 워크벤치**다 (DNS 가 옛 VPS 를 가리키거나, 저쪽
   5003 을 옛 터널이 잡고 있다).
7. 랩 PC 를 재우거나 랜을 뽑았다 꽂는다 → 90초 안에 저절로 돌아온다.
8. `bml stop` → 저쪽 `ss` 에서 5003 이 사라진다.  랩 PC 에 ssh 도 감독자도
   안 남는다.
9. VPS 재부팅 → 대문이 저절로 선다.
10. `sudo certbot renew --dry-run`.

## 대가

- **기계 한 대를 돌봐야 한다.**  Oracle Cloud Always Free 의 AMD micro(1 GB)면
  요금은 안 나오고 이 일에 충분하지만, 공짜라도 보안 갱신은 우리 몫이다.
- **"평생" 인 것은 요금이지 이 인스턴스가 아니다** (Codex #18).  Oracle 은
  7일 CPU·network 사용률이 기준 아래인 Always Free 인스턴스를 idle 로 보고
  **회수할 수 있다.**  조용한 relay 는 그 후보가 되기 좋다.  이름(DNS)은
  남지만 다시 만들 때까지 대문은 죽는다.  그래서 인스턴스가 사라진 것을
  **밖에서** 알 수 있어야 하고 (외부 health 확인), 다시 만드는 절차를 적어
  두어야 한다.  정책을 피하려고 가짜 부하를 돌리지는 않는다.
- **VPS 가 죽으면 밖에서 아무도 못 본다.**  랩 안(`bmlin`)은 그대로다.
- localhost.run 갈래와 Cloudflare 갈래를 지우지 않았다.  이 길이 막히는 날
  (VPS 를 잃거나 22 가 막히거나) 되돌아갈 곳이 있어야 한다.
