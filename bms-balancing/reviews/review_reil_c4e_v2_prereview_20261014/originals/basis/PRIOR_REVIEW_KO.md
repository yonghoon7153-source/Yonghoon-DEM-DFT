## 4. C4E-N2 — 관측 행 종결과 E3a 성공·운영 종결의 혼합

중요도 P1 · 좌표: 요청 139–144, 169–171, 227, 243행.

### N2-a 지역 오류

`scripts/reil_c4_e3a.py:286–305`는 util 지역 오류를 `termination=error`, X/F/G=None, `state=COMPLETED`인 행으로 만든다. 이 상태는 감싸는 실행기가 오류를 관측·기록해 반환했다는 뜻이다. 내부 `run_optimization`이 끝까지 정상 반환했다는 뜻은 아니다.

자료 없이 가능한 제어 흐름 반례: 각 최상위 호출의 첫 평가에서 util 지역 ValueError가 발생한다고 가정한다. 모든 오류가 분류·기록되고 해시가 불변이면 요청 §4-7의 세 조건은 66 오류 행으로도 성립한다. 그러나 GA 호출마다 뒤의 seed들은 수행되지 않아 v2 §2의 “노트북 경로가 끝까지 도는가”와 §6-3의 GA 20 seed 결과 전부를 충족하지 않는다. 이는 실행으로 재현한 반례가 아니라 현재 코드의 예외→행 변환을 읽은 반례다.

정정안:

- 66 = COMPLETED(returned/error 분리) + STARTED_INTERRUPTED + NOT_STARTED라는 관측 집계는 유지한다.
- **E3a COMPLETE는 66개 모두 `termination=returned`이며 기록·운영 조건까지 충족할 때로 한정한다.** 지역 오류 하나라도 있으면 E3a INCOMPLETE, C4-A 관문 false다. 오류 뒤 나머지 승인된 시도를 계속 관측하는 정책 자체를 금지할 필요는 없다.
- 반환된 결과의 X/F/G 없음·비유한·제약 위반은 기존대로 구분·기록한다. `returned` 조건을 feasible 해·수렴·`success=True` 조건으로 바꾸지 않는다.
- 지역 오류도 H 선행 완료로 인정하고 싶다면 기존 문구의 해석이 아니라 별도 프로토콜 변경안이다. 이번 검토는 그 변경을 수용하지 않는다.

### N2-b 운영·최종 기록

66개 done 이후라도 마지막 감시 실패 또는 최종 기록의 시간·용량 위반이 가능하다. `monitor.py:194–195`는 done 행을 COMPLETED로 유지하고, 중지·잔존 자식·exitcode는 별도 필드(`:332–336`)다. `final_record`(`:344` 이하)도 최종 쓰기 후 `RECORD_INCOMPLETE`/`OUTPUT_LIMIT_EXCEEDED`를 반환할 수 있다. 현재 요청의 세 조건에는 이 필드가 없다.

E3a COMPLETE의 필수 AND 조건에 다음을 넣는다: 전역 중지/구조 오류 없음, 예상 작업자 정상 종료와 소유 자식 잔존 0, drain/기록 경계 수용, 최종 `record_state=COMPLETE`, 한도 위반 없음, 기록 재읽기·끝 식별 수용. 모두 완료된 행을 지울 필요는 없으며 단계 판정만 INCOMPLETE로 둔다. s_2/s_4에 “66 returned 뒤 감시 실패”, “최종 쓰기 후 시간·용량 초과”, “지역 오류 1개”를 별도 대조로 고정한다.

## 5. C4E-N3 — 1,800초 상한과 늦은 완료·시간 좌표 미정

중요도 P2 · 좌표: 요청 60–64, 86–117, 146–151, 158–163행.

reserve 1,800초, 단일 run 원점, 최소 8 returned 호출·위쪽 중앙 순서통계·누적 창·작업자별 투영 규칙은 선택 자체가 구체적이다. 다만 다음 경계를 E0 구현 전에 고정해야 한다.

1. **표본 사이 반환.** 직전 표본의 호출 경과가 1,799.5초이고 호출이 1,800.2초에 반환한 뒤 다음 tick에서 done을 수신할 수 있다. 진행 중 호출만 검사하면 초과를 놓치고, 완료 wall도 검사하면 요청 102행의 “그 호출은 STARTED_INTERRUPTED”와 실제 반환 기록이 충돌한다. 활성 호출과 완료 호출 모두의 상한 계측 기준, 늦은 완료 우선순위, 초과 전체 INCOMPLETE, stop 신호 뒤 신규 시작 금지, 원본 returned 행 보존을 명시한다. 표본 감시를 1,800.000초의 OS 강제 차단 보증으로 쓰지 않는다.
2. **공통 좌표.** 현 `monitor.worker_loop:167`의 start.t는 절대 monotonic이고 요청 snapshot의 now_rel은 상대다. `now_rel=clock()-run_t0`, `started[tid]=event.t-run_t0`처럼 단위·원점을 고정한다. 0이 아닌 t0와 표본 사이/늦은 완료 대조를 추가한다.
3. **통계 입력.** wall 유한 비음수, n_eval 양의 정수, progress 비음수 정수 및 작업 ID 집합 등 검증 규칙을 고정한다. 잘못된 값으로 표본을 임의 탈락시키거나 0 보충하지 않는다. 시작/완료 집합에서 활성·미시작을 어떻게 나누는지도 정의한다. progress는 평가 진입 때 증가(`e3a.py:247–249`)하므로 완료 평가 수가 아니라 관측된 진행 proxy다.
4. **원시 판단 근거.** 중지 tick의 상대 시각, 포함 returned task ID·표본 수·각 wall/n_eval, m, 작업자별 남은 기대 평가/R_w, 판정값·사유를 기록한다. X/F/G는 넣지 않는다.
5. **표현과 정리.** 113행은 “고정 비용 투영 모형에서 측정 마감 초과로 추정”으로 좁힌다. 60초 grace 이후 kill/join·잔존 확인도 reserve에 포함한다. 현 monitor의 kill 뒤 join은 별도(`:318–325`)이므로 grace를 모든 정리 완료 보증으로 부르지 않는다.

이는 callback 명세·합성 대조를 닫으라는 요구다. 새 중단 규칙이 실제 실행에서 실패했다고 판정한 것이 아니다.

원본의 CRLF 846개를 LF로 정규화하고 끝 LF 1개를 추가하면 사본 전체 바이트와 정확히 같다. 따라서 **“원바이트는 줄바꿈 정규화와 끝 LF 차이, 줄바꿈 정규화 뒤에는 끝 LF 1바이트 차이”**로 고친다. 이번 비교는 메모리상의 바이트 변환·해시 대조이며 원본/사본 파일을 수정하지 않았다. 원본 util 크기 33,754 B도 반입 기대값에 넣는다.

오류 분류는 실제 로드한 경로를 `ctx.util_file`로 넘겨 비교한다(`e3a.py:130–147`, `c5.py:775–788`). 사본 경로가 P0/C5와 다르다는 사실 자체가 오류 분류상 불이익은 아니다. 원본 사용 권장은 유지할 수 있지만 이 이유는 좁혀 쓴다.

요청 7행의 “부속 A §6-3”는 **v2 §6-3**로 정정한다. A에는 §6-1·§6-2가 있고 해당 §6-3은 v2에 있다.
