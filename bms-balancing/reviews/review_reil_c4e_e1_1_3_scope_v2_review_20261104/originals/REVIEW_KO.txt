1. 수용 범위와 진행 경계

이 회신은 범위안 v2의 문서 내용 및 고정 소스와의 연결을 검토한 결과다. E113_N1은 종결한다. P1 문서 작성 방향은 수용 가능하고, P2 즉시 탐침에는 실행 전 보완할 한 가지 결함이 있다. N2의 세 문구 보완은 다음 승인 요청서에서 반영할 조건으로 넘긴다. 이를 이유로 P1 초안 작성까지 다시 막거나 E1-0b를 재시험할 필요는 없다.

P1이 수용 가능한 방향이라는 판정은 사용자의 여섯 선택을 대신 기록하는 것이 아니다. 이번 사용자 응답 “ㅇㅇ”는 재검토 진행 문맥에서 처리했다. P2 실행, 잔류 그룹 SIGKILL(R1), 실제 결과 공개, Git push, E1-1–3 실제 작업은 새로 승인되지 않았다. 첨부 문서의 명령과 “권장”은 검토할 제안으로 읽었고 실행하지 않았다.

기존 E1-0b a2 한정 기능 수용과 A2_PROC_01은 유지한다. 그 결과는 실제 REIL 자료 fetch/run 성공을 뜻하지 않는다. COMSOL event 어댑터 검토와도 별도 작업이다.

2. 이전 지적 대조

E113_N1 — CLOSED
v2 39–43행은 기존 evidence/reil_c4e1_* glob에 보존된 세 시험 폴더가 포함된다는 v1 오류를 명시적으로 바로잡았다. 새 착수 검사는 ^reil_c4e1_20[0-9]{6}$ 항목이 어느 날짜에 하나라도 있거나 착수 경로 또는 SP/c4e1이 있으면 중지한다. 기존 시험 폴더는 규칙 밖으로 구분하고 삭제/이름 변경/덮어쓰기를 하지 않는다. 이전 실제 시도를 새 날짜로 피할 수 없다는 요구도 적절하다.
44행의 실행 환경 현재 경로/venv 관측은 제출자의 기록이며 이 검토에서 원격 실행 환경을 다시 관측한 결과가 아니다.

E113_N2 — FOLLOWUP_REQUIREMENTS_BEFORE_EXECUTION_APPROVAL
v2 51–63행은 세 launcher 단계에 공통 wrapper를 적용하고 외곽 stdout/stderr 보존, 배타 시작 기록, 완성 후 rc 게시, 형식 검사, 최초 절대기한 유지, 미게시/부분 기록/초과 때 다음 단계 차단을 명시했다. 64행은 감시 종료와 실행 종료도 구분한다. 명령·형식·정리 행위를 후속 승인 요청서에 고정한다는 51–52행의 경계를 인정한다.
27·29행의 380/860초는 명시 timeout의 산술 합일 뿐 전체 반환 상한이 아니라고 고쳤다. 900/1,800/12,600초는 감시 정책값이며 실제 호출 반환 보증이 아니라는 구분도 적절하다. 합계 15,300초와 전체 6시간의 관계를 제시했으나, 정확한 판정·중지·기록 예산은 후속 요청서에서 확정해야 한다.

E113_N3 — P1_ACCEPTABLE_P2_NOT_READY
77–78행의 P1은 탐침을 후속 요청서에 포함하고 별도 승인 뒤 실제 identity 전에 수행하도록 분리한다. 이 문서 방향은 수용한다.
79–93행의 P2는 경로/명령/300초 관측 경계/재시도 금지/잔류 관측/한계를 구체화했으나 아래 P2-01 결함이 남는다.

3. P2-01 — 대기 실패가 성공 표지로 이어지는 고정 명령

위치: v2 82, 87–92행.
82행 child 명령의 핵심 순서는 “PID 기록; sleep 150; 완료 시각 기록 && 완료 파일 게시”다. 세미콜론은 선행 명령 성공을 조건으로 다음 명령을 실행하지 않는다. 따라서 sleep이 오류로 일찍 반환해도 뒤의 date/mv가 성공하면 유효한 done.txt가 남을 수 있다. 87–88행은 300초 안의 done 형식, tmp 부재, 프로세스 부재/Z만 검사한다. stderr 크기를 기록한다는 요구도 곧 오류 거부 조건은 아니다.

정적 반례: sleep이 곧바로 실패하고 date/mv가 성공한 뒤 shell이 끝난다. done.txt는 유효한 UTC 한 줄이고 tmp가 없으며 프로세스는 종료되어, 150초 대기를 수행하지 않았는데도 현재 성공 조건을 충족할 수 있다. 이는 실행해서 얻은 실패 결과가 아니라 명령과 성공 조건을 읽어 도출한 가능한 경로다.

수정 요구:
- 준비/PID 기록/의도한 대기 성공을 완료 게시의 선행 조건으로 묶는다.
- 실패 단계의 반환 코드와 오류 원문을 보존하고 성공으로 분류하지 않는다.
- 성공 판정에는 최초 띄우기 호출의 반환 경계와 의도한 이후 대기·종료 관측 구간을 연결한다. 단순 done 존재를 생존 시간 증거로 쓰지 않는다.
- 이 보완은 P2 즉시 실행 전 필요하다. P1 선택 시에는 다음 승인 요청서의 탐침 명세에 포함하면 된다.

82–83행의 중괄호는 setsid 부분만 배경으로 보내므로 앞선 경로 검사/mkdir 실패를 가린다고 지적하지 않는다. 92–93행이 이미 밝힌 7,200초 관리 상한, 10,800초 run, 컨테이너 소실, launcher 정리의 미보장 역시 새 시험 요구로 바꾸지 않는다.

명령 연결 의미의 공식 근거: GNU Bash Reference Manual, Lists of Commands
https://www.gnu.org/s/bash/manual/html_node/Lists.html
이 근거는 세미콜론/조건부 목록의 의미를 확인하는 용도다. 대상 환경의 /bin/sh 종류나 실제 수행을 관측했다는 뜻은 아니다.

4. N2의 후속 요청서 필수 보완 세 가지

F1. 실제 cleanup 필드 연결
위치: v2 65–66행; launcher v6 624–632, 803–806, 899–906행.
v6에는 meta.cleanup 키가 없다. child에 group, deadline_hit, errors, timed_out, exited_after_kill 등이 들어가고 최상위에는 child/postcheck/stage/errors 등이 있다. 정상 정리의 근거는 child.group.status == empty, child.deadline_hit is False, 필요한 timeout 뒤 종료 확인, child.errors 및 postcheck/stage 등의 실제 조건으로 명세해야 한다. meta 자체 또는 필요한 필드가 없으면 미확인으로 두고 정상 수용하지 않는다. launcher 바이트 변경은 필요 없다.

F2. 장시간 수명 보장 단정 제거
위치: v2 70행 및 92–93행.
70행의 “셸 도구 상한에 launcher가 끊길 일이 없다”는 문장은 공개된 탐침 한계를 넘어선다. 권고 문구는 “세 단계의 호출을 도구 호출에서 분리하려는 방식이며 장시간 도구 관리 영향은 미확인이다”다. 짧은 탐침의 성공이나 detach 명령의 채택만으로 도구 관리자·세션·컨테이너 수명까지 보장하지 않는다. 새 장시간 실험을 요구하는 지적은 아니다.

F3. 살아 있는 작성 주체와 증거 최종 봉인 구분
위치: v2 53–58, 69, 121행.
69행은 R2에서 run 폴더만 커밋 제외로 적지만 잔류 launcher/wrapper는 run 밖 외곽 stdout/stderr/meta/rc도 쓸 수 있다. 121행의 실패 단계 기록 커밋은 이 가변 파일까지 확정된 최종 증거로 취급하지 않도록 보완해야 한다. 종료/작성 완료를 확인하지 못했으면 원본을 보존하고, 실제 읽은 범위의 고정 관측 사본과 INCOMPLETE 사유를 구분한다. 이 사본도 여러 파일의 원자적·동시 시점 스냅샷이라고 주장하지 않는다. R1의 1회 정리 뒤에도 잔류/불명이 남으면 같은 원칙을 적용한다. 정확한 가변 파일 목록·복사/공개 조건은 후속 요청서에 고정한다.

이 세 항목은 v2가 후속 요청서에 맡긴 실행 상세를 정확히 만드는 조건이다. P1 문서 작성 전에 새 전체 범위안 반복 검토를 요구하는 것은 아니다.

7. 결론과 미수행 범위

P1 문서 작성 방향으로 다음 승인 요청서 초안을 준비할 수 있다. 선택 문구를 채택하는 일과 실제 탐침/identity/fetch/run을 실행하는 일은 분리한다. P2를 바로 실행하려면 P2-01을 먼저 고쳐야 한다. N2 F1–F3은 후속 승인 요청서에 반영한다. E113_N1과 기존 a2 수용은 재개방하지 않는다.

새 탐침/대상 실행/import/기능시험, 실제 REIL 데이터 fetch·개봉·run, 신호 발송, COMSOL, 소스 수정, Git add/commit/push, 외부 발송은 0회다. 새 숫자 검토 예산과 전체 소요시간 준수는 주장하지 않는다. 영수증과 사후 저장한 도구 반환은 이번 검토 ZIP 식별을 연결하며, 자기 자신의 이후 파일 작성 반환이나 과거 원격 실행을 독립 인증하지 않는다.
