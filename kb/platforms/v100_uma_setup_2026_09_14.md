# 임대 V100 에 UMA 를 올리는 레시피

2026-09-14 하루를 통째로 쓴 경로다. 같은 기계를 다시 빌릴 때 **이 순서대로** 하면
반나절이 한 시간이 된다. 함정이 일곱 개였고 **전부 서로 다른 원인**이라, 하나씩 겪으면
"왜 아직도 안 되지" 가 반복된다.

⚠ ⑥·⑦ 은 UMA 를 올린 **뒤에** 나왔다 (repo 를 올리는 단계). ⑤ 까지 끝나도 안 끝난다.

> 검증 종점: `max|F| 0.1626 eV/Å · Tesla V100-PCIE-32GB`. 여기까지 나와야 끝난 것이고,
> `import` 성공은 **끝이 아니다** (아래 ④·⑤가 그 뒤에 있다).

## 기계 조건 (2026-09-14 실측)

| 항목 | 값 |
|---|---|
| GPU | Tesla **V100-PCIE-32GB** (sm_70) |
| 로컬 디스크 | overlay 928 G · 915 G 여유 — **컨테이너 재시작 시 소멸** |
| 네트워크 저장소 | `$STORE=~/runyourai/1` (NFS) 98 G · **63 G 여유** (체크포인트·repo 올린 뒤) |
| 바깥 | ⛔ `huggingface.co`·`github.com` **타임아웃** (egress 막힘) · HF 토큰 없음 |
| 안쪽 | ✅ kgy(`59.12.161.91:22`) 는 **열려 있다** → 파일·repo 는 kgy 에서 끌어온다 |
| `~/.ssh` | ⛔ **root 소유·쓰기 금지** (`drwxr-xr-x root root`) — 아래 ⑥ |

## 함정 ① — NFS 에 conda env 를 깔면 2시간

**증상**: `conda create` 가 끝날 기미가 없다.
**원인**: 용량이 아니라 **파일 개수**다. conda env 는 작은 파일 10만 개쯤이고 NFS 는
파일마다 네트워크 왕복이 생긴다. 로컬이면 10–15분.

**실측 (import 한 번)**

```
real 1m29s   user 0m6.0s   sys 0m1.1s
```

CPU 는 6초, **나머지 83초는 순수 대기**다. 20배 손해.

**판단**: 그래도 **옮기지 않는다.**
- 옮기는 것 자체가 10만 파일 복사라 20–40분이고, 컨테이너 재시작하면 날아가 또 복사다.
- 우리가 던질 것은 긴 MD(200 ps × 30런)라 한 잡이 몇 시간이다. 35 스텝 × 1.5분 ≈ 52분,
  전체의 1–2 %.
- ⭐ 그리고 그 대기 동안 **GPU 는 논다** — 비용 상한이 GPU-h 기준이면 예산을 안 먹는다.

**옮길 값어치가 생기는 경우**: 짧은 잡을 수백 번 돌릴 때.

## 함정 ② — torch 를 fairchem **뒤에** 깔지 않으면 sm_70 이 빠진다

**증상**: 설치는 성공했는데 `torch.cuda.get_arch_list()` 에 `sm_70` 이 없다 → V100 에서 못 돈다.
**원인**: `fairchem-core` 의 의존성 해결이 PyPI 기본 torch 를 끌어와 cu126 빌드를 cu130 으로
**덮어쓴다**. cu130 에는 sm_70 이 없다.

**순서**: fairchem 먼저 → **torch 를 마지막에 강제 재설치**

```bash
pip install --force-reinstall torch==2.14.0 --index-url https://download.pytorch.org/whl/cu126
```

**검증**

```bash
python -c "import torch; print(torch.__version__, torch.cuda.get_arch_list())"
# sm_70 이 목록에 있어야 한다
```

⚠ pip 가 이런 경고를 뱉는데 **무해하다** (실측 확인):
```
fairchem-core 2.22.0 requires torch~=2.13.0, but you have torch 2.14.0+cu126
```
⛔ 단 `import` 성공을 동작 확인으로 읽지 말 것. 추론까지 봐야 한다 (⑤).

## 함정 ③ — `libstdc++` 는 시스템 것이 먼저 잡힌다

**증상**
```
ImportError: /lib/x86_64-linux-gnu/libstdc++.so.6: version `CXXABI_1.3.15' not found
  (required by .../envs/uma/.../libicui18n.so.78)
```
`import fairchem` → `ase.db.sqlite` → `sqlite3` 에서 죽는다.

**원인**: conda env 의 `libicui18n` 이 GCC 13+ 의 `libstdc++` 를 요구하는데 시스템 것이 낡았다.
env 안에는 새 것이 있는데 `LD_LIBRARY_PATH` 가 비어 있어 시스템 것이 이긴다.

**확인**
```bash
strings "$CONDA_PREFIX/lib/libstdc++.so.6" | grep -c CXXABI_1.3.15   # ≥1 이어야
strings /lib/x86_64-linux-gnu/libstdc++.so.6 | grep -c CXXABI_1.3.15  # 0 이면 원인 확정
```

**고침** — ⛔ **셸에 export 하지 말고 python 명령 앞에만 붙인다.**
```bash
env LD_LIBRARY_PATH="$CONDA_PREFIX/lib" HF_HUB_OFFLINE=1 "$CONDA_PREFIX/bin/python" -u <스크립트>
```
자식 프로세스(MD 드라이버 등)는 물려받고, **ssh 는 안 물려받는다.**

⛔ **정정 (2026-09-14 당일)**: 이 카드는 처음에 *"`~/.bashrc` 에 박아라"* 라고 적었다.
그게 함정 ⑥ 을 만들었다 — 전역 `LD_LIBRARY_PATH` 가 `ssh` 까지 conda 의 `libcrypto` 로
끌고 가 repo 전송을 통째로 막았다. **처방이 다음 함정의 원인이었다.** `.bashrc` 에
넣었다면 지우고 위 형태로 바꾼다.

## 함정 ④ — 체크포인트는 **파일로 옮긴다**. 그리고 **두 폴더**다

바깥이 막혀 있고 토큰도 없으므로 다운로드는 불가능하다. kgy 에서 가져온다.

**⛔ 어디 있는지가 안 보인다**
- HF 표준 캐시(`~/.cache/huggingface`)는 **비어 있다** — fairchem 은 `~/.cache/fairchem` 를 쓴다.
- 실물은 `blobs/` 가 아니라 `snapshots/<rev>/` 아래다. `find -maxdepth 4` 로는 못 찾는다(depth 5).

**kgy 원본** (`rev = be2896459a03fcde05e20d2fcefd11f450601fce`)

| 파일 | 크기 | sha256 |
|---|---|---|
| `checkpoints/uma-s-1p1.pt` | 1,173,759,575 | `07068e9c76702ca173d13155095f2117c1b327ec228557e64cd2709c777b824a` |
| `references/form_elem_refs.yaml` | 11,770 | `6de4f5105106bbb31fdc04b3fa215c50d379f043f3b6527e287475a3c2255c75` |
| `references/iso_atom_elem_refs.yaml` | 9,000 | `8d6b57a33c6a139f80cd706f253a030bd9d93cbfb1bbe33fba066e23b7e8c29e` |

⭐ **`references/` 를 빠뜨리면 체크포인트만 있어도 실패한다.** 그 에러가 두 번째 관문이었다:
```
Cannot reach .../references/iso_atom_elem_refs.yaml: offline mode is enabled
```

**배치** — 큰 파일은 NFS(영속), 캐시에는 심볼릭 링크
```bash
REV=be2896459a03fcde05e20d2fcefd11f450601fce
S=~/.cache/fairchem/models--facebook--UMA/snapshots/$REV
mkdir -p "$S/checkpoints" "$S/references" ~/.cache/fairchem/models--facebook--UMA/refs
ln -sfn ~/runyourai/1/models/uma-s-1p1.pt "$S/checkpoints/uma-s-1p1.pt"
printf '%s' "$REV" > ~/.cache/fairchem/models--facebook--UMA/refs/main   # 40 바이트, 개행 없음
```

⛔ **yaml 을 텍스트로 붙여넣지 말 것.** 숫자 하나가 조용히 바뀌면 기준에너지가 틀어지고
에러도 안 난다. 해시 대조되는 파일 전송으로만 옮긴다.

## 함정 ⑤ — 실행할 때마다 오프라인 선언이 필요하다

`HF_HUB_OFFLINE=1` 을 ③ 과 같은 `env …` 앞자리에 같이 붙인다.
없으면 fairchem 이 온라인 확인을 시도하다 **조용히 멈춘다** (에러도 안 나고 몇 분씩).

## 함정 ⑥ — 전역 `LD_LIBRARY_PATH` 가 **ssh 를 깬다**

**증상** — repo 를 옮기려는데 ssh 가 손도 못 대고 죽는다.
```
OpenSSL version mismatch. Built against 30000020, you have 30600040
fatal: Could not read from remote repository.
```

**원인**: ③ 에서 셸에 export 한 `LD_LIBRARY_PATH` 가 **모든 자식 프로세스에 상속된다.**
시스템 `/usr/bin/ssh` 는 OpenSSL 3.0 빌드인데 conda env 의 `libcrypto.so.3`(3.6)을 먼저
집어서 자기 빌드와 안 맞는다. ssh 바이너리 문제가 아니다 — **환경변수 오염**이다.

⚠ 오진하기 쉽다. `which -a ssh` 가 conda 것을 가리키면 "conda ssh 탓" 으로 읽게 되는데,
여기서는 후보가 `/usr/bin/ssh` 하나뿐이었다. **후보가 하나인데 mismatch 면 원인은 변수다.**

**고침**
```bash
env -u LD_LIBRARY_PATH ssh …          # ssh 만 깨끗한 환경으로
```

**`~/.ssh` 가 root 소유라 설정 파일을 못 쓴다** → 옵션을 명령줄로 준다:
```bash
export SSHOPT="-o StrictHostKeyChecking=accept-new -o UserKnownHostsFile=$HOME/known_hosts \
-o ControlMaster=auto -o ControlPath=$HOME/.cm-%r-%h-%p -o ControlPersist=30m"
env -u LD_LIBRARY_PATH ssh $SSHOPT kgy@59.12.161.91 …
```
`known_hosts` 를 `$HOME` 바로 아래 두면 호스트키를 **한 번만** 묻는다. `ControlPersist` 는
30분 안의 뒤 연결이 비번을 안 묻게 한다.

## 함정 ⑦ — repo 는 `--filter=blob:none` 으로 가져오지 않는다

**증상**: clone 은 되는데 checkout 에서 터지고, 그 뒤 **blob 하나마다 ssh 를 새로 연다**
(호스트키 확인 + 비번을 파일 개수만큼 묻는다).
```
error: Server does not allow request for unadvertised object …(v3d_noli.png)
fatal: unable to checkout working tree
```

**원인 둘**
1. partial clone 의 지연 인출은 서버에 `uploadpack.allowAnySHA1InWant` 가 있어야 한다.
   `allowFilter` 만으로는 부족하다.
2. cone 모드 sparse-checkout 은 **루트 파일을 무조건 포함**한다 — 이 repo 루트엔 png 가 있다.

**고침 — 협상을 없앤다.** `git archive` 는 커밋 하나의 내용을 **한 스트림**으로 뱉는다.
연결 1회 · 비번 1회.

```bash
# kgy 쪽: 내보낼 ref 하나 (체크아웃은 안 건드린다)
git -C ~/lldvar fetch origin claude/friendly-meitner-lldvar
git -C ~/lldvar update-ref refs/heads/v100-serve FETCH_HEAD

# V100 쪽: ① 메타데이터만 얕게 (384 K) ② 내용은 한 스트림으로
git clone --depth 1 --filter=blob:none --sparse --branch v100-serve \
  kgy@59.12.161.91:/home/kgy/lldvar ~/lldvar          # checkout 실패해도 HEAD 는 박힌다
env -u LD_LIBRARY_PATH ssh $SSHOPT kgy@59.12.161.91 \
  "git -C ~/lldvar archive --format=tar v100-serve tools db kb | gzip -1" \
  | tar xzf - -C ~/lldvar
```

**왜 clone 을 남겨 두나**: 파일럿이 기록에 `code_id = git rev-parse HEAD` 를 박는다.
git repo 가 아니면 그 자리가 **빈 문자열로 조용히 채워진다** — 실패가 아니라 침묵이라
나중에 "어느 코드로 돌렸나" 를 못 답한다.

⚠ 이렇게 만든 repo 는 **`git status` 가 의미 없다** (blob 이 비어 있고 sparse 설정이 남음).
읽기 전용으로만 쓴다. 내용이 그 커밋에서 나왔다는 것은 **해시 대조로** 증명한다:

| 파일 | sha256 (앞 16) |
|---|---|
| `db/structures/cascade_pilot/H0_host.xyz` | `5bca9a4f1d9bc119…` |
| `tools/doping/run_eprime_pilot.py` | `34de555f58eacc3a…` |

⛔ **litdb(1.7 G)를 끌고 오지 않는다.** 전체 워킹트리는 1.9 G, `git bundle` 은 **1.95 G** 다
(실측). `tools db kb` 만 뽑으면 **84 M**.

## 최종 검증 사다리 — 여기까지 가야 끝이다

```bash
env LD_LIBRARY_PATH="$CONDA_PREFIX/lib" HF_HUB_OFFLINE=1 "$CONDA_PREFIX/bin/python" -u - <<'PY'
print("① import", flush=True)
import torch
from ase.build import bulk
from fairchem.core import pretrained_mlip
from fairchem.core.calculate.ase_calculator import FAIRChemCalculator
print("② 모델 로드", flush=True)
pu = pretrained_mlip.get_predict_unit("uma-s-1p1", device="cuda")
print("③ 로드 끝", flush=True)
at = bulk("Li","bcc",a=3.44,cubic=True).repeat((2,2,2)); at.rattle(0.05, seed=1)
at.calc = FAIRChemCalculator(pu, task_name="omat")
print("④ 추론", flush=True)
F = at.get_forces()
print("⑤ max|F|", round(float(abs(F).max()),4), "eV/Å ·", torch.cuda.get_device_name(0), flush=True)
PY
```

**⭐ `python -u` + 단계별 print 가 핵심이다.** 버퍼링된 스크립트는 다 끝날 때까지 아무것도
안 보여서 "멈춘 건가 느린 건가" 를 못 가른다. 오늘 두 번 그걸로 헤맸다.

| 어디서 멈추나 | 원인 |
|---|---|
| ① 전 | ③ libstdc++ |
| ② → ③ | ④ 체크포인트 없음 / `references/` 없음 / ⑤ `HF_HUB_OFFLINE` 없음 |
| ④ → ⑤ | torch 커널 컴파일 (첫 실행만, 정상) |

## 멈춤 vs 느림을 가르는 법 (다른 창에서)

```bash
PID=$(pgrep -n -f python)
grep -E "^(State|VmRSS)" /proc/$PID/status
grep -E "^(rchar|read_bytes)" /proc/$PID/io; sleep 20; grep -E "^(rchar|read_bytes)" /proc/$PID/io
cat /proc/$PID/wchan; echo
ss -tnp 2>/dev/null | grep -w "$PID"
nvidia-smi --query-gpu=memory.used,utilization.gpu --format=csv,noheader
```

- ⛔ **2026-09-21 정정 — `read_bytes` 로는 못 가른다.** NFS 읽기는 블록 계층을 안 타서
  `read_bytes` 가 **0 에 고정**된 채 `rchar` 만 는다 (실측: G-B7 발사 후 `read_bytes` 0→0,
  `rchar` 45.3→51.7 MB / 20 s, `wchan = rpc_wait_bit_killable`, State D). **`rchar` 를 본다.**
- `rchar` 증가 → NFS 읽는 중. **속도를 같이 본다**: 실측 **0.3 MB/s** 였고 그 속도면 1.17 GB
  체크포인트에 ~65 분이다 — 계산(18 사건 × 7.5 분)보다 로딩이 길면 기다리지 말고
  체크포인트를 **로컬 디스크로 복사**해 캐시 링크를 바꾼다 (아래 반론 절 "NFS 판단" 참조).
- `rchar` 고정 + State D + `rpc_wait_bit_killable` → NFS 가 멈춘 것. `df` 가 답해도 파일
  하나가 막힐 수 있다. `kill` 은 먹는다(killable).
- 고정 + 소켓 있음 → 네트워크 대기 (⑤ 빠뜨림)
- 고정 + 소켓 없음 + CPU 100 % → 커널 컴파일
- `user`+`sys` ≪ `real` → **I/O 대기**, CPU 문제 아님

## ⛔⛔ 함정 ⑧ — **이 env 는 공유다. 다른 워크로드가 갈아엎는다** (2026-09-21 실측)

**증상**: 아침에 멀쩡히 돌던 UMA 가 오후에 `import torch` 부터 죽는다.
```
ImportError: libnccl.so.2: cannot open shared object file
ldd .../torch/lib/libtorch_cuda.so | grep "not found"
  libcusparseLt.so.0 / libnccl.so.2 / libnvshmem_host.so.3
```
`site-packages/nvidia/nccl/` 와 `nvshmem/` 이 **빈 디렉터리**인데 `.dist-info` 는 남아 있다
(`nvidia_nccl_cu12-2.29.3.dist-info/RECORD` 는 `libnccl.so.2` 가 **394 MB** 라고 적는다).

**원인 — pip 이 돌았다.** mtime 이 시각을 준다:
| 시각 | 무엇 |
|---|---|
| 15:45 | `~/.cache/pip/selfcheck` — pip 시작 |
| 16:19 | `nvidia/nccl` 비워짐 |
| 16:20 | `nvidia/nvshmem` 비워짐 · **`nvidia/cu13` 신규(include 만)** |
| 16:32 | `nvidia/cudnn` 갱신 |
| 09-14 | 나머지 nvidia 트리 전부 |

즉 **cu12 payload 를 지우고 cu13 으로 갈아엎다 멈췄다.** `torch-2.14.0+cu126.dist-info` 는
남아 있는데 그 torch 가 요구하는 payload 가 없다. `~` 잔해가 없는 것은 uninstall 은 끝내고
install 에서 멈췄다는 뜻이다. 디스크는 그만큼(≈2 GB) 풀렸다 — `df` 가 57G→55G 로 줄었다.

⛔ **고칠 수 없다.** kgy 에서 채울 수 있는 건 nccl(2.27.3 · soname 호환)·cusparselt(0.7.1)
**둘뿐**이고 **nvshmem 은 kgy 에 없다**. 바깥이 막혀 pip 도 안 되고, V100 엔 `uma` env
하나뿐이라 대안도 없다.

## 반론·한계

- **이 레시피는 이 컨테이너 한 대의 실측이다.** 다른 임대 기계는 시스템 libstdc++ 버전도,
  네트워크 정책도 다를 수 있다. ③·⑤ 는 **확인하고 넘어가는 항목**이지 무조건 적용이 아니다.
- **`torch 2.14.0` + `fairchem 2.22.0` 조합은 공식 지원이 아니다.** 경고가 뜨고, 우리는
  단일점 추론 한 번으로만 무해함을 봤다. 장시간 MD 에서 다른 경로가 깨질 가능성을
  배제하지 못한다 — E′ 파일럿 초반 출력을 한 번 더 본다.
- **NFS 를 놔두기로 한 판단은 워크로드에 묶여 있다** (긴 MD). 짧은 잡이 많아지면 뒤집힌다.
  ⭐ **2026-09-21 에 실제로 뒤집혔다.** 소셀 G-B7(18 사건 · 사건당 ~7.5 분)에서 NFS 가 0.3 MB/s
  로 내려앉아 로딩이 계산보다 길어졌다. 처방: `~/models/uma-s-1p1.pt` 로컬 사본(sha256
  `07068e9c…` 대조) → `~/.cache/fairchem/…/snapshots/$REV/checkpoints/uma-s-1p1.pt` 링크를
  로컬 사본으로 → 사건 폴더도 `$HOME/local_runs/` 에 복사해 거기서 돌리고 결과만 NFS 로 되돌린다.
  ⚠ 로컬 사본은 **컨테이너가 소멸하면 같이 사라진다** — 영속본은 여전히 NFS 다.
- **⑥ 은 이 카드가 스스로 만든 함정이다.** 처방(전역 export)이 다음 단계를 깼다. 환경변수를
  셸에 박는 처방은 *"이걸 물려받으면 안 되는 자식이 누구냐"* 를 같이 적어야 한다 — 안 적으면
  다음 사람이 같은 자리에서 또 걸린다.
