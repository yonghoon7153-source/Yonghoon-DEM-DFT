## 4. 잔여 반례와 최소 해결

### ULKRF-01 P2 같은 재개 사건이 승인을 복제함

**자리:** `ul_reader.py:108–126`, `:140–151`, 사건 정리 `:190–195`.

`_resume_auth`가 같은 `(k, step)`을 사건마다 추가하고, `_supersede`는 경계가 아니라 그 **목록 인덱스**를 사용 완료로 표시한다. 따라서 러너의 `resume_from` 한 줄과 상태 파일 하나가 동일 RESUME 두 줄에 의해 두 개의 승인으로 바뀐다.

실제 함수 사슬에 준 입력:

```text
run_manifest: resume_from=3310000 한 줄
state: ul_k=1, ul_rstep=3310000 한 파일
events: 같은 RESUME(1,3310000) 두 줄
기록: 실패한 k2의 4창+단 끝 기록 두 묶음, 이어서 정상 새 기록
```

결과:

```text
resume_auth=[[1,3310000],[1,3310000]]
n_superseded_rows=10, problems=[]
primary=OK, rho_pct=0.2026077873428664
selection=need_UV, gate(UVa)=ALLOW
```

**같은 두 묶음에 RESUME를 한 줄만 두면 UNIDENTIFIED/UVa 거부**다. 중복 사건 한 줄이 거부를 허용으로 바꾼다는 대조다. `run_unload.sh:88`의 정상 러너는 두 번째 재개를 막으므로, 이것을 실제 두 번째 재개가 발사된 증거로 확대하지 않는다. 무너지는 것은 판독기의 **“경계마다 한 번” 무결성 보증**이다.

**최소 해결:** 승인·소비를 고유 경계/시도와 연결하고 중복 또는 상충하는 RESUME를 사유 있게 거부. 사건 정리도 같은 규칙 사용. 기존 정상 재개 양성 유지.

**재현:** `python -X utf8 -B probes/resume_recheck.py` → `one_auth_two_rollbacks`와 `one_event_two_rollbacks`.

### ULKRF-02 P2 승인된 재개의 유지 시간이 길어지면 새 단 기록을 거부함

**자리:** `ul_reader.py:138`, `:692–695`; 생산 덱 `decks/ps_7_3_r45/in.UT.liggghts:267,319–330`.

롤백 판별은 새 `step`이 앞 행보다 작거나 같을 때만 시작한다. 같은 k를 다시 수행해도 끝 시간이 더 늦으면 이전 단 끝 행은 남는다. 생산 덱은 **단 CSV를 먼저 쓰고 그 뒤 restart/상태를 쓴다.** 그 사이 중단이면 이전 k1 체크포인트로 돌아가면서 이미 남은 k2 행을 정리해야 한다.

합성 사례의 승인 경계는 `(k1,3310000)`. 옛 k2는 4창 뒤 `3360000`, 새 k2는 5창 뒤 `3370000`에 끝난다. 새 5창 기록 단독은 OK다. 옛 4창 기록 뒤에 승인된 새 기록을 놓으면:

```text
창 CSV: 오래된 4행 제거
단 CSV: k=[0,1,2,2,3,4] 그대로
primary=UNIDENTIFIED, selection=SELECTION_UNRESOLVED, UVa 거부
```

5창 종료 자체는 생성된 UT 덱의 제어 흐름에 실제로 넣어 확인했다. k2의 창 압력 `[0.0010,0.0009,0.0008,0.0008,0.0008]` 덱 MPa에서 S1은 `[0,0,0,1,1]`, S2는 모두 1이므로 정상 완료는 다섯째 창이다. 새 4창 재시도는 통과한다. 원자·접촉·thermo는 합성이고, **실제 LIGGGHTS 재개에서 창 수 변화를 측정했다는 뜻은 아니다.** 판독기가 지원한다고 한 유효 기록 배치의 경계 사례다.

**최소 해결:** 승인된 시도 경계로 CSV의 새 구간을 식별하거나, 검증된 경계 이후 반복 k를 안전하게 정리. 단순히 모든 중복 k를 삭제하면 ULKRR-02 원결함이 돌아온다. 옛 완료 창 수보다 새 것이 짧음/같음/김과 승인 없는 중복을 함께 시험할 것.

**재현:** 같은 탐침 → `fresh_completed_hold_5_windows`, `resume_completed_hold_4_windows`, `resume_completed_hold_5_windows` 및 생성 덱 trace.

### ULKRF-03 P2 G2c 열 결손은 구조화된 실패 대신 예외 발생

**기존 원장:** ULKRR-04의 잔여 경로. **자리:** `ul_gates.py:252–256`, `g2c_compare:285–291`, `ul_reader.py:1335`.

## 5. Q1부터 Q6까지

### Q1 승인된 재개 경계와 정상 재개

**부분 동의.** 사건+영수증+상태 파일+남은 행 구조를 대조하는 방향은 맞고, 원반례와 경계 결손 시험은 닫힌다. 그러나 고유한 승인 횟수와 길이가 달라진 새 단 기록 처리가 빠졌다(ULKRF-01/02). UTc는 별도 부모 경계를 사용하므로 일반 재개의 로컬 `resume_from`을 억지로 요구하면 안 된다. 정상 UTc는 주 값 OK·보조 DONE으로 유지됐고 부모 RESUME 결손/다른 k는 거부됐다.

### Q2 영수증의 적용 범위

**RJ/RJ2/EXT 증서 재사용에 대해서는 동의. 모든 기술 실패 잡에 대한 전칭 보증에는 반대.**

실제 arm CLI도 stdout이 닫히면 파일 발행 뒤 rc120이 된다. UT 영수증은 실패지만 폴더를 새로 읽으면 `primary=OK → need_UV → UVa 허용`이다. 유효 관측 뒤 화면에 늦은 ERROR·실패 단계 영수증을 추가한 합성 사례, 완료 영수증이 없는 사례도 같은 결과다. UVa의 실패 영수증을 두어도 새로 읽은 선택 t1이 다른 침대 UB·G_UB를 허용한다(`ul_reader.py:971–989,1038–1093`).

재계산은 낡은 `arm_verdict.json`을 신뢰하지 않는다는 장점이 있으나 **프로세스 성공·완료 증명은 아니다.** stdout 실패나 주 측정 뒤 보조 단계 실패만으로 앞의 유효 수치를 지워야 한다는 결론도 아니다. 기존 등록은 유효 주 값 보존을 허용한다.

권고 문구: **“복원/EXT 증서는 성공 완료 영수증이 필수이며, 일반 팔의 주 관측은 원 폴더에서 재판독한다. 재판독 가능성이 잡의 기술 성공을 뜻하지는 않는다.”** 실패 팔의 관측 보존과 다음 제출 권한을 분리하려면, 값은 보존하되 다음 제출에 최신 성공 영수증을 요구하는 정책을 명시해야 한다. 이 예외를 정하지 않은 채 “기술 실패 산출물 승인 재사용 0”이라고 종결하지 말 것. 원 ULKRR-03 반례의 닫힘을 이 정책 질문 때문에 철회하지는 않는다.

### Q3 ID 규약의 완전성

**부분.** 이번 독립 시험에서 원자 ID·S3 쌍 참조의 일반적인 오형식은 모두 막혔다. G2c 열 결손은 ULKRF-03이다. 별도의 비차단 한계로, float 변환 뒤의 exact_id는 원문 토큰까지 정확함을 보증하지 않는다. `9007199254740993`이 float에서 `9007199254740992`가 되어 허용된다. 실제 침대의 ID 규모 문제를 입증한 것은 아니므로 별도 실행 차단 항목으로 세지 않는다. `k/w/step`의 반올림 허용도 입자 ID 수정과 다른 영역이다.

### Q4 본 R 전 문법 검사와 출처

**배선은 동의, 증서 신뢰 범위는 한정해야 한다.** `run_unload.sh:93–102,123,137`에서 RJ/RJ2/EXT 실행 전에 검사한다. 누락·FAIL·검사값 오형식·다른 바이너리·덱/판 바이트 차이는 거부한다.

알려진 `039abb141` 판독기로 얻은 같은 덱·같은 바이너리의 실제 PASS를 최신 러너 SHA가 아니라는 이유만으로 폐기할 필요는 없다. 그러나 임의 판독기까지 허용된다는 뜻은 아니다. 실제 보고 묶음의 당시 판독기·표 출처를 확인하거나 승인된 판독기로 raw 자료를 다시 읽어야 한다.

자동 관문의 한계를 실제로 재현했다. 정상 판독기가 만든 PASS JSON을 그대로 두고 GA 화면에 ERROR 추가, GB mesh 위치 변경, GB 화면 삭제, GB 상태 값 변경을 각각 가하면 **raw 판독은 네 건 모두 FAIL, 사전 점검은 네 건 모두 허용**이다. 이는 요청서가 공개한 캐시 신뢰 경계다. 새 미고지 P1로 세지는 않되 **JSON만 반입해서 실제 실행 PASS를 인증하면 안 된다.** `grammar_prereq=PASS` 줄은 검사 수행 영수증이지 원자료 재계산 증서가 아니다.

### Q5 W와 빈 구간 뒤 새 선언

**동의, 요청 반례 범위 닫힘.** 덱 W·등록 표의 UB/UT/UV/UTc/G_* 매핑을 대조했다. w3 누락·간격 1,000 step 오류는 이전 분리 연속을 끊고 주 값은 보존했다. 빈 구간 뒤 적법한 SEPARATE 0 창 두 개와 새 사건이 있으면 다시 선언할 수 있다. w12 선언→w15 완료도 §14-7의 예산 해석과 맞다. POST 창을 새 SEPARATE 창으로 임의 재라벨한 검증은 아니다.

### Q6 실제 문법 PASS만 남았는가

**아니다.** ULKRF-01/02/03 수정·좁은 재검증과 Q2의 보증 범위 정리가 남는다. 그 뒤 실제 ibb 실행 2의 원 보고 묶음·동일 바이너리·덱 출처·판독 PASS가 확인되어야 본 R 및 10:0 연장의 선행 조건이 채워진다. H0–H5 재실행은 요구하지 않는다. U는 R/EXT/RJ2 및 등록된 개발·선택 관문을 계속 따라야 하며, 문법 PASS 하나로 일괄 승인되는 것이 아니다.
