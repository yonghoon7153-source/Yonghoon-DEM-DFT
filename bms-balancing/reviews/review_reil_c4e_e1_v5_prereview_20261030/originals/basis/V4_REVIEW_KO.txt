2. V4-01 (P2) — S5의 l27/r11 입력이 비 UTF-8 Git stdout을 만들지 못한다

위치:
- docs/REIL_C4E1_LAUNCHER_CONTROLS_DRAFT_v4_20261021.py.txt:775–781 (assert 781)
- docs/REIL_C4E1_RUNNER_CONTROLS_DRAFT_v2_20261021.py.txt:548–552 (assert 552)
- docs/REIL_C4E_E1_APPROVAL_REQUEST_v4_20261021.md:216,223,259–261

두 시험은 ff fe 바이트를 담은 메시지 파일을 만든 뒤 기본 설정의 git commit -F로 저장하고,
git log -1 --format=%B의 반환에 U+FFFD가 있어야 한다고 검사한다.
각 _git_env는 상속 GIT_*를 제거하고 시스템/사용자 설정을 읽지 않게 하며, fixture는 i18n.commitEncoding을 지정하지 않는다.

요청서가 설치 버전으로 명시한 Git 2.43.0의 공식 소스는 다른 경로를 보여준다.
기본 UTF-8 커밋 작성 경로에서 verify_utf8가 잘못된 바이트를 Latin-1 문자로 간주해 UTF-8로 바꾼 뒤 커밋 객체를 저장한다.
따라서 이 입력의 ff fe는 c3 bf c3 be, 즉 ÿþ로 저장된다. 기본 log 출력은 이미 유효한 UTF-8이다.
의도한 UTF-8 디코딩에서 errors="replace"는 U+FFFD를 삽입하지 않으므로 두 최종 assert의 기대가 성립하지 않는다.
다른 locale에서 우연히 대체 문자가 나온다 해도, 명시한 비 UTF-8 입력 경로를 고정한 검증이 되는 것은 아니다.

공식 1차 근거:
https://github.com/git/git/blob/v2.43.0/commit.c#L1578-L1609
https://github.com/git/git/blob/v2.43.0/commit.c#L1632-L1677
확인한 원파일 Git blob: 8405d7c3fceab23c6eafd16e36d76c7172c44923.
웹 텍스트 렌더러의 줄 번호가 아니라 원파일 줄을 사용했다.

이는 실행 실패 관측이 아니라 입력 생산자→저장→출력→assert의 정적 도달 판단이다.
S5의 errors="replace" 구현 자체를 부정하지 않는다. /proc 부분의 V3-03 대조도 이 결함과 분리된다.
앞선 대조가 모두 기대대로 진행된다고 가정하면 GREEN -x는 먼저 l27에서 멈추고 뒤의 runner 대조에 도달하지 못한다.
그러므로 "두 실패를 관측했다"거나 "65개 중 나머지는 통과했다"고 기록하면 안 된다.

최소 보완 권고:
- 두 fixture가 wrapper stdout에 실제 잘못된 UTF-8 바이트를 전달하는 입력·환경을 고정한다.
- Git을 사용한다면 커밋 저장 인코딩, log 출력 인코딩, Python 디코딩 환경을 모두 고려한다. 대안 fixture를 택하더라도 선언된 범위 안의 동일 decoder 경로를 겨냥한다.
- U+FFFD 검사를 삭제하거나 ÿþ로만 바꾸면 비정상 바이트 처리 검증이 사라지므로 적절한 정정이 아니다.
- 정정한 두 대조의 크기/SHA, runner EXPECT와 runner 자체 식별, 승인안/발송문의 입력·기대·이유·수·hash를 함께 다시 고정한다.
- 이 회신은 정정 구현이나 시험 승인이 아니다. 별도 정정 범위 채택 뒤 비활성 초안과 정적 봉인까지만 진행하는 방식이 적절하다.
