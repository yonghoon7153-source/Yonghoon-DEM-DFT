Q1 — V4-01 종결
소스: launcher controls v5:787–799, runner controls v3:562–574.
각각 정해진 바이트를 tmp 파일에 쓰고 hash-object -w --no-filters로 blob을 만든다. 같은 cat-file blob 명령을 wrapper 밖의 byte-mode subprocess로 먼저 읽고 stdout == data와 strict UTF-8에서 UnicodeDecodeError를 확인한다. 그 뒤 AST keyword 검사와 대상 wrapper 호출을 거쳐 정확한 data.decode("utf-8","replace"), rc 0, error 없음에 도달한다. 리터럴은 두 파일에서 동일하다.
Git 2.43.0 hash-object 문서는 기본 타입 blob 및 --no-filters의 입력/개행 변환 배제를 규정한다. 해당 태그 hash-object.c는 type=blob과 no_filters일 때 path=NULL을 전달한다. cat-file.c의 명시적 blob 경로는 stream_blob을 호출하고 이는 필터 없이 stdout으로 전달한다. v4의 commit 메시지 정규화 경로를 사용하지 않는다는 정적 판단을 지지한다.
fixture 생산자 자체가 기대와 다르면 target wrapper 전에 assertion/예외로 실패할 계획이다. 자기 확인이 실패해도 계속 진행하는 fallback은 없다.
RED-L에서는 l27의 선행 L.proc_members, RED-R에서는 r11의 선행 R.observe에서 선언된 골격/인터페이스 오류가 먼저 나므로 Git 부분의 RED 도달을 주장하지 않는다. 이는 공개한 기존 RED 범위다.
이 결론은 V4-01의 잘못된 입력 생산 가정 해소이며 GREEN 통과 관측이 아니다.

Q2 — S6와 디코딩의 영향
소스: launcher v5:380–388, runner v5:140–149; AST helper LC:111–118 / RC:152–159.
두 대상 함수 모두 직접 subprocess.run 1개이며 text=True, encoding="utf-8", errors="replace"가 리터럴로 지정된다. 현재 고정 함수에 대한 AST 검사는 적정하다. 실행/동적 데이터흐름/모든 subprocess 경로의 일반적 증명으로 확대하지 않는다.
HEAD는 ASCII 40자리 hex에 대해 기존 regex 검사가 유지된다. UTF-8 명시로 ASCII 값의 해석은 바뀌지 않는다. porcelain/config에도 같은 디코더가 적용된다. ASCII 구조 구분자와 현재 고정 URL/키 조건은 유지되며 비 UTF-8 바이트는 U+FFFD로 손실 변환된다. 따라서 이 기록을 raw bytes의 가역 보존, 비 UTF-8 경로의 정확한 복구, 모든 locale/설정에 대한 동작 검증으로 읽지 않는다. stdout/stderr 개행 정규화는 이미 text=True였으므로 v5에서 새로 생긴 동작은 아니다.
Python 3.11 문서의 encoding/errors/text 및 binary-mode 정의와 맞는다. 이번 l27/r11의 LF-only 고정 입력은 text 개행 변환 때문에 기대값이 달라지지 않는다.
fixture helper _git은 변경되지 않은 text=True 경로이며 소비되는 출력은 hash-object/rev-parse의 ASCII 객체 ID다. 비 UTF-8 자기 확인은 별도의 byte-mode 호출이다. 요청서 §8-26의 제한과 일치하므로 helper까지 새 범위로 바꾸라고 요구하지 않는다.
FUTURE-01의 설정 원천 격리, 절차 Git의 KEY/VALUE 내용 검증 미포함은 S6로 닫히지 않는다.
