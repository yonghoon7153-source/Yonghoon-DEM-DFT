## 끝까지 확인한 반례 후보: 수신 표지의 범위

`git clone --no-checkout`으로 **객체·ref를 받은 뒤 checkout 전 끊김**과 같은 작은 상태를 만들고 문서 수신 순서를 재시도했다. 이 명령은 과학 결과나 원장 기록을 손으로 고친 것이 아니라, 수신 중간 상태를 결정적으로 만드는 모형이다.

```sh
git clone --no-checkout -b main <합성 bundle> ca1_ledger
# 후보 명령 문서 (5)의 받는 쪽을 다시 실행하는 제어 흐름:
# parked 없음 → clone은 기존 폴더 때문에 실패 → 마지막 HEAD 대조
```

- 기대: `RECV_OK`가 원장 사용 가능성까지 증명한다고 해석하면 나오지 않아야 한다.
- 실제: clone rc 128이어도 마지막 HEAD가 기록과 같아서 수신 블록의 마지막 조건은 참이다. 정상 수신 뒤 세션 응답만 끊긴 재시도에서도 같은 현상이다.
- 추가 확인: 정확한 `_ledger_now` 본문은 checkout되지 않은 `rint_r_attempts.jsonl`을 HEAD blob과 대조하여 `ATTEMPT_LEDGER_MISMATCH`를 낸다. 따라서 이 상태로 잘못된 결과를 받는 반례가 아니다. 문서의 `RECV_OK` 의미도 명시적으로 **끝 커밋 대조**이므로 새 P2로 세지 않는다. 운영 시 `RECV_OK`를 완전한 사슬 검증으로 확대 해석하지 않는다.

`flock` 관련 정적 확인: 송신 잠금 파일은 사슬 `_ledger_lock_path`와 같다(사슬 3164–3170, 명령 문서 708줄). 덧붙임은 잠금 안에서 `_ledger_now`를 다시 읽는다(3383–3386줄). 원장이 parked이면 배타 잠금 파일 열기 실패가 `ATTEMPT_LEDGER_MISMATCH`가 된다(3182–3185줄). 실제 잠금 경합 검증은 이번 모의 범위 밖이다.
