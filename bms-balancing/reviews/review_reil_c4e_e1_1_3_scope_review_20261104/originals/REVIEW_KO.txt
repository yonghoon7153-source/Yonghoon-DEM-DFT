E113_N1 [P2] 과거 증거와 실제 착수 이름을 구분
대상: 범위안 38행 및 80행. 소스: reil_c4e1_launch.py 121, 927행.
범위안은 evidence/reil_c4e1_*가 없다고 쓰고, 같은 glob이 있으면 새 착수를 멈추도록 한다. 그러나 보존된 evidence/reil_c4e1_0b_a2_20261104가 이 패턴에 일치한다. 이전 증거를 정상적으로 보존하면 중지 조건이 이미 성립한다. 이는 기록을 제거해 해결할 문제가 아니다.
정정: 실제 E1 실행 이름 규칙 ^reil_c4e1_20[0-9]{6}$에 해당하는 항목과 정확한 새 착수 경로의 충돌을 검사하도록 대상을 정한다. 이전 시험 증거는 별도로 식별·보존한다. 현재 상태의 부재 주장도 동일한 검사 범위로 제한한다. 새 이름으로 재시도를 우회하는 권한을 만들지 않는다.

E113_N2 [P2] 분리 실행의 실패 증거·완전한 반환 게시·감시 마감
대상: 범위안 31, 33, 36, 45–49, 54행.
소스: launcher 786, 816–823, 875–889, 908–915행; 기존 고정 요청서 537–540행.
a) 제안 wrapper는 외부 stdout/stderr를 /dev/null로 보낸다. launcher는 meta.json 쓰기 실패 시 stderr에 첫 오류와 meta_write_failed를 적고 rc 4를 반환한다. 이 실패 원문이 사라지면 기존 기록 정책의 마지막 증거 경로를 잃는다. 자식 stdout.log/stderr.log와 외부 launcher stdout/stderr는 서로 다른 자료다.
b) outer_rc 파일의 존재만 확인하면 파일 생성과 내용 쓰기 완료 사이에 일회 판정이 시작될 수 있다. 시작 실패/셸 소실/반환 쓰기 실패이면 파일 자체가 생기지 않을 수 있다. 지금의 until 루프와 “감시만 다시 건다”만으로는 유한 종결 경로가 없다.
c) 감시 종료는 실행 종료가 아니다. launcher가 자식을 별도 세션으로 시작하므로, 감시 또는 바깥 셸이 끝났다는 사실만으로 계산 자식의 정리를 주장할 수 없다.
d) identity 380초와 fetch 860초는 명시된 subprocess 대기 timeout을 합한 값으로 산술은 맞다. 하지만 고정 요청서는 정리 기한 전에 시작한 /proc 관측 하나가 무한히 지연될 수 있다고 이미 공개했다. 해시·파일 I/O·사후 대조도 그 단순 합으로 전체 반환이 제한되지 않는다. 따라서 “최악”이라는 보편적 상한 표현은 부정확하며, identity/fetch가 도구의 600/7,200초 안에 반드시 끝난다는 근거가 아니다.
요구하는 최소 보완: 외부 출력 보존, 한 실행의 식별/시작 상태, 완전한 반환 게시 확인, 재등록에도 유지되는 최초 절대 감시 마감, 미게시/부분 기록/시작 실패/마감 도달의 실패 종결 및 잔류 책임을 범위 요구로 적는다. 6시간 전체 한도에서 미완/끝 기록 시간을 어떻게 남기는지 후속 요청서에 고정한다. 정확한 명령·형식·관측과 허용 정리 행위는 후속 승인을 받는다. 감시 재시작을 run 재실행으로 바꾸지 않는다.
이는 기존 launcher 변경이나 E1-0b 재시험 요구가 아니다. 현재 “읽기 전용·개입 0” 감시를 유지한다면 그 감시가 책임질 수 없는 잔류 실행 처리를 누가 수행할지 구분해야 한다.

E113_N3 [P2] 즉시 실행 탐침을 구체적 선택으로 만들기
대상: 범위안 6–7, 50–51, 91–93행.
A 선택이 문서 작성뿐 아니라 요청서 작성 전 실제 sleep 150 탐침 1회를 허용한다는 점은 명시돼 있다. 숨겨진 실행이라고 판단하지 않는다. 다만 아직 정확 명령/cwd, 기존 경로 존재 시 중지, 관측 종료기한, 표지 누락·부분 기록·미종결 처리, 보존/잔류 책임이 없다. 실제 프로세스가 생기는 선택이므로 이를 후속 승인 요청서에서 나중에 채우겠다는 일반 문구만으로 충분하지 않다.
두 가지 정정 중 하나면 된다. (1) 이번 A는 분리 실행의 문서 방향만 선택하고 탐침도 구체 명세/검토 후 별도로 승인한다. (2) 이 범위안에 탐침 1회의 명령·제약·종결을 충분히 넣어 사용자가 그 실물을 선택하게 한다. 이 검토가 둘 중 하나를 대신 선택하지 않는다.
150초 탐침은 최초 시작 셸 호출이 반환된 후 표지가 생성되는지 확인할 뿐이다. 7,200초 관리 상한을 넘기는 실제 동작, 10,800초 연구 실행, 컨테이너 소실 또는 launcher 정리의 보증은 아니다. 장시간 도구 관리의 영향은 여전히 미확인이다.
공식 GNU 설명에서도 nohup은 hangup 신호를 무시하도록 실행하며 자체 실패·호출 실패·명령 없음에 별도 반환값이 있다. 컨테이너 수명 보장이란 설명은 없다. 이 문서 확인은 해당 실행 기기의 설치본/세션 정책을 관측한 결과가 아니다.
https://www.gnu.org/s/coreutils/manual/html_node/nohup-invocation.html

3. 이미 올바르게 구분된 부분
- E1-0b a2의 수용은 tmp fixture/가짜 자식 등 봉인된 범위에 한정되며 실제 REIL 자료 fetch/run 성공으로 바뀌지 않는다.
- 고정 launcher의 REQUEST가 기존 E1-0b 문서 경로를 인용하면서 새 승인 §NN을 결속하는 설계는 실제 build_argv 381–385행과 맞는다. 과거 요청서 원문을 소급 수정할 필요가 없다.
- E1-3의 launcher 단계 판정과 실험 결과를 따로 기록하고 C4-A를 별도 승인으로 두는 경계는 유지됐다. launcher 단계 판정도 final.complete를 이용하므로 둘이 통계적으로 독립이라는 뜻은 아니다.
- 외부 util_LFP.py의 import/실행을 자료 개봉 범위에 공개한 점은 적절하다. 현재는 그 실행이 승인되지 않았다.
- 새 판정기/작성기 초안의 정적 작성, 결과 공개 정책 A/B, 절차 Git add/commit/log와 작성 저장소 동기화 fetch/push 분리는 문서 방향으로 제시할 수 있다. 현재 첨부만으로 실행/커밋/공개 선택이 접수된 것은 아니다.
- A2_PROC_01 이력은 그대로 유지한다. 현재 세 보완은 새 범위안의 조건이며 지난 기능 결과를 무효화하지 않는다.

4. 후속 요청서에 고정할 항목 — 별도 새 차단 건수로 세지 않음
자료 개봉 실제 순서: reil_c4e_run.py 581–593행은 시작 바이트 식별 검사 → 발췌/경로 확인 → 새 산출 폴더 → P0 기록 읽기 → util import → 자료 적재 → 적재 결과/P0 결속 검사다. P0 파일/원천 식별과 자료 적재 후의 의미 결속 검사를 구분한다. “P0 결속 완료 뒤 util import”라고 단정하지 않는다.
결과 필드: child 05_run.stdout.log 마지막 JSON의 final.complete, final.E3a, final.c4a_gate와 launcher 자신의 단계 요약 stdout을 구분한다. 소스의 final_verdict는 함수명/의미이며 literal 최상위 JSON 키를 전제하면 안 된다. 후속 판정기에 정확 파일/필드/실패 조건을 고정한다.
전체 시간: 6h는 이번 검토에 적용한 예산이 아니라 미래 실행 제안이다. 승인 기록부터 끝 기록까지의 범위와 외곽 감시 실패 처리까지 새 요청서에서 맞춘다.
디스크: 약 26GB는 a2 종결 파일의 과거 관측이다. 지금의 독립 실측으로 재표현하지 않는다. 설치본/현재 여유 재확인은 이후 승인 범위에 맞춰 수행한다.
새 하네스·판정기 SHA, 정확 argv/cwd, 결과 공개 검사와 명령 문자열을 후속 요청서에서 작성하겠다는 유보 자체는 결함으로 세지 않았다.

5. 수행과 한계
사용자 첨부·고정 GitHub 코드/변경 메타데이터·기존 검토 사본을 읽고 자체 자료 비교 도구로 해시/글롭/산술만 확인했다. GNU 공식 문서도 열람했다. 원격 연구 저장소(REIL-UConn)의 fetch/읽기 경로 추가, 받은 프로그램 import/시험, detach 탐침, 실제 E1 identity/자료 개봉/run, COMSOL, 코드 수정, 저장소 commit/push, 외부 발송은 하지 않았다.
수신자 자료 도구가 처음에 재사용 run 파일의 식별을 첫 인덱스에서만 찾아 KeyError를 냈다. 보조 식별 인덱스까지 병합한 뒤 정상 대조했다. REVIEWER_DATA_TOOL_NOTE.json에 남겼다. 이 오류는 입력 바이트 결함이나 대상 프로그램 시험 실패가 아니다.
원천 프로그램에 새로운 결함을 증명한 기능 시험은 없다. 셸/도구 수명은 제안 문구와 일반 문서의 한계만 검토했으며 원격 환경에서 실험하지 않았다. 현행 수용과 원본을 변경하지 않는다.
