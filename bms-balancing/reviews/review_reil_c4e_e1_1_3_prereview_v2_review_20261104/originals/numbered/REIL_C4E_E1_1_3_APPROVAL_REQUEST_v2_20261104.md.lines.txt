348: - 작성 저장소의 fetch · push 는 g 의 끝 기록 뒤에만 한다 (g3). 기록에는 **"작성 저장소 동기화 fetch"** (이 저장소 `origin` 의 이 브랜치) 로 적어 E1-2 의 fetch
349:   (REIL 저장소의 자료) 와 나눈다.
350: - **g3 의 재시도 (유일한 재시도):** push 가 원격 · 네트워크 오류 (예: `Internal Server Error` · 연결 끊김) 로 실패하면 i 를 늘려 같은 g3 줄을 다시 — 시도 사이
351:   2 · 4 · 8 · 16 s · 최대 다섯 시도. `merge-base` 실패 (origin 이 앞섬) · 거부 (non-fast-forward · 정책) 는 재시도하지 않고 멈춰 묻는다.

353: ## 9. 예산 · 시간
354: 
355: | 구간 | 상한 | 근거 |
356: |---|---|---|
357: | p 탐침 | 생존 관측 `t_ret` + 10 s · 끝 관측 `t0` + 300 s | §5-1 |

361: | 감시 호출 | 조각 6,600 s (셸 도구 배경 실행 상한 7,200 s 안) · c · e 는 한 번 · f 는 많아야 두 번 | 외곽 도구 `WAIT_SLICE_S` |
362: | 전체 | T_a (a0) → g3 의 push 가 실제로 돌아온 시각 ≤ 21,600 s · R = 1,800 s · 예산 변경 0 | `00_overall.json` · §109 |
363: 
364: - **착수 조건:** wrapper 는 `epoch + 감시 여유 ≤ T_end − R` 일 때만 launcher 를 띄운다 (넘으면 외곽 오류 · launcher 없음 · 그 단계 미완). 그래서 **f 는 T_a +
365:   7,200 s 안에** 시작해야 한다 (21,600 − 1,800 − 12,600).
366: - 단계 기한은 관측 상한이지 launcher 가 그 안에 돌아온다는 보장이 아니다. R 은 사용자가 채택한 정책 값이지 정리 · I/O · 네트워크 · 반환의 물리 상한 증명이
367:   아니다. 통제 밖 I/O 등으로 T_end 를 넘으면 실제 시각과 미완 사유를 남기고 준수를 주장하지 않는다 (§7-5). g3 뒤의 결과 § · 발송문은 예산 밖의 문서이고 실행이
368:   없다.

370: ## 10. 밝힐 것 (공개 한계)
371: 
372: 1. **F2 — 장시간 관리:** 세 단계를 셸 도구의 호출에서 떼어 놓으려는 방식이다. 셸 도구 관리자 · 세션 · 컨테이너의 장시간 수명에 대한 영향은 미확인이고, 탐침의
373:    성공이나 분리 명령의 채택만으로 7,200 s · 10,800 s 의 동작을 보증하지 않는다. run 도중 세션 · 컨테이너가 끝나면 run 과 기록을 잃는다 → 멈춤 · 재시도 없음.
374: 2. **잔류 식별:** 표지 (세션 id · pycache 경로 · `<E>` 경로) 밖의 프로세스는 보지 않는다. /proc 관측은 원자적이지 않고, PID 재사용은 시작 시각 대조로 줄일 뿐
375:    없애지 못한다.
376: 3. **외곽 도구의 기다림:** wrapper 는 launcher 를 기다리기만 하고 죽이지 않는다. launcher 가 멈추면 wrapper 도 남고, 감시 기한 뒤 R1 이 둘의 그룹을 정리한다.
377: 4. **외부 코드 실행:** E1-3 의 prep 은 받은 `util_LFP.py` (고정 sha) 를 venv 자식 안에서 import · 실행한다. sha 대조가 바이트를 묶지만, 그 코드의 행동을
378:    이 저장소가 검증한 것은 아니다.
379: 5. **두 판정의 관계:** 실행 유효성과 실험 결과는 따로 적지만 독립이 아니다 (§5-3).
380: 6. **읽기 경로:** `add_repo` 는 세션에 저장소를 붙이는 바깥 동작이다. 그 응답의 상태 문장만 기록한다.
381: 7. **승인 문구:** run 의 승인 문구는 launcher 의 `REQUEST` 대로 E1-0b 요청서 경로를 인용한다. 이 요청서와 §NN 의 결속은 상태 문서의 승인 기록이 맡는다.
382: 8. **분리 실행 명령의 셸 의미:** POSIX 목록 · `setsid` · `nohup` · `set -C` 의 공개 의미에만 기댄다 — 탐침 (p) 이 그 첫 관측이다.
383: 9. **E1-0b a2 의 범위:** 그 수용은 봉인된 대조 범위의 기능 종결이고, 실제 자료 성공이 아니다 (§101).
384: 10. **시계 · 파일 시스템:** 시작 창 · 기한 · 관측 시각은 같은 호스트의 실시간 시계 (`time.time()` · `date +%s`) 다 — 시계가 뛰면 틀어질 수 있고 기록될 뿐 막지
385:     못한다. 시작 경로의 경합 해소는 로컬 파일 시스템의 원자적 `link` · `O_EXCL` 의 공개 의미에 기댄다 (이 컨테이너에서 관측한 것은 아니다).
386: 11. **보수적 실패:** poll 5 s 때문에 기한 직전의 게시가 기한 뒤에 처음 관측되면 `late` 다. 도구가 조각 기록 전에 감시를 끊거나 게시 도중 남은 임시 이름이 있으면
387:     run 이 정상이어도 그 단계는 실패 종결된다 — 거짓 수용 대신 거짓 실패를 택한다.
388: 12. **관측 시각의 성격:** `observed_epoch` 는 감시가 자기 기록을 쓰기 전에 찍은 자기 시계 값이다. 게시 완료 시각 · 파일 시각 같은 다른 근거로 앞선 게시를 추정하지
389:     않는다. 끝 기록의 시각은 순서 검사에만 쓴다.
390: 13. **커밋 관문의 범위:** x5 는 git 을 부르지 않고 git 이 쓴 출력 파일 (`SP/e113_commit_*`) 을 읽는다 — staged 집합 · blob 과 검사한 버퍼의 일치를 보지만, git 의
391:     다른 상태 (훅 · 설정) 를 보증하지 않는다.
