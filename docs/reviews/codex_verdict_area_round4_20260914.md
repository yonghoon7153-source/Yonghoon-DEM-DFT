## 1. §3 A — 0/+∞ 경계는 유효하다

### 1.1 baseline을 본다는 것 자체가 부정한 선택은 아니다

**조건부 CONFIRMED.** `docs/area_contract_20260913.md:673`의 사전 고정 규칙을 모든 등록 ID에 동일하게 적용하여 유효한 σ_old>0만 상대변화 정의역으로 삼는 것은 방어 가능하다. 분모가 0/미정인 경우 상대변화가 정의되지 않는 문제와, S3 결과가 유리한 ID만 고르는 문제는 다르다.

그러나 baseline을 "결과와 무관한 입력 상태"라고 부르는 것은 부정확하다. baseline도 계산 결과이고, B_ch는 **baseline이 유효하고 양수인 조건부 집합**이다. 고정 130 전체의 보편적 효과를 추정하는 것이 아니다. baseline의 입력·solver 정책·유효성 기준·재시도 규칙을 정해 놓고 모든 ID의 상태를 보존해야 한다. 어떤 ID가 빠지는지 본 뒤 기준이나 재시도 여부를 바꾸면 이 방어는 사라진다.

따라서 보고 이름은 "등록 130 ID 중 채널 ch의 유효 양수 baseline n건에 대한 중앙 상대변화"가 적절하다. OLD_ZERO/OLD_NONE/PENDING_BASELINE는 별도 절대량·상태 표에 남긴다. 프로그램 예외를 물리적 NO_NETWORK로 바꾸는 현행 구현은 이 논증의 전제를 깨며, R4-01이 바로 그 반례다.

### 1.2 정확한 순서통계 경계

N=|B_ch|≥1, 미정 수 k, 알려진 유한 비음수 변화 M=N−k개를 x₁≤…≤x_M으로 정렬한다. 중앙 순위 집합은 홀수 N에서 {(N+1)/2}, 짝수 N에서 {N/2,N/2+1}이다.

중앙 순위 j에서:

- 하한 값 L_j = 0 (j≤k), 아니면 x_(j−k).
- 상한 값 U_j = x_j (j≤M), 아니면 +∞.
- 홀수는 그 값, 짝수는 두 중앙 값의 산술평균을 취한다.

이것이 모든 가능한 미정값 완성의 중앙값을 감싼다. 고정 ρ에서 `docs/area_contract_20260913.md:699`의 각 라벨이 차지하는 d 구간은 연속이므로, **양 끝이 같은 유효 라벨이면 그 사이 모든 완성도 그 라벨**이다. 결측이 무작위라는 가정은 필요 없다. 다만 B_ch나 ρ를 완성별로 재계산해서는 안 된다.

독립 명세 시험: 경계 3,431종, 완성-라벨 대조 251,935회, 동일 끝점 검증 66,803회, **잘못된 인증 0**. 이것은 문구의 수학 검증이지, 아직 없는 생산 판정기의 통과 기록은 아니다.

| 알려진 값 (%) | N | k | ρ | 하한·상한 중앙값 | 라벨 | 해석 |
|---|---:|---:|---:|---|---|---|
| 2×65, 20×64 | 130 | 1 | 0 | 2, 11 | h0 / h1 | 단 1건 미정도 갈라놓는다 |
| 2×129 | 130 | 1 | 0 | 2, 2 | h0 / h0 | 미정값이 무엇이든 중앙값은 2 |
| 20, 20 | 4 | 2 | 0 | 10, +∞ | h1 / h1 | 정확히 절반 미정이어도 강건 h1 가능 |
| 100, 100 | 5 | 3 | 0 | 0, +∞ | h0 / h1 | 미정이 엄격 과반이면 갈라진다 |
| 6×65, 20×62 | 130 | 3 | 0 | 6, 13 | BOTH_REJECTED / h1 | R3 반례를 v4는 거부한다 |
| 2×65, 20×64 | 130 | 1 | 6 | 2, 11 | UNRESOLVED_NUMERIC / 동일 | 동일해도 과학적 h0/h1은 아니다 |

**k만으로 일반적인 발행 여부를 결정할 수 없다.** k>floor(N/2)이면 하한 0·상한 +∞로 반드시 갈라지지만, 그 이하에서는 알려진 값의 순위와 고정 ρ가 결정한다. "과반이 알려졌다"는 사전 승인도, "미정이 조금 있으니 무조건 거부"도 틀리다.

k가 작아 같은 라벨이 나오는 것은 v2처럼 미정을 무해로 대입한 것이 아니다. 가능한 모든 미정값에서 중앙값 라벨이 같음을 보인 것이다. 이 보증은 **중앙값 라벨에만** 적용된다. 1건의 미정이 물리적으로 작다는 뜻은 아니다.

필수 경계 명시:

> N=0은 EMPTY_DOMAIN으로 보고하며 과학 라벨을 발행하지 않는다. ρ 미정·비유한·음수는 INVALID_RHO로 별도 거부한다. 동일한 오류 상태 두 개는 "동일 라벨 인증"이 아니다. +∞는 순서통계의 상한 기호로만 사용한다.

### 1.3 설정 변경, 다중 판정, 중앙값의 의미

- **REFUSED를 줄이기 위한 사후 조정 차단: 문구만으로는 미보증.** 실패율을 본 뒤 solver·입력 정책을 바꾸면 미정 구성이 달라진다. 등록된 자동 재시도는 허용하되, 결과를 본 뒤 선택한 재시도/설정은 주 분석에 덮어쓰지 말고 별도 버전·추가 분석으로 보존해야 한다. 현행 봉인은 실제 입력과 정책의 완전한 연결도 없으므로 기계적 차단 주장은 REFUTED다.
- **3×2가 독립 검정 6개라는 해석: REFUTED.** 두 경계는 한 채널의 한 불완전 자료에 대한 구간 분석이다. 현재 h0/h1은 확률적 검정의 p값이 아니라 고정 기술 구간 라벨이다. 자동으로 여섯 번의 유의성 보정을 요구할 근거는 없다. 대신 확률적 유의성·오차율 통제를 주장하면 안 된다.
- **A-7이 금지하는 것:** 결과를 보고 OR/다수결/가장 좋은 채널 선택을 새 전체 성공 규칙으로 만드는 것. "전자 채널 h1, 이온 채널 …, 열 채널 …"라는 세 결과의 사실 보고는 금지하지 않는다. 판정기의 출력도 고정 세 채널 벡터로 하고 등록되지 않은 overall_success를 만들지 않는 편이 맞다.
- **중앙값을 당장 바꿔야 하는가: 아니다.** 전형적 설계 케이스라는 estimand와는 맞는다. 66건 0%·64건 100%의 중앙값은 실제로 0%다. 따라서 h0를 "모든 케이스에 무해"라고 쓰지 않고 전 케이스 표·미정 수·꼬리를 병기해야 한다. 꼬리 안전성 자체가 목적이라면 별도 사전등록된 지표가 필요하며, 결과를 본 뒤 주 지표를 교체하면 안 된다.

## 2. §4 봉인 — 새 P1 두 건

### R4-01 [P1] 정상 raw가 세 채널 모두 NO_NETWORK로 바뀐다

같은 6입자·4접촉 합성 raw를 올바른 덱 사상과 경계로 현행 build/solve에 넣으면:

|---|---:|

하지만 실제 sealer main은 ion/electron에 KeyError, thermal에 NoneType 산술 오류를 내고, **세 B_ch를 모두 0개로 만들어 봉인 rc=0**을 발행한다. 미래 허용 분기를 확인하기 위해 날짜만 시험 모듈 안에서 09-17로 주입했다. OS 날짜나 운영 기준일을 바꾸지 않았다.

채널 철자만 고쳐도 빈 type_map·plate 인자 결손이 남는다. 숫자는 합성 함수 결과이며 실제 전극 전도도의 측정값이 아니다. 무너지는 것은 **정상 baseline의 정의역 보존**이다. 기술적 오류를 "물리적으로 망이 없음"으로 숨기면서 primary 집합을 비운다.

필수 대조: 정상 raw→덱 상 사상·경계→세 양수 baseline→B_ch에 해당 ID가 들어감→파일 왕복 확인. 잘못된 채널/읽기 실패/예외는 ERROR 상태와 불완전 진단을 남기되 실행 허가 봉인은 발행하지 않아야 한다.

### R4-02 [P1] 인용한 지문과 소비한 파일·ID 집합이 다를 수 있다

`scripts/seal_s3_prerun.py:102`은 TSV의 case/status만 남기고 raw 경로·SHA·step을 버린다. `scripts/seal_s3_prerun.py:196`의 loader는 현재 폴더에서 파일을 다시 발견한다. 설계 CSV도 해시만 찍고 ID 대조에는 쓰지 않는다.

실제 파일 반례:

1. step 100 atom/contact를 TSV에 봉인한다.
2. 같은 폴더에 step 200을 추가한다.
3. TSV SHA는 불변인데 loader는 step 200을 읽고 sealer는 그대로 rc=0이다.

R4-01 때문에 이 실행에서 "바뀐 σ가 유효 baseline으로 채택됨"까지 증명한 것은 아니다. **다른 파일을 읽는데 봉인 지문은 그대로라는 독립적인 연결 결함**을 증명했다. 철자/인자 수정으로 없어지지 않는다.

또한 실제 함수에서 중복 ID는 마지막 행이 덮어쓰고, 등록 밖 rogue도 허용된다. 현재 TSV의 perc까지 131개를 주 코호트로 순회한다. 빈 TSV와 없는 설계 CSV를 허용일 분기에 넣으면 n_cohort_ids=0·빈 design SHA의 봉인을 rc=0으로 쓴다.

## 5. ρ의 R3-03/04 — 일부는 고쳐졌지만 end-to-end 폐쇄는 아니다

### R4-04 [P2] 동일 정지 기준이 TIGHTEN_NOOP를 통과한다

현대 SciPy의 rtol+atol 동시 경로 수정은 CONFIRMED다. 실제 정지 기준은 1.4142135623730953e−5→1.4142135623730952e−8로 줄었고 해도 비트 동일하지 않았다.

그러나 `scripts/measure_rho.py:226`의 조건은 crit_B < crit_A×(1+1e−12)다. **같은 양수 기준도 참**이다. `scripts/measure_rho.py:92`의 legacy tol 분기는 atol을 함께 줄이지 않는다.

실제 SciPy를 tol→rtol 호환 shim으로 호출한 대조:

    tol A=1e−5, B=1.0000000000000002e−6
    atol A=B=.001
    결속 기준 A=B=.001
    CG info A=B=0, 해 비트 동일

이와 같은 criterion A=B=.001을 갖는 합성 solve_pair 기록을 현행 measure_case 분류기에 공급하면 OK·delta_pct=0이다. 앞부분은 실제 SciPy 호출, 뒷부분은 그 기준값을 반영한 합성 기록 주입을 이용한 분류기 단위시험이며 실제 코퍼스에 이미 이 행이 있다는 뜻은 아니다.

legacy 지원을 유지한다면 결속 절대 기준도 함께 조여야 한다. 양의 유한 criterion에서 **엄격히 줄어듦**과 **등록 factor와의 일치**를 따로 검사하고, 같은 기준을 허용오차 명목으로 통과시키면 안 된다.

### R4-05 [P2] 새 필드 8개가 파일에서 사라진다

`scripts/measure_rho.py:492`의 CSV fieldnames가 옛 18열이고 extrasaction=ignore다. 실제 main을 합성 1행으로 실행하고 CSV를 다시 읽으면 rc=0인데 다음이 전부 없다.

    cg_info_final_A, cg_info_final_B, crit_A, crit_B,
    fallback_A, fallback_B, n_cg_A, tol_gate

요약 JSON도 per-case 필드를 복구하지 못한다. **메모리에서 수집했다**는 것과 **회수한 산출물이 증서를 갖고 있다**는 것은 다르다. 새 필드를 명시적인 행 스키마로 만들고 실제 CLI→CSV 재독입 통합 회귀를 넣어야 한다.

NaN/Inf를 NONFINITE로 분류하는 변경은 실제 분기에서 CONFIRMED다. 그러나 R4-03의 최종 direct 오분류와 이 저장 손실 때문에 "최종 채택 상태·기준이 실제 배포 기록에 보존된다"는 R3-04 전체 폐쇄는 REFUTED다. 과거 저장 30건의 숫자를 이번 반례만으로 모두 잘못됐다고 판정하지 않는다.

## 6. §7 SELF-32 — pandas는 잡았지만 후보 선택 사각지대는 남았다

### R4-09 [P2] 후보 집합을 늘리면 검사가 약해진다

실제 direct 43개와 driver 확장 116파일을 포함하여 pandas가 새 의존 집합에 들어오는 수정은 CONFIRMED다. 원격 CI run 532–535의 로그 자체를 이번에 재검증하지는 않았다.

하지만 `scripts/check_selftest_inventory.py:292`은 전체 AST 모드 direct 뒤에 top-only expanded를 넣고 LIFO로 꺼낸다. `scripts/check_selftest_inventory.py:296`의 seen이 파일만 보므로 약한 검사를 먼저 하면 강한 검사가 생략된다.

실제 함수, 동일 합성 파일:

    direct에만 포함 → {r4_definitely_uninstalled_package}
    direct와 expanded 양쪽에 포함 → 빈 집합

실 리포에서도 expanded를 추가하면 direct에서 발견하던 adjustText/cupy/cupyx/pyamg 네 이름이 사라진다. 그 네 패키지가 선택된 모든 CI flag에서 필수라는 증거는 아니다. **범위 추가가 기존 검사 강도를 보존하지 않는 처리 결함**의 증거다. 파일별 검사 모드를 강한 쪽으로 병합하고 승격 시 재방문해야 한다.

함수 안 필수 import를 사용하는 합성 selftest도 만들었다. 현행 inventory의 실제 run은 rc=0·errors=[]인데 같은 selftest를 실행하면 ModuleNotFoundError·rc=1이다. 따라서 "함수 안 import라 불필요"는 성립하지 않는다. 반대로 모든 선택적 GPU 패키지를 무조건 설치하는 것도 맞지 않는다.

### 9종을 모두 설치해야 하는가

cupy/cupyx/taichi/mph/sklearn/h5py/joblib/docx/pptx의 import를 각 진입 Python 프로세스에서 막고 관련 **실제 19개 flag**를 실행했다. selftest가 띄우는 하위 프로세스까지 강제 차단한 완전한 최소 의존 격리환경은 아니다.

- 18개 rc=0: 해당 import가 선택 경로에 없거나, 의도한 부재 대조/CPU fallback으로 통과했다.
- step6_surrogate 한 개는 optional sklearn 검사 전에 Windows의 하드코딩 python3 실행별칭 문제(rc=9009)로 멈췄다. `scripts/step6_surrogate.py:1328`의 별도 환경 문제이며 Linux CI 실패 증거로 쓰지 않는다. 그 뒤 guard까지 실행 완료했다고 주장하지 않는다.

**9종 전부 필수 설치라는 결론은 지지되지 않는다.** 동시에 optional backend 계산을 검증했다는 뜻도 아니다. CI가 실제 선택한 (파일, flag)별로 성공·의도된 skip·fallback을 기록하고 최소 의존 환경에서 실행해야 한다. 정적 import 감사는 완전한 실행 의존 폐포라고 부르지 말아야 한다. 이번 19개 검사가 전체 116파일의 실행을 인증하는 것도 아니다.
