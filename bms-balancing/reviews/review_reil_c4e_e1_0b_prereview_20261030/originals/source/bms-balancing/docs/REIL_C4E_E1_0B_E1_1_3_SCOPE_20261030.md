## 1. RED 판정 문구 (회신 제안을 그대로 쓴다)

- 다음 요청서의 RED 판정은 `PROPOSED_RED_CRITERIA_KO.txt` (§86) 를 문구로 고정한다:
  - 짧은 요약의 FAILED full nodeid 집합 = 사전 고정 기대 집합 (누락 · 추가 · 중복 없음).
  - 각 nodeid 의 실패 보고서를 파일 경로와 전체 시험명으로 일대일 대조해 최종 예외 종류와 사전 지정 메시지 또는 접두를 확인한다.
  - E 줄 개수 · 첫 E 줄 하나는 판정식으로 쓰지 않는다. 짧은 요약의 메시지 생략 · 줄바꿈 · 순서 · 폭은 판정 조건이 아니다.
  - rc · 기대 실패 수 · 통과 / skip / xfail / xpass · 수집 / 내부 오류 · 중단 · 정리 · 해시 · 기한 · 기록 조건은 따로 모두 만족해야 한다.
- **실행자 규칙 (E1_0_N1 재발 방지):** 요청서가 정한 판정 근거의 위치 · 형식이 실제 출력과 다르면, 다른 위치로 대체하지 않고 그 자리에서 멈춘다. 그 뒤의
  판단은 사용자와 검토자의 몫이다.
- 요청서에는 기대 nodeid 집합 (파일 경로 + 전체 시험명) 과 nodeid 별 최종 예외를 표로 고정한다.

## 2. E1-0b — FUTURE-01 (fetch 의 Git 설정 원천 격리)

- **문제 (§76 FUTURE-01):**
  - fetch 사전 검사 (launcher `fetch_source_precheck` · v5 l.406–417) 는 WORK 문맥에서 `git config --list --show-origin` 과 `ls-remote --get-url` 을 본다.
  - 실제 fetch 는 run 모듈이 새 `data/git` 에서 한다 (`reil_c4e_run.py` l.676–712).
  - 그래서 `includeIf` gitdir 같은 조건부 설정 (예: `data/git` 에만 걸리는 URL 바꿈 · TLS 검증 끔) 이 사전 검사에 보이지 않는다. 사후 검사 (v5 l.420–439) 는
    접근이 끝난 뒤다.
- **권장 A — launcher 가 fetch 자식의 설정 원천을 고정한다 (다섯 모듈 · SOURCES.json 은 바꾸지 않는다):**

  | 부분 | 안 |
  |---|---|
  | 왜 launcher 만으로 되는가 | run 의 fetch 는 `env = dict(os.environ, GIT_ALLOW_PROTOCOL=…, GIT_TERMINAL_PROMPT="0")` 로 자식 env 를 그대로 물려받는다 (l.690). launcher 가 자식 env 에 넣은 설정 원천 변수가 run 의 모든 git 호출에 걸린다 |
  | 자식 env (fetch 단계) | 지금의 정제 (`child_env` — `GIT_SSL_CAINFO` 밖의 `GIT_*` 제거) 뒤에 `GIT_CONFIG_NOSYSTEM=1` · `GIT_CONFIG_GLOBAL=/dev/null` 을 넣고, 필요한 키만 launcher 의 고정 목록으로 `GIT_CONFIG_COUNT` / `KEY_n` / `VALUE_n` 에 넣는다. 시스템 · 사용자 · XDG 설정과 그 안의 `includeIf` 가 모두 빠진다 |
  | 사전 검사 | 같은 env 로 빈 임시 폴더에서 `git config --list --show-origin --show-scope` → 항목이 모두 command line 출처이고 고정 목록과 정확히 같아야 한다. 파일 출처 항목이 하나라도 있으면 멈춘다. `ls-remote --get-url` = 고정 URL 은 그대로 |
  | 사후 검사 | 받은 `data/git` 의 `config --local --list` 를 허용 목록 (`git init` · `remote add` · `fetch --filter` 가 쓰는 키) 과 대조한다. 목록 밖 키 · `include` / `includeIf` 가 있으면 단계 실패. 원격 URL · 유효 출처 · shallow · alternates 검사는 그대로 |
  | E1-0b 대조 | 가짜 HOME · 시스템 설정에 `includeIf "gitdir:…"` 로 URL 바꿈 · TLS 끔을 심은 tmp 저장소에서, launcher 의 fetch env 를 쓰면 그 설정이 보이지 않고 사전 · 사후 검사가 정확한 기대를 낸다. 로컬 git 만 쓰고 네트워크는 0 이다. 기존 env 로는 보인다는 것을 RED 로 보인다 |

- **대안 B (설명만 · 권장하지 않음):** 상속 설정은 두고, 사전 검사를 `data/git` 와 같은 경로의 빈 저장소에서 한 번 더 한다. gitdir 패턴 · 환경에 따라 달라지는
  조건을 모두 재현하지 못한다.
- **함께 정할 것 — 프록시 인증 키:** `GIT_CONFIG_GLOBAL=/dev/null` 이면 사용자 설정의 `http.proxyAuthMethod` (§77 에서 이름만 확인 · 값은 읽지 않음) 도 빠진다.
  - 이 환경의 fetch 는 `HTTPS_PROXY` 와 `GIT_SSL_CAINFO` (유지) 로 프록시를 지난다. 그 키가 없어도 되는지는 이 저장소가 관측하지 않았다.
  - **권장:** 초안 작성 때 그 키의 값 하나만 읽고 (인증 방식 이름 · 비밀이 아님 · 다른 키 값은 읽지 않음), 설정돼 있으면 같은 값을 launcher 고정 목록에 넣는다.
    읽은 값은 요청서에 적는다.
  - 대안: 넣지 않는다. fetch 가 실패하면 E1-2 에서 멈춘다 (재시도 없음 · 승인 한 번을 쓴다).

## 3. launcher 운영 정리 정책

- **지금 (v5):**
  - `run_child` (l.657–691): timeout 이면 그룹 SIGKILL → `KILL_WAIT_S` 10 s 대기 → `group_status`.
  - `group_status` (l.628–641) 는 관측을 먼저 하고 시간을 나중에 본다 (grace 5 s). 살아 있으면 다시 SIGKILL 하고 다시 5 s 관측한다.
  - 공통 절대 기한이 없고, 관측 하나의 길이에 상한이 없다 (요청서 v5 §8 의 18).
- **권장 A — 외곽 실행기의 V3-01 규칙을 launcher 에도 맞춘다:**
  - 정리 단계에 들어갈 때 공통 절대 기한을 한 번 만든다: 원점 + 20 s = 지금의 명목 배정 kill 대기 10 + 그룹 관측 5 + 재관측 5.
  - 모든 루프는 관측을 시작하기 **전에** `지금 < 기한` 을 본다. 기한 뒤에는 그 관측 결과에 따른 즉시 동작 (회수 · SIGKILL) · 비차단 확인 · 기록만 한다.
  - 끝 상태: empty · killed · alive · unverified · unknown (오류 우선). 단계 통과는 empty (+ 기한 안) 뿐이다. 지금도 사후 검사는 empty 만 통과로 본다
    (v5 l.560 — `alive_then_killed` 는 실패). 이 기준은 그대로 두고 기한 규칙만 더한다.
  - 정리 안의 예외는 정리가 잡아 같은 기한으로 비상 동작만 한다 (새 기한 없음).
  - 넘을 수 있는 것은 기한 전에 시작한 /proc 관측 하나이고, 그 길이에는 상한이 없다 (감시 스레드 없음 · 공개 유지).
  - E1-0b 대조: 외곽 실행기의 r3 · r9 · r10 과 같은 종류 — 관측 비용이 있는 가짜 시계 · 늦은 예외 · 기한 뒤 동작.
- **대안 B:** 지금 루프를 두고 명목 배정만 공개한다 — 회신이 요구한 "실제 운영 정리 정책" 을 닫지 못한다.
- **차단 기준 (A · B 공통):**
  - `cleanup.status` ≠ empty · `cleanup.errors` 있음 · 기한 도달 · unverified · 기록 (HEAD · porcelain · 원천 해시 · meta) 실패 중 하나라도 있으면 단계 판정은
    false 이고 멈춘다.
  - `first_error` 는 첫 오류를 그대로 둔다. 판정과 소비자는 `first_error=null` 하나로 성공을 판단하지 않고, `cleanup.status` · `cleanup.errors` 를 본다.

## 4. 오류 수용 기준 (E1-1–3)

- **권장 — 무관용:**
  - 단계마다 launcher 단계 판정이 참이어야 한다: precheck_ok AND child_ok AND rc 0 AND timeout 없음 AND postcheck_ok AND §3 의 정리 · 기록 기준.
  - 하나라도 거짓이면 그 단계에서 멈추고 재시도하지 않는다. 부분 수용은 없다.
- **E1-3 (run) 의 두 판정을 나눠 적는다:**
  - 실행 유효성 = launcher 단계 판정.
  - 실험 결과 = run 의 최종 판정 (`final_verdict` — 사전 판정 AND `record_state` COMPLETE AND 위반 0 → `E3a` COMPLETE · `c4a_gate`).
  - 중지 규칙 · 기록 미완 · 위반으로 INCOMPLETE 이면 결과는 그대로 기록하되 E1-3 은 통과가 아니다.
  - C4-A 로 가는 문은 둘 다 참일 때만 열린다 (그 문을 여는 것도 별도 승인).
- E1-1 (identity) · E1-2 (fetch) 는 판정 하나 (실행 유효성) 다. E1-2 는 사후 검사의 자료 두 파일 sha256 · bytes = 고정값 (`DATA_FILES`) 을 포함한다.
