# COMSOL 미세단락 S1-O 발송문 검토

**판정: S1-O 오프라인 준비 범위로 적합하다.** S0의 미결 8항목과 준비 산출물이 잘 대응하고, 검증 실행 및 S1-P·M·N은 별도 승인으로 분리되어 있다. 설계를 다시 처음부터 짤 필요는 없다. 아래 네 명확화는 S1-O 계약과 비활성 구현에 반영할 조건이며, 아직 요청 중인 산출물이 없다는 이유로 새 결함을 만든 것이 아니다.

이번에 한 것은 발송문과 근거의 검토다. S1-O launcher·consumer·parent를 구현하지 않았고, COMSOL/JVM/컴파일/solve·입력 gate·제공 프로그램·합성 시험도 실행하지 않았다. 원장에 인용된 이전 승인을 현재 요청인 “검토”보다 넓은 작업 권한으로 사용하지 않았다.

## 네 가지 명확화

### S1O C1 비활성 표시와 실행 차단을 구분

**위치 33행.** “실행 가능한 상태로 두되 활성화 금지 표시”는 S0의 비활성 원칙보다 약하게 읽힐 수 있다. S0 후보는 확장자만 바꾼 것이 아니라 main/run/model 진입을 거부하고 실제 runAll·export·실환경 경로를 제거한 텍스트였다.

S1-O에는 구현 구조와 원문 소스를 완성할 수 있지만, 그것이 기능 검증 완료·실행 배치·native-ready를 뜻하지 않는다고 써야 한다. 경고 주석이나 approved=false 문서만으로 실환경 호출이 가능한 parent를 전달하지 않는다. 기본 실행 경로는 승인·release 부재에서 COMSOL 시작과 runtime 쓰기 전에 거부하도록 설계하고, 실제 승인/release/token/runtime은 생성하지 않는다. 추후 활성화에 바이트 변경이 필요하면 새 바이트·manifest·승인 결속을 다시 확정한다.

이는 악성 동작을 막았다는 실증이 아니라, 오프라인 후보의 수용 조건이다. 이번 합성 검증 0 조건도 그대로다.

### S1O C2 readback을 구성과 초기화와 완료로 분리

**위치 31–32행.** “실행 직후”만으로는 설정 불일치를 runAll 뒤에 발견할지, solve 전에 막을지가 불명확하다. 다음 세 시점을 구분해야 한다.

1. 구성 후 solve 전: 입력 설정·선택영역·단위와 확인 가능한 생성식/계수 연결.
2. 일관 초기화의 명시한 t=0 또는 0+ 상태: 전극별 평균/표면 조성, 고체·전해질 재고, 전위·전류.
3. 완료 후: 실제 시각·저장·guard·결과·외부 종료 기록.

설정 문자열 readback과 실제 생성식에서 소비된 유효 계수는 다른 증거다. 설치본 변수명/API가 아직 확인되지 않으면 이름을 추측해 “확인”으로 채우지 않고 OPEN으로 남긴다. 초기화만 따로 실행하거나 solver를 나눠야 한다면 추가 호출·비용·승인 영향을 명시한다. 별도 solve를 숨겨서는 안 된다.

S1-O 완료는 이 검사 순서와 실패 경로를 설계했다는 뜻이다. 유한 σ 초기화가 실제로 통과했다는 뜻이 아니다. P는 높은 σ 한 점이므로 near-zero와 유한 세 점의 초기 재고 일치 실측까지 P에서 끝났다고 쓰지 않는다.

### S1O C3 near-zero와 초기 시각에 엄격한 부호를 강제하지 않음

**위치 36행.** near-zero를 상대오차 분모에서 빼는 것에 더해, 부호 판정에도 절대 허용 범위를 적용해야 한다. S0 축약값에서 기준 σ=1e−20의 누설은 약 1.49e−15 A/m²이며 1시간 ΔxN은 약 5.5e−17 수준이다. 이를 모든 저장 시각에서 엄격한 N 감소/P 증가로 요구하면 반올림·0 이동량 때문에 정상 기준을 탈락시킬 수 있다. t=0의 qI=qN=qP=0도 정상이다.

계약은 허용 범위 안의 0·작은 양/음 잔차와, 충분히 분해되는 유한 σ의 일관된 이동을 나눠야 한다. 허용 범위를 넘는 역방향 수지 오류와 신호 분해능 부족도 서로 다른 상태로 기록한다. 허용오차를 넓혀 신호를 억지로 수용하는 규칙은 금지한다.

j와 RN/RP의 A/m², I의 A, q의 C/m² 또는 C를 통일해 비교한다. A_c=1이라 숫자가 같아도 단위를 생략하지 않는다. qI의 수치 적분 격자·기법·허용오차도 고정해, 성긴 출력의 적분 오차를 물리적 Li 비보존과 혼동하지 않도록 한다.

### S1O C4 중지 요청과 강제 종료의 의미를 명시

**위치 37행.** “terminate → grace → kill”은 Windows에서 모호하다. TerminateJobObject는 프로세스가 처리하거나 지연할 수 없는 종료이므로 graceful 요청으로 사용하면 안 된다. [Microsoft TerminateJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject).

권고 계약은 “지원이 확인된 협조적 중지 요청 → 정해진 대기 → 남은 소유 Job 강제 종료 → 종료 확인”이다. 협조적 중지 수단이 없으면 없다고 적고 승인된 강제 종료 경로를 제안한다. 소유 증명 없이 이름이 COMSOL인 프로세스를 일괄 종료하는 fallback은 두지 않는다. 대기·종료 확인도 전체 예산 안에 포함한다.

RSS/working set, 프로세스 private commit, 시스템 commit, 디스크 증가의 측정 대상·범위를 구분한다. 주기 관측의 최대값을 실제 순간 peak 또는 OS 강제 상한으로 부르지 않는다. 감시 실패·샘플 누락·Job 결속 실패·종료 미확인 때의 판정도 필요하다. Job 정책은 알림만 주는 경우와 실제 제한을 강제하는 경우가 다르다. [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

이 문구 정정은 지금 Job API를 시험하거나 새 native 제어기를 실행하라는 지시가 아니다. 기존 재사용 제어부와 새 변경부를 구분하고, 필요한 검증을 다음 승인안에 포함한다.

255개 공통 시각은 187+50+18로 맞는다. 401개는 3600초 주 실행의 요청 수여서 모순되지 않는다. 전극별 241개 출력 좌표는 메시 요소 수나 입자 해상도와 구분한다.

120초 pilot이 300초 이후 cap을 검증하지 못한다는 제한을 요청문이 이미 인정한다. 이를 다시 결함으로 지적할 필요는 없다. 다만 해소안은 후기 대조의 단계·σ·fresh 시작점·끝시각·비교 설정·고유 실행 수를 명시해야 한다. 120초 네 번 안에 숨은 추가 solve를 넣지 않는다. 짧은 후기 대조를 2700–3600초 기울기 및 3600초 종점의 K로 대신하지 않는다. 동일한 한 번의 후기 실행이 K와 정책 대조를 모두 충족하면 재사용 조건을 명시해 중복 계산을 피할 수 있다.

## 검증 계획과 시간 경계

새 검증안에는 사례별 실제 대상 함수·엔진·버전/식별·횟수·시간/디스크 상한·양성 대조·정확한 거부 이유와 도달 단계를 적는다. Python에서 다시 쓴 parent 판정 모형만으로 PowerShell 생산 함수를 검증했다고 세지 않는다. 모듈 import 부작용, 실환경 경로 쓰기, 실제 승인 생성 및 native 위임이 fixture에서 차단되는지도 포함한다.

요청문의 “COMSOL 없이 가능한 것”은 다음 검증안의 범위이지 현재 JVM·컴파일 허가가 아니다. 이번 S1-O는 해당 실행 0을 유지하고, 향후 JVM helper·PowerShell·OS 자식/Job 시험이 필요하면 종류별로 별도 승인 여부를 명시한다. 기존 389개 등 전체 suite를 자동 반복하지 않는다.

“시간을 충분히”는 3600초 상한을 넘길 권한이 아니다. 작성1800·정적600·설계900·전달300의 원점, 단계 전환, 포장·재읽기·manifest 기록·최종 반환 전 snapshot의 경계를 미리 정한다. 내부 snapshot과 도구 wall time을 더해 종결 시간을 만들지 않는다. 최종 전달/미완 기록을 위한 시간을 예약하고, 상한이 가까우면 새 작업을 시작하지 않는다. 이 3600초는 향후 S1-O 예산이며 이번 사전 검토나 native 예산과 혼합하지 않는다.
