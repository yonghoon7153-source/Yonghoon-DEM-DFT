# ADR 0048 — 데이터가 늘어도 화면은 빨리 열린다: 업로드는 서버를 붙잡지 않고, knee 는 디스크에 남는다

- 상태: 채택 (2026-10-23)
- 관련: ADR 0019 (EIS), ADR 0021 (knee onset), `apps/api/app/memo.py`, `apps/api/app/deps.py`,
  `apps/api/app/routers/runs.py` · `eis.py` · `gitt.py` (업로드), `apps/api/app/settings.py`
  (`knee_dir`), `tools/backup.py`

## 맥락

랩: "데이터를 많이 넣으니까 약간 늦어지는 것 같다" — 다시 물으니 "화면 열 때가 느린 것 같다".

랩 데이터는 이 컨테이너에 없다. 그래서 합성 데이터를 진짜 업로드 경로로 채워 화면이 부르는 요청을
쟀다 (4 코어 컨테이너).

- 처음 판: 셀 40·80 (셀당 150 사이클), EIS 300·600 장 (맞춤 하나씩), 대칭셀 온도 스캔 30·60,
  GITT 15·30. 화면 요청 대부분은 0.5 초 아래였다 — 셀 라이브러리 0.13·0.24 초, EIS 대시보드
  0.18·0.31 초, EIS 라이브러리 0.26·0.44 초. 데이터에 비례해 늘지만 아직 빠르다.
- 랩에 가까운 판: 셀 40 (셀당 400 사이클 — 랩의 긴 시험), EIS 300 장에 맞춤 셋씩, SOC 스캔
  (스윕 20)·온도 스캔 (스윕 9), 재료 상수를 적은 GITT.

늦은 것은 둘이었다.

1. **업로드가 서버 전체를 멈춘다.** 업로드 라우트 셋이 `async def` 였고, 파싱·맞춤을 이벤트
   루프 위에서 돌렸다. 서버는 프로세스 하나다. 업로드 화면은 파일마다 `fit=auto` 를 보내고, 그
   맞춤이 한 장에 전고체 풀셀 25 초 · 대칭셀 11 초 · 온도 스캔 7 초 · 액체 3 초다. 실측: 업로드가
   도는 동안 다른 요청의 `GET /api/samples` 가 0.13 초에서 **25.6 초**가 됐다. 전고체 풀셀 스무
   장이면 8 분 동안 모든 화면이 멈칫거린다 — 같은 서버를 쓰는 다른 사람 화면도.
2. **서버가 다시 뜬 뒤 첫 충방전 대시보드가 셀마다 knee 를 다시 센다.** `bml` 은 pull 할 때마다
   서버를 다시 띄우고, 대시보드는 앱을 열면 처음 뜨는 화면이다. 셀 40 · 셀당 400 사이클에서
   첫 요청이 **9.08 초**였다 (그 뒤는 메모리 캐시로 0.49 초). 그리고 메모리 캐시는 128 개였다 —
   셀이 128 개를 넘으면 이름순으로 도는 대시보드가 한 번도 못 맞힌다 (순서대로 훑으면 늘 방금
   밀려난 것을 찾는다). 그때부터는 30 초마다 다시 부르는 그 화면이 매번 모든 셀을 다시 센다.

## 결정

1. **업로드 라우트는 일반 함수다.** FastAPI 가 스레드에서 돌리고, 이벤트 루프는 그동안 다른 요청에
   답한다. 업로드끼리는 자물쇠 하나 (`deps.one_upload_at_a_time`) 로 예전처럼 한 줄로 선다 — 같은
   바이트의 중복 검사와 삽입 사이에 다른 업로드가 끼거나, 사이클 번호 다시 매기기가 섞이면 안
   된다. 맞춤은 쓰기 트랜잭션 밖에서 돈다 (`_run_fit` 은 다 맞춘 뒤에 행을 넣고 곧바로 커밋한다) —
   맞추는 25 초 동안 SQLite 쓰기 잠금을 쥐고 있지 않는다.
2. **knee 의 답은 디스크에도 남는다** (`data/knee/<지문>.json`).
   - 키는 입력 전부의 sha256 지문이다 — 사이클·용량의 float64 바이트, 옵션, 그리고
     `wrdkit/knee.py` 소스와 numpy 판. knee 코드가 바뀌면 옛 답은 저절로 안 쓰인다. "고치면
     상수를 올려라" 같은 규칙은 잊히므로 소스 자체를 키에 넣었다.
   - 메모리에는 4096 개. 키가 32 바이트 지문이 돼서 넉넉히 둘 수 있다.
   - 디스크는 4000 개 상한이다. 구동 중인 셀은 사이클이 늘 때마다 새 답을 남기므로, 넘으면 가장
     오래 안 쓴 것부터 지운다. 지워진 답은 한 번 다시 셀 뿐이다.
   - JSON 이다. 들여다보고 의심할 수 있어야 캐시다. 돌려받은 답이 계산한 답과 JSON 글자 하나까지
     같은지를 테스트가 고정한다 (NaN 이 낀 입력까지).
   - 계산 캐시라 백업하지 않는다 (`tools/backup.py` 는 원본과 데이터베이스만 옮긴다).

## 대안

- **맞춤을 업로드 뒤로 미루기 (백그라운드 큐).** 업로드는 빨라지지만, 화면이 "맞추는 중" 을 알아야
  하고 실패를 어디에 보일지 새로 정해야 한다. 랩이 짚은 것은 "화면 열 때" 라 이번에는 하지 않았다.
- **맞춤의 시작점을 여러 코어에 나누기.** 맞춤 시간의 99 % 가 시작점 34–38 개 훑기이고 (전송선
  회로), 그것들은 서로 독립이라 결과는 같고 코어 수만큼 빨라진다. 업로드 속도의 일이라 미뤘다.
- **knee 를 데이터베이스에.** 표가 하나 늘고 무효화 규칙이 필요하다. 지문 키는 무효화가 필요 없다.
- **서버를 여러 프로세스로 (`--workers`).** 메모리 캐시와 실시간 알림(live)이 프로세스마다 갈린다.

## 결과

- 업로드가 도는 동안에도 화면이 답한다. 테스트가 맞춤 자리에 2 초 잠을 넣고 그동안 셀 목록을
  부른다 — 옛 코드에서는 2.02 초를 기다렸고, 이제는 곧바로 온다 (`test_busy_uploads.py`).
- 서버가 다시 떠도 첫 대시보드는 knee 를 다시 세지 않는다. 셀 40 · 셀당 400 사이클: 9.08 초 → 0.68
  초 (디스크에서 40 개). 셀이 128 개를 넘어도 매번 다시 세지 않는다.
- 대가: 업로드와 다른 쓰기가 이제 동시에 돈다 (전에는 업로드가 끝날 때까지 다른 요청이 서 있었다).
  업로드의 쓰기 트랜잭션은 짧아서 SQLite 의 기본 잠금 대기 (5 초) 안에서 풀린다.
- 대가: 맞춤이 도는 동안 다른 요청은 CPU 를 나눠 쓴다 (GIL). 멈추지는 않지만 조금 느려진다.
- `data/knee/` 가 생긴다. 지워도 된다.

## 보완 1 (2026-10-23) — 수치 라이브러리의 스레드는 하나

랩에 가까운 판으로 화면마다 다시 재다가, 스펙트럼 상세 화면이 데이터 양과 상관없이 느린 것을
봤다 — 처음 1.2 초, 다른 일이 같이 돌 때는 4 초가 넘었다. 시간은 DRT λ 훑기(`/drt/sweep`, BVLS 일곱
번)에 있었고, 그 안의 `numpy.linalg.lstsq` 하나가 260×93 행렬에 65.8 ms 였다.

까닭은 계산이 아니라 **스레드**다. numpy 의 OpenBLAS 는 기본으로 코어 수만큼 스레드를 띄우는데, 이
앱의 행렬은 작고 서버는 요청마다 스레드를 따로 쓴다. 작은 계산 하나에 스레드 여럿이 붙어 서로
기다리고, 다른 요청이나 업로드의 맞춤이 같이 돌면 더 나빠진다 (업로드가 이제 스레드에서 돌므로
결정 1 이 이것을 키울 수 있었다).

**결정:** 서버 패키지(`apps/api/app/__init__.py`)가 numpy 를 import 하기 전에 `OPENBLAS_NUM_THREADS`
· `OMP_NUM_THREADS` · `MKL_NUM_THREADS` 를 1 로 둔다. `setdefault` 라 밖에서 준 값이 이긴다.

**결과 (4 코어):** lstsq 65.8 → 2.25 ms, DRT λ 훑기 1.0 → 0.044 초, 스펙트럼 상세 첫 열기 1.21 →
0.41 초 · 다시 열기 0.37 → 0.08 초. knee 는 이것으로 빨라지지 않았다 (9.64 → 8.87 초) — 그쪽은
`curve_fit` 과 파이썬 반복이 시간을 쓴다. 그래서 결정 2 가 따로 필요했다.
