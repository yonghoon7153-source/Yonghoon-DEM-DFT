## 5. 러너가 화면 · 로그에 σ 를 찍는가 (코드에서 확인)

- 결과 σ 는 기본이 가림이다. payload 는 `--show-results` 가 없으면 σ 자리에 봉인 표지를 찍는다: `scripts/mpm_webapp_payload.py` 1097–1103 행 (규칙) · 1154–1162 행 (`_blind` · `_sig_str`) · 2716–2720 행 (σ_e 결과 줄) · 2757–2766 행 (집전체 시나리오 줄). dof · 잔차 · 초는 가리지 않는다.
- 러너는 킷이 SDCP 기본 둘이 아니면 봉인도 원값 덤프도 돌리지 않는다: `scripts/sdcp_gain_vox015_8arm.sh` 1007–1011 행. 원값 표를 찍는 가지 (1051–1055 행) 는 기본 킷 + 팔 수가 8 이 아닐 때만이라 `KITS=kit_SBE_vgcf100` 에서는 닿지 않는다.
- 이 컨테이너에서 같은 축으로 실제 러너와 실제 payload 를 픽스처 킷에 돌려 확인했다 (시험 R1b · R1c · R2c): 화면에 봉인 표지가 있고, 팔 JSON 의 σ 류 수 (유효숫자 8 자리) 가 러너 로그에 없다.
- 그래도 로그에 수가 남는 자리가 셋 있다. 입력 σ_VGCF 는 찍힌다 (러너 779 · 902 행 · 등록 값 1e4 에서 직경 보존으로 나온 입력이지 결과가 아니다). 실패 경로에서는 팔 검사 사유가 찍히는데 (러너 951–959 행), σ 가 유한한 양수가 아닐 때 그 값이 사유 글에 들어간다 (`scripts/run_contract.py` 1783 행). 미수렴 때 증서 실패 줄에는 상대 Δσ 가 찍힌다 (`scripts/step3_sigma.py` 2363–2365 행).
- 그래서 묶음에는 runner.log 원본을 넣지 않는다. 걸러 낸 줄 (다시 적은 수치 진단 + 수를 가린 실패 줄) 만 넣는다. runner.log 는 로그 폴더에 그대로 두고 sha256 만 meta 에 적는다.
- 반복 수와 판 전류 불균형은 러너 화면에 없다 (팔 JSON 에만 · §4). kgy 명령 문서 `docs/reviews/rint2_kgy_commands_20261020.md` §2-2b 의 "러너 화면의 반복 수 · 판 전류 불균형 줄" 은 화면이 아니라 이 판독기의 표로 읽어야 한다.

## 6. maxiter 제안과 근거

조수 제안 = 400000 → **결정 (본 세션 11-10) = 1500000** (블록과 원장 줄에 이 값).

- 결정의 까닭: 아래 산술로 필요한 수는 rtol 1e-12 주 풀이 기준 18 만 초과 121 만 이하다. 400000 은 N8 이 5.4 만–6.6 만 이하일 때만 모이고 (N8 의 범위 3 만–20 만의 아래쪽), 한도에 닿으면 필요한 반복 수를 얻지 못한 채 최악 2 배를 쓴다. 1500000 은 그 위 끝을 덮는다.
- 1500000 의 비용 [추정]: 모이면 그 반복 수만큼만 돈다 (한도가 커도 더 돌지 않는다). 아래 시간 어림 (반복당 0.10 초는 위 한계) 으로 필요한 수가 18 만–121 만이면 주 풀이 약 5–34 시간이다. 안 모이면 최악 300 만 반복 (약 83 시간) 이고, 그 전에 블록이 찍어 주는 stop early 줄로 멈출 수 있다.
- 아래 표와 산술은 제안 때의 글 그대로다.

| 후보 | 근거 (파일 · 줄) | 걸리는 점 |
|---|---|---|
| 200000 | 러너 주석의 예시 (`scripts/sdcp_gain_vox015_8arm.sh` 320 행). σ_VGCF 7854 꼴 (대비 785,400 배 · rtol 1e-8 · 08 월 침대 · 접합 없음) 이 30000 에서 못 모이고 (`scripts/step3_sigma.py` 481–486 행) 200000 에서 모였다 (`docs/reviews/a_track_verdict_20260829.md` 51 · 61 행). 등록 스윕도 이 값을 썼다 (`docs/reviews/sigma_closure_sweep_prereg_20260902.md` 173 행: 모이는 점에는 영향 없음) | 아래 산술로는 필요한 수의 아래 끝 근처다 |
| 400000 | 다음 세대 꼴 (섬유 7,853.98 · AM 0.0041 · 접합 R_j 1e6 · rtol 1e-14 까지) 을 실제로 푼 유일한 자리인 증서 봉인 표의 한도 (`scripts/step3_conv_cert.py` 110 행 `PROBE_MAXITER`) | 합성 41,472 dof 표의 한도다. 실침대를 보증하지 않는다 |
| 1000000 | 문서 근거 없음 (아래 산술의 위쪽을 덮으려는 값) | 안 모이면 낭비가 가장 크다 |

- 산술 [우리 산술 · 추정]: σ_VGCF 7854 꼴의 rtol 1e-8 반복 수 N8 은 30000 초과 200000 이하다 (위 두 기록). 합성 표의 반복 비 (접합 꼴 rtol 1e-12 는 접합 없는 꼴 1e-8 의 6.05 배 · 1e-14 까지는 7.37 배 · 등록 R §10-4 표) 를 곱하면 필요한 수는 18 만–22 만 초과, 121 만–147 만 이하다. 200000 은 그 아래 끝이고 400000 은 N8 이 5.4 만–6.6 만 이하일 때까지 덮는다.
- 이 산술의 약한 곳: N8 의 근거는 다른 침대 세대 · 다른 AM σ 의 기록이고 (대비 785,400 배 · 지금 꼴은 7,853.98 / 0.0041 = 약 192 만 배), 반복 비는 합성 침대의 것이다. 실침대는 더 클 수도 작을 수도 있다. 이 탐침이 재려는 값이다.
- 한도에 닿으면 얻는 것 (실물로 확인 · 시험 R3): 주 풀이가 한도에서 끝나고 (`cg_iters` = 한도 · `cg_info` = 한도) payload 가 팔을 `.failed` 로 킷 런 폴더에 남기며 러너는 받아들이지 않는다. 판독기가 거기서 반복 수 · 잔차 · 불균형 · 시간을 읽는다 (rc 3). 반복당 시간은 나오지만 필요한 반복 수는 안 나온다.
- 한도에 닿을 때의 비용 (실물로 확인 · R3): ⓒ 이어 풀기는 주 풀이가 안 모여도 같은 한도로 한 번 더 돈다 (`scripts/step3_conv_cert.py` 216 행 · `scripts/step3_sigma.py` 2347–2351 행 · 픽스처에서 한도 2 일 때 이어 풀기 반복 수 2). 최악은 한도의 2 배 반복이다.
- 시간 어림 [추정]: 10-20 SDCP 최종 16 팔의 DBE 팔 (접합 없는 꼴 · rtol 1e-8) 이 30000 반복을 3,054 초 안에 돌았다 (`docs/session_20260923_progress.md` 1130 행 · raster 포함이라 반복당 0.10 초는 위 한계). 그 값이면 20 만 반복 약 5.6 시간, 40 만 약 11 시간이고 최악 (2 배) 은 그 두 배다. 발사 전에는 모른다.
- GPU 경로의 전처리는 Jacobi 고정이다 (`scripts/step3_sigma.py` 485 · 580 행). AMG 는 CPU 경로뿐이다.

- 합성 폴더는 실제 러너가 쓴 팔 JSON · 영수증 · 화면 줄의 꼴을 본떴고 (이 컨테이너의 픽스처 킷 런에서 옮김) σ 류 자리마다 표식 0.00713331… 을 심었다. 판독기 화면 · 보고 JSON · 걸러 낸 로그 · 묶음 어디에도 그 표식이 없는지를 본다.
- 감시 셸의 멈춤 조건 14 가지는 종료 코드와 함께 화면의 STOP 줄이 그 사유인지를 본다 (F08). 다른 사유로 멈춘 것은 통과가 아니다.
- 감시 셸 변이 (묶음 W · 고를 때만 = `--only W` · 게이트 기본 실행에 없다): 감시 셸을 한 군데씩 망가뜨린 사본 20 개로 F 묶음을 통째로 다시 돌린다. 20 개 전부 잡힌다 (변이마다 잡은 검사 이름이 화면에 나온다). 한 번에 883 초 (약 15 분 · 다른 가벼운 검사와 함께 돌린 값) 라 게이트에 넣지 않았다. 첫 실행에서 하나 (핀 작업 트리 밖의 사본도 받음) 가 살아남았다. 밖의 사본으로 돌리는 멈춤 조건이 시험 대상이 아니라 이 폴더의 감시 셸을 부르고 있었기 때문이고, 시험을 고친 뒤 잡힌다.
- 실물 묶음 (R) 은 `scripts/test_rint_r_chain_e2e.py` 의 픽스처 침대와 `scripts/test_ca_ext_runner.py` 의 가짜 python3 (규율 관문 둘만 건너뜀) 을 그대로 쓴다.
  - R1: 등록 축에서 백엔드만 cpu 로 바꿔 러너를 직접 돌리고 판독기가 실물 꼴을 읽는지 본다. R1h 는 생산 킷 꼴 (payload 줄에 `--joule-heat` · `--save-step4-grid`) 이 payload 입구에서 거부되는 것을 본다 (감시 셸 멈춤 조건의 근거).
  - R2: 감시 셸을 등록 축 그대로 (GPU 기대 · 폴백 금지) 돌린다. 이 기계에 GPU 가 없어 cupy 자리에 numpy · scipy 로 이은 대역을 둔다. payload 의 GPU 풀이 가지가 그대로 돌고 러너가 팔을 받아들인다. GPU 계산은 아니다. S0 계획은 실제 계획에서 입력 지문만 픽스처 침대의 것 (S0 도구 `scripts/ca_s0_census.py` 의 `kit_input_record` 가 낸 값) 으로 바꿔, 같은 침대 대조가 실제 두 생산자 (S0 도구와 payload) 사이에서 서는지 본다. R2e 는 같은 팔을 실제 계획으로 읽어 다른 침대로 잡히는지 본다.
  - R3: 같은 자리에서 한도 2 로 돌린 미수렴 실물. R4: cupy 는 불러와지지만 풀이 모듈이 없는 기계. payload 가 CPU 로 내려가지 않고 멈춘다 (`scripts/step3_sigma.py` 583–594 행).
- 시험하지 못한 것: 진짜 GPU 풀이. 실침대 크기 (팔 JSON 수십 MB 이상) 에서 판독기가 걸리는 시간. `/usr/bin/time` 이 있는 기계의 경로 (이 컨테이너에는 없다. 그 파일을 읽는 함수는 합성 파일로 시험했다). kgy 의 nvidia-smi 출력 꼴 (가짜 nvidia-smi 로 시험했다).

## 8. 한정 · 이 탐침이 닫지 않는 것

- 원장 밖에서 돈 그림자 런을 기계적으로 막지 못한다 (원장 §4 그대로). 이 준비물이 막는 것은 감시 셸을 거친 시도 안에서의 일이다.
- S0 단계 1 의 "새 SV 계약이 모두 닫혔다" 는 결론을 이 탐침에서 뽑지 않는다 (원장 §4).
- 탐침은 한 점이다: SBE · arm 0 · R_j 1e6 Ω · P0 · c 0. 사다리의 다른 R_j (바닥 · 천장 포함) · 다른 origin · DBE 침대의 반복 수는 다를 수 있다. 그래서 등록 R 은 maxiter 를 넉넉하게 두라고 한다 (§11 ④).
- 감시 셸이 러너를 띄우기 전에 멈추는 조건 (화면에 `STOP: … (runner not started)` · 종료 코드 2): 인자 꼴 · 로그 폴더가 새것이 아님 · 출력 폴더가 비어 있지 않음 · 출력 폴더 이름에 `_arm1` 없음 · 핀 다름 · 작업 트리가 깨끗하지 않음 · 감시 셸이 핀 작업 트리 밖의 사본 · venv 없음 · 킷이나 압밀 런 폴더 없음 · 킷 런 폴더 이름이 S0 계획과 다름 · 킷 payload 줄에 `--joule-heat` 나 `--save-step4-grid` 가 있음 · 킷 payload 줄에 `--step3-gpu` 가 없음 · nvidia-smi 없음 · cupy 를 못 불러옴 · 여유 메모리 부족. 이때는 아무것도 풀지 않았다. 그 줄을 본 세션에 그대로 전하면 된다. 이런 멈춤을 원장 줄로 셀지는 본 세션이 정한다 (§9 정할 것 6).
- 킷 payload 줄의 두 조건은 헛도는 시도를 막으려는 것이다. `--joule-heat` · `--save-step4-grid` 는 다음 세대 payload 가 입구에서 거부한다 (`scripts/mpm_webapp_payload.py` 942–945 · 1830–1833 행 · 시험 R1h). kgy 의 새 킷은 그 두 토큰을 뺀 것으로 기록돼 있다 (`docs/reviews/rint2_kgy_commands_20261020.md` §1-1 73 · 82 · 83 행). `--step3-gpu` 가 없으면 payload 가 CPU 로 풀고 러너가 그 팔을 받지 않는다 (같은 검사 = `scripts/sr01_stamp_ab.sh` 92 행 · 킷 생성기는 늘 넣는다 = `scripts/mpm_input_from_case.py` 906 행).
- 상태가 VALID_ZERO_TOPOLOGY 나 ELECTRODE_SHORT 이면 그 이름이 곧 σ 의 상태 (0 · 게시 안 됨) 를 말한다. 그때 판독기는 상태 이름만 내고 rc 3 을 낸다. CG 가 돌지 않으므로 반복 수는 없다.
- 실패 줄은 수를 `#` 하나로 가려 보고에 넣는다. 수의 크기 · 자릿수는 남지 않지만 부호와 `nan` · `None` 같은 낱말은 남는다.
- 명령 줄의 입력 값 (0.0041 · 256.6 · 1e4 · 1e6 등) 은 등록 R 에 적힌 입력이지 결과가 아니다. command.txt 와 원장 줄에는 그대로 적는다.
- 판독기는 팔 파일의 값이 옳은지 판정하지 않는다. 수렴 증서의 판정은 payload 와 러너의 계약 검사 (`check_arm`) 가 한 것이고, 판독기는 그 결과 칸을 옮길 뿐이다.
- 감시 셸의 메모리 상한 (기본 = min(46, 시작 때 여유 − 6) GB · 11-06 S0 감시 셸과 같은 규칙) 에 닿으면 러너를 끝낸다. 그 시도는 실패로 보존된다. 시간 상한은 없다.
- 이 준비물은 실행 승인이 아니다. 발사는 1저자 GO 와 원장 줄 커밋 뒤다.

## 9. 문서와 다른 점 · 본 세션이 정할 것 · 미확인

문서와 다른 점 (러너 코드로 확인):

1. 등록 R §10-1 (2) 와 kgy 명령 문서 §2-2b 의 블록은 러너를 킷 뿌리에서 띄우지 않는다 (앞 줄이 다른 폴더로 cd 한다). 러너는 `KITS` 를 현재 폴더 기준으로 찾아 "~/sdcp 에서 돌릴 것" 으로 멈춘다 (`scripts/sdcp_gain_vox015_8arm.sh` 973–974 행). 감시 셸은 킷 뿌리로 cd 한 뒤 띄운다.
2. 같은 블록의 `OUTDIR=~/sdcp/ca1_probe` 는 그대로 쓰이지 않는다. 팔 수가 8 이 아니면 러너가 이름에 `_arm1` 을 붙인다 (594–597 행). 감시 셸은 이름에 `_arm1` 이 든 출력 폴더만 받는다.
3. 러너는 킷 런 폴더에 쓴다: 생성 스크립트 (842 행) · time 기록 (909 행) · payload 출력 (924 행 · 검사 통과 뒤 961 행에서 출력 폴더로 옮김). 킷의 역할 파일은 건드리지 않는다. 같은 이름의 앞 시도 파일은 덮인다 (§3 실패 보존 칸의 사본이 그 대비다).

본 세션이 정할 것:

1. maxiter 값 (§6 · 조수 제안 400000 → 본 세션 11-10 결정 1500000). 바꾸면 블록의 MAXITER 와 원장 줄 초안의 값을 같이 바꾼다 (시험 S04e 가 둘을 대조한다).
2. 붙잡아 둔 상대 칸 넷을 허용 칸에 넣을지. 사슬은 그 가운데 판독 보장 오차 (ⓓ 의 `target_err_bound_rel`) 를 공개 칸으로 둔다 (`scripts/rint_r_chain.py` 2146–2148 행 `ARM_PUBLIC` 의 err_rel). 넣으려면 발사 전에 판독기 표와 시험을 고친다.
3. 감시 셸의 메모리 상한 규칙을 그대로 둘지, 시간 상한을 둘지.
4. 블록의 `BASE` (기준 체크아웃 자리 · 등록 R §10-1 (0) 의 값을 썼다).
5. 원장 §3 줄과 §2 "기계 / 환경" 칸 채우기, `<PIN>` 채우기.
6. 감시 셸이 러너를 띄우기 전에 멈춘 것 (풀이 없음) 을 원장 §3 에 줄로 적을지.

미확인:

- kgy 에 `/usr/bin/time` 이 있는지. 없으면 time 칸은 NONE 이고 표본 RSS 가 남는다.
- kgy 의 nvidia-smi 가 프로세스별 GPU 메모리를 보여 주는지. 안 보이면 "우리 몫" 은 0 이고 전체 사용량은 남는다.
- kgy 킷의 payload 줄이 지금도 기록대로인지 (`--step3-gpu` 있음 · 두 토큰 없음). 아니면 감시 셸이 러너를 띄우지 않고 멈춘다.
- 실침대 팔 JSON 의 크기와 판독 시간.
- 핀에서 러너의 런 전 관문 (규율 검사 · 미정의 이름 검사) 이 kgy venv 로 통과하는지. 본 세션 게이트와 kgy 실행이 확인한다.
