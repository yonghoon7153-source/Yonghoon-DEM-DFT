# Independent challenge of root G5/G6 findings

Reviewed the root-owned `evidence_g56/probe_contracts.py` and `contract_results.json`, then the actual producer/helper/consumer source. I did not edit or rerun root evidence. Its runner fixture substitutes only network file creation; the real helper, merge, validators, provenance, tau helper and grade derivation execute. Thus these are strong integration-level **contract mutation tests**, not proof the unmutated numeric solver currently emits the malformed fixtures.

## 1. Stop-contract failure occurs after irreversible acceptance — sustain

`webapp/app.py:3178` discards the previous network stash after the older channel-content gate; `:3190` stamps the new run success; `:3238`–`:3274` merges and writes its full_metrics. Only afterwards, `:3298`, the network-stop contract executes. A failed stop contract only appends a failed stage and returns (`:3303`–`:3305`); it does not roll back files/provenance/metrics or record the attempt failed.

Root's L9 mutation consequently has summary **failed** (the front-door status is correctly red), yet active provenance is success/valid, full_metrics network_solver_status is success, and old_marker is gone. This is an actual atomic-publication defect, not merely a missing field. Existing comments at `:3148`, `:3154`–`:3158` promise the opposite behavior, and `pipeline_service.py:604`–`:612` document the same category of previously fixed defect.

Severity: P1 for acceptance/rollback integrity once a required gate fails; qualify reachability. The fixed current boundary producer uses L0/L1/L2, so the mutation does not show that normal current solver emits L9. A malformed new result, a merge failure, or another required stop-contract failure is the triggering condition. Do not describe this as a normal successful simulation becoming falsely `done`; it is a failed candidate left as the successful active scientific generation. Minimal fix: validate the complete candidate, including merge and stop gate, before dropping the old stash/promoting provenance, and preserve old full_metrics as well as the four network files. Alternatively explicitly invalidate and retain recoverable old generation on failure; merely changing meta.json status is insufficient.

## 2. Missing tau prerequisites passes network stop — sustain, P2 / scope qualification

`pipeline_service.network_stop_verdict:696` validates dimensional sigma and a narrow subset of fields, not the actual tau dependency closure. `tau_flux.py:185` requires percolating_fraction; `:198` requires mode-specific sigma0/temperature; `:208` requires dimensionless sigma_full; `:141` requires the contact ledger. Root removes network sigma_full/percolating_fraction/temperature_provenance/sigma_grain_S_cm. Real helper reports done; tau correctly reports NOT_COMPUTED/missing_input for both modes.

Counterargument: the request deliberately permits meaningful downstream HOLD states (L1/L2 band fallback, nonpercolation, model below continuum bound). Therefore `network done` must **not** mean every tau row must be numeric/OK. Also the pinned producer writes these network fields on its normal successful path (temperature/sigma0 at `network_conductivity.py:1364`–`:1365`); the malformed fixture is not an observed current numeric run. Nevertheless missing prerequisites are not a physically meaningful HOLD result; they contradict the stated purpose at `pipeline_service.py:649`–`:651` that all handover outputs exist. Require structural inputs and internally consistent statuses, while permitting declared physical/interpretive HOLD states. Grade's 3.0 fallback in this malformed case is a separate legacy-policy consequence, not proof the absent metadata is valid.

## 3. Per-mode physics 99 versus dual 0.15 — sustain, P2 cross-artifact consistency

`network_content_verdict:629`–`:643` reads separate per-mode files, checking each channel's status, but never compares them to dual. The merge intentionally treats dual as authoritative for physics (`pipeline_service.py:116`–`:121`); `network_stop_verdict:681` and `:696` compare full_metrics only against that same dual. Therefore the root counterexample is real: all stages pass while one same-generation artifact says 99 and the other 0.15.

Counterargument: consumers in the probe choose dual so the specific numeric tau/grade answer stays correct. Fresh producer normally emits consistent copies, so this is a trust-model/corruption/mutation hole rather than evidence of a normal solve changing 0.15 to 99. Value equality of full_metrics to the merge source verifies the copy, not independently the solve or generation. Minimal fix: validate common typed fields across legacy/Hertz/per-mode/dual before promotion, with one documented canonical record and explicit mode tags; a generation identifier/hash alone must not replace content consistency checks.

## 4. Stale baseline temperature pairing on network retry — sustain; reachable route exists

`NET_MERGE_KEYS` (`pipeline_service.py:83`–`:106`) omits temperature_provenance and sigma_grain_S_cm. The actual merge purges and copies only that list (`app.py:3238`–`:3243`). Consequently a valid old full_metrics temperature factor survives a newly computed room-temperature sigma. `se_material.sigma_grain_context:251`–`:253` uses the surviving factor as “paired”; `tau_flux.tau2_from_metrics:94`–`:96` divides this sigma0 by the new raw Hertz sigma. Root's factor4 fixture gives sigma0 12 instead of 3, tau2 24 instead of 6, and grade tau 4.8989794856 instead of 2.4494897428. Raw-dual tau remains correct and disagrees with the grade.

Reachability: `app.retry_network:6390` invokes this same helper on existing full_metrics without rerunning contact analysis. The helper's command `app.py:3136`–`:3138` has no --temp-c, hence the fresh numeric solve uses default temperature convention. Existing temperature-tagged imported/previous outputs are a plausible legitimate input; no user tampering is required. Stage E has its own differently named temperature namespace and does not repair a stale baseline key.

Counterargument / scope: a clean LHS run first rewrites full_metrics via contact analysis (`analyze_contacts.py:651`; full pipeline contact → coverage → helper), so the specific seeded stale-temperature condition is **not shown for all 194 fresh LHS cases**. Clean 25°C inputs retain matching default sigma0 and the root healthy control is correct. Grade/COMSOL unification algebra is correct if metadata is correctly paired; the defect is the producer-to-consumer provenance bridge. P1 for scientific provenance on retry/previous-corpus use, or P2 if grading solely against the clean25°C new-batch scope. Minimal fix: own/purge/merge baseline sigma0 and temperature metadata together with sigma, compare mode-specific pairing, and add temperature→room-temperature retry and fresh-room-temperature controls. Do not just disable the temperature correction or replace it with an unconditional 3.0.

## 5. “None + any nonempty power-share reason” nuance

The root internal_solver_exception mutation passes because `network_stop_verdict:707`–`:709` accepts arbitrary noncomputed nonempty status for null power share, exactly as current request §5-2 item④ says. That is an under-specified acceptance policy, not an implementation departure from that item. Distinguish legitimate nonpercolating/not-defined statuses from internal solver failure and require them to agree with sigma/percolation. Recommend P2 contract hardening; do not silently reclassify every null share as failure.

## Bottom line

G5 HOLD is well supported by publication ordering even though the failure summary itself is correct. The other G5 tests expose incomplete/circular receipt-style validation, not observed current producer corruption. G6 HOLD is supported for a reachable retry/imported-metadata path; the clean fresh-25°C LHS path is not shown numerically wrong. This qualification should accompany any claim that the proposed 194-case batch itself is unsafe for the temperature reason.
