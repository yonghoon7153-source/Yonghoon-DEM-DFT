2026-11-24 KST · 정적 문서/소스 검토 · 구현/시험/실행 승인 아님

판정: REVISION_REQUIRED_BOOTSTRAP_ALLOWLIST_CYCLE

v2의 세부 지적 12개 중 11개와 비차단 C2를 문서 범위에서 종결합니다. N3·N4·N6은 종결하고, N1에서는 bootstrap 한 항목만 남깁니다. 기존 N2·N5·N7·C1 종결은 유지합니다. 남은 것은 수집을 시작하기 전에 필요한 허용표와 그 수집이 만들어 내는 허용표 사이의 순환 의존입니다. 이는 문서 절차의 결함이며 실행해 발견한 기능 실패가 아닙니다.

검토 대상은 제출 커밋 c7062ced9c48a97bf47d042882fd79451332adf9의 docs/REIL_C4A_IMPL_REQUEST_v3_20261124.md입니다. 크기 96,546 B, SHA-256 2156f12d35c05c3a41307c4c254ce0bf836f9bdcbc33485c1eba2bb995d71c5b가 발송문과 일치합니다. 아래 요청서 행 번호는 이 바이트를 기준으로 합니다.

1. 남은 지적 — C4A-IMPL-V3-N1 [P2], 기존 N1/bootstrap 잔여

근거: 요청서 198–199, 433, 453–455, 459–460행.

198–199행은 플러그인이 --c4a-allow <ALLOW_A.json>과 --c4a-allow-sha256을 받아 수집 전에 원바이트 해시를 확인하도록 정합니다. 433행은 세 실행에서 그 계수기 인자가 같다고 합니다. 그런데 b0(453행)가 미리 만드는 것은 함수/패턴 기준 ALLOW_A_TABLE.json이고, 실제 nodeid 기준 ALLOW_A.json은 b1 수집 결과(454행)입니다. 따라서 새 폴더에서 첫 b1을 시작할 때 요구된 ALLOW_A.json과 그 해시가 아직 없습니다. 누락을 허용하면 수집 전 fail-closed 규칙이 깨지고, 이전 ALLOW를 재사용하거나 계수기를 끄는 방식도 이 요청서의 봉인/수집 계약과 다릅니다.

정정 방법은 다음처럼 두 입력을 구분하는 것입니다. 파일명은 예시이며 필수 사항은 생성 순서와 소비 결속입니다.

- b0: 함수별 상한표 ALLOW_A_TABLE.json과 별도로, collect/session의 K1–K7이 모두 0인 수집 전용 ALLOW_COLLECT_A.json을 작성하고 각각의 SHA를 BOOTSTRAP_A.json에 봉인합니다. 플러그인은 이 수집 모드를 지원해야 합니다.
- b1: 수집 전용 표와 그 봉인 해시를 실제 인자로 받아 확인한 뒤 수집 1회만 수행합니다. NODEIDS_A.txt와 함수표의 매핑으로 실행용 ALLOW_A.json을 만듭니다. 입력 표의 해시, 수집된 nodeid 집합, 결과 표의 해시를 함께 기록합니다. 매핑 불일치나 허용하지 않은 모듈 건너뜀은 중단합니다.
- b2/c: 실행용 ALLOW_A.json의 고정 해시를 사용합니다. RED와 GREEN에서는 같은 실행용 표를 유지하고, 수집용 표와 혼동하지 않습니다. “세 실행의 인자가 같다”는 문장은 플러그인 옵션 체계는 같되 b1과 b2/c가 소비하는 파일/해시는 다르다는 뜻으로 정정합니다.
- T16의 허용표 검증 명세에 잘못된 모드·해시·표 전용 바꾸기·수집과 실행 표 혼용의 거부를 넣습니다. 지금 새 시험을 하라는 요청은 아닙니다.

대안으로 b0의 봉인된 패턴 표를 수집 모드에서 직접 소비하게 해도 됩니다. 이 경우도 b1 전에 존재하는 입력과 b1 뒤의 정확한 nodeid 표를 구별해야 합니다. 단순히 ALLOW_A_TABLE.json을 ALLOW_A.json으로 이름만 바꾸고 기존 모드/해시 설명을 그대로 두는 것은 해결이 아닙니다. 이 정정은 새 pytest 세션이나 시간 상한을 요구하지 않습니다.

2. 지적별 종결

N1 allowlist — 문서 범위 수용. 함수별 표에 0b1*/0b2의 fork K5와 중단 경로 K4가 들어갔고, git의 K6⊂K3 동시 예약도 명시됐습니다. test_c_8의 두 supervise wave는 고정 소스 774–776행 및 HB stage_a/rho_wave와 맞습니다. launcher 파일의 함수별 숫자를 b0에서 정적 산출하여 수집 전에 봉인하는 방식은 허용 가능합니다. 요청서에 모든 수치를 지금 적어야 한다는 별도 요구는 없습니다. 다만 아직 없는 숫자표까지 검증했다고 하지는 않습니다. b0의 호출 자리·분기/반복 횟수·상한·프로그램 식별은 구현 결과 검토 대상입니다.

N1 coverage — 좁힌 문서 범위를 수용합니다. 수집 전 설치, 기본인자/from-import 감사, 단계 귀속, fork 원장 공유와 시작/종료 결속, spawn/forkserver 차단을 명시했습니다(205–240행). 분리 해석기 내부와 손주 내부 호출은 미계수입니다. 그 경로에서 확인하는 것은 생성·프로그램 식별·종료·그룹 잔류 여부이며, 이 자료로 모든 후손의 K1–K7 호출 상한을 입증할 수는 없습니다. 같은 제한을 CALLS와 결과 요약에 유지해야 합니다. 대상 모듈 밖의 임의 호출까지 막는 보안 경계나 실제 계수기의 완전성을 수용한 것은 아닙니다.

N1 before_call — 215–225행의 잠금→권한/잔여 확인→예약→원 함수, 위반 시 원 함수 미실행, 원장 실패 시 차단, 예외 삼킴의 사후 실패 처리 방향을 수용합니다. 분류/예약과 실제 호출 결과를 분리해 사후 집계를 사전 차단으로 오인하지 않습니다. 구체 구현의 동시성·기록 실패 처리는 아직 시험되지 않았습니다.

N1 bootstrap — 시험/골격/완성 계수기를 b0에서 준비하고, RED에서 계수기 자체 검증의 PASS와 대상 골격의 예상 NotImplementedError를 분리한 점은 수용합니다. 앞 절의 허용표 순환 의존 때문에 이 세부 항목만 OPEN입니다.

N3 distinct — 종결. overflow와 잘림이 모두 0일 때만 원문 고유 수가 exact이고, 그 밖에는 len(keys)+int(overflow>0)를 하한으로 둡니다. 접두사 충돌 T11과 집계의 “잘린 키 기준” 표지가 들어갔습니다(119–152, 350행). 기존 세 기대 dict의 값은 잘림/overflow가 없어 그대로입니다.

N3 retained_bytes — 종결. 키 payload 4,800 B와 객체/계수 개수 제한만 주장하고, 무제한 정수 때문에 전체 고정 메모리 바이트 상한은 주장하지 않습니다. U4의 고정 표현 후보는 미채택입니다. 그 후보의 4,984 B도 Python 전체 메모리 크기가 아닙니다.

N3 stderr — 종결. 1 GiB를 표본 중지 임계값으로 한정하고, 감시→runner P6→run-a 최종 기록 뒤→launcher 자식 종료 뒤→외곽/판정기 최종 확인의 책임을 나눴습니다(134–149, 189, 311–328행). 초과 시 유효성 false·인계 0, wave 사이 P6 실패는 다음 wave 전에 지속 중지입니다. 실제 쓰기 상한은 여전히 없으며 U5는 선택하지 않습니다.

N4 late_completion — 종결. 마지막 완료가 900초 안에 관측된 경우만 루프 안에서 닫고, 관측이 늦으면 완료 하한 초과와 미확인을 구별해 중지합니다(166–177행). monitor의 start 사건(173행)이 H의 지역 t_start(814행)보다 앞서므로 started+wall을 완료 하한으로 쓰는 방향이 맞습니다. 최종 행의 t_end(876–877행)를 쓰는 P5와 T12/T17이 연결됐습니다. 미확인은 실제 초과의 확정이 아니지만 중지 사유로 유지합니다. 정상 실행을 계속하면서 최종 t_end까지 미루도록 바꾸라는 권고는 하지 않습니다.

N4 late_row_validation — 종결. 사유 유무와 관계없이 최종 drain을 포함한 모든 COMPLETED에 같은 판정 함수를 적용합니다. converged/budget의 양의 n_eval·유한 비음수 wall과 solver_error의 n_eval=0을 구별하고, 시간 필드 일치 및 추가 오류 기록을 요구합니다(87–100, 157–162, 306–308행). 정상 행의 0 평가나 wall 누락을 통과시키던 틈을 닫았습니다.

N4 cleanup_gate — 종결. alive/drain/필수 증거 실패가 HB 반환 전에 문자열 global_stop으로 결속되고 이후 runner 호출은 supervise를 하지 않습니다(92–103행). HB의 1109–1120/1168–1174행이 이 문자열을 받아 다음 rho 실행을 막는 구조와 맞습니다. HB가 남기는 완료 대조 사건과 최종 C4-B 인계를 구별한 설명도 유지합니다.

N4 time_boundaries — 종결. 중지 경로의 명목 join 40초와 정상 경로 80초, 별도 drain을 구별하고 이를 반환 wall 상한으로 주장하지 않습니다. 기록 창은 정리/HB 반환 후 t_rec0→D_rec이며, 일찍 끝나면 900초보다 길 수 있다고 명시합니다(466–500행). 300+900+25,800+600+900+300=28,800, 5,400+28,800+1,800=36,000의 산술은 맞습니다. launcher/외곽의 기한은 감독·정리 정책의 경계이며 각 동기 호출과 OS 종료의 실제 반환 상한 인증이 아닙니다. U2와 자식 기한 28,500초는 채택하지 않습니다.

N6 approval_binding — 종결. 단순한 원장 절 존재 대신 종류·긍정 결정·고정 범위·승인된 요청서 경로/SHA를 확인하고, 그 요청서의 결속 블록을 실제 소스목록·입력·시간/자원·경로와 대조합니다(264–286행). T14의 무관/거절/구현 전용/중복/동시 교체/소비값 불일치 부정 사례는 앞 지적에 대응합니다. 사용자 원문의 인용이 승인자의 신원을 독립 인증하는 것은 아니라는 제한도 명시돼 있습니다.

C2 — 종결. 미완 행의 unit은 계획 매핑에서 유도하되 원행에 unit이 있으면 먼저 불일치를 검사하고 원행을 덮어쓰지 않습니다(302–304, 346행). N2·N5·N7·C1의 기존 문서 종결은 유지합니다.

3. 발송문 여섯 질문에 대한 답

Q1: 전부 종결은 아닙니다. 12개 중 11개+C2 종결, N1/bootstrap 한 항목 OPEN입니다.
Q2: launcher 숫자를 b0에서 정적으로 만들고 수집 전에 봉인하는 방법은 수용합니다. 수집 입력/산출 허용표의 구별은 위 N1 정정이 필요합니다. 분리 해석기 내부 미계수라는 제한을 분명히 유지한 좁은 주장도 수용합니다.
Q3: 사전 예약/차단과 자체 검증 우선의 RED 구성은 수용합니다. 별도 최상위 실행 세션을 추가하도록 요구하지 않습니다. 부정 경로는 359–361행대로 하위 pytest에서 수행해야 하며, T16a의 K7 차단 부분도 그 원칙을 따릅니다. 하위 pytest의 예상 실패는 바깥 자체 검증의 PASS와 구분하고, 하위 원장/반환/대상 미진입 근거를 보존해야 합니다. 외부 K3만으로 내부 호출을 세었다고 해서는 안 됩니다. 새 시간 숫자는 제안하지 않습니다.
Q4: v2의 N3 지적을 닫기에 충분한 문서 정정입니다. U4/U5 미채택 상태와 실제 메모리/쓰기 강제 상한 부재는 그대로입니다.
Q5: 보수적 미확인 중지와 최종 t_end 판정을 함께 두는 방향을 수용합니다. P1–P6와 단계 기한의 문서 정합성 수용이며 실제 감시기의 기한 내 반환을 검증한 것은 아닙니다.
Q6: 기존 N6을 닫기에 충분한 문서 결속입니다. 구현 결과에서 정확한 스키마·중복/누락·실제 소비 경로와 부정 사례의 동작을 검토해야 하며 현재 승인 기록을 새로 만들지 않습니다.

4. 입력과 검토 경계

첨부 SEND_READY는 9,148 B / SHA-256 ebd14f641cf2132c8ab8f39befbe6ae008b03273cee85a46a9f68375df3cd847입니다. 저장소의 발송문 v3는 별도 9,640 B 파일이며 같은 바이트라고 주장하지 않습니다.

고정 제출 커밋에서 참조 파일 27개를 원바이트로 받아 Git blob SHA와 SHA-256을 확인했습니다. 기존 로컬 v2 검토 사본과 비교 가능한 24개 중 원장 이외 23개는 동일합니다(문서 4개, scripts 8개, 회귀 시험 11개). 원장은 이전 파일 전체를 정확한 접두부로 보존하고 §130/§131을 덧붙였습니다. 나머지 새 발송문·conftest·util 보존 사본은 이번에 받은 고정 커밋 자료이며 이전 로컬 사본과 동일하다는 주장은 하지 않습니다. util 보존 사본 32,909 B를 실자료 util 33,754 B와 동일 파일로 간주하지 않았습니다.

커밋 비교 응답의 변경 파일 목록은 300개여서 전체 저장소 무변경의 근거로 삼지 않았습니다. 이번 결론의 근거는 명시된 파일별 원바이트 대조와 소스 읽기입니다. 새 계수기·ALLOW 숫자표·runner_a/launcher_a는 아직 구현되지 않았으므로 구현 정확성이나 실제 통과를 판정하지 않습니다. AST 호출 색인은 텍스트 분석 보조이며 동적 호출 수 측정이 아닙니다.

검토용 자료 디코딩 도구에서 처음에 GitHub base64의 개행을 허용하지 않아 입력 형식 오류 1회가 있었습니다. base64 표현의 공백만 제거해 디코딩하고 Git blob 해시로 원바이트를 대조했습니다. 이 검토 보조 도구 정정은 대상 프로그램의 수정/재시험이나 제출자의 중지 조건 실행이 아닙니다. 오류 반환은 REVIEW_TOOL_NOTE.json에 보존했습니다.

이번 수행은 읽기 전용 GitHub 조회, 로컬 문서/소스 읽기·AST/식별 대조, 검토 파일 작성과 포장입니다. 받은 프로그램 import/실행·pytest 수집·기능 시험·실자료 해석·최적화·설치·OS 실험·COMSOL·대상 저장소 변경·외부 발송은 0입니다. 새 검토 시간 예산이나 전체 소요/준수 주장은 없습니다.

다음 제출물은 기존 v1/v2/v3를 보존한 별도 문서 정정본과 N1/bootstrap 응답입니다. N3·N4·N6 및 기존 종결을 다시 실행해 확인할 필요를 이번 회신이 만들지 않습니다. U2/U4/U5 미채택·구현/시험/실자료 실행 미승인을 유지합니다. COMSOL은 사용자의 현재 지시에 따라 보류하고, 사용 가능해졌다고 사용자가 알려준 뒤 해당 범위에서 재개합니다.
