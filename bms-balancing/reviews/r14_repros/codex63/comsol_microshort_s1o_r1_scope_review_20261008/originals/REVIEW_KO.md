# S1O R1 한정 정정 범위 검토

검토일 2026-10-08. 대상 문서 작성일 2026-10-07.

## 결론

**문서 범위 적합. S1O-N1–N4의 좁은 오프라인 정정 계획을 수용한다. 새 차단사항은 발견하지 않았다.** 사용자 별도 승인 후 정정본 작성·정적 확인·검증안 갱신·봉인까지 진행할 수 있는 범위다. 이번 검토 요청은 그 착수 승인이 아니다.

이 판정은 N1–N4의 구현 종결이나 기능 PASS가 아니다. R1 수정 소스가 아직 제출되지 않았으므로 기존 결함의 수정 여부는 후속 소스와 검증으로 확인해야 한다. `native_ready=false`를 유지한다.

## 승인과 검증 경계

- 3행과 §0은 사용자 채택 전 초안임을 명시한다. 현재 “ultra로 봐줘”는 검토 요청으로 해석했다.
- §3 제목은 검증안을 **제시·봉인만 하고 실행하지 않는다**고 명시한다. 35행의 실제 Python 출력→JSON→PowerShell은 후속 기능 검증의 설계 요건이지 지금 실행하라는 명령이 아니다.
- 37행은 기존 98 ID와의 대응 및 새로운 실제 사례 수를 요구한다. 따라서 98개를 유지하기 위해 새 반례를 삭제하거나 기존 양성을 줄이는 안이 아니다.
- §0은 시도 1회, 새 총 2700초를 제시한다. 1200+600+600+300=2700초이며 이전 3600/1500초를 재사용하지 않는다. 문서상 예산 제안의 합계가 맞다는 뜻이지 수행 시간을 관측했다는 뜻은 아니다.
- 코드 import·함수 호출·기능 시험·Java 컴파일/JVM·COMSOL·approval/release/runtime/token 생성은 금지되어 있다. 기능 검증과 S1-P/M/N은 별도 승인이다.
- §5의 `fixed/partial/open`은 정정 결과를 정적으로 보고하는 상태다. `fixed`를 기능 검증 PASS로 바꾸지 않고 `functional_validation=NOT_RUN`을 함께 유지해야 한다.

## 승인문 채택 때 명확히 할 사항

아래는 새 P1/P2나 재심사 사유가 아니라 실행 담당자가 경계를 일관되게 기록하도록 하는 비차단 명확화다. 전체 문서를 다시 만들거나 구현 범위를 넓힐 필요는 없다.

1. **새 폴더와 원점:** 이전 범위 초안은 작업 폴더·횟수·예산을 착수 승인문에서 확정하도록 했다. 이번 문서에는 횟수/예산은 있으나 절대경로는 없다. 사용자 채택 시 실제 새 폴더의 절대경로 한 줄을 추가한다. 존재하면 중지하고 삭제·재사용·다른 이름 자동 fallback을 하지 않는다. 새 monotonic 원점, 단계별 경계, 포장 후 snapshot과 후속 반환 전사의 범위를 `TIMING.json`에 구분한다. 이번 회신에서 임의 경로나 소급 원점을 만들지 않았다.
2. **사례 수 표현:** §0 마지막의 “98 사례 기능 검증”은 “갱신 검증안의 기능 검증(기존 98 ID와 대응 및 새 실제 사례 수 명시)”으로 바꾸면 §3과 더 명확히 맞는다. 실제로는 §3이 이미 새 사례 수를 허용하므로 승인 경계의 모순은 아니다.
3. **N3 범위:** 27–28행의 “유한성·순서·중복·정확 시각”에 “범위”를 추가하면 이전 회신의 교집합 범위 검사와 직접 대응한다. 원회신을 그대로 적용한다고 명시했으므로 현 문서에서 누락된 새 결함으로 세지 않는다.
4. **실행 0의 대상:** §5에서는 “후보/수신 코드 함수·기능 시험·COMSOL/JVM 실행 0”으로 명시한다. 정적 구문 parse·해시·문서 포장 도구의 사용까지 없었다고 기록하지 않는다. 정적 도구가 후보를 import/call하는 경로는 허용되지 않는다.

## 다음 순서

사용자가 범위와 새 기록 경로를 채택 → 실행 담당자가 새 폴더에서 오프라인 R1 정정 → 새 source/manifest/diff/검증안/보존·시간 기록 제출 후 정지 → R1 소스 검토 → 기능 검증 별도 승인이다.

R1 소스 검토와 이후 한정 검증이 통과해도 설치본 및 어댑터 OPEN이 자동 종결되지는 않는다. native는 별도 준비·승인 대상이며 24회/60시간 포괄 승인은 없다. 기존 수용·실패·전체/정상 gate INCOMPLETE·정책/실제 코어 UNVERIFIED는 유지한다.

이번 검토에서는 원본 문서를 수정하지 않았고 후보 소스·시험·COMSOL을 실행하지 않았다. 문서 작성 스킬은 이전 판정의 수용 범위와 현재 승인 경계를 분리한 독립 회신을 작성하는 데 사용했다.
