## 2. 제안 — 첫 항목은 ④ 를 B 단계부터

1. **COMSOL 없이 끝까지 닫을 수 있는 OPEN 은 ④ 하나다.** B (공식 근거 · 비활성 구현 · 한정 검증) 와 E (비-COMSOL 무해 자식 1 · 소유 Job 1) 로 닫힌다. ① ② ③ 은 모두 C 또는 D 의 COMSOL 관측이 있어야 닫힌다.
2. **native 승인의 문턱이다** (의존 2). C · D 도 COMSOL 프로세스를 띄운다. 소유 Job · 표본기 · 중지가 먼저 서 있으면 그 관측을 같은 감시 아래 돌릴 수 있다.
   다만 C 같은 solve 0 의 readback 에도 이 조건이 걸리는지는 문서에 없다 (Q5).
3. 다른 OPEN 에 기대지 않는다.
4. 준비본이 낸 A–E 순서에서 A 다음이 B 다.
5. **표본기 결함은 이 저장소의 다른 흐름에서 실제로 나왔다.** REIL C4 사전 검토의 C4-N2 · N3 이다:
   - 늦게 도착한 성공 표본이 공백을 덮었다.
   - 표본을 모은 뒤 마감을 다시 보지 않았다.
   - 래퍼 · 임시 산출 루트가 합산에서 빠졌다.
   - 비슷한 접두사의 형제 경로를 소유로 봤다.

   같은 유형을 B 의 표본기 규칙과 검증안에 넣었다 (발송문 초안 §2).

## 3. B 단계 범위 요지 (발송문 초안 §0 · §2)

- **기준:** OPEN-R1 정정본 (CODE_MANIFEST `feb12ef6…8ecc` · resource source `f45e6531…5816` · `OS_API_MATRIX.json` `ec3ab0c2…622c`) 과 `_003` 회신 (`879cff57…0d17`).
- **새 폴더:** 하나 — `…/outputs/microshort_s1_os_b_prep_20261013/`. 있으면 중지한다.
- **산출 ① 근거 대응표:** 지표마다 API · class · 구조체 · 필드 → 문서 좌표 → 최소 OS → 등급 (문서 확인 / 못 찾음 / 후보).
- **산출 ② 비활성 후보:** 구성원 handle · PID + 생성 시각 · 구성원 목록 (용량 · 경합) · 구성원 RSS · Job 현재 commit (문서에 있을 때만) · Job commit 상한 설정 / 재확인 · host commit · 주기 표본기 · 소유 산출 수집기 · 중지 순서 (협조 → 한정 대기 → 소유 Job 강제 → 확인). 원본 대비 최소 diff 를 함께 낸다.
- **산출 ③ 변경부 검증안:** 작성만 한다. 가짜 OS seam · 이유 · 도달 · 양성 대조 · 엔진 / 세션 / 예산 제안을 담는다.
- **OS 식별:** 판 · 빌드를 읽기 전용으로 한 번 볼 수 있다 (Q3).
- **상한:** 새 원점 총 3,600 초 — 근거 대응 600 · 후보 작성 1,800 · 정적 대조 600 · 보존 · 전달 480 · 미완 정리 120. 새 폴더 ≤ 50 MiB · 시작 디스크 여유 ≥ 512 MiB (읽기 전용).
- **승인하지 않는 것:** 프로세스 · Job 생성 · OS API 호출 시험 · 기능 시험 · COMSOL / JVM / compile · 설치본 관측 · 정책 · prefs 변경 · 12 GiB 상한 제거 · force-only 채택 · 협조적 중지 인정 · approval / token 생성.
- **대체 금지:** 문서에서 못 찾은 counter (예: Job 현재 commit) 는 OPEN 으로 남긴다. peak · 구성원 합으로 대신하지 않는다.

## 4. 근거 문서를 어디서 읽을지 — 고르실 것

- **(a)** 실행 PC 가 공식 문서 URL 목록만 읽는다. 지난 S1 OPEN 연결부 발송문은 네트워크를 뺐으므로, 승인 전에 그 줄을 바꿔야 한다.
- **(b)** 이 저장소가 같은 URL 목록을 받아 사본 묶음으로 첨부한다. 각 사본에 URL · 받은 시각 · HTTP 상태 · 원 바이트 sha256 을 붙인다.
  - 실행 PC 는 네트워크를 열지 않는다.
  - 사본은 공개 저장소에 넣지 않고 zip 으로만 전달한다. 원장에는 식별만 남긴다.
- **권장은 (b)** 다. 실행 PC 권한 변경이 0 이고, 검토자가 같은 바이트를 볼 수 있다.
- 두 안의 공통 한계: 문서 시점의 서술일 뿐 실행 OS 의 실제 지원 확인이 아니다 (그것은 E).
- URL 후보는 발송문 초안 §1 에 있다. 이 초안은 열어 보지 않았다.

## 5. 그 뒤 순서 (각각 별도 승인 · 이번 범위 아님)

1. B 변경부 검증 — 가짜 OS seam.
2. E — 비-COMSOL 무해 자식 1 · 소유 Job 1 의 관측. PID + 생성 시각 · 구성원 변화 · counter / 상한 재확인 · 종료 / 정리를 본다. 협조적 중지가 끝내 없으면 force-only 채택 여부는 사용자가 정한다.
3. C 관측본 준비 → C 1 회 — 모델 구성 · mesh · study sequence · readback 만 하고 solve 는 0 이다. ④ 감시 아래 돈다. ① ② 의 설정 · 생성식 층을 얻는다.
4. ② mapping 봉인 — 생성식 변수 · 평가법을 검토한 뒤.
5. ③ 오프라인 구현:
   - loader 순서 `numeric_table → bind_grid → charge_projection` 와 종료 로그 문법.
   - 적분오차 방법 — `CHARGE_BALANCE.json` 의 구간 곡률 bound 후보.
   - t0 / 계수 provider.
6. D = 한 P0 runAll — t0 · 평가 계수 · native 원문으로 ① ② ③ 의 마지막 층을 얻는다. 그 전에 다음을 푼다:
   - Parent manifest 세대 연결: R1 manifest 와 V1 `authorize_execution` 의 schema 가 다르다 — 조용히 맞추지 않는다.
   - 단일 argv / cwd 와 승인 경로.
